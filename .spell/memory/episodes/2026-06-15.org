** ITEM Fixed find/get tool dead-end on binary scheme:// URLs (artifact://, agent://, etc.). Root cause: get.ts renderSchemeNode dropped node.metadata.source_path and rendered `[§empty]` + the kernel note "Use sourcePath-aware tools to inspect it" — without ever surfacing the resolved fs path. Agent then scanned `find /` → 300s timeout. Kernel (napi.rs ~L1181) DOES forward source_path in metadata for fs-backed schemes; the TS renderer just ignored it. Fix: made renderSchemeNode a GetTool method that (1) for content.kind==="bytes" with a source_path, re-classifies off the resolved path and behaves like a real file read — image→image block via readImageFile, other binary→marker naming the path; (2) always attaches sourcePath meta; (3) fallback names the path instead of bare [§empty]. Single chokepoint covers both `find` (FindTool delegates to GetTool) and `get`. Tests in packages/coding-agent/test/get.test.ts.

** ITEM Debugged "pi-knowledge-worker stuck at 0 + hogging computer (4.2GB RSS, 60min CPU, zombie)". Three INDEPENDENT root causes, none was the embed logic (which was correct + tested):

1. STALE DEPLOYED BINARY (primary). The deployed packages/natives/native/pi-knowledge-worker and the cargo release artifact were both built ~13min BEFORE the four fix commits (69cbeade8 persist/chunked-progress/CPU-cap, f6231e40d recency, d7469f7da graph-once, 159876028 title-fix) landed. Diagnosed by `strings <binary> | grep -F 'org_vec_meta|recency gate|affinity cap'` → all ABSENT in deployed, PRESENT in source. So none of the "recent improvements" were actually running. Fix = cargo build --release + cp to native/. Lesson: when a fix "doesn't work", FIRST verify the deployed binary actually contains it (strings probe + mtime vs commit date) before re-debugging logic. Related deploy gap: BUG-471 (build-native reads ./target/debug, cargo emits to ~/.cache).

2. IDLE-EXIT KILLS LONG COLD WARM (BUG-483). Warm-load runs on a detached thread touching neither INFLIGHT nor LAST_REQUEST_AT. Cold warm of 4148 org items under the CPU-affinity cap takes ~1h, but build_vec_index_with only persists the vector cache at END of a complete build. The 30min idle-exit fires mid-embed → discards everything → re-embed from scratch next lifetime. THIS is why ~/.cache/spell/knowledge/<repo-hash>/ never appeared despite the daemon reaching warm/4147-in-RAM repeatedly. Fix: ACTIVE_WARMS atomic + RAII WarmActiveGuard, idle gate also checks !warm_in_flight().

3. ZOMBIE ON EVERY SPAWN. embedding_worker::spawn_daemon did Command::spawn() then dropped Child without wait(). --daemonize double-forks; the fork-parent exit(0)s immediately → <defunct> reparented to the spell process, never reaped. Fix: child.wait() (returns in ms; real daemon setsid'd away).

Verification technique that nailed it: query the LIVE daemon over its unix socket with socat (`printf '{"command":"stats"}\n' | socat - UNIX-CONNECT:/run/user/1000/spell/knowledge.sock`) — showed status=warm, item_count=4147, but the on-disk cache dir for that exact repo_hash was MISSING. RAM-warm + disk-empty = the smoking gun. Then proved the fix: cold warm persisted a 17.5MB vectors.uidx (4148×1024×4), and a close+reopen re-warm jumped to done=4129 instantly (carry-forward) embedding only ~28 new items → warm in seconds not 55min.

Two hashers to not confuse: daemon handle = repo_cache::repo_hash → "fnv:%016x"; cache dir = pi-knowledge-core::cache::repo_hash → "%012x". Different widths/prefix over the same FNV-1a of the canonical path.
