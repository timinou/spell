** ITEM pi-code-graph semantic backend layer (PLAN-319)

## What

`pi-code-graph::semantic` — configurable LSP-backed layer for the type-inference
capabilities that tree-sitter can't statically compute. Hides LSP servers behind
a `SemanticBackend` trait so the agent's `find`/`edit`/`get`/`create` surface
stays unified.

## Architecture

```
agent calls find { ::Sym #hover_inferred }
  ↓
pi-natives::code_path::type_resolver::dispatch
  ↓  picks workspace's CompositeSemanticBackend (file-ext routing)
  ↓
pi-code-graph::semantic::SemanticBackend trait
  ↓
either:
  • AnnotationSemanticBackend (reads SymbolNode::detail, written sigs)
  • LspSemanticBackend (spawns expert/vtsls/rust-analyzer/etc., JSON-RPC)
```

## Design rules

1. **Tree-sitter for static, LSP for type inference.** All lexical work
   (def→/ref→/call→/import→/implements→/inherits→/dispatches→/#hover-written
   /§symbols) stays in pi-code-graph. LSP only fills genuine type-inference
   gaps (#hover_inferred / #type_definition / [type_aware] / #diagnostics /
   #signature / #inlay).
2. **Synchronous LSP client.** The SemanticBackend trait is sync. An async
   client would force `block_on` everywhere and force tokio into a crate
   that doesn't need it.
3. **One BM25.** pi-knowledge-core::bm25 is the home; pi-code-graph and
   pi-org-engine consume it. No tantivy/fst/mmap proliferation.
4. **One umbrella config.** All pi-code-graph options (cache + BM25 + LSP
   wiring) live under a single `semantic {}` KDL block.
5. **Coordinates: 1-indexed line+col throughout.** Matches SymbolNode.
   LSP conversion happens AT the LSP boundary (semantic_to_lsp_position).
6. **Capability honesty.** `derive_capabilities` from LSP initialize result
   must not claim narrow_dispatch=true if LspSemanticBackend uses the
   default trait impl (W1g P1 fix).
7. **Layered config = Some-wins merge.** Scalars are Option<T>; merge
   takes higher.or(lower); load_layered resolves any still-None to
   compile-time defaults at the end (W2g P1 fix).
