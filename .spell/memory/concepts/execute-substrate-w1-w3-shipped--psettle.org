ARCHITECTURE FACTS (load-bearing for future work):
- The E1/BUG-426 OOM point is `GenServer.reply(from, {:ok, r})` in peer.ex dispatch: it COPIES the decoded tool result onto the sandbox worker's heap before any builtin runs. Fix = park large results in a HandleStore process BEFORE the reply; reply a small %Handle{}.
- BEAM copy semantics make handles subtle: :ets.lookup copies the whole term to the caller (re-OOM). Projections MUST run in the owner process (GenServer.call whose reply is the slice). Not ETS.
- Sizing MUST use :erlang.external_size/1 (counts off-heap binary payloads), NOT :erts_debug.flat_size (undercounts string-heavy results like org bodies by orders of magnitude — the exact payload offload targets). Threshold 256KB.
- ptc_runner already has cross-program persistence via (def x v)→step.memory; session bindings (W3) reuse it by threading memory in the Peer. NO parallel bind/ namespace.
- do_eval/do_apply_fun clauses must be grouped; a helper inserted between clauses trips Elixir's clause-grouping warning. Put helpers in the helper region.
- Untrusted name→atom must use SourceAtoms.intern/1 (bounded vocab), never String.to_atom (atom-table growth, #953).
- A %Handle{} bound via (def x (tool/big)) has its per-execute bucket released at teardown; W3 re-homes it (HandleStore.rehome/3) to a persistent @session_bindings bucket so it stays a small handle and doesn't OOM the next execute's SMALLER bounded compile heap (~10MB vs 50MB execute heap).
