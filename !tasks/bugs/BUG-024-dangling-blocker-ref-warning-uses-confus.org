## Audit Findings

### 1. Gate rejection silently drops non-status field updates
- **What**: When the smart gate rejects an `in_progress` transition, the `break` exits the entire `update` case, discarding any co-submitted field changes (content, notes, details, blockers, etc.) without mentioning them in the error.
- **Where**: `packages/coding-agent/src/tools/todo-write.ts` ~line 373 (the `break` statement)
- **Why**: A caller sending `{op: "update", id: "task-2", status: "in_progress", notes: "starting this"}` gets an error about the status, but the notes update is silently lost. The whole op is rejected, which is defensible, but the error message only mentions the status transition — the caller doesn't know other fields were dropped. Low real-world impact since agents rarely combine `in_progress` with other fields, but it's a contract nuance.
- **Effort**: small (apply non-status fields before the gate check, or mention "entire update op rejected" in the error)

### 2. "Errors: Warning:" double prefix on dangling ref messages
- **What**: Dangling blocker ref warnings use the format `"Warning: task-1 references non-existent blocker task-99"` and are pushed into the `errors` array, which renders as `"Errors: Warning: task-1 references..."`.
- **Where**: `packages/coding-agent/src/tools/todo-write.ts` ~line 416
- **Why**: The model sees a slightly confusing "Errors: Warning:" prefix. Not user-visible (model text only), but muddies the distinction between real errors and warnings.
- **Effort**: trivial (drop the "Warning:" prefix from the message, or use a different rendering path for warnings)

### 3. Missing test: `remove_task` creating dangling blocker ref
- **What**: The plan specified testing that `remove_task` on a task referenced as a blocker by another task produces a dangling-ref warning. This test was not implemented.
- **Where**: `packages/coding-agent/test/tools/todo-write.test.ts`
- **Why**: Low risk — the dangling ref validation is a single post-ops pass that doesn't depend on which op caused the dangle. But the plan explicitly specified this scenario.
- **Effort**: trivial

### 4. Missing test: `add_phase` with `in_progress` blocked task demotion
- **What**: The plan specified testing that `add_phase` ops with `in_progress` and unresolved blockers get demoted by `normalizeInProgressTask`. Only `replace` is tested.
- **Where**: `packages/coding-agent/test/tools/todo-write.test.ts`
- **Why**: Low risk — both `replace` and `add_phase` go through the same `normalizeInProgressTask` demotion pass. But the plan explicitly specified both.
- **Effort**: trivial

### 5. Missing test: BLOCKER property round-trip integration
- **What**: FEAT-098 plan specifies an integration test: create org item with `properties: { BLOCKER: "FEAT-001-test" }`, read it back via `org get`, verify `parseOrgDependProperties()` extracts blockers. Not implemented.
- **Where**: Should be in `packages/coding-agent/test/plan-mode/plan-mode-approved-prompt.test.ts` or a new test file
- **Why**: The org-depend parser already has unit test coverage for BLOCKER extraction. The missing test covers the org *write* → *read* path specifically, which is already proven by other org tests. Low risk since no code changes were needed to the org infrastructure.
- **Effort**: small
