What happened?

* Initial Message

The `grep` tool crashed Spell while searching `SERVER_DOMAIN`.

Observed panic:
- `oxc_resolver-1.12.0/src/lib.rs:238:13`
- `assertion failed: path.starts_with(package_json.directory())`
- crash crossed the native async boundary and aborted Spell (`SIGABRT`)

Repo evidence gathered during planning:
- `crates/pi-code-graph/Cargo.toml` currently pins `oxc_resolver = "1.12"`.
- `crates/pi-code-graph/src/language/typescript.rs` calls `resolver.resolve(from_dir, request.specifier).ok()` directly inside `TypeScriptImportResolver.resolve()`.
- `crates/pi-code-graph/src/indexer.rs` calls each language resolver from `CodeGraphBuilder.build()`.
- `crates/pi-natives/src/code_graph.rs` and `crates/pi-natives/src/code_buffer.rs` build runtime graphs through `CodeGraphBuilder`, so an uncaught resolver panic can abort the native Spell process.
- Upstream has already fixed this assertion class; current crates.io default is `oxc_resolver 11.19.1`, while our lockfile still resolves `1.12.0`.

Settled design decisions:
1. One BUG item is sufficient: this is one coherent crash class at one invariant boundary (`TypeScriptImportResolver.resolve()` inside `pi-code-graph`).
2. Fix scope = bump `oxc_resolver` from `1.12` to `11.x`, add a local panic guard around `TypeScriptImportResolver.resolve()`, and add regression coverage.
3. The local guard must preserve current success/miss semantics: valid resolutions stay unchanged, and panic paths degrade into the existing `fallback_relative_path()` / `None` behavior instead of inventing a new user-visible success shape.
4. Do not broaden scope into general code-graph query redesign, grep UX redesign, or a full dependency sweep.
5. Runtime proof must include a rebuilt native addon before manual repro because the live Spell path goes through `crates/pi-natives/src/code_graph.rs`; this follows the repo evidence plus `memory://root/memory_summary.md`, which explicitly warns that native binary rebuilds are required after Rust changes.

Plan parent: created after this BUG item.

* Scope

In:
- Stop Spell from aborting when semantic graph indexing or lookup reaches an `oxc_resolver` panic from TypeScript/JavaScript module resolution.
- Upgrade the TypeScript resolver dependency in `crates/pi-code-graph/Cargo.toml` (and lockfile) from `1.12` to `11.x`.
- Add a local panic guard inside `TypeScriptImportResolver.resolve()` so any future resolver panic is contained before it crosses the NAPI/runtime boundary.
- Keep the current fallback behavior (`fallback_relative_path()` and final `strip_prefix(project_root)`) as the degraded path when guarded resolution fails.
- Add targeted regression tests that lock in both valid-resolution behavior and panic containment.
- Manually re-run the previously crashing semantic path after rebuilding the native addon.

Out:
- Reworking general graph query semantics in `pi-code-graph`.
- Changing successful TypeScript import-resolution semantics for well-formed projects.
- Adding a new top-level code-graph error contract unless implementation proves existing miss semantics are insufficient.
- Broad `oxc_*` dependency refreshes unrelated to the resolver crash.
- Tool/prompt rewrites in `packages/coding-agent` unless implementation reveals a truthful-surfacing gap.

Rationale:
- The user-visible defect is not a wrong result; it is a process abort.
- Upstream fixed the known assertion class, but local containment is still required because the Spell host must not die if a third-party resolver regresses again.
- `TypeScriptImportResolver.resolve()` already models misses via `Option<PathBuf>` plus fallback logic, so panic containment should degrade into that contract instead of inventing a new parallel API.

* Existing Patterns

- `crates/pi-code-graph/src/language/typescript.rs`
  - `TypeScriptImportResolver.resolve()` owns TypeScript import resolution.
  - `fallback_relative_path()` is the existing degraded-resolution path; reuse it rather than adding a second fallback convention.
  - Existing tests in the same file already cover extractor and builder behavior; extend this file first before inventing a new test module.
- `crates/pi-code-graph/src/indexer.rs`
  - `CodeGraphBuilder.build()` is the graph-build contract that calls `registered.resolver.resolve(ResolveRequest { ... })` for imports.
  - Builder tests already use temp workspaces and should remain the integration-level proof for graph survival after resolver changes.
- `crates/pi-natives/src/code_graph.rs`
  - `execute_code_graph()` / `run_code_graph()` are the runtime entrypoints that make a resolver panic user-visible as a Spell crash.
  - Prefer fixing the invariant below this layer in `pi-code-graph`; do not duplicate parallel panic handling in multiple callers unless a single guard proves impossible.
- `crates/pi-embedding-worker/src/main.rs`
  - `panic::catch_unwind(AssertUnwindSafe(...))` is an existing in-repo precedent for containing Rust panics before they escape a long-lived host boundary.
  - Mirror that pattern narrowly around the external resolver call instead of wrapping the whole graph build.
- `crates/pi-code-graph/src/language/elixir.rs` and `crates/pi-code-graph/src/language/generic.rs`
  - Resolver tests use temp directories and direct `ResolveRequest` assertions; use the same style for any new TypeScript resolver tests.

* Edge Cases

- Symlinked or hoisted package layouts where the upstream resolver used to panic because package-root and resolved-path prefixes diverged.
- Relative specifiers that should still resolve via `fallback_relative_path()` if the guarded external resolver path fails.
- Non-relative specifiers: panic guard must still degrade cleanly to `None`, not a fake local path.
- Valid workspaces whose imports previously resolved under 1.12: the guard must not perturb successful cases.
- A future third-party resolver panic unrelated to this exact assertion: Spell still must not abort.
- Builder integration: one import panic must not corrupt unrelated graph state or produce a plausible-but-false edge.
- Native runtime proof must happen against a rebuilt addon; otherwise the manual repro can lie by exercising an old `.node` binary.
