## Audit Findings

### 1. Silent data loss when deserializing TS items in NAPI bridge
- **What**: `parse_items_from_options` in `org_buffer.rs` silently drops items that fail serde deserialization via `filter_map(|v| serde_json::from_value(v.clone()).ok())`. TS `OrgItem` objects lack `byte_range` (a required field with no `#[serde(default)]`), so ALL items will fail to deserialize, producing an empty vec.
- **Where**: `crates/pi-natives/src/org_buffer.rs:229-232` and `crates/pi-org-engine/src/item.rs:41` (missing `#[serde(default)]` on `byte_range`)
- **Why**: `cmdWave` and `cmdGraph` in tool.ts pass TS-constructed items to `executeOrg({ command: "computeWaves", items })`. These items will all be silently dropped, causing wave/graph commands to return empty results or fail with "Missing required field: source or items". This breaks `org wave` and `org graph` entirely.
- **Effort**: `trivial` — add `#[serde(default)]` to `byte_range` and `clocks` fields in `OrgItem`

### 2. Priority comparison operators silently discarded
- **What**: `parseKeywordQuery` in tool.ts extracts only the priority value (`B`) from `priority:>=B`, discarding the operator (`>=`). The TS `applyFilter` does exact string match only. * Problem

The =parseKeywordQuery= function in =packages/org/src/tool.ts= has two bugs in priority handling:

1. **Missing =#= prefix**: The regex =/^(>=|<=|=)?([A-C#])$/= captures just the letter (e.g. =B=), but =item.properties.PRIORITY= stores values as =#B=. The filter value =B= never matches =#B= in =applyFilter=, so priority filtering returns no results.

2. **Operator silently discarded**: =priority:>=B= is documented as supported syntax (copied from the original Emacs-backed implementation). The operator (=>=, <=, ==) is captured by the regex but immediately discarded — only =match[2]= (the value) is stored.

Combined effect: =org query priority:>=B= returns zero results when it should return items with priority A and B.

* Design Decision

Expand the priority set at parse time rather than adding operator support to =OrgQueryFilter=:
- =priority:A= or =priority:#A= → =filter.priority = [\"#A\"]=
- =priority:>=B= → =filter.priority = [\"#A\", \"#B\"]= (A and B are >= B)
- =priority:<=B= → =filter.priority = [\"#B\", \"#C\"]= (B and C are <= B)
- =priority:=B= → =filter.priority = [\"#B\"]=

This keeps =applyFilter= unchanged (set-inclusion logic) and requires no type changes to =OrgQueryFilter=.

The priority ordering is: A > B > C (A is highest).

#+begin_src typescript
const PRIORITY_ORDER = ["#A", "#B", "#C"];

function expandPriorityFilter(op: string, value: string): string[] {
    const idx = PRIORITY_ORDER.indexOf(`#${value}`);
    if (idx === -1) return [`#${value}`];
    switch (op) {
        case ">=": return PRIORITY_ORDER.slice(0, idx + 1);
        case "<=": return PRIORITY_ORDER.slice(idx);
        case ">": return PRIORITY_ORDER.slice(0, idx);
        case "<": return PRIORITY_ORDER.slice(idx + 1);
        default: return [`#${value}`];
    }
}
