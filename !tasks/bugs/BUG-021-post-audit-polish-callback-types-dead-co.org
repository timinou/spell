### Finding 1: `onPhase1Complete` never fires on exception paths in the try block
- **What**: If anything inside the `try` block at line 270 throws (e.g., `collectThreads`, `upsertThreads`, `resolveMemoryModel`), the `finally` block closes the DB but `onPhase1Complete` is never called. The callback fires on all 4 early-return paths and the success path, but not on uncaught exceptions.
- **Where**: `packages/coding-agent/src/memories/index.ts` lines 270–413 (the try/finally block)
- **Why**: The callback contract is inconsistent — callers can't distinguish "phase1 hasn't started yet" from "phase1 threw." Currently the only consumer (`sdk.ts`) just logs, so impact is low. But if any future consumer depends on "callback always fires," they'll have a bug. Easy fix: add `options.onPhase1Complete?.(null)` in a catch clause, or move the call to the `finally` block.
- **Effort**: `trivial`

### Finding 2: Inline callback type duplicated 3 times
- **What**: `(stats: { usage: { input: number; cacheWrite: number } } | null) => void` is inlined in 3 separate function signatures (lines 138, 227, 240).
- **Where**: `packages/coding-agent/src/memories/index.ts`
- **Why**: Violates DRY at 2. If the callback shape changes (e.g., adding `output` to usage), three signatures need updating. Extract to a named type like `type Phase1CompleteCallback = ...`.
- **Effort**: `trivial`

### Finding 3: Budget filter's try-catch is dead code for `Bun.file().size`
- **What**: `Bun.file(path).size` returns `0` for nonexistent files — it does not throw. The try-catch at line 315 never catches anything. The comment says "Stat failed (file deleted?)" but this path is unreachable.
- **Where**: `packages/coding-agent/src/memories/index.ts` lines 315–320
- **Why**: Dead code misleads readers into thinking missing-file handling exists. The actual behavior (size=0, claim included with 0 token estimate) is correct but accidental. Removing the try-catch and adding a comment explaining `Bun.file().size` returns 0 for missing files would be clearer. Alternatively, keep the try-catch as a defensive guard against future Bun changes — but update the comment.
- **Effort**: `trivial`

### Finding 4: Exit summary suppression compares against magic string
- **What**: `if (summary !== "Session: no tokens recorded")` at line 1348 compares against a literal string that lives inside `formatExitTokenSummary`. If the wording changes in `token-summary.ts`, the check silently stops working and empty-session summaries always print.
- **Where**: `packages/coding-agent/src/modes/interactive-mode.ts` line 1348
- **Why**: Fragile coupling. Better to check `stats.tokens.input > 0 || stats.tokens.output > 0 || stats.cost > 0` before calling the formatter, or export a sentinel constant from `token-summary.ts`.
- **Effort**: `trivial`

### Finding 5: `formatStartupTokenNote` remains dead code
- **What**: `formatStartupTokenNote` in `token-summary.ts` is still not called from any production code. FEAT-091's deviation notes explain that the startup note was implemented as `logger.debug` only, and the callback doesn't call `formatStartupTokenNote`. The function and its `StartupTokenInfo` interface are tested but dead.
- **Where**: `packages/coding-agent/src/session/token-summary.ts` lines 22–45
- **Why**: Dead code that may mislead future readers into thinking it's wired. The plan documented this as a deviation, which is good, but the code doesn't indicate it's awaiting integration.
- **Effort**: `trivial` (add a `@todo` comment) or `small` (wire it properly via a future item)

### Finding 6: Budget test doesn't verify the filtering count directly
- **What**: Budget tests assert `completeSimple` call counts (stage1 + phase2) as a proxy for "how many claims were processed." This couples the test to phase2 behavior. If phase2 stops running (e.g., watermark logic changes), the test fails for the wrong reason. A more direct assertion would spy on `markStage1SucceededWithOutput` or check `stats.claimed` via the debug log.
- **Where**: `packages/coding-agent/test/memories-runtime.test.ts` lines 493–549
- **Why**: Test brittleness — any change to phase2 triggering could break budget tests even if budget filtering is correct. The existing e2e test already covers phase2 independently.
- **Effort**: `small`
