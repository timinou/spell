## Audit Findings

### 1. CHANGELOG not updated
- **What**: `packages/coding-agent/CHANGELOG.md` has no entries under `[Unreleased]` for this plan's changes.
- **Where**: `packages/coding-agent/CHANGELOG.md`, under `## [Unreleased]`
- **Why**: AGENTS.md requires changelog entries for all changes. This is a 4-item plan with user-facing features (new model role, new status line segment, enriched payloads). Missing entries make the next release opaque.
- **Effort**: `trivial`

### 2. `setCanvasTaskCount()` has no callers — TUI badge is invisible
- **What**: `StatusLineComponent.setCanvasTaskCount()` is defined but nothing calls it. The `canvas_tasks` status line segment always shows `canvasTaskCount: 0` and remains hidden.
- **Where**: `packages/coding-agent/src/modes/components/status-line.ts` line 97
- **Why**: The FEAT-252 acceptance criterion says "TUI shows a badge/indicator when canvas tasks are active" — this is not satisfied. The infrastructure is in place but the glue (calling `setCanvasTaskCount(manager.getActive().length)` from the render/event cycle) is missing. Note: the pre-existing `setSubagentCount()` has the same pattern — also never called — so this is consistent with existing code, but the feature intent is unmet.
- **Effort**: `small`

### 3. Theme icon type cast is fragile
- **What**: `canvasTasksSegment` uses `(theme.icon as typeof theme.icon & { canvas?: string }).canvas ?? ""` to access a `canvas` icon that doesn't exist in the theme type.
- **Where**: `packages/coding-agent/src/modes/components/status-line/segments.ts` line 194
- **Why**: The cast silently resolves to `""` (empty string), so the segment renders without an icon. This works but obscures the fact that no canvas icon exists. If a `canvas` icon is later added to the theme, this cast will need to be cleaned up. Minor maintenance cost.
- **Effort**: `trivial`

### 4. Split imports from same module
- **What**: `canvas-task-manager.ts` lines 16–17 split type and value imports from `"../task/types"` into two separate import statements. Same pattern in the test file lines 18–19.
- **Where**: `packages/coding-agent/src/orchestrators/canvas-task-manager.ts` lines 16–17; `test/tools/canvas-task-tier.test.ts` lines 18–19
- **Why**: Could be a single import: `import { TASK_SUBAGENT_PROGRESS_CHANNEL, type AgentDefinition, type AgentProgress, type SingleResult } from "../task/types"`. Biome didn't flag it, so this is purely cosmetic.
- **Effort**: `trivial`

### 5. Duplicate `durationMs` computation on success path
- **What**: `Date.now() - startTime` is computed once for the logger call (line 210) and again for the bridge message (line 222), ~12 lines apart. These will differ slightly.
- **Where**: `packages/coding-agent/src/orchestrators/canvas-task-manager.ts` lines 210, 222
- **Why**: The logger and bridge message will report slightly different durations for the same task. Trivial in practice (microsecond difference), but could be a `const durationMs = Date.now() - startTime` once.
- **Effort**: `trivial`

The =taskManager= lives on the =ToolSessionResult= returned by =createAgentSession()= in sdk.ts.
The TUI =InteractiveModeContext= needs a reference to it so the event-controller can call:
=ctx.statusLine.setCanvasTaskCount(ctx.taskManager?.getActive().length ?? 0)=

The simplest wiring: on each =statusLine.invalidate()= in event-controller, also update the canvas task count. This piggybacks on existing invalidation triggers (turn start, turn end, message update) which is frequent enough.

Alternative (lighter): subscribe to =CANVAS_TASK_CHANNEL= and =CANVAS_EVENTS_CHANNEL= from event-controller and update on task start/stop only. But this duplicates subscription logic already in CanvasTaskManager. Prefer the invalidate piggyback.
