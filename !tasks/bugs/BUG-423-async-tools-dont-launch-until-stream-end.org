* Symptom

User reports that even an "async" bash call (=async: true=) appears to only start executing once the assistant message has finished streaming. Latency from "model emits the tool_use block" to "background job actually begins doing work" includes the whole tail of the streamed assistant turn (further text, more tool blocks, thinking content, etc.).

* Confirmed: this is the current behaviour

=packages/agent/src/agent-loop.ts::runLoop= (lines 248-274):

#+begin_src ts
const message = await streamAssistantResponse(currentContext, config, signal, stream, streamFn);
newMessages.push(message);
...
const toolCalls = message.content.filter(c => c.type === "toolCall");
if (hasMoreToolCalls) {
    const toolExecution = await executeToolCalls(...);
}
#+end_src

The whole assistant message is streamed to completion (or barrier-cut, post FEAT-788) BEFORE =executeToolCalls= ever runs. Even for tools declaring async behaviour internally, the harness can't dispatch them until the model's assistant turn ends.

The =bash= tool's async branch (=packages/coding-agent/src/tools/bash.ts:409-466=):
- Returns a synchronous "Background job started" result the moment its =execute()= is called.
- Registers the actual long-running work as a callback in =AsyncJobManager= which runs it on a separate scheduler.
- BUT =execute()= itself is only invoked from inside =executeToolCalls=, which only runs post-stream.

∴ "Async" tools are async in the sense that they don't block the agent loop on completion — they DO block on the stream finishing first. The user's intuition is correct.

* Why this matters

For a tool-heavy turn (Opus 4.8 often emits 30-100 tool calls in one message), the model can take many seconds to finish streaming all of them. If the first tool is an async background bash like a build or test, that build does NOT start while the model is still emitting tool 7-100's args. The operator is waiting on:

  (stream-emission-time) + (build-time)

instead of:

  max(stream-emission-time, build-time)

For a 60-second build emitted early in a 5-second stream, that's a 5s preventable latency. Cheap. For a 30-second stream where build is async, 30s of build is wasted on stream wait.

This compounds the FEAT-788 stream-barrier symptom: the barrier cuts at the first sequential tool, but everything before it still streams to completion before dispatch starts.

* Goal

Dispatch parallel-mode tools as soon as their =toolcall_end= event fires, instead of waiting for the whole assistant message. Sequential-mode tools continue to wait for the stream (the FEAT-788 barrier already handles that case — those tools cut the stream and become a batch boundary).

Concretely: in =streamAssistantResponse='s =toolcall_end= branch, if the tool is registered AND =tool.executionMode !== "sequential"=, fire =tool_execution_start= and begin =tool.execute()= immediately. The result is collected by the time the stream finishes; =executeToolCalls= then sees it already-completed.

* Existing patterns

- FEAT-788 barrier (=packages/agent/src/agent-loop.ts::streamAssistantResponse=) already inspects each =toolcall_end= and looks up the tool by name; the early-dispatch decision can piggyback on the same lookup.
- =AsyncJobManager= (=packages/coding-agent/src/async/job-manager.ts=) is the dispatch sink the bash async branch uses; no changes needed there.
- =executeToolCalls= currently iterates =records= and runs each. To preserve its contract, we'd need a path that says "this record's result is already set — skip execute, just emit the result message and continue."
- =stream.push("tool_execution_start" / "tool_execution_update" / "tool_execution_end")= are the visible events the TUI consumes. Already work mid-stream — they go through the same SYNC =#emit= chain as message_update events.

* Edge cases

- Tool whose args were partially streamed but never completed (=toolcall_end= never fires) — same as today, dispatch waits.
- Tool not in =context.tools= (=resolveUnknownTool= path) — current code defers resolution; early dispatch would need to defer too or fail open.
- Tool args fail validation — early dispatch would surface the error mid-stream as a =tool_execution_end= with error. Strictly better than today (where it surfaces at batch dispatch).
- Tool with =intent= field — the post-stream intent-extraction step strips =__intent= from args. Early dispatch would need the same pass.
- Sequential tools — never early-dispatched (FEAT-788 barrier cuts at them anyway).
- Tool callbacks fire =onProgress= / =reportProgress=; these turn into =tool_execution_update= events. Already non-blocking via the SYNC emit chain.
- Interrupt handling (=interruptMode: "wait"=) — currently checked between sequentially-executed tools. Early-dispatched parallel tools would need the same check between their dispatch and the next stream event. Today there are no parallel-tool interrupt checks mid-batch either, so this is no regression.
- The result-emission order: today, parallel tools emit results when =Promise.allSettled= resolves; the assistant-message turn_end carries them. Early dispatch needs to ensure the same ordering — emit results in =records= order, not in completion order, to keep the API's tool_use/tool_result pairing stable.
- Per-tool concurrency: the bash tool spins up an ephemeral subprocess per call; concurrent dispatches are safe. =edit= uses kernel per-file locks; safe. =todo_write= uses a per-session mutation chain; safe. Everything in the parallel set already supports being called concurrently from the post-stream batch — early dispatch just shifts the timing earlier.

** Implementation notes worth keeping

- The eager-dispatch promise wraps tool errors into =isError: true= results instead of throwing back through the IIFE. This means the awaited side never sees a rejection and the existing error-emission channels in =executeToolCalls= work unchanged.
- =record.started = true= flips before =emitToolResult= is called so the duplicate =tool_execution_start= path is correctly suppressed (=emitToolResult= already checks =record.started= to decide whether to fire it).
- Signal: early-dispatched tools receive the OUTER signal only (caller's), not the steering-controller signal. The steering controller is created inside =executeToolCalls=, after the early-dispatch path has already kicked off. This is a conscious trade-off: =interruptMode: "immediate"= can no longer interrupt an already-running early-dispatched tool mid-execution. The signal still aborts pending operations though, and steering messages still take effect for any tool that hasn't started yet. If we later need exact parity, hoist the steering controller up to =runLoop=.
- =getToolContext= is called with =batchId: =eager_<toolCallId>=, index: 0, total: 1= for early-dispatched tools \u2014 they're not part of the batch yet at dispatch time. The post-stream =executeToolCalls= still computes the real batch metadata, but it never calls =execute()= for eager-dispatched tools (short-circuit), so the eager-side batch metadata is the only one the tool sees. Acceptable: =getToolContext= is informational/diagnostic, not contractual.

** Discovery during TDD (worth preserving for future test authors)

=AssistantMessage.content= is MUTATED through streaming \u2014 every =message_update= event carries a shared reference to the same content array. A test that reads =events[N].message.content= after the stream completes sees the FINAL state, not the snapshot at index N. The test caught it: a "tool#2 first appears in content" predicate matched the very first =message_update= because by test-read time the array contained tool#2.

The stable per-event payload is the =assistantMessageEvent= sub-field on =message_update= events. It carries =toolcall_start= / =toolcall_end= / =text_delta= etc. with the immutable per-event data the consumer saw in real time. Tests asserting "what was the stream state at this point" must use this sub-field. The pattern is documented inline in =agent-loop-early-dispatch.test.ts=.
