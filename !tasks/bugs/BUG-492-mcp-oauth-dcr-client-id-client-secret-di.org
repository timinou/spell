** Root cause (verified this session)

Notion's MCP server requires OAuth 2.0 Dynamic Client Registration (RFC 7591) — confirmed via =https://mcp.notion.com/.well-known/oauth-authorization-server=, which exposes a =registration_endpoint= and *no* static =client_id= anywhere in its metadata. Per Notion's own docs (developers.notion.com/guides/mcp/build-mcp-client), each DCR registration issues a fresh =client_id=/=client_secret=, and *refreshing a token later requires the original client_id that issued it*.

Traced the persistence path in =packages/coding-agent/src/mcp/=:

1. =oauth-flow.ts::MCPOAuthFlow= performs DCR (=tryRegisterClient()=, ~L200) and stores the result in *private* fields =#resolvedClientId= / =#registeredClientSecret=. Neither is exposed on the object.
2. =flow.login()= returns only =OAuthCredentials= (=access=/=refresh=/=expires=) from =exchangeToken()= — the DCR-issued client_id never leaves the flow instance.
3. =mcp-command-controller.ts= (=#handleLogin=/=#handleReauth=, ~L580) builds the persisted =auth= block as:
   #+begin_src typescript
   auth: { type: "oauth", credentialId, tokenUrl: oauth.tokenUrl, clientId: oauth.clientId ?? found.config.oauth?.clientId }
   #+end_src
   Here =oauth= comes from server-metadata discovery (=discoverOAuthEndpoints=/=analyzeAuthError= in =oauth-discovery.ts=), NOT from the DCR registration performed inside =MCPOAuthFlow=. Notion's metadata has no =client_id= field, so =oauth.clientId= and =found.config.oauth?.clientId= are both =undefined= → persisted =clientId= is =undefined=.
4. Confirmed directly in the user's =~/code/myke/llm-work-assistant/spell.kdl=: the notion server's =auth= node has =credentialId==/=tokenUrl== but **no** =clientId== attribute.
5. On proactive/forced refresh, =manager.ts::#resolveAuthConfig= calls:
   #+begin_src typescript
   const refreshed = await refreshMCPOAuthToken(auth.tokenUrl, credential.refresh, auth.clientId, auth.clientSecret);
   #+end_src
   with =auth.clientId === undefined=. Notion's token endpoint requires the exact client_id that issued the refresh token (DCR semantics) → refresh fails (=invalid_client=/=unauthorized_client=).
6. Failure is swallowed silently:
   #+begin_src typescript
   } catch (refreshError) {
     logger.warn("MCP OAuth refresh failed, using existing token", { credentialId, error: refreshError });
   }
   #+end_src
   The manager proceeds with the stale/expired access token, the HTTP connection 401s, and every subsequent tool call surfaces as "MCP server not connected". Any session started after the (short, ~1hr) token lifetime inherits this and forces a full browser reauth, which re-runs DCR and repeats the cycle every time.

** Why this is a real bug, not a schema gap

=kdl-server-resolver.ts::configToEntry= (landed under BUG-491) already round-trips the full OAuth coordinate set on the =auth= KDL node — =type=, =credentialId=, =tokenUrl=, =clientId=, =clientSecret= are all serialized/deserialized symmetrically. The KDL schema and read/write path are NOT the problem. This is purely a TS-side wiring gap: the DCR-resolved client credentials are computed but never threaded from =MCPOAuthFlow= into the object that gets persisted.

** Fix

1. =packages/coding-agent/src/mcp/oauth-flow.ts= — expose the DCR-resolved =client_id=/=client_secret= after =login()= completes (e.g. add public readonly getters or include them in the =OAuthCredentials=-adjacent return value / a sibling field on =MCPOAuthFlow=), so callers can read what registration actually produced instead of only what auth-server metadata advertised.
2. =packages/coding-agent/src/modes/controllers/mcp-command-controller.ts= (=#handleLogin=/=#handleReauth=, and any other =#persistServer= call sites) — read the DCR client credentials off the flow instance after =await flow.login()= and merge them into the persisted =auth= object, with precedence: explicit user-configured =clientId=/=clientSecret= (if present) > DCR-issued > metadata-discovered.
3. Regression coverage: unit test simulating a DCR-only provider (metadata with =registration_endpoint=, no static =client_id=) — assert the persisted =MCPServerConfig.auth.clientId=/=clientSecret= reflect the DCR registration response after login, and that a subsequent forced-refresh call receives a defined =clientId=.
4. Manual/integration check: exercise =/mcp reauth notion= (or equivalent) against a DCR-only mock token endpoint and confirm the KDL file (=spell.kdl=) round-trips a non-empty =clientId= attribute for the entry.
