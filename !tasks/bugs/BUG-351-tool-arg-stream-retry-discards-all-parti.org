* Initial Message

When an Anthropic tool-arg stream stalls, all 3 retry attempts re-stream from scratch, burn ~12.5 minutes total, and fail at the same byte position every time.

* Cause

=packages/ai/src/providers/anthropic.ts:899-905= resets all output state on retry:

#+begin_src ts
providerRetryAttempt++;
await abortableSleep(getToolCallStreamRetryDelayMs(providerRetryAttempt), options?.signal);
output.content.length = 0;          // ← discards partial JSON
output.stopReason = "stop";
firstTokenTime = undefined;
started = false;
#+end_src

=stalled_incomplete_tool_args= is classified as transient (=isTransientStreamParseError(streamError) || stallDiagnostic?.state === "stalled_incomplete_tool_args"=). The retry budget is 3 attempts. Anthropic has no "continue this tool call from byte N" API, so each retry literally re-asks the model. For a deterministic stall (same prompt + context produces the same pause), every retry hits the same wall.

Evidence: session =14d6b8621f4e3f90= had identical =rawPartialJsonArtifact= bytes across retries 1, 2, 3.

* Fix

Two levers, apply both:

1. Track a high-water mark of =rawPartialJson.length= across attempts. If a retry produces ≤ same bytes as a prior retry, classify as non-transient and abort retries instead of running the full budget.
2. Reduce =TOOL_CALL_STREAM_MAX_RETRIES= when the stall is =stalled_incomplete_tool_args= specifically. Empirically these don't recover; one retry max is enough to absorb genuine transients without compounding cost.

Apply same logic to all providers that call =getToolArgumentStreamIdleTimeoutMs=: anthropic, amazon-bedrock, azure-openai-responses, better-ccflare, openai-codex-responses, openai-responses.

* Acceptance

- Tool-arg stalls that don't make progress across attempts fail fast (≤ 1 retry, not 3)
- Total wall-clock for a deterministic stall capped near (idleTimeout × 2), not (idleTimeout × 3 + retry delays)
- Test that asserts a stalling stream with no progress is NOT retried 3 times
