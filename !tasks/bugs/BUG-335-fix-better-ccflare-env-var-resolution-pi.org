**Intention & Purpose**
Fix the better-ccflare provider so it correctly uses OAuth passthrough mode (no auth header) when `ANTHROPIC_AUTH_TOKEN` is not set, instead of picking up `ANTHROPIC_API_KEY` from `.env` and sending it as an `x-api-key` header (which better-ccflare rejects with 401 because it expects `btr-` prefixed keys).

**Context & Narrative**
When a user has `ANTHROPIC_API_KEY=sk-ant-...` in their `.env` file and uses better-ccflare (at localhost:8080), the current env var resolution chain causes the Anthropic API key to be sent to better-ccflare. Better-ccflare rejects this with 401 "invalid x-api-key" because it requires `btr-` prefixed API keys.

The intended behavior (documented in memory and implemented in `buildBetterCcflareHeaders`) is OAuth passthrough: when no auth token is provided, NO auth header is sent. The `buildBetterCcflareHeaders` function at line 73-79 already handles this correctly — it only adds auth headers when `options.apiKey` is truthy. The bug is in the upstream key resolution that feeds a value into `apiKey` when it should be empty.

*** Root cause
better-ccflare provider's serviceProviderMap entry included ANTHROPIC_API_KEY as a fallback in the $pickenv chain. When a user has ANTHROPIC_API_KEY=sk-ant-... in .env (for the anthropic provider), the better-ccflare provider would pick it up and send it as an x-api-key header. Better-ccflare rejects sk-ant- prefixed keys with 401 "invalid x-api-key" because it requires btr- prefixed tokens.
*** Fix
Removed ANTHROPIC_API_KEY from the $pickenv fallback for "better-ccflare" in serviceProviderMap. Now only ANTHROPIC_AUTH_TOKEN is checked. When unset, getEnvApiKey returns undefined, and buildBetterCcflareHeaders sends no auth header → OAuth passthrough mode.
