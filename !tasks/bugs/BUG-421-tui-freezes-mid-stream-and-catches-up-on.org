* Symptom

During a long Opus 4.8 assistant turn (high tool count, long text), the TUI does not visibly update mid-stream. The chat response, text, tool cells all appear in one paint at or near =message_end=. Reproduced anecdotally across "latest sessions" by the user.

Not the same as BUG-419 (pending cells never finalize): cells DO finalize here — they just appear all at once at the end of the turn instead of streaming.

* Investigation so far

** Synthetic repros run from this session

1. Pure event-loop repro (200 events arriving synchronously in one I/O batch): only 1 setImmediate fires (gated by =#renderRequested=). Confirms gating behaviour but is not the live shape.

2. Realistic-cadence repro (200 events × 50ms throttle window): 20 renders fire, distributed across the window. **Renders keep up.** So the basic chain alone does NOT reproduce the symptom.

3. Slow-render repro (60ms render time, back-to-back events): 200 renders fire serially, ~60ms each. **No render skipping, no batch-to-end collapse.**

∴ event-chain + render-loop alone are not enough to cause the symptom. There must be specific live conditions that combine.

** Live candidates (ranked by suspicion)

*** A. CSI 1004h focus-tracking sets =minRenderInterval = 500ms= and never restores

=packages/coding-agent/src/modes/interactive-mode.ts:472-476=:

#+begin_src ts
const focusedInterval = this.ui.minRenderInterval; // captured at init
const unfocusedInterval = Math.max(focusedInterval, 500);
this.#terminalFocusUnsubscribe = this.ui.terminal.onFocusChange(focused => {
    this.ui.setMinRenderInterval(focused ? focusedInterval : unfocusedInterval);
});
#+end_src

Focus-out (=\x1b[O=) sets throttle to 500ms. Focus-in (=\x1b[I=) restores it. If the user is on a workspace switcher (niri overview, tmux popup, swallowed by another app) and a stream is in flight, OR if the terminal sends focus-out but never focus-in (Wayland edge cases, multiplexer focus-loss without focus-regain), the throttle stays at 500ms for the whole stream — exactly matching "no updates mid-stream, everything paints at the end."

User on ghostty 1.3.2 + niri-style WM is a plausible host for this.

Test: =PI_DISABLE_FOCUS_TRACKING=1= (no such env exists yet — we'd need to add a guard) OR manually verify with =stty -echo; printf '\x1b[O'= to force focus-out and observe.

*** B. Component-level dirty propagation hazard outside LiveToolBatch

Commit =07c179a97= fixed exactly this class of bug in =LiveToolBatchComponent= (BUG-391 follow-up). The fix routes invalidations through =Container.invalidate()= which unconditionally calls =#parent.markDirty()=.

Audit found other components overriding render or invalidate without proper propagation:
- =packages/coding-agent/src/modes/components/footer.ts::invalidate()= only clears its cached branch, never calls =super.invalidate()= or =#parent?.markDirty()=. (Filed as separate BUG — different scope, not the streaming symptom.)

Audit pending for the chat path:
- =AssistantMessageComponent= → calls =super.invalidate()= ✓
- =Markdown= setText → calls =#parent?.markDirty()= ✓
- =ToolExecutionComponent= → not audited yet (see tool-execution.ts:348)
- =ReadToolGroupComponent= → not audited
- =LiveToolBatchComponent= → fixed in 07c179a97

If any cell or group in the chat tree has a stuck-dirty hazard, the parent =chatContainer= stops getting re-marked after the first paint of the burst, so subsequent setImmediates fire but =Container.render()= short-circuits via the =if (!#dirty && cached) return cached= cache path. Effect: paints are scheduled and execute but emit the SAME output as the previous frame. Visually identical to "no update". Then at =message_end= something forces a full invalidate (e.g. =setUsageInfo=, =setExpanded=) → real repaint.

*** C. AssistantMessageEventStream throttle interacting with very fast burst

=packages/ai/src/utils/event-stream.ts:140-180=: deltas batch with #throttleMs = 50. The flush timer uses =setTimeout(...).unref?.()=. If the event loop has unref'd timers but no other work, they SHOULD still fire. But if the agent-side promise chain is awaiting a long async (e.g. =syncContextBeforeModelCall=, =extensionRunner.emit=), the flush MIGHT be delayed past expectation. Low confidence — defaults look correct.

*** D. ExtensionRunner.emit blocking

If any loaded extension's handler is slow on =message_update=, it adds latency per event. =#emitExtensionEvent= awaits =this.#extensionRunner.emit(event)= which iterates handlers sequentially. With high event rate, accumulated latency could starve the render scheduler. Low confidence without knowing the user's loaded extensions, but worth measuring.

** Why is FEAT-788 NOT a fix

FEAT-788 only changes WHICH events the agent loop emits (it cuts the stream early at sequential toolcall_end). The TUI repaint cadence during the events that ARE emitted is unchanged. So FEAT-788 may *reduce frequency* of the symptom (shorter streams less likely to land in a focus-loss window), but it does not address the root cause.

** Synthetic repro of candidate A confirms the shape

=/tmp/repro-unfocused.ts= (in this session) runs the same event-loop chain as the real harness with =MIN_INTERVAL = 500ms= (the unfocused throttle). Results on a 2.2-second stream emitting 200 events:

#+begin_example
UNFOCUSED throttle (500ms):
  stream duration: 2222ms
  events scheduled: 5
  renders fired: 4
  effective fps: 1.8
  → user perceives ~4 updates across a 2.2s stream
  → if last render lands AT or NEAR end (likely), it looks like "all at once at end"
#+end_example

200 update events → only 4 paints. With 500ms inter-render gap, the *temporal alignment* of those 4 paints near the end of bursty model output (large text chunks then quiet) makes "stuck at start, fully painted at end" the dominant operator-perceived behaviour.

The same repro at =MIN_INTERVAL = 16ms= (focused) fires ~140 renders across the same 200 events — fully smooth.

∴ Candidate A is the most likely root cause. The remaining open question is whether the live terminal actually drops focus during the user's reproduction. Three live triggers:

1. User switches workspace / app while stream is running. CSI 1004h focus-out fires → throttle = 500ms for rest of stream until focus-in.
2. Wayland/X edge: terminal sends focus-out without later focus-in if compositor doesn't deliver the focus-in event before the user looks back. Ghostty + niri + a niri-overview switch is a known pattern.
3. Multiplexer focus opacity: tmux / zellij don't always proxy CSI 1004h correctly. Some send focus-out on pane switch but never focus-in.

** Why I am NOT yet patching

Three reasons:
- The fix may be more nuanced than "remove unfocused throttle." 500ms is intentional (FEAT-358 / focus-aware throttle was added to save CPU/battery when invisible). Naïve removal regresses that case.
- Need to verify with live capture (=PI_TUI_PROFILE=1=) that the throttle is actually pegged at 500ms during a user-reported freeze, not at 16ms-with-stuck-dirty (candidate B).
- The fix should preserve the throttle intent but ensure visible streams paint reasonably even when "unfocused" — e.g. allow setImmediate-rate up to some cap during active streams, fall back to 500ms only when truly idle.

** Suggested fix shape (for the implementation session)

Option 1 — restore focused interval whenever an agent stream is active:
- Plumb a "isStreaming" signal from =AgentSession= to the focus-throttle subscriber.
- =unfocusedInterval = isStreaming ? focusedInterval : 500=.
- Pro: zero perceptual cost during streams; preserves idle savings.
- Con: minor plumbing across module boundaries.

Option 2 — cap unfocused throttle at 100ms instead of 500ms:
- Single number change.
- Pro: trivial.
- Con: gives back ~5x CPU savings, less aligned with original intent.

Option 3 — fire a forced render every K events regardless of throttle:
- Counter inside =requestRender=; every N=10 calls bypass throttle.
- Pro: caps perceived freeze to a bounded number of events.
- Con: complicates the throttle contract; harder to reason about.

Recommend Option 1.

** Fix shape: Option 1 from the triage update

Extracted the (focused, streaming) → throttle decision into =packages/coding-agent/src/modes/focus-render-throttle.ts= as a pure class with one method per signal and an =applyInterval= sink. Wired it in =interactive-mode.ts= via:

- existing =terminal.onFocusChange= subscriber → =setFocused(focused)=
- new =session.subscribe= filter on =agent_start= / =agent_end= → =setStreaming(true|false)=

Decision table the throttle implements:

| focused | streaming | interval          |
|---------+-----------+-------------------|
| true    | *         | focusedInterval   |
| false   | true      | focusedInterval   |
| false   | false     | unfocusedInterval |

Idle CPU/battery savings (FEAT-358) preserved: as soon as =agent_end= fires while still unfocused, the 500ms interval restores.

** Implementation notes worth keeping

- Construction does NOT call =applyInterval=. The caller already created the TUI with its own default; an apply on construction would be noise. =#lastApplied= dedupe ensures no spurious calls on idempotent state transitions.
- The clamp =unfocusedInterval = max(focusedInterval, unfocusedInterval)= sits in the throttle constructor — if a caller (or settings override) ever picks a smaller unfocused, we silently raise it. Observable through =currentInterval= getter (used by tests).
- Multiple focus toggles during a single stream stay at focusedInterval — verified by the "multiple focus toggles during a single stream" test. The streaming signal pins the responsive interval; focus chatter has no effect.

** Why this is not a regression of FEAT-358

FEAT-358 saved CPU/battery for IDLE unfocused terminals (background omp running with nothing happening). This fix preserves that exact case (idle + unfocused = 500ms) and only changes ACTIVE + unfocused, which is the case the operator actually cares about.
