* Initial Message

I think that when the model sends several tool calls at the same time in the same thread, they seem to be queued and not asynchronous, which makes it much slower. Am I right? Please investigate and report back

* Symptom
In a live session the TUI shows tool cells stuck in *pending* state (bare title, no result icon, no output) even though the session is actively running and later tool calls complete. Reloading a session shows the same phantom-pending cells permanently.

* Root Cause
A tool cell renders pending iff its =ToolExecutionComponent= never receives =updateResult(result, /*isPartial=*/false)=. Two cleanup paths drop the =pendingTools= entry *without finalizing the component*:

1. Live path — =packages/coding-agent/src/modes/controllers/event-controller.ts= =agent_end= case (~line 578):
#+begin_src ts
for (const toolCallId of Array.from(this.ctx.pendingTools.keys())) {
    if (!this.#backgroundToolCallIds.has(toolCallId)) {
        this.ctx.pendingTools.delete(toolCallId);   // deletes tracking, never finalizes
    }
}
#+end_src
The component object stays a child of =chatContainer= frozen with =#result === undefined=, so =#formatToolExecution()= returns only the title line (=if (!this.#result) return ...=). Visually pending forever.

2. Replay path — =packages/coding-agent/src/modes/utils/ui-helpers.ts= history render, trailing =this.ctx.pendingTools.clear()= (~line 375). A =toolCall= with no matching =toolResult= is added to =pendingTools= (and a cell to the container), the match loop only finalizes cells that *have* a result, and =clear()= discards the rest without =updateResult=. Ghost pending cell on every reload.

* Trigger
An assistant =toolCall= with no persisted =toolResult=. Produced by:
- Hard process kill mid-execution (reboot / crash / SIGKILL / OOM) — observed in session =14edc1bec5a09a49= line 2145 (a =task= call orphaned by "my computer had to reboot").
- Steering-skip results (="Skipped due to queued user message"=) are streamed to the UI but appear *not persisted* to JSONL (0 occurrences in the transcript scan), so on reload those skipped cells also lack a =toolResult=.
- A batch of =exclusive= tools (bash/edit) interrupted mid-run leaves *all not-yet-run* calls in that assistant message unpaired at once → a whole cluster of pending cells.

* Scope
In:
- Finalize lingering =pendingTools= components instead of silently dropping them, at BOTH sites (=agent_end= sweep + replay tail).
- Genuinely-still-running background tool calls (=#backgroundToolCallIds=) must be left untouched.
- A terminal =updateResult({ isError: true, content: [{type:"text", text:"Interrupted (no result recorded)"}] }, false, id)= so the cell flips out of pending.

Out:
- The durable transcript-pairing repair (separate bug; see Related). This bug is the UI-only immediate fix.
- Any change to =exclusive= concurrency scheduling.

* Existing Patterns
- =event-controller.ts= already finalizes on error stop in =message_end= (=hasErrorStop && toolFailureMessage= branch) via =component.updateResult(..., false, id)= then =pendingTools.delete=. Mirror that shape in the sweep.
- =ui-helpers.ts= already calls =component.updateResult(message, false, ...)= when a matching =toolResult= exists; the fix is to also finalize the *unmatched* leftovers before =clear()=.
- =ToolExecutionComponent.updateResult= (=packages/coding-agent/src/modes/components/tool-execution.ts=) and =ReadToolGroupComponent.updateResult= both accept the terminal call.
