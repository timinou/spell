* Problem

=applyOps= in =packages/coding-agent/src/tools/todo-write.ts= validates blocker references via a post-snapshot sweep (lines 640-649):

#+begin_src typescript
// Validate dangling blocker refs — warn but don't change behavior (missing = resolved)

This runs on every =todo_write= call regardless of whether the current op touched blockers. When =AgentSession='s auto-clear timer (see sibling bug [[id:BUG-190-todo-auto-clear-preserves-blocker-refere][BUG-190 todo auto-clear preserves blocker-referenced completed tasks]]) physically removes a completed blocker target, every dependent's =blockers= array retains the stale id. Each subsequent =todo_write= call emits one error per dangling ref, forever, until the session dies.

The functional behavior is already correct — =hasUnresolvedBlockers= at line 430 treats missing refs as resolved — but the validator noise is misleading: it frames a legitimate post-clear state as a data integrity failure.
* Scope

This item fixes the *validator + self-healing* side of the problem. The *auto-clear prevention* side is covered by the sibling bug [[id:BUG-190-todo-auto-clear-preserves-blocker-refere][BUG-190 todo auto-clear preserves blocker-referenced completed tasks]]. Both items are needed together. They touch disjoint files and can be implemented in parallel.
* Design decisions

1. *Validation is per-op, not per-snapshot*. An error is produced only when the current =ops= batch creates or updates a task with a blocker id that does not resolve in the final state. Pre-existing dangling refs (from auto-clear fallout or external mutations) are never flagged.
2. *Silent self-healing*. After validation, every remaining task's =blockers= array is rewritten to drop any id that no longer resolves to a task in the final state. This is silent — no error, no warning, no log entry. The rationale: the intended behavior of a completed/removed blocker is exactly "resolved", and a dangling id carries no information the system needs to preserve.
3. *Validation order*. Validate FIRST (so a user-supplied bad ref in the current op surfaces), then prune (so the resulting file is always clean). This means a user who submits =update id=task-7 blockers=["task-99"]= in the same batch that also has pre-existing dangling refs on task-8 will see exactly one error for task-7, and task-8's blockers will be pruned silently.
4. *Tracking which tasks to validate*. Maintain a =validateBlockersFor: Set<string>= inside =applyOps=. Populate from the ops:
   - =replace=: every new task id whose =blockers= is non-empty.
   - =add_phase=: every new task id whose =blockers= is non-empty.
   - =add_task=: the new task id if =blockers= is non-empty.
   - =update=: the task id iff =op.blockers !== undefined=.
5. *Error message format stays identical*. The existing test =`dangling blocker ref produces warning`= at =test/tools/todo-write.test.ts:357-375= asserts =`task-1 references non-existent blocker task-99`=. The new per-op validator must produce the same string for the same input.
6. *Pruning applies to every task*, not just tasks in =validateBlockersFor=. Non-touched tasks with pre-existing dangling refs also get cleaned. This is the whole point of self-healing.

   // Validate blockers only for tasks whose blockers were set in this ops batch.
   const allTaskIds = new Set(file.phases.flatMap(p => p.tasks.map(t => t.id)));
   for (const phase of file.phases) {
       for (const task of phase.tasks) {
           if (!validateBlockersFor.has(task.id)) continue;
           if (!task.blockers?.length) continue;
           for (const blockerId of task.blockers) {
               if (!allTaskIds.has(blockerId)) {
                   errors.push(`${task.id} references non-existent blocker ${blockerId}`);
               }
           }
       }
   }

   // Prune dangling blocker refs across ALL tasks (self-healing).
   for (const phase of file.phases) {
       for (const task of phase.tasks) {
           if (!task.blockers?.length) continue;
           const cleaned = task.blockers.filter(id => allTaskIds.has(id));
           if (cleaned.length !== task.blockers.length) {
               task.blockers = cleaned;
           }
       }
   }
   #+end_src

* Edge cases

- *User sets =blockers= to empty array in =update=*. =op.blockers !== undefined= → task id added to =validateBlockersFor= → validator loop sees =!task.blockers?.length= and skips. No false positive. Good.
- *User sets =blockers= to an array containing only already-resolved ids*. Validator passes (ids exist), prune is a no-op (all ids exist). No behavior change.
- *User sets =blockers= to a mix of valid + invalid ids*. Validator emits errors for the invalid ones. Prune then strips the invalid ones from the final state. The net effect: the user sees the error AND the valid blockers are preserved. Intentional: the user gets told, and the state stays clean.
- *Replace op with cross-references*. =replace= creates tasks sequentially with ids task-1, task-2, etc. A task-2 with =blockers: ["task-1"]= is valid because task-1 is already in the phase tasks array by the time task-2 is built. The finalize step runs after ALL replace phases are built, so the =allTaskIds= set contains every id. No issue. Contrast: a task-1 with =blockers: ["task-2"]= (forward ref within same replace) is also valid because finalize runs post-build.
- *Prune order*. Prune is idempotent — running it twice produces the same result. Running it once per =applyOps= call is sufficient.
