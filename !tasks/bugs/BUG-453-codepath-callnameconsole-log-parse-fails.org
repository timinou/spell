## Symptom
The edit tool's own cheat sheet documents `src/**/*.ts::§call[name=console.log]` for structural replace. But that target **parse-fails**: `unexpected trailing input: "[name=console.log]"`. Same for any dotted attribute value (`[name=a.b.c]`).

## Root cause (parse)
`crates/pi-code-path/src/parser.rs::attribute_predicate` parsed the unquoted value via `ident`, which only accepts alphanumeric + `_` + `-` → stops at the first `.`. The `=` then has dangling input.

## Fix (parse)
Unquoted attribute value now consumes a free token up to `]`/space (matching `compare_predicate`'s RHS grammar), so `name=console.log` and `name=a.b.c` parse. Quoted values still take precedence. Regression test `predicate_attribute_dotted_value`. All 525 pi-code-path lib tests pass; `[ext=ts]`, `[lang=rust]`, `[name="*.test.ts"]` unaffected.

## Remaining gap (resolver semantics) — follow-up
Even with the parse fixed, `§call[name=console.log]` resolves to ZERO nodes. The `name=` predicate matcher (`code_resolver/predicates.rs`) compares against `node.child_by_field_name("name")`, but a `call_expression`'s callee `console.log` is a `member_expression`, not a `name` field — so call-name matching never succeeds. The working alternative is `§call[text~="console.log"]` (verified). Either the resolver should special-case call callees for `name=`, or the docs/recipe should switch to `text~=`. Filed as the follow-up dimension; the parse blocker (the syntactic failure) is fixed here.
