## Symptom

User-facing failure, not retried:

```
Codex error event: An error occurred while processing your request. You can
retry your request, or contact us through our help center at help.openai.com
if the error persists. Please include the request ID
4c5a67ac-7cc9-4e41-a6db-28e82c9f72cd in your message. (code=server_error)
```

Expectation (user + repo convention): all transient/server-side errors (5xx,
408, 429, connection resets, provider-declared transient codes) should be
retried with exponential backoff. Only auth (401/403) and other 4xx
user-input errors should NOT retry.

## Root cause

Three independent "is this retryable?" classifiers exist and have drifted:

1. `packages/ai/src/utils/retry.ts::isRetryableError` — status-aware (retries
   ≥500, 408, 429; blocks 4xx via `VALIDATION_MESSAGE_PATTERN`). This is the
   *correct* semantics per the user's stated rule. **Exported but has zero
   runtime consumers — dead code.**
2. `packages/ai/src/providers/openai-codex-responses.ts` —
   `CODEX_RETRYABLE_EVENT_CODES = {model_error, server_error, internal_error}`
   + `CODEX_RETRYABLE_EVENT_MESSAGE` regex. Correctly classifies the reported
   error as retryable, but only runs in-stream, gated off by
   `context.output.content.length > 0` (any partial content already emitted
   → no retry) and a 5-attempt cap (`CODEX_MAX_RETRIES`). Backoff here is
   **linear** (`CODEX_RETRY_DELAY_MS * attempt`), not exponential.
3. `packages/coding-agent/src/session/agent-session.ts` —
   `#isRetryableErrorMessage` + `isProviderRetryableError` (from
   `providers/anthropic.ts`). This is the **final backstop** once the
   provider layer gives up / rethrows as a `stopReason:"error"` assistant
   message. It is pure phrase-regex and is the weakest of the three — it
   does NOT match the reported error.

Verified empirically (node repro against the exact reported string):

```
PROVIDER code=server_error retryable: true
PROVIDER msg regex match: true
SESSION  #isRetryableErrorMessage match: false   ← backstop says NO
SESSION  isProviderRetryableError match: false
utils/retry TRANSIENT match: false (also misses it, missing "server_error" code token)
```

∴ Provider layer knows this is transient; the session backstop (which is
what actually gates the user-visible retry loop after provider retries are
exhausted or content had started streaming) does not, so the retry chain
never starts and the raw error reaches the user.

## Confirmed retryable-but-not-retried cases (session backstop)

Tested via live regex extraction, session layer (`#isRetryableErrorMessage`
∨ `isProviderRetryableError`):

| error | retried today | should retry |
|---|---|---|
| `code=server_error` + "processing your request" (reported case) | ✗ | ✓ |
| `code=model_error` | ✗ | ✓ |
| "Please retry your request" / "temporarily unavailable" | ✗ | ✓ |
| HTTP 408 (request timeout) | ✗ | ✓ |
| HTTP 520/522/524 (Cloudflare edge) | ✗ | ✓ |
| HTTP 529 (Anthropic overloaded, bare status w/o other keywords) | ✗ | ✓ |
| `ECONNRESET` / `socket hang up` | ✗ | ✓ |
| `ETIMEDOUT` / `EAI_AGAIN` (DNS) | ✗ | ✓ |

429/500/502/503/504/"overloaded"/"rate limit" etc. already work correctly —
do not regress those.

4xx user errors (401/403/400/404/422) must remain non-retryable — preserve
`VALIDATION_MESSAGE_PATTERN`-equivalent blocking.

## Fix direction (agreed)

1. Consolidate: make the session backstop (`#isRetryableErrorMessage`)
   delegate to `packages/ai/src/utils/retry.ts::isRetryableError` (status
   extraction) as the primary check, keeping today's phrase-regex as a
   secondary fallback (don't lose existing matches).
2. Extend the retryable token set (session + central classifier as
   appropriate) to cover: `server_error`, `model_error`, `internal_error`,
   `408`, `520`, `522`, `524`, `529`, `ECONNRESET`, `ETIMEDOUT`, `EAI_AGAIN`,
   `socket hang up`, `please retry|processing your request|temporar(y|ily)`.
3. Keep 401/403/400/404/422 non-retryable — do not weaken
   `VALIDATION_MESSAGE_PATTERN` blocking semantics.
4. (Secondary, lower priority) provider-layer Codex in-stream retry backoff
   is linear (`CODEX_RETRY_DELAY_MS * attempt`) vs. session's exponential
   (`baseDelayMs * 2^attempt`) — align to exponential + jitter for
   consistency. Not the cause of this incident (session backstop gap is),
   but worth fixing alongside.
5. Add a regression test asserting the exact reported error string
   (`"Codex error event: An error occurred while processing your request. …
   (code=server_error)"`) is classified retryable by the session-level
   classifier.
