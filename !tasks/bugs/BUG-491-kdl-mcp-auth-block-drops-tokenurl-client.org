* Defect

`McpServerKdlEntry.auth` (packages/coding-agent/src/config/kdl-compatibility.ts:308) is typed `{ type: "oauth"|"apikey"; credentialId?: string }`. The runtime `MCPAuthConfig` (packages/coding-agent/src/mcp/types.ts:47) additionally carries `tokenUrl?`, `clientId?`, `clientSecret?` — all required by `MCPManager.#resolveAuthConfig` for proactive + forced token refresh. The KDL reader (`readMcpServers`, ~:391) and writer (`writeMcpServers`, ~:445) both silently drop these three fields.

Consequence: a `auth {}` block serialized to spell.kdl loses the refresh coordinates. On next launch the token cannot be refreshed → 401 on expiry. Blocks the entire feature: WAVE 2 writes this block and WAVE 3 depends on it surviving a round-trip.

* Fix (three edits, MUST move together)

1. `McpServerKdlEntry.auth` type — add `tokenUrl?: string`, `clientId?: string`, `clientSecret?: string`.
2. `readMcpServers` — read `tokenUrl`, `clientId`, `clientSecret` props off the `authNode` (mirror existing `credentialId` handling). Only accept strings.
3. `writeMcpServers` — emit those three props on the `auth` node when present (mirror existing `credentialId` write).

Note the existing reader/writer ALREADY handle the `auth {}` and `oauth {}` child nodes — this is purely widening which props are carried.

* Secret handling

`clientSecret` in KDL must be an env-var NAME, not a literal. Do NOT special-case here — `#resolveAuthConfig` already runs every header/env value through `resolveConfigValue` (env indirection). Just carry the string through faithfully. Document in a code comment that literal secrets must never be written.
