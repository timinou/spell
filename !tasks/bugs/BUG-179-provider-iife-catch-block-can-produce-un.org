* Problem
All 13 LLM provider stream functions use an async IIFE pattern:
#+begin_src typescript
(async () => {
  try {
    // ... stream processing ...
    stream.push({ type: "done", ... });
    stream.end();
  } catch (error) {
    const failure = await handleCodexStreamFailure(failureContext, error);
    stream.push({ type: "error", ... });
    stream.end();
  }
})();
#+end_src

If ~handleCodexStreamFailure~ (which calls ~await finalizeErrorMessage()~) throws, or if ~stream.push()~ / ~stream.end()~ throw in the catch block, the error escapes the IIFE as an unhandled rejection, crashing the process silently.

Additionally, ~agentLoop()~ and ~agentLoopContinue()~ in ~packages/agent/src/agent-loop.ts~ kick off ~runLoop()~ in an unguarded ~(async () => { await runLoop(...) })()~. If the provider error propagates through ~streamAssistantResponse()~, it becomes an unhandled rejection.

This is the root cause of session crashes where the process dies silently after writing a tool result but before the model responds.

* Design Decisions
1. Add a nested try/catch inside each provider's catch block so that ~handleCodexStreamFailure~ / ~finalizeErrorMessage~ failures don't escape
2. Add a ~.catch()~ on each provider's IIFE for defense-in-depth — if anything escapes the try/catch, push an error event to the stream and end it
3. Add try/catch wrapping around ~await runLoop()~ in the agent-loop IIFEs, pushing an ~agent_end~ event with error details to the stream
4. The ~.catch()~ handler should create a minimal error message (just the error string) and push ~{ type: "error", reason: "error", error: <minimal AssistantMessage> }~ followed by ~stream.end()~

* Edge Cases
- ~stream.push()~ may no-op if ~stream.done~ is already true — this is safe (the push method checks ~if (this.done) return~)
- ~stream.end()~ may be called twice — this is safe (it just sets ~done = true~ and notifies waiters)
- ~createAssistantOutput~ may not exist in every provider — each provider has its own output creation helper. Use the provider-specific one. For the ~.catch()~ fallback, create a minimal object inline.
- Some providers don't use ~finalizeErrorMessage~ (sync-only error handling) — still add the nested try/catch for consistency
