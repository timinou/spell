* Problem
Telegram's file download API returns =application/octet-stream= as =Content-Type= for photo files. The bridge passes this through to =ImageContentRef.mimeType=, which flows unchecked to the Anthropic provider. The provider unsafely casts it (line 306: =block.mimeType as "image/jpeg" | ...=) and sends it to the API, which rejects it with: =media_type: Input should be 'image/jpeg', 'image/png', 'image/gif' or 'image/webp'=.

Evidence from raw HTTP log (=1775215658404-2jmi8xr2b0rjl.json=):
#+begin_example
"type": "image",
"source": {
  "type": "base64",
  "media_type": "application/octet-stream",  <-- wrong
  ...
}
#+end_example

* Root Cause
=downloadTelegramFile= in =telegram-to-rpc.ts= uses =response.headers.get("content-type") ?? fallbackMediaType=. The fallback (="image/jpeg"=) is only used when the header is =null=, not when it's a non-image type like =application/octet-stream=. No validation or normalization exists anywhere in the path.

** Implement =normalizeImageMediaType= pure function
#+begin_src typescript
const VALID_IMAGE_MEDIA_TYPES = new Set(["image/jpeg", "image/png", "image/gif", "image/webp"]);

function normalizeImageMediaType(bytes: Uint8Array, headerMediaType: string, fallback: string): string {
    const stripped = headerMediaType.split(";")[0]!.trim().toLowerCase();
    if (VALID_IMAGE_MEDIA_TYPES.has(stripped)) return stripped;
    return detectImageTypeFromBytes(bytes) ?? fallback;
}
#+end_src
