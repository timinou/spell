## Audit Findings

### 1. `hasGate()` does not include `orgItemId`, causing silent gap in post-completion directives

- **What**: A task with only `orgItemId` (no other gate fields) triggers two-phase completion via `hasRequiredGate()`, but after completing with `verified: true`, line 461 uses `hasGate(task)` which returns `false`. The "Gate Requirements" section won't fire for orgItemId-only tasks, and the phase-completion aggregate at line 581 also misses them.
- **Where**: `packages/coding-agent/src/tools/todo-write.ts`, lines 461 and 581
- **Why**: Low practical impact because the two-phase checklist already forces the agent to acknowledge the orgItemId gate before completion. But it's an asymmetry — every other required gate gets a post-completion directive, orgItemId-only tasks don't. The fix is to either: (a) add `orgItemId` to `hasGate()`, or (b) change lines 461/581 to use `hasGate(task) || task.orgItemId`. Option (b) preserves the semantic distinction between `hasGate` (any gate including advisory) and `hasRequiredGate` (required gates only).
- **Effort**: `trivial`

### 2. `todo-reminder.ts` guard duplicates logic instead of reusing `hasRequiredGate`

- **What**: Line 51 uses `!hasGate(task) && !task.orgItemId` as a manual union rather than using a single predicate. If the set of fields in either function changes, this guard silently drifts.
- **Where**: `packages/coding-agent/src/modes/components/todo-reminder.ts`, line 51
- **Why**: Maintenance risk — if a new gate-like field is added, this guard must be manually updated. A single `!hasGate(task) && !hasRequiredGate(task)` would be future-proof and consistent.
- **Effort**: `trivial`

### 3. `findTodoItem` in `template.ts` duplicates `findTask` from `todo-write.ts`

- **What**: `template.ts:62` defines `findTodoItem(id, phases)` — identical logic to `todo-write.ts:154` `findTask(phases, id)` (only argument order differs). Both iterate phases and find by id.
- **Where**: `packages/coding-agent/src/task/template.ts`, line 62 vs `packages/coding-agent/src/tools/todo-write.ts`, line 154
- **Why**: Low risk since both are private. But `findTask` could be exported from `todo-write.ts` and reused, avoiding the second copy. The argument order difference (`phases, id` vs `id, phases`) makes this slightly fiddly.
- **Effort**: `small`

### 4. No test covers the two-phase rejection through `applyOps` end-to-end

- **What**: The tests cover `hasRequiredGate` and `formatSummary` with `pendingVerificationTasks`, but no test calls `applyOps` (or the tool's `execute` method) to verify the actual rejection flow — that passing `{status: "completed"}` on a gated task leaves the status unchanged and populates `pendingVerificationTasks`, and that a follow-up `{status: "completed", verified: true}` then succeeds.
- **Where**: `packages/coding-agent/test/tools/todo-write-gates.test.ts` — missing integration-level test
- **Why**: The `formatSummary` tests prove the rendering is correct given a `pendingVerificationTasks` array, but they don't prove `applyOps` actually populates it. If the two-phase check in `applyOps` regresses, no test catches it. The blocker rejection path (analogous feature) has full end-to-end coverage via the tool test file.
- **Effort**: `small`

### 5. `add_task` op does not support `after` positioning despite prompt documentation

- **What**: The `todo-write.md` prompt example at line 129 shows `after: "task-2"` in an `add_task` op, but neither the schema nor `applyOps` supports an `after` field on the `add_task` op. This pre-dates this PR but the new prompt content sits alongside it.
- **Where**: `packages/coding-agent/src/prompts/tools/todo-write.md`, line 129
- **Why**: The agent will send `after` in the JSON, it'll be silently ignored by the schema (TypeBox doesn't reject extra keys by default with `strict: true` on the tool level but not on individual union members). Pre-existing issue, not caused by this PR.
- **Effort**: `trivial` (to fix the prompt; `small` to implement the feature)

* Summary
The =add_task= example in =todo-write.md= line 129 has two problems:
1. Uses =after: "task-2"= which is not in the schema and is silently ignored
2. Nests fields in a =task: {content: ..., details: ...}= object, but the actual schema expects =content= and =details= as top-level properties of the op

This causes the agent to generate malformed add_task payloads that either fail validation or lose fields.
