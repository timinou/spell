* Initial Message

Noticed during triage of TUI mid-stream freeze (session =14f5aa3ae1ce24f4=). Same hazard family as =07c179a97= (LiveToolBatch dirty propagation) and BUG-391 (stuck-dirty root pattern).

* Symptom

=packages/coding-agent/src/modes/components/footer.ts::invalidate()= only clears its own cached branch state:

#+begin_src ts
invalidate(): void {
    // Invalidate cached branch so it gets re-read on next render
    this.#cachedBranch = undefined;
}
#+end_src

It does NOT call =super.invalidate()= (which is =Container.invalidate()=) and does NOT call =this.#parent?.markDirty()=. Effect: when an external trigger fires =footer.invalidate()=, the dirty bit is reset on the Footer itself, but the parent container never gets notified — so on the next render the parent's cache short-circuits and the footer's new branch value never reaches the screen.

In practice the footer is in the editor area, repainted on most events anyway, so the bug is mostly masked. But it is a latent stuck-dirty hazard of exactly the same shape as the LiveToolBatch one that was fixed in =07c179a97=, and it WILL surface if anything ever calls =footer.invalidate()= without an accompanying parent invalidation.

* Scope

In:
- Fix =Footer.invalidate()= to call =super.invalidate()= (which propagates =#parent?.markDirty()=) — or call =this.#parent?.markDirty()= directly.
- Add a unit test that calls =invalidate()= and asserts =markDirty= reaches the parent.

Out:
- Other dirty-propagation hazards (separate audit, tracked under the TUI-freeze investigation BUG).
- Footer rendering changes.
- The actual cache-clearing logic — that part is correct.

* Edge cases

- The cache clear must happen BEFORE the parent is notified, so the parent's next render sees fresh state. Both options preserve this order.
- =setExpanded= / =setUsageInfo= adjacent on other components mutate state then call =updateContent= or =invalidate=. Footer has no such pattern — its only state is the cached branch — so no additional call sites need updating.
