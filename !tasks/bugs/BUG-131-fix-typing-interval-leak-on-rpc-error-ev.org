## Audit Findings

### Finding 1: Typing interval leak on `error` event

- **What**: The inline `error` event handler (line 152-160) sets `#finalized = true` and clears the draft timer, but does **not** call `#clearTypingInterval()`. This is a separate code path from `#finalize()` — the `setInterval` continues firing indefinitely after an RPC error.
- **Where**: `packages/spell-server/src/telegram/bridge/rpc-to-telegram.ts`, line 154 (the `case "error":` handler)
- **Why**: Leaked `setInterval` calling `replyWithChatAction("typing")` indefinitely on a dead conversation. Each tick hits the Telegram API and logs a warning if it fails. In long-running bot processes, leaked intervals accumulate per errored conversation. This is a real resource leak.
- **Effort**: `trivial` — add `this.#clearTypingInterval();` after `this.#clearDraftTimer();` on line 154.

### Finding 2: No test for typing interval cleanup on `error` event path

- **What**: The `error` event path (finding 1) has no test asserting typing cleanup. The existing "forwards RPC error events" test (line 325) doesn't check `_chatActions` or interval behavior.
- **Where**: `packages/spell-server/test/telegram/bridge.test.ts`, around the "forwards RPC error events" test
- **Why**: The leak in finding 1 went undetected because this path has no typing-related coverage. A test sending an error event then waiting 50ms and asserting no new typing actions would catch this.
- **Effort**: `trivial` — add similar assertions to the existing error event test or create a dedicated test.

### Finding 3: `#chatId` field is now only used as a guard, not passed to any API

- **What**: `#chatId` was previously passed as an argument to `sendDraft(ctx, chatId, text)`. After the fix, it's only used as a null-check guard in three places. The `replyWithDraft`/`replyWithChatAction` context methods resolve `chatId` from their own `this.chatId`. The field still serves its purpose (preventing calls when no chat context exists), but the field name and the `#resolveChatId()` fallback logic (checking `ctx.message.chat.id` via cast) may be doing redundant work since grammY's context will throw internally if `chatId` is missing.
- **Where**: `packages/spell-server/src/telegram/bridge/rpc-to-telegram.ts`, lines 101, 237-246
- **Why**: Not a bug, but the dual resolution (our manual check + grammY's internal `orThrow`) is redundant. Low priority — the guard short-circuits work before building draft text, which is a minor optimization. Leave as-is.
- **Effort**: `small` — could simplify by trusting grammY's internal guard, but the short-circuit is marginally useful.

* Problem
