* Scope
Test: test/swarm/blackboard.test.ts "does not emit artifact events without DATA_URI and preserves metadata in reads".

Sequence:
1. `blackboard.open({sessionId:"sess-2", agent:"main", title:"Swarm Run"})` \u2014 writes lifecycle item `SWARM-sess-2`.
2. `blackboard.write({type:"finding", agent:"alpha", ...})` \u2014 writes `SWARM-sess-2-001`.
3. `blackboard.write({type:"progress", agent:"beta", ...})` \u2014 writes `SWARM-sess-2-002`.

Expected `read()` result: 3 entries in order. Observed: only the `beta/progress` entry.

Root cause (hypothesis, needs confirmation): `src/swarm/blackboard.ts::open/write` both call `appendItemToFile` from `@oh-my-pi/pi-org`, which dispatches `executeOrg({command:"createItem", id, ...})`. The native `createItem` may be replacing an existing file or not appending a new heading when the file already exists. Alternatively, `readCategory` may be deduping by filename.

The filter `.filter(item => item.id.startsWith(this.#runId ?? ""))` is correct (all three IDs start with `SWARM-sess-2`), so the issue is upstream of the filter.

In scope: restore "each write appends a distinct item heading" invariant so `read()` returns all three.
Out of scope: change the swarm data model; move to a different backing store.
