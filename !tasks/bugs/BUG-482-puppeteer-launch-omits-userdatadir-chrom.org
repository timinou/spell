* Initial Message

Chrome profile dirs `puppeteer_dev_chrome_profile-*` leak into the session's project tree (40+ found in ~/code/ora/verse). This is the one confirmed Spell-INTERNAL cwd-write leak; all other internal writes correctly use ~/.spell dir helpers (model cache → getModelDbPath SQLite, images → os.tmpdir).

* Root cause

packages/coding-agent/src/tools/browser.ts =#resetBrowser= calls =puppeteer.launch({...})= WITHOUT a =userDataDir=. Puppeteer/Chrome then creates its default profile (`puppeteer_dev_chrome_profile-*`) in =process.cwd()=. Because the interactive CLI/TUI runs many sessions + all subagents in ONE process and =setProjectDir= does a process-global =process.chdir=, process.cwd() is whatever project was last selected — so the profile can even land in the WRONG project.

* Fix

Pass an explicit =userDataDir= under ~/.spell/puppeteer (helper getPuppeteerDir() already exists). Must be UNIQUE per live browser to avoid Chrome's single-writer profile lock when multiple in-process sessions/subagents run browsers concurrently → use a per-session subdir (sessionId, fallback per-instance Snowflake): =path.join(getPuppeteerDir(), "profiles", <discriminator>)=. Best-effort rm the dir on =dispose()= (session shutdown) to bound cache growth.

* Acceptance

- puppeteer.launch receives userDataDir pointing under ~/.spell/puppeteer/profiles/<id>.
- No puppeteer_dev_chrome_profile-* can appear in cwd.
- Concurrent in-process browsers get distinct profile dirs (no profile-lock contention).
- tsgo check green; existing browser tests unaffected.
