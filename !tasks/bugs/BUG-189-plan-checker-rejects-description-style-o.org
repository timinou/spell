* Problem

=exit_plan_mode= rejects valid org description-style id links. A PLAN body that
contains only links like:

#+begin_example
- [[id:FEAT-072-webhook-health-pill-and-status-poller-vi][FEAT-072]] — Webhook health + poller visibility (2h)
#+end_example

fails with:

#+begin_example
PLAN item "PLAN-018-ubikom-survey-ops-excellence" must include at least one child reference using [[id:...]] links in its body.
#+end_example

even though description-form links are valid org syntax and render correctly in
Emacs, the elisp =org-fluid-plan--extract-plan-child-ids= extractor, and
anywhere else the user writes them.

* Root cause

Two independent TypeScript extractors both hard-code the trailing double-close-bracket
with no allowance for the org description form =[[target][description]]=:

1. =packages/org/src/id-links.ts= — canonical strict extractor used by
   =exit_plan_mode= via =extractIdLinks=. Current regex (see file, line 7):

   - literal =[[id:=
   - capture: =[A-Z]+-\d+(?:-[a-z0-9-]+)?(?:::[a-z0-9-]+)?=
   - literal =]]=
   - flag =g=

2. =packages/coding-agent/src/loop/ingestion/parser.ts= — loose extractor
   used by loop-ingestion validator to cross-reference =[[id:...]]=
   references against discovered CUSTOM_IDs. Current regex (see file, line
   35):

   - literal =[[id:=
   - capture: one-or-more non-close-bracket characters
   - literal =]]=
   - flag =g=

Both regexes require the captured target to be followed immediately by two
close brackets, so =[[id:X][desc]]= never matches. The elisp side
(=packages/org/elisp/tools/org-fluid-plan.el=,
=org-fluid-plan--extract-plan-child-ids=) already uses a single trailing
close bracket and handles both forms correctly — no elisp change needed.

Symptoms today:
- =exit_plan_mode= rejects PLANs whose manifest uses description links (user
  reproduction).
- =spec-ingestion= =validateParsedSpecs= silently flags description-form
  references as broken =[[id:]]= links because they are never extracted into
  =file.links=.

* Fix

Extend each regex to accept an optional non-capturing description segment
between the target's closing bracket and the link's final bracket:

- after the captured target, match one close bracket
- optionally match =[=, zero-or-more non-close-bracket characters, =]=
- then match the final close bracket

This preserves each extractor's capture group exactly — the strict extractor
keeps its strict CUSTOM_ID grammar, the loose extractor keeps its loose
any-non-close-bracket grammar. Neither is loosened; only the terminator is
extended to tolerate a description segment.

1. =packages/org/src/id-links.ts= line 7 — new regex (ASCII-only
   description to avoid any tooling escape issues; in the source file it is a
   single JavaScript regex literal):

   - literal =[[id:=
   - capture group: =[A-Z]+-\d+(?:-[a-z0-9-]+)?(?:::[a-z0-9-]+)?=
   - literal =]=
   - optional group: =(?:\[[^\]]*\])?=
   - literal =]=
   - flag =g=

2. =packages/coding-agent/src/loop/ingestion/parser.ts= line 35 — new regex:

   - literal =[[id:=
   - capture group: =[^\]]+=
   - literal =]=
   - optional group: =(?:\[[^\]]*\])?=
   - literal =]=
   - flag =g=

Do not introduce a new shared helper; the two callers have different
strictness by design and should not be unified as part of this fix.
