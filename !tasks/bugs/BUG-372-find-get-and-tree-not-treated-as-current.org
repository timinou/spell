Please explain what went wrong.


* Initial Message

In a session whose cwd was =/home/user/code/ora/cais= the agent issued:

#+begin_example
find { target: ".#tree" }
#+end_example

and received:

#+begin_example
[§no-results] .#tree
  reason:    no-match
  try next:  verify path/symbol exists, or try target: "."
#+end_example

The hint sent the agent to =target: "."= — which then returned
=[§no-results]= as well. In effect, the CodePath grammar refuses
to admit the most basic shell affordance: =.= as "this directory".

* Symptom
1. =find { target: ".#tree" }= → no-match (parser reads =.= as a
   hidden filename literal, not a directory).
2. =find { target: "." }= → empty (walker doesn't recognise the
   literal =.= as the root alias).
3. =find { target: "./" }=, =find { target: "./#tree" }= — both fail
   the same way.

Bare =.= and =.#tree= must Just Work. Every shell, every CLI, every
fs API treats =.= as the cwd; CodePath silently dropping it is
hostile to anyone reaching for the lowest-friction listing call.

* Root Cause
=crates/pi-code-path/src/parser.rs::path_until_kernel_op= happily
consumes =.= as a literal FS segment. =tokenise_fs_path= produces
=FsLocator { segments: [Literal(".")] }=. Then in
=crates/pi-code-path/src/dialects/fs/walker.rs=:

#+begin_example
let pattern = fs_locator_to_glob(loc);  // "."
let globset = build_globset(&pattern);  // matches paths literally named "."
…
let rel = path.strip_prefix(&opts.root)?;  // "" for the root entry
if !gs.is_match(rel) { continue; }        // "" never matches "."
#+end_example

So the literal =.= glob never matches the empty relative path that
=ignore::WalkBuilder= emits for the root directory. =FsResolver=
returns =Ok([])= and the qualifier loop has nothing to apply
=#tree= to.

* Acceptance
- =find { target: "." }= returns =#listing= of the walker root
  (matches the behaviour the TS-side auto-attach already promises
  for bare directory paths).
- =find { target: ".#tree" }= returns the recursive tree of the
  walker root.
- =find { target: "./" }=, =find { target: "./src" }=,
  =find { target: "../" }= behave consistently with their non-=.=
  equivalents.
- =edit { target: ".", action: ... }= is still rejected for
  ambiguity — this fix only touches read-side resolution.

* Edge Cases
- Hidden file actually named =.= or =.foo= must still resolve
  normally (covered by tokenising =.= followed by another path
  segment as a literal name rather than a cwd alias).
- =..= alias outside the project root: surfaced via BUG-373
  (OUT_OF_PROJECT_ROOT for non-bare-plain absolute targets).
- =cd= isn't a thing here — the walker root is the session cwd
  (find delegates with =root: session.cwd=).
