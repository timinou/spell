* Symptom
The find tool doc (packages/coding-agent/src/prompts/tools/find.md) Qualifiers table lists:
| #match | file, symbol | — |
But `find { "foo.ts::greet#match" }` → `[unsupported_operation] unknown qualifier 'match'`.

* Root cause
`#match` is implemented only in the *text* dialect and requires a preceding `TextMatch` predicate:
- crates/pi-code-path/src/dialects/text/qualifiers.rs:26 `"match" => resolve_match(...)`
- :91 `"#match requires preceding TextMatch predicate"`
It is registered in introspection (crates/pi-code-path/src/introspection.rs:190) which is presumably what the doc generator picked up, but no fs/symbol dialect resolves it. So the capability matrix in the doc over-promises.

* Fix direction (pick one)
A. *Doc-truthful*: regenerate the qualifier table from actual per-dialect resolver support so `#match` is shown only where it resolves (text/grep contexts with a TextMatch predicate). Cheapest, correct.
B. *Implement-symbol-match*: define `#match` on symbol/file targets as "the matched node's full span text" (≈ `#text` of the resolved node) and wire it into the fs/code dialects. More work; only if there's a real use distinct from `#text`/`#body`.

Recommend A unless a symbol-level `#match` has a concrete consumer. Either way the doc and the resolver capability set must agree (FEAT-728/727-style invariant test would catch this drift).
