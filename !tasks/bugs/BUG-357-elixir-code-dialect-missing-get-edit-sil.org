* Initial Message

User reported recent Elixir sessions kept reaching for Python to mutate `.ex`/`.exs` files. Investigation traced the cause: the elixir tree-sitter grammar and `LanguageProfile` exist, but no `LanguageDialect` is wired in, so the code-path resolver falls back to the text dialect.

* Symptom

`get .scratch/elixir/calculator.ex::Calculator.add` returns:
#+BEGIN_EXAMPLE
.scratch/elixir/calculator.ex  [§file]

Diagnostics:
[unsupported_operation] no code dialect for extension ex; falling back to text dialect
#+END_EXAMPLE

The fallback returns the *whole file* with the dialect diagnostic — visually similar to "no symbol exists", which led prior sessions to abandon the structural path.

`edit … file.ex::Symbol …` (findAndReplace, delete, rename, insertAfter) actually *works* because the engine's edit resolver uses the parser+profile directly. But:
- `edit file.ex … findAndReplace …` (no `::Symbol` scope) fails with `no resolver supports action FindAndReplace`.
- `wrap` produces broken `$BODY` substitution on elixir defs.
- `get … #stat` and `get … ::Symbol` both degrade.

* Root cause

- =crates/pi-code-engine/src/language/mod.rs:1626= sets =dialect: None= in =elixir_profile()=.
- =crates/pi-code-path/src/dialects/= has no =elixir.rs= module. Spec at =crates/pi-code-path/src/dialects/mod.rs= lists 8 planned dialects (TS, Rust, Python, Go, Haskell, HTML, CSS, MD/Org); Elixir was never on the list.
- The walker at =crates/pi-natives/src/code_path/code_resolver/walker.rs:60-66= reads =profile.dialect=, errors with the diagnostic, and returns =Err(NoMatches…)= which the upstream coerces to a degraded full-file payload.
