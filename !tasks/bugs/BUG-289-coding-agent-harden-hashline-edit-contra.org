What is the problem?

* Scope

In scope:
- Prevent malformed hashline =edit= requests from failing opaquely in =packages/coding-agent/=, with focus on anchorless or unparseable =replace= requests.
- Preserve the strict safety policy already encoded in =packages/coding-agent/src/patch/index.ts::resolveEditAnchors=: never guess anchors, never silently widen a replace, never fall back to whole-file replacement.
- Improve the end-to-end contract across prompt guidance, request validation, runtime errors, and user-visible render/reporting so an agent can recover by re-reading and retrying with valid =LINE#ID= anchors.
- Add targeted regression coverage for the edit contract and the hashline failure paths.
- Reference overlap with [[id:PLAN-254-cross-session-edit-coordination]] only where shared edit/TUI surfaces exist, especially =packages/coding-agent/src/patch/shared.ts= and adjacent edit-result rendering paths that PLAN-254 follow-up work will touch.

Out of scope:
- Broker, journal, socket, undo/redo attribution, or any other core coordination work from PLAN-254.
- Auto-recovery that invents anchors or rewrites the request into a whole-file replace.
- CRDT/Loro, peer conflict policy, or CodePath transaction changes.

Rationale:
The observed failure mode is a coding-agent edit-contract bug: the file exists, but the edit request reaches hashline =replace= without any valid anchor, producing the generic message =Replace requires at least one anchor (tag or end).= The system needs stricter, more actionable guidance before and at failure time, while keeping the existing safety boundary intact.

* Tests

User / agent workflows that MUST be covered:
1. Agent reads a hashline-rendered text file, then submits a valid single-line =replace= with =pos= → succeeds unchanged from today.
2. Agent submits =replace= with neither =pos= nor =end= → strict failure, but the surfaced error explicitly tells the caller that =replace= requires at least one valid anchor and that the recovery path is to re-read and retry with =LINE#ID= references.
3. Agent submits =replace= with a malformed anchor string that cannot parse as =LINE#ID= → strict failure that distinguishes malformed references from missing references.
4. Agent submits =replace= with a stale hash → existing =HashlineMismatchError= mapping and remap guidance still works; the new work MUST NOT collapse stale-hash failures into the new missing-anchor diagnostic.
5. Streaming / rendered edit output still shows enough context for the operator to understand what failed, and future PLAN-254 peer-activity/footer work in the shared renderer is not boxed into a conflicting format.
6. Code-supported file redirect behavior still wins before text-hashline mutation where applicable; this work is for unsupported/text-file hashline flows such as =Cargo.toml=, not a rollback of the =code edit= preference.

* Edge Cases

- The caller may provide =pos= or =end= fields that exist syntactically but are empty, whitespace-only, or copied with polluted display prefixes. Distinguish parse failure from absence cleanly.
- Preserve current heuristic cleanup of copied hashline display content where safe, but do not let that mutate a malformed anchor into a silently accepted different target.
- Do not regress create-file behavior where anchorless =append= / =prepend= is already intentionally allowed for missing files.
- Do not degrade code-supported-file redirect behavior. If the path is code-supported, =code edit= guidance remains the correct answer.
- Any new UI hinting in shared edit renderers must not block or conflict with PLAN-254 peer-activity footer/status work.
