* Problem

When the QML daemon socket closes unexpectedly (concurrent session race, daemon restart, etc.),
the bridge delivers ~socket_disconnected~ events to the phoenix inspector's event loop. The event
loop receives them — ~waitForEvent~ correctly wakes and returns events with ~name: "socket_disconnected"~.
However, ~startBridgeEventLoop~ iterates the events and passes only ~event.payload~ to ~handleBridgePayload~,
never checking ~event.name~. The payload ~{ message: "Daemon socket closed unexpectedly" }~ has no ~action~,
~_tier~, or ~_tool~ field, so ~handleBridgePayload~ falls through to ~if (!action) return~ at line 326 and
silently discards the disconnect signal. The loop then calls ~waitForEvent~ again — if ~QmlProcess.autoReconnect~
succeeds in the background (within ~3.1s), events resume. If it fails after 5 attempts, ~waitForEvent~ blocks
for the full 10-minute timeout, making the inspector appear frozen.

The canvas tool (~packages/coding-agent/src/tools/canvas.ts~ lines 406-417) already handles this correctly:
it checks ~raw.some(e => e.name === "socket_disconnected")~ BEFORE iterating payloads, then sleeps 2s for
autoReconnect and retries up to 3 times. The inspector must adopt the same pattern.

* Root Cause Analysis

Event flow on socket disconnect:
1. ~QmlProcess~ socket close handler dispatches ~{ type: "socket_disconnected", id: "__socket__", message: "..." }~
2. ~QmlBridge.#handleEvent~ pushes ~{ name: "socket_disconnected", payload: { message } }~ to all active window event queues
3. ~waitForEvent~ listener wakes (line 269: ~event.type === "socket_disconnected" && win.events.length > 0~) — events delivered
4. ~startBridgeEventLoop~ iterates events: ~for (const event of events) { await handleBridgePayload(event.payload, ...) }~
5. ~handleBridgePayload~ sees payload ~{ message: "..." }~ — no action/tier/tool → ~if (!action) return~ at line 326
6. Loop re-calls ~waitForEvent~ — if autoReconnect failed, hangs for 10 minutes

The canvas tool intercepts at step 4, before payload iteration. The inspector doesn't.

* Design Decisions

1. Do NOT call ~bridge.reconnect()~ explicitly — ~QmlProcess.autoReconnect~ runs in background automatically. Canvas relies on this same pattern.
2. Use ~Bun.sleep(2000)~ to wait for autoReconnect, matching canvas.ts pattern. AutoReconnect delays total ~3.1s, so 2s sleep with up to 3 retries (6s total) gives adequate coverage.
3. Show toast notification via ~activeContext?.ui.notify("Phoenix inspector bridge reconnecting...", "warning")~ on first disconnect.
4. Show error notification via ~activeContext?.ui.notify("Phoenix inspector disconnected: bridge reconnect failed.", "error")~ when max retries exceeded.
5. Log via ~pi.logger.warn~ for debugging.
6. Max 3 reconnect attempts, matching canvas.ts.
7. Reset reconnect counter on successful event delivery (any non-disconnect batch).
8. Do NOT add ~reconnect()~ to ~QmlBridgeLike~ interface — not needed since autoReconnect handles it. Keeps the change minimal.
