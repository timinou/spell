### 2. `StateStoreManager` constructor throws on missing SQLite file

- **What**: `new Database(resolvedPath, { readonly: true })` throws a synchronous error if the file doesn't exist. The constructor has no try/catch. If a KDL manifest declares a state store pointing to a not-yet-created database, the entire server startup crashes.
- **Where**: `packages/spell-server/src/state/store-manager.ts`, line 39
- **Why**: Production crash if the state store path is wrong or the DB hasn't been created yet. Startup failure prevents the entire server from running, including goals unrelated to state stores.
- **Effort**: `small` — wrap in try/catch, log warning, skip the connection

### 3. State store manager only collects from setups, misses goal-level state stores

- **What**: The constructor iterates `manifest.setups.values()` but `ManifestGoal` also has an optional `stateStores` field. Goal-level state stores are silently ignored.
- **Where**: `packages/spell-server/src/state/store-manager.ts`, lines 29-41
- **Why**: If a project declares state stores at goal level, they won't appear in the API. Currently growth doesn't use goal-level state stores, so no immediate impact, but the contract is incomplete.
- **Effort**: `small` — add a second loop over `manifest.goals.values()`

### 4. `queryTable` columns come from schema, not actual DB — possible mismatch

- **What**: `queryTable` returns `columns: table.columns.map(c => c.name)` from the KDL schema, but `rows` come from `SELECT *` on the actual SQLite table. If the schema is out of sync with the real table (e.g., a column was added via migration but not declared in KDL), the `columns` array won't match the row keys, and the frontend will render blank cells for undeclared columns.
- **Where**: `packages/spell-server/src/state/store-manager.ts`, lines 95 and 87-89
- **Why**: Silent data loss in the UI. Users see rows with data in columns not listed in the header.
- **Effort**: `small` — derive columns from `Object.keys(rows[0])` when rows exist, fall back to schema

### 5. `renderCellValue` double-parses JSON objects

- **What**: For strings starting with `{`, the function calls `JSON.parse(value)` on line 984 to validate, then calls `JSON.parse(value)` again on line 985 inside the template. Wastes CPU on every JSON cell render.
- **Where**: `packages/spell-server/src/http/frontend/index.html`, lines 984-985
- **Why**: Minor perf issue. Doubles parse cost for every JSON-valued cell in the state store data browser.
- **Effort**: `trivial` — capture the result of the first parse

### 6. `handleTableCount` runs a full `SELECT *` query just for count

- **What**: `handleTableCount` calls `manager.queryTable(storeName, tableName, 0, 0)` which executes both `SELECT * ... LIMIT 0 OFFSET 0` and `SELECT count(*)`. The `LIMIT 0` query is harmless but unnecessary. A dedicated count method would be cleaner.
- **Where**: `packages/spell-server/src/http/routes/state.ts`, line 51
- **Why**: Negligible impact since `LIMIT 0` returns no rows, but the pattern is misleading — it looks like it queries data when it only needs a count.
- **Effort**: `trivial` — either accept the current approach (it works) or add a `countTable` method

### 7. `toManifestJson` serializes Maps inside goals/setups as `{}`

- **What**: `Object.fromEntries(manifest.goals)` converts the top-level Map, but each `ManifestGoal` and `ManifestSetup` contains nested `stateStores: Map<string, NamedStateStore>`. `JSON.stringify` on a `Map` produces `{}`. State stores declared at goal/setup level are silently lost in the API response.
- **Where**: `packages/spell-server/src/http/routes/goals.ts`, lines 24-25
- **Why**: Frontend consumers never see state store configurations per goal/setup. This is pre-existing (the old code had the same issue), but now that the manifest API is the primary data source for the dashboard, the information gap is more visible.
- **Effort**: `medium` — need a recursive serializer that converts nested Maps to plain objects

### 8. No tests for the state store query API

- **What**: No test file for `state.ts` routes or `store-manager.ts`. The state store API was verified manually via curl but has no automated test coverage.
- **Where**: Missing `packages/spell-server/test/http/state.test.ts` and `packages/spell-server/test/state/store-manager.test.ts`
- **Why**: Regression risk — future changes to routing or query logic have no safety net. The FEAT-292 acceptance criteria called for tests.
- **Effort**: `medium` — need a fixture SQLite DB, tests for happy path, 404s, pagination, count
