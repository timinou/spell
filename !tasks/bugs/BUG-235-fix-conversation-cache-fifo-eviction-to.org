* Problem
In =packages/ai/src/providers/cursor.ts=, =setConversationCacheEntry()= (lines 132-150) uses two parallel ES6 Maps for conversation state and blob data. Eviction is FIFO based on Map insertion order. When an existing entry is updated via =Map.set()=, insertion order is NOT refreshed — the entry stays at its original position. This means an older but actively-used conversation can be evicted before newer but unused conversations.

* File
=packages/ai/src/providers/cursor.ts=, function =setConversationCacheEntry= (lines 132-150)

* Change
Use delete-then-insert pattern to refresh Map insertion order when updating existing entries. Before =.set()=, delete both keys first:

#+begin_src typescript
function setConversationCacheEntry(
	conversationId: string,
	conversationState: ConversationStateStructure,
	blobStore: Map<string, Uint8Array>,
): void {
	const isExisting =
		conversationStateCache.has(conversationId) || conversationBlobStores.has(conversationId);
	// Delete before set to refresh insertion order (Map.set on existing key does not move it)
	if (isExisting) {
		conversationStateCache.delete(conversationId);
		conversationBlobStores.delete(conversationId);
	}
	conversationStateCache.set(conversationId, conversationState);
	conversationBlobStores.set(conversationId, blobStore);
	if (isExisting || conversationStateCache.size <= MAX_CONVERSATION_CACHE_ENTRIES) {
		return;
	}
	const oldestConversationId = conversationStateCache.keys().next().value as string | undefined;
	if (!oldestConversationId || oldestConversationId === conversationId) {
		return;
	}
	conversationStateCache.delete(oldestConversationId);
	conversationBlobStores.delete(oldestConversationId);
}
#+end_src

The eviction guard =if (isExisting || ...)= still correctly skips eviction when updating an existing entry (size didn't grow), but now =isExisting= is computed before the delete, so the logic is unchanged.

* Verification
** =bun check:ts= passes.
** Verify: after the change, a conversation that is frequently updated (via checkpoints during streaming) stays at the "newest" position in Map iteration order and is evicted last, not first.
** =MAX_CONVERSATION_CACHE_ENTRIES= remains 20. The 21st unique conversation triggers eviction of the least-recently-used, not the least-recently-inserted.

* Edge Cases
- New entry (not previously cached): delete is a no-op, behavior unchanged.
- Entry updated multiple times in rapid succession: each update refreshes position correctly.
- Eviction of self: the guard =oldestConversationId === conversationId= prevents a newly-inserted entry from evicting itself (important when it was just deleted and re-inserted).
