* Scope
When the rendered transcript exceeds a threshold (~messageCount > N~ or
~markdown.length > Mbytes~), call a cheap model to produce a TL;DR section that:

1. is *prepended* to the markdown fed into the renderer (so the PDF gets a
   "Summary" card on page 1),
2. is *also used* as the body of the Telegram caption (so the message-body
   text isn't just the verbatim last assistant turn — it's a thoughtful
   summary covering what's pending and why).

KDL config:

#+begin_src kdl
attach renderer="pdf" {
    transcript "full"
    on "ask" "hook_input" "plan_approval"
    summarize when="message-count>30" {
        model "gpt-5.4-nano"
        max-tokens 250
        prompt-style "needs-input-recap"
    }
}
#+end_src

* Tests (TDD)
- ~messageCount~ below threshold → summarizer not called; existing flow unchanged.
- ~messageCount~ above threshold → summarizer called once; TL;DR prepended to markdown
  AND used as caption body.
- Summarizer error → fall back to last-assistant-text caption + un-summarized PDF
  (no fatal failure on user-facing path).
- Summary cached by transcript hash (so re-fires don't re-summarize the same content).
- Summary respects ~max-tokens~ (truncated cleanly with ellipsis).
- Prompt style ~"needs-input-recap"~ produces TL;DR oriented around what the user
  is being asked to decide (verified by snapshot test of the system prompt).

* Edge Cases
- Model not found → boot diagnostic; ~summarize~ block ignored at runtime.
- Network failure to upstream → fall back without retry storm.
- Threshold expression (~"message-count>30"~) parse error → boot diagnostic.
