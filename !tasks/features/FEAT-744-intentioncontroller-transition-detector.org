* Implementation
1. New ~packages/coding-agent/src/modes/controllers/intention-controller.ts~ exporting ~IntentionController~:
   - Constructor: ~(deps: { sessionManager, settings, modelRegistry, getBlockingEvent: () => BlockingEventLike | undefined, getCurrentModel: () => Model<Api> | undefined, getSessionId: () => string | undefined })~.
   - Owns ~#lastBriefedStatus: AgentStatus | null~, ~#pendingGen: AbortController | null~, ~#activeEntryId: string | null~.
   - ~handleStatusChange(prev, next)~ — pure logic, exhaustively unit-tested.
   - ~#fireBriefing(trigger)~ — synchronously appends placeholder via ~appendCustomMessageEntry(INTENTION_SUMMARY_MESSAGE_TYPE, buildIntentionSummaryContent({did:"", ask:"", trigger}), true, { …details, pending:true }, "agent")~; stores returned id; kicks off ~generateIntentionSummary(...)~ from FEAT-742; on resolve mutates the same entry by walking ~getEntries()~ to find the entry by id, updating ~entry.content~ + ~entry.details~, then awaiting ~rewriteEntries()~.
   - ~#supersedePrior()~ — finds prior intentionSummary entries with ~details.superseded !== true~, sets ~superseded:true~, then ~rewriteEntries()~.
   - ~dispose()~ — abort pending, drop subscription.
2. In-place mutation note: ~rewriteEntries()~ is documented as "use sparingly". Briefings happen at most a handful of times per session, so frequency is acceptable. If the cost ever matters, the controller can batch supersede + resolve into a single ~rewriteEntries~ call.
3. Wire in ~packages/coding-agent/src/modes/interactive-mode.ts~:
   - Construct ~IntentionController~ next to other controllers (search for ~InputController~ instantiation site).
   - Where ~AgentStatus~ is currently computed for ~deriveAgentStatus~ consumers, ALSO call ~intentionController.handleStatusChange(prev, next)~. A small ~#lastDerivedStatus: AgentStatus | null~ field on the mode keeps the prev/next pair without coupling new infrastructure.
   - Add ~intentionController.dispose()~ in the existing shutdown path next to other controller disposals.
4. Resume rehydration: at controller construct, run a single sweep over ~sessionManager.getEntries()~:
   - find the latest entry with ~type === "custom_message" && customType === INTENTION_SUMMARY_MESSAGE_TYPE~;
   - if its ~details.pending~ is true → mark ~superseded:true~ (orphan from previous run) and persist.
   - set ~#lastBriefedStatus~ from the current derived status so the very first ~handleStatusChange~ call after construct does not double-fire.

* Edge Cases
- Multiple rapid transitions: ~#pendingGen?.abort()~ before each new fire.
- ~user_paused~: treat any transition into ~user_paused~ as "no new briefing" and treat coming back from ~user_paused~ to ~needs_input~ as "still the same briefing" (do not re-fire). Encode this by treating the (user_paused → needs_input) edge as NOT a rising edge.
- BlockingEvent superseded by a new one (different ~eventId~) without an intervening non-briefing state: treat as a fresh briefing trigger; supersede the prior card.
- Generator latency exceeds the session lifetime: placeholder remains as ~pending:true~ on disk; T8 covers cleanup on next resume.
