* Scope

**In scope:**
- Chained transitions: ~afterComplete~ frontmatter field triggers next mode after current exits (e.g., ~afterComplete: audit~ to run audit after plan completes)
- Nested modes: parent mode suspends while child mode runs, parent resumes after child exits. Implemented as a mode stack. The existing plan->audit pattern is the canonical example.
- Context policies in frontmatter: ~contextPolicy: 'fresh' | 'carry' | { type: 'summarize', description: '...' }~
  - ~fresh~: new session, cleared context (current plan execution behavior)
  - ~carry~: keep full conversation context across mode transition
  - ~summarize~: run LLM compaction at mode exit with user-defined description guiding what to keep
- Context passing: next mode receives previous mode's output artifacts (plan file path, org item IDs, findings)

**Out of scope:**
- Multiple simultaneous modes (strictly one active mode, possibly with suspended parent)
- Loop-specific transitions (FEAT: Loop Mode Integration)
- Canvas-specific transitions (FEAT: Canvas Integration)

**Boundary rationale:** Transitions and context management form a cohesive unit: you can't implement chained modes without deciding what context flows between them. The mode stack for nested modes is the most complex part and justifies a dedicated item.

* Edge Cases
- Chained to self: mode A with ~afterComplete: 'A'~ -> error at validation, not infinite loop
- Nested mode exit while parent was deleted from .spell/modes/ -> degrade gracefully, enter no-mode
- Summarize policy with very long conversation -> compaction may take several seconds; show progress indicator
- Chained mode not found at runtime (deleted between activation and exit) -> warn, enter no-mode
- Stack serialization for session persistence -> serialize full stack, not just top
- Context policy on the FIRST mode entry (no previous mode) -> fresh and carry are no-ops; summarize is no-op
