* Scope

**In scope:**
- Per-phase prompt customization via mode config: mode's ~## Instructions~ section injected into each loop phase (plan, code, review) prompt
- Mode-specific loop gate configuration: mode config ~gates~ applied to loop gate evaluator
- Loop role prompts customizable: mode config can provide role-specific instructions via ~## Plan Phase~, ~## Code Phase~, ~## Review Phase~ body sections
- Mode context injection: mode's ~## Context~ section available to all loop phases
- Loop phase pipeline stays hardcoded (plan->code->review) — custom phase sequences are future work

**Out of scope:**
- Custom phase sequences (plan->code->review stays fixed)
- Loop monitoring canvas UI (FEAT: Canvas Integration)
- Loop creation from UI (future Phase 3+)
- Full loop state machine changes

**Boundary rationale:** The loop system is in PoC state. This item adds the minimal integration surface: mode configs can customize WHAT the loop does in each phase (prompts, gates) without changing HOW it executes (state machine, phase sequence). This is the safe first step that enables cofounders to define custom loop workflows without destabilizing the loop kernel.

- Loop started before mode activated -> no mode injection
- Mode deactivated during active loop -> loop continues with whatever context was injected at start

- Very large mode context + phase instructions -> may approach context limits; no truncation, let LLM window be the bound
