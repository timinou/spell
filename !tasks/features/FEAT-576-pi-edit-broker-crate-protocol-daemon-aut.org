* Scope
Ship a new crate =crates/pi-edit-broker/= producing a standalone Rust binary `pi-edit-broker`. The binary self-daemonizes, listens on `~/.spell/edit-broker.sock`, accepts the protocol defined in the design spec, tracks session/intent/commit state in memory, reaps dead sessions via `kill(pid, 0)`, and exits 30s after last client disconnects. Independent of `pi-code-engine` — parallel-safe with FEAT-*A.

Out of scope: engine integration (FEAT-*C), NAPI glue (FEAT-*D), TS surface (FEAT-*E), TUI (FEAT-*F).

Scenarios:

1. `auto_spawn_by_first_client`
   Given no running broker (socket absent, pid file absent), a helper `spawn_broker_if_absent()` `execvp`s the binary with `--daemonize`, then a test client connects within 2s. Broker receives `hello`, replies `welcome`. Test kills broker at teardown.

2. `second_client_sees_first_in_peers`
   Client A connects with sessionId `s1`, sends `hello`. Client B connects with sessionId `s2`. B's `welcome.peers` contains exactly one entry with `sessionId == "s1"`.

3. `peer_joined_broadcast`
   A connected. B connects and sends `hello`. A receives `{type: "peer_joined", sessionId: "s2"}` within 500ms.

4. `intent_grant_on_unclaimed_node`
   A: `{type:"intent", file:"/tmp/a.ts", codePaths:["::Foo.bar#body"], baseRevision: 41, ttlMs: 5000}`. Broker replies `{type:"intent_ack", granted:true}`.

5. `intent_conflict_when_peer_holds`
   A intents `::Foo.bar#body`. Within 100ms B intents the same. B receives `{type:"intent_conflict", conflictingSession:"s1", peerIntentTs: <a's ts>}`.

6. `intent_auto_expires_after_ttl`
   A intents with `ttlMs: 200`. After 300ms, B intents same path and receives `granted:true`.

7. `commit_broadcasts_to_subscribers`
   A: `subscribe {files:["/tmp/a.ts"]}`. B commits `/tmp/a.ts` revision 42. A receives `{type:"peer_committed", sessionId:"s2", revision:42, codePaths:[...], ts:...}` within 500ms.

8. `commit_conflict_when_parent_outdated`
   A commits r42 with parentRevision 41. B tries to commit with parentRevision 41 (also). Broker replies `{type:"commit_conflict", peerSession:"s1", peerRevision:42}`. (Broker tracks latest committed revision per file.)

9. `session_reaping_by_dead_pid`
   A registers with its real pid. Test kills A's process. Within 6s (one reap cycle + heartbeat), B receives `{type:"peer_left", sessionId: <A>}`.

10. `last_client_disconnect_exits_broker_after_grace`
    Single client connects, then `bye`s. Broker stays alive for 30s grace period (configurable via env `PI_EDIT_BROKER_GRACE_MS` for tests; use 500ms in test). After grace, broker process exits; socket file removed.

11. `protocol_rejects_unknown_message_type`
    Send `{"type":"bogus"}`. Broker replies `{"type":"error","code":"UNKNOWN_TYPE"}` and does not drop connection.

12. `heartbeat_keeps_session_alive`
    Connect, do not send further messages, send heartbeat every 3s. After 10s, session remains in peer list and is not reaped (simulate a long-lived tool call).

13. `socket_file_cleaned_on_graceful_exit`
    Send SIGTERM to broker with no clients connected. Broker removes `~/.spell/edit-broker.sock`. Retry start succeeds.

* Edge cases
- Broker already running, new broker spawn attempt — detect via pid file + `kill(pid, 0)`; exit silently if a healthy instance exists.
- Socket file stale (previous broker crashed): if `connect()` fails, unlink the stale socket before binding.
- Two spell processes race to auto-spawn: `flock`-style exclusive lock on pid file during spawn — loser waits for socket to appear.
- JSON line longer than 1 MiB: reject with `MESSAGE_TOO_LARGE` error and close connection.
- Client sends `hello` twice with same sessionId: replace prior connection (mirror `SocketSessionRegistry::register` in spell-server — close old connection).
- Client sends `commit` before `hello`: reply `{type:"error", code:"NOT_REGISTERED"}` and close.
- `daemonize` fork fails on platforms without setsid support: log, run in foreground.
