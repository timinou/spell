* Initial Message

How does this coding harness manage token caching, especially with Anthropic Opus? Is there any room for improvement? Look at usage statistics if you can find them.

* Problem
Cache retention defaults to ~"short"~ (5-minute TTL) regardless of model cost. For Opus 4 at $15/MTok input, a 5-minute cache expiry means any pause >5 minutes forces a full re-cache of the entire prompt (system prompt + tools + conversation = often 50-150k tokens). The 1h TTL (available via ~PI_CACHE_RETENTION=long~) would save the cache write cost ($18.75/MTok) on resume.

The write cost penalty for extended caching on Anthropic direct API is zero — 1h TTL is a free API feature. Users just don't know about it and the default is conservative.

* Approach
Two changes:

** Change 1: Default retention to "long"
In ~resolveCacheRetention()~ (~packages/ai/src/utils.ts~), change the default from ~"short"~ to ~"long"~:
#+begin_src typescript
export function resolveCacheRetention(cacheRetention?: CacheRetention): CacheRetention {
    if (cacheRetention) return cacheRetention;
    if ($env.PI_CACHE_RETENTION === "short") return "short";
    return "long";
}
#+end_src

~PI_CACHE_RETENTION=short~ and ~PI_CACHE_RETENTION=none~ still work as explicit overrides.

** Change 2: Remove the api.anthropic.com gate for 1h TTL
In ~getCacheControl()~ (~packages/ai/src/providers/anthropic.ts~, line 160), remove the ~baseUrl.includes("api.anthropic.com")~ check so that the 1h TTL is sent for any Anthropic-compatible endpoint (including custom proxies):
#+begin_src typescript
const ttl = retention === "long" ? "1h" : undefined;
#+end_src

Rationale (user decision): most Anthropic-compatible proxies forward ~cache_control~ as-is, and unknown TTL values are typically ignored by APIs that don't support them. Users who set a custom base URL are already making an informed choice; gating a free optimization behind hostname matching is unnecessarily restrictive.
