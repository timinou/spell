* Context
=ElixirImportResolver= in =crates/pi-code-graph/src/language/elixir.rs= converts module names like =MyApp.Tools.Helper= to =my_app/tools/helper.ex= and tries 4 candidates at the project root only. Standard Elixir/Mix projects place source under =lib/=:
- Mix: =lib/my_app/tools/helper.ex=
- Phoenix: =lib/my_app_web/controllers/page_controller.ex=
- Umbrella: =apps/my_app/lib/my_app/tools/helper.ex=

None of these are tried. On any real Elixir project, every alias/import fails to resolve and the graph has zero cross-file edges.

* Design Decisions
1. Detect Mix projects by checking for =mix.exs= at =project_root=. Only add =lib/= prefix candidates when =mix.exs= exists.
2. When =mix.exs= exists, prepend =lib/= to each candidate path. The full candidate list becomes:
   - =lib/<snake_path>.ex=
   - =lib/<snake_path>.exs=
   - =lib/<snake_path>/index.ex=
   - =lib/<snake_path>/index.exs=
   - =<snake_path>.ex= (root fallback, keeps current behavior)
   - =<snake_path>.exs=
   - =<snake_path>/index.ex=
   - =<snake_path>/index.exs=
3. Umbrella detection (=apps/*/lib/=) is out of scope for this item. It can be a follow-up.
4. The =mix.exs= check is a simple =Path::is_file()= call per resolution request. This is cheap (filesystem metadata cached by OS). No caching needed in the resolver.
5. The =camel_to_snake= conversion and =module_name_to_path= remain unchanged — they're correct.

** Implementation
1. In =resolve()=, detect Mix project:
   #+begin_src rust
   fn resolve(&self, request: ResolveRequest<'_>) -> Result<Option<PathBuf>> {
       let base_path = module_name_to_path(request.specifier);
       let is_mix_project = request.project_root.join("mix.exs").is_file();

       let mut candidates = Vec::with_capacity(8);

       // lib/ prefix candidates (Mix projects)
       if is_mix_project {
           candidates.push(request.project_root.join("lib").join(&base_path).with_extension("ex"));
           candidates.push(request.project_root.join("lib").join(&base_path).with_extension("exs"));
           candidates.push(request.project_root.join("lib").join(&base_path).join("index.ex"));
           candidates.push(request.project_root.join("lib").join(&base_path).join("index.exs"));
       }

       // Root candidates (fallback, also covers non-Mix projects)
       candidates.push(request.project_root.join(&base_path).with_extension("ex"));
       candidates.push(request.project_root.join(&base_path).with_extension("exs"));
       candidates.push(request.project_root.join(&base_path).join("index.ex"));
       candidates.push(request.project_root.join(&base_path).join("index.exs"));

       Ok(candidates
           .into_iter()
           .find(|candidate| candidate.is_file())
           .and_then(|candidate| {
               candidate
                   .strip_prefix(request.project_root)
                   .ok()
                   .map(Path::to_path_buf)
           }))
   }
   #+end_src

* Edge Cases
- =mix.exs= at a subdirectory: The resolver only checks =project_root/mix.exs=. If the graph is built from a subdirectory of a Mix project, the marker won't be found and =lib/= candidates won't be tried. This is acceptable — the graph root should be the project root.
- Phoenix web modules: =MyAppWeb.PageController= maps to =my_app_web/page_controller.ex=. With the =lib/= prefix, this becomes =lib/my_app_web/page_controller.ex=, which is the standard Phoenix layout. Correctly handled.
- Umbrella: =apps/<app>/lib/...= is NOT handled. This is a deliberate scope cut. The resolver returns =None= for umbrella sub-apps. Follow-up work.
