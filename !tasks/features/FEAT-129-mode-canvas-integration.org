* Scope

**In scope:**
- Mode-spawned companion canvas windows: ~ui.canvas~ in MODE.md frontmatter specifies a QML file path (relative to mode directory) spawned when mode activates
- Canvas-primary modes: ~ui.primary: 'canvas'~ routes agent output to canvas window; TUI shows only agent reasoning/tool calls
- Mode overlay from QML: ~ui.overlay~ specifies a QML overlay component rendered in TUI (extends current plan mode badge)
- Loop monitoring dashboard: a built-in canvas component that displays loop iteration progress, ticket status, gate results with pause/resume/approve controls
- Canvas window lifecycle: window opens on mode enter, closes on mode exit (or stays if mode config says so)
- Bridge communication: mode canvas receives agent events (findings, progress, artifacts) via bridge.messageReceived

**Out of scope:**
- Loop creation from canvas UI (future work)
- Full TUI replacement by canvas (future work — requires canvas chat affordances)
- Custom QML component library for mode canvases (users write their own QML)

**Boundary rationale:** Canvas integration is the UI surface of the mode system. It depends on the lifecycle generalization (mode enter/exit events) but is otherwise independent. The loop monitoring dashboard is included here because it's a canvas component, not a loop system change.

* Edge Cases
- QML file not found in mode directory -> warn, skip canvas spawn, mode still activates
- Canvas window closed by user manually -> mode continues without canvas
- Canvas-primary mode but QML bridge not built -> fallback to TUI-only with warning
- Multiple canvas windows from nested modes -> each mode manages its own window
- Loop dashboard opened but no loop active -> show empty state with 'No active loop'
