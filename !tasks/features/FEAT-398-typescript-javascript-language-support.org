* Context — Why This Exists
This is one of two Phase 1 language implementations for the pi-code-graph engine (the other is Elixir). TypeScript/JavaScript is the primary language of the Spell codebase and the most common language the agent works with.

This item implements the =LanguageExtractor= and =ImportResolver= traits defined in [[id:FEAT-397-core-graph-engine-and-trait-interfaces]] for TS/JS/TSX/JSX files.

** What This Enables
After this item, running =code index= on a TS/JS project produces a graph with:
- Every function, class, interface, type alias, enum, variable, method, and React component as symbol nodes
- Every import statement resolved to either a local file, external package, or Node built-in
- Call edges between symbols (=foo()= in function =bar= → edge from bar to foo)
- Inheritance edges (=class B extends A= → edge from B to A)
- Type reference edges (=param: UserService= → edge from containing symbol to UserService)
- Barrel file re-export chains resolved (=import { Foo } from "./index"= traces through to defining file)

** Key Design Decisions
1. =oxc_resolver= crate (v3) for import resolution — production-grade, handles tsconfig paths, workspaces, barrel files, =node:*= built-ins. Used by swc-node and knip.
2. Separate tree-sitter parsers for TS vs TSX vs JS vs JSX (different grammars). Thread-local instances for rayon parallelism.
3. React component detection: any function in a TSX file that returns JSX → =SymbolKind::Component=.
4. Barrel files: =export * from "./x"= creates =BarrelReExportAll= edge. Named re-exports get direct edges bypassing the barrel.

** 3. Symbol extraction implementation
Implement =TypeScriptExtractor::extract= — the symbol extraction portion.

Walk tree-sitter AST root children. Node types to handle:
- =function_declaration= → name from =name= child → =SymbolKind::Function=
- =class_declaration= → name from =name= child → =SymbolKind::Class=, walk body for method_definition children
- =interface_declaration= → =SymbolKind::Interface=, walk body for property_signature children
- =type_alias_declaration= → =SymbolKind::TypeAlias=
- =enum_declaration= → =SymbolKind::Enum=
- =lexical_declaration= → check =variable_declarator.value= — if =arrow_function= then =Function= else =Variable=
- =export_statement= → unwrap inner declaration, set =is_exported = true=
- For TSX: check if function body contains =jsx_element= or =jsx_self_closing_element= → =Component=

** 5. Import extraction implementation
Handle these tree-sitter node types:
- =import_statement= → extract =source= (string literal = specifier), =import_clause= children
  - =named_imports= → =import_specifier= children → name + optional alias
  - =identifier= (default import) → =ImportedName { name: "default", alias: Some(ident) }=
  - =namespace_import= → =ImportedName { name: "*", alias: Some(ident) }=
- =call_expression= where callee is =require= → =ImportKind::Require=
- =call_expression= where callee is =import= → =ImportKind::EsmDynamic=

* Edge Cases and Error Handling
- Malformed TS files (syntax errors) → tree-sitter still produces a partial tree with ERROR nodes. Extract what we can, skip ERROR subtrees.
- Files with only type exports (no runtime symbols) → still create symbol nodes (interfaces, type aliases)
- Circular imports (a.ts imports b.ts imports a.ts) → graph naturally represents this (cycles in directed graph). No special handling needed.
- Dynamic imports with non-literal specifiers (=import(variable)=) → skip, can't resolve statically
- =require= with non-literal argument → skip
- Workspace monorepo: multiple tsconfig.json files → use the one closest to each file being resolved
