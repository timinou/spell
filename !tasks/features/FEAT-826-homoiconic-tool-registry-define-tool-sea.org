* Change
** SpellAgent.ToolRegistry (ETS or Agent-backed, process-global for the session)
- entry: `%{name, params :: [atom], source :: String.t() (PTC-Lisp), doc :: String.t(), kind: :ptc}`
  (also support `kind: :native, fun: (map -> term)` so built-ins live in the same table).
- API: `put(entry)`, `get(name)`, `all()`, `remove(name)`.
- Seed with native tools (e.g. an `execute`-style passthrough; later find/edit via NIF).

** A defined tool IS a stored PTC-Lisp program (homoiconic, = W4 vision)
- `define-tool` does NOT capture an Elixir closure. It stores SOURCE TEXT. This makes a tool
  code-as-data: durable, diffable, inspectable, re-runnable. Strong foundation > closure capture.
- Resolver for a `:ptc` tool: when `(tool/NAME args)` fires, look up NAME in the registry; run its
  `source` through the SAME sandboxed PTC execution path the `execute` tool uses
  (Lisp.run/2 or the runtime's program executor — read beam/ptc_runtime peer.ex for how `execute`
  invokes a program), with `args` bound as `data/` context (so the source reads `data/sym` etc.).
  Return the program's value to the caller. Tool-call limits / heap caps / psettled all still apply.

** Host functions exposed to the agent (callable from inside any PTC program)
- `(define-tool {:name "x" :params [:a :b] :doc "…" :source "<ptc-lisp string>"})` → registers; returns :ok/name.
- `(define-config {:key "model" :value "…"})` → sets a live config cell (model id, thinking level,
  system-prompt addendum). v0 scope: a small whitelist of keys; reads feed back into SubAgent.run opts.
- `(list-tools)` → returns the registry as data (name/params/doc) so the agent can introspect what it built.
- These are themselves entries in the tools map (native kind), so the agent invokes them as `(tool/define-tool …)`.

** System-prompt rendering
- The defined tools must appear in the agent's tool inventory so the LLM knows they exist.
  PtcRunner renders tools via `SubAgent.Namespace.Tool` (verified). Ensure registry entries
  (params+doc+name) flow into the rendered inventory each turn (re-render from registry, not a static snapshot),
  so a tool defined in turn N is callable in turn N+1.

* Edge
- Recursion / cycles: a defined tool whose source calls itself or another defined tool — rely on the
  existing `max_tool_calls` / loop limits to bound it; document that cycles are the user's responsibility in v0.
- Name collision with a native tool → registry resolver order is define-FIRST; warn (or reject) on shadowing a native.
- Bad source (parse error) at define time: VALIDATE by attempting to parse the PTC source on `define-tool`;
  reject with a clear error rather than failing at first call. (Reuse the preflight/parse pass if exposed.)
- args→data binding: confirm how the execute path binds the `context` map to `data/<key>`; bind each param by name.
- Persistence: v0 = in-memory only (lost on restart). Durable storage (org/memory stored program) is a follow-up.

* Accept
- Unit (no LLM): register `(define-tool {:name "double" :params [:n] :source "(* 2 data/n)"})`,
  then resolving `(tool/double {:n 21})` returns 42.
- A defined tool that calls a NATIVE tool works: e.g. source `"(tool/execute {:program \"(+ 1 1)\"})"` resolves.
- `(list-tools)` returns the newly defined tool in its data.
- Defining a tool with malformed PTC source returns a clear `{:error, …}`, not a crash.
- A tool defined in one turn appears in the rendered tool inventory for the next turn (assert the rendered string contains the name).
