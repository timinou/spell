* Initial Message

How does this coding harness manage token caching, especially with Anthropic Opus? Is there any room for improvement? Look at usage statistics if you can find them.

* Problem
The Anthropic direct API provider places up to 4 cache breakpoints (tools, system, penultimate user, last user), but the Bedrock Converse provider only places 2 (system prompt, last user message). This means Bedrock Opus sessions miss cache opportunities on tool definitions and earlier conversation, paying full input token pricing for content that could be cached.

With Opus 4 on Bedrock at $15/MTok input vs $1.5/MTok cache read, every cache miss on tool definitions (~2-4k tokens) costs 10x more than it should.

* Approach
Add cache points in ~packages/ai/src/providers/amazon-bedrock.ts~:
1. Tool definitions: Add a ~cachePoint~ after the last tool in ~convertToolConfig()~
2. Penultimate user message: Mirror the Anthropic strategy in ~convertMessages()~ by adding a ~cachePoint~ to the second-to-last user message's content blocks

Bedrock uses ~CachePointType.DEFAULT~ blocks appended to content arrays rather than Anthropic's ~cache_control~ field on individual blocks. The Bedrock API supports up to 4 cache points for Claude models.

- ~packages/ai/src/providers/amazon-bedrock.ts~ — ~convertMessages()~ and ~convertToolConfig()~
