Scenarios (each asserts exact error shape or exact success payload):

1. *shrink-guard rejects PLACEHOLDER-style clobber* — existing code-supported file with 2 048 bytes of valid Rust; `write` with 11 bytes of `PLACEHOLDER` → tool returns error with `code: "WRITE_SHRINK_BLOCKED"` and no disk mutation. Read back shows original bytes intact.

2. *shrink-guard allows same-size replacement* — existing 2 048 B file; `write` 2 048 B of new valid Rust → success.

3. *shrink-guard allows small file replacement* — existing 200 B file (below 256 B threshold); `write` 20 B → success (small files are not gated).

4. *new file allowed* — non-existent target path; `write` 50 B → success (new-file path is always allowed regardless of size).

5. *parse-regression guard rejects broken replacement* — existing valid Rust file; `write` content that fails tree-sitter parse (mismatched braces) while original parsed cleanly → error `code: "WRITE_PARSE_REGRESSION"`, no mutation.

6. *parse-guard skipped when original already broken* — existing file with parse errors; `write` of equally broken content → success (do not gate authors who are repairing a file in multiple passes).

7. *force=true bypasses both guards* — same as (1) but with `force: true` → success + output includes compatibility notice from `formatCodeTextCompatibilityNotice` plus an extra line naming the bypassed guard.

8. *guard does not fire on non-code-supported paths* — write PLACEHOLDER to `README.txt` → success (text writethrough path untouched).

* Edge Cases

- *Symlinks* — resolve to real path before running shrink check; do not follow into areas outside `session.cwd` sandbox (enforced by existing `enforcePathWrite`).
- *Concurrent writes* — guard reads old size, then native edit replaces. If another session writes between probe and replace, worst case is a false-positive shrink block. Acceptable; retry with `force` on user request.
- *Generated files* — large auto-generated `.d.ts` files may shrink legitimately. Still blocked. Exit via `force: true`; guard is advisory-with-teeth, not security-grade.
- *Binary or UTF-16 content* — managed buffers only apply to code-supported extensions, which are UTF-8; non-issue.
- *File-creation race* — when `create: true` and file now exists because a peer created it post-probe, guard still evaluates on the found content. Acceptable.
- *pi-code-engine reload coordination* — after block, do not call native `edit`; the engine state must be identical to pre-call. Ensure test #1 asserts buffer version unchanged.
