* ProcessManager consolidation
telegram-bridge's ProcessManager and spell-server's SessionManager overlap significantly:
- Both manage RpcClient instances keyed by a string
- Both handle idle timeouts
- Both handle lifecycle (create/kill/killAll)
- ProcessManager adds: project resolution, session state persistence, mode tools
- SessionManager adds: generic type parameter, lifecycle strategy pattern, pending dedup

Strategy: Keep SessionManager<K> as the core abstraction. Create a =TelegramBotService= class in =packages/spell-server/src/telegram/service.ts= that:
1. Owns a =SessionManager<string>= with =TelegramLifecycle=
2. Wraps session state persistence (load/save bridge state)
3. Provides the CommandContext (config, processManager facade, telegramPrompt)
4. Starts/stops the grammy bot
5. Starts/stops the log-viewer HTTP server (if configured)

The existing ProcessManager interface (getOrCreate, kill, getSession, etc.) becomes a thin facade over SessionManager with project resolution logic.
