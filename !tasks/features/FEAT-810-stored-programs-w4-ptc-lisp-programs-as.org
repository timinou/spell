* North star

Today a PTC-Lisp program is EPHEMERAL: written, run once, discarded. W4 makes a
program a DURABLE, NAMED, RE-RUNNABLE value. The program text is stored (memory /
org / canvas) and re-executed later by a NEW caller (a save, a tick, a refresh).
This is the vision doc's P4 property and WS-B's "policy as data" lane, collected with
ZERO new runtime — the execute lane (F0/W1/W2/W3 shipped) IS the engine.

Reads with: specs/beam-orchestrator/01-vision.md (destination),
06-execute-substrate.md (W4 build-order line), 07-execute-substrate-status.md
(W4 scoped as thin integration), 04-where-ptcrunner-shines.md (the program corpus).

* Scope (this FEAT = READ-ONLY stored programs only)

Read/aggregate programs only: find/org/memory/bash-read/get/count/group-by/etc.
WRITE-flavored stored programs (edit/create inside a stored program) are EXPLICITLY
out of scope here and gated on D3 (transactional write lane) — see sibling FUP
"W4-write". Rationale: a stored program re-run unattended that does (edit ...) and
fails halfway leaves partial effects (error class E4); read-only programs have no
effects to roll back, so they are safe to store and re-run TODAY.

* HARD prerequisite

BUG "Execute HandleStore + session bindings leak — no reaper" (sibling, #A). A stored
tile re-running every tick parks a handle every tick; without the reaper this is
guaranteed unbounded growth. W4 MUST NOT merge before the reaper. (Verified:
handle_store.ex @session_bucket is never released today.)

* Architecture: one stored-program contract, three callers

A stored program is just `{ program: string, signature?: string, context?: map }` —
the exact ExecuteParams shape (packages/coding-agent/src/tools/ptc-runtime/execute.ts,
`executeSchema`). "Store" = persist that triple as a value; "re-run" = feed it to the
existing `ExecuteTool.execute` path (which already does spawn/effects-gate/render/
artifact-handoff). NO new execution machinery — W4 is a STORAGE + INVOCATION shim.

Verified existing surfaces to reuse:
- Node entry: `ExecuteTool.execute(...)` in execute.ts (the whole gated lane).
- Client: `client.execute({program,context,signature,timeoutMs,maxHeapWords,signal})`
  → peer.ex `run_program/2` → `{:execute_done, id, wire_result, memory}` (peer.ex:429).
- Effects policy: `policy.ts` DEFAULT_POLICY already classifies read vs write tools —
  W4-read enforces "read-only" by REUSING that classifier (reject a stored program
  whose static tool set intersects the write set), NOT by inventing a new gate.
- Preflight lint (W1b): a stored program is lint-checked at STORE time (0 effects) so
  a typo can never be persisted as a live tile.

* The three callers (deliverable surfaces)

   - `memory save kind=playbook` may carry a fenced PTC-Lisp `:program` block.
   - A new verb path "run this playbook" feeds the block to ExecuteTool.execute.
   - Surface: packages/coding-agent/src/tools/memory.ts (save path) +
     packages/coding-agent/src/memories/index.ts (storage).
   - "How's the repo?" → re-execute the stored health program instead of re-deriving.

   - An org item may carry a stored program in a PROPERTIES drawer (e.g.

   - On `org dashboard`, a tile re-runs its program and renders the value. Each tick

3. canvas health panel
   - A canvas window (rule://canvas-activation territory) re-runs a stored program on

* The stored-program value contract (freeze this)

```
StoredProgram = {
  program:   string         ; the PTC-Lisp source (lint-clean at store time)
  signature?: string        ; optional output contract (validated each run)
  context?:  map            ; static data bound under data/<key> (D-6 convention)
  title:     string         ; human label
  readOnly:  true           ; W4-read invariant; WRITE programs rejected at store
}
```
Stored as: a fenced block in the memory/org body (text-first, diff-able, travels as a
value — the P4 property). Re-run = parse block → ExecuteParams → ExecuteTool.execute.

* Tests

- Store a read-only :program playbook → persisted; re-run → returns the SAME value as
  running the program inline (round-trip identity).
- Store a program with a write tool (e.g. (tool/edit ...)) → REJECTED at store time
  with a clear "W4-read is read-only; write programs need D3" message.
- Store a program with a typo'd builtin → REJECTED at store time (preflight, 0 effects).
- Re-run a stored program N times in a session → session store stays bounded (proves
  the reaper prereq is wired; cross-check BUG reaper acceptance).
- A signature on a stored program is validated on each re-run (drift → typed rejection).

* Acceptance

A read-only health program saved as a memory playbook re-runs and reproduces its
inline value; a write program and a typo'd program are both rejected at STORE time
(not at first run); repeated re-runs stay memory-bounded. `bun test
stored-program.test.ts` green; execute.test.ts still green; tsc clean for touched files.
