* Initial Message

I want to customise the TASK tool even further. Look at how subagents are currently being launched and how I could e.g. assign all explore agents to a specific model. I think there's something around kdl policies about this somewhere?

* Intention & Purpose
Expose `model: string` on the task tool's JSON schema at both the batch level and per-task-item level so a calling agent can dispatch a single task to a specific model without editing config. Highest-priority override in the new resolution chain. Per-task wins over batch when both supplied.

* Context & Narrative
- The executor (`packages/coding-agent/src/task/executor.ts:182`) already accepts `modelOverride?: string | string[]` and propagates it. The plumbing reaches `runSubprocess(modelOverride, ...)` (line 1583, 1637, 1731).
- What's missing: the JSON schema seen by the LLM. `taskItemSchema` (`packages/coding-agent/src/task/types.ts:37`) and the batch schema (`createTaskSchema`, line 77) do not include a `model` field, so the calling LLM cannot select a model per dispatch.
- Today the only model selection paths are: settings DB (`task.agentModelOverrides[agentName]`) and agent frontmatter `model:`. Both are static.
- This item adds the user-facing schema; FEAT-646 wires it into the resolution chain.

* Scope
- In-scope:
  - Add `model?: string` to `taskItemSchema` (per-task) and to the batch object schema returned by `createTaskSchema` (batch default).
  - Validate that values resolve to either an explicit `provider/id` form, a configured role alias (`pi/subtask`, `pi/smol`, `pi/task`, `default`), or a model pattern parsable by `resolveConfiguredModelPatterns`. Validation surface = a soft warning at dispatch time; invalid strings fall through to the next priority (no hard error — keeps the schema permissive).
  - Update `TaskItem` and `TaskParams` static types accordingly (already auto-derived via `Static<typeof ...>`).
- Out-of-scope:
  - `thinkingLevel`, `tools`, `disabled` at per-call level — declarative-only via spell.kdl rules.
  - Caller-supplied multi-model fallback list — keep `string`, not `string[]`. Fallback chains stay declarative.

* Existing Patterns
- `taskItemSchema` (`src/task/types.ts:37`) — TypeBox object with `Type.Optional(Type.String({ description: "..." }))` shape. Match it.
- `createTaskSchema` (`src/task/types.ts:77`) — function-built object schema with `properties` map. Add `model` at the top-level `properties` object.
- Description text style (concise, no emojis, action-first imperative) — see `agent`, `phase`, `context` descriptions.
- Resolution: `resolveConfiguredModelPatterns(value, settings)` (`src/config/model-resolver.ts:385`) handles role aliases. Pass per-call value through this in FEAT-646.

* Edge Cases
- Empty string `model: ""` — treat as omitted (do NOT pass through). Use `value?.trim() || undefined` at consumption.
- Both batch and per-task `model` set: per-task wins. Batch is the default for all tasks that don't specify their own.
- Role alias `pi/task` (parent-inherits): per-call request to inherit. Resolves through `resolveAgentModelPatterns` in FEAT-646; behaves like agent frontmatter `model: pi/task`.
- Caller passes a model the user hasn't configured (no API key): falls back to next priority via `resolveModelCandidates` — already handled in `runSubprocess` startup-fallback logic.
