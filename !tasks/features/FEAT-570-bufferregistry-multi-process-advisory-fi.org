* Scope

In: wrap `CodeBuffer::save` and the `BufferRegistry::open` revalidation read in OS-level advisory file locks (`fd-lock` crate) so that concurrent edits from separate Spell processes (CLI, TUI, stats, MCP server, external tools that cooperate) do not interleave half-writes; on lock contention, wait up to N ms then surface `LOCK_TIMEOUT` / `EXTERNAL_MODIFICATION`.

Out: coordinating in-session concurrency (covered by FEAT-571); durable sentinel files; multi-machine coordination.

* Background

User goal: "play well with the other code editing services running by any other spell service". Currently a second Spell process writing the same file races against the first: no coordination. Advisory file locks narrow the race to the moment between stat and write.

We use OS advisory locks (`flock`/`LockFileEx`) so cooperating processes (any Spell-family crate linking `pi-code-engine`) observe the lock. Non-cooperating editors (vim, VS Code) remain uncoordinated — that is the fs-watcher's domain (FEAT-569).

* Existing patterns

- `crates/pi-code-engine/src/buffer.rs:204-221` — `CodeBuffer::open` reads file bytes.
- `crates/pi-code-engine/src/buffer.rs:571-586` — `CodeBuffer::save` writes.
- No existing lock infrastructure in this repo (verified by grepping for `fd-lock`, `fs2`, `FileExt`).

* Edge cases

- Windows: `fd-lock` uses `LockFileEx`; same semantics.
- NFS: advisory locks are best-effort; document limitation in `code.md`.
- Lock held by dead process (Linux): kernel auto-releases on process exit; no stale-lock cleanup needed.
- Process that never `save`s (pure readers): no lock acquired; no contention.
- File created via `open_or_create` before first save: lock acquired against the new file.
