* Problem
Repo-wide CodePath text queries are pathologically slow compared to ripgrep/native grep:

- =find "**/*::§line[text~=\"overloaded_error|overloaded\"]"= measured ≈36.9s in this repo.
- =find "**/*::§line[text~=\"glm|GLM\"]"= measured ≈34.4s in this repo.
- Native pi grep / rg equivalents measured ≈0.5–1.3s.

Root cause: =find= / CodePath TextResolver does not use the existing ripgrep-grade search engine. It walks files, reads each file fully, builds a line index, tests regex per line, and allocates CodePath nodes. Separately, =pi-natives::grep= already uses the ripgrep crate family (=grep-regex=, =grep-searcher=, =grep-matcher=) plus ignore/glob/rayon. This is a parallel implementation of the same need.

User requirement: no parallel impl. Make =find= fast, period. Prefer a Rust package/shared crate over shelling out to =rg= unless analysis proves otherwise.

* Decision
Use ripgrep's Rust crates as the canonical text-search substrate, not the =rg= subprocess.

Create a host-agnostic shared crate (proposed: =crates/pi-text-search=) that owns text search and filesystem walking for grep-like needs. Then:

- =pi-natives::grep= becomes a NAPI DTO/task wrapper over =pi-text-search=.
- =pi-code-path::TextResolver= delegates =§line[text~=...]= / =match= search to =pi-text-search= and maps matches to CodePath =NodeRef=s.
- Existing per-line regex logic in TextResolver is retained only for non-search line operations or fallback semantics, not as a repo-wide text-search engine.

Do not introduce a subprocess dependency on =rg=.

* Rationale
** Why not =rg= subprocess
- Subprocess startup on every =find=.
- stdout parsing, escaping, captures/context mapping, and binary/error semantics become fragile process plumbing.
- Packaging/version drift across environments.
- Harder cancellation and streaming integration.
- Harder to produce exact CodePath =NodeRef= metadata and byte ranges robustly.

** Why ripgrep crates
- Already used in =crates/pi-natives/src/grep.rs=.
- =grep_searcher::Searcher= provides efficient line-oriented search, multiline support, context lines, binary detection, mmap decisions, and =SinkMatch= metadata.
- =SinkMatch= exposes =line_number()=, =absolute_byte_offset()=, =bytes()=, and =bytes_range_in_buffer()=, sufficient to map results back into CodePath line nodes.
- Keeps search core host-agnostic and reusable by NAPI, future Rustler/BEAM skins, and CodePath kernel.

* Risks / edge cases
- Byte range mapping: CodePath nodes prefer accurate byte ranges. =grep_searcher::SinkMatch= exposes offsets, but mapping full line ranges may require care.
- Match count semantics: native grep count mode vs CodePath one-node-per-line semantics may differ; preserve existing public contracts separately.
- Context semantics: grep context and CodePath =<<= / =>>= context combinators must remain compatible or explicitly fallback.
- Binary/large file behavior: native grep currently caps file reads at 4 MiB for file search. TextResolver currently reads full files. New shared behavior must be pinned by tests.
- Invalid regex diagnostics: preserve useful CodePath diagnostics rather than silently returning no matches.
- Dependency layering: =pi-code-path= must not depend on =pi-natives=. Shared crate must remain host-agnostic.
