** Bot as subsystem
TelegramBotService (from FEAT-233) integrates with spell-server's existing SessionManager pattern:
- The bot gets its OWN SessionManager<string> with TelegramLifecycle (separate from the autonomy SessionManager)
- Session idle timeouts come from TelegramChannelConfig per-user settings
- Bot sessions are conversational (5min idle default), autonomy sessions are persistent (no idle)

** Notification sender coexistence
The existing =createNotificationSender()= for goal hooks only needs botToken + owners. The full bot (grammy instance) is separate. They share the same bot token but serve different purposes:
- NotificationSender: one-way notifications for goal completion (existing, unchanged)
- TelegramBotService: two-way interactive bot with commands and RPC sessions (new)

Both can coexist — NotificationSender uses raw HTTP API, bot uses grammy long-polling. This is fine; grammy handles updates via getUpdates while NotificationSender just calls sendMessage.

** Log viewer consolidation
The log-viewer HTTP server from telegram-bridge can either:
- Run on its own port (as before, via log-viewer-port config)
- OR be folded into the main spell-server HTTP server as additional routes

Keep it on its own port for now — simpler, no route conflicts. The main HTTP server handles goal dashboard + API + webhooks; log-viewer handles session browsing.
