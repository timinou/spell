Implement a session bridge client in coding-agent that connects to the spell-server's Unix domain socket and enables remote interaction with blocking events.

* Architecture

** Bridge Client (=src/session-bridge/client.ts=)

- Connect to =~/.spell/server.sock= on startup (best-effort — if socket doesn't exist, bridge is disabled)
- Send =register= message with session metadata
- Expose methods:
  - =emitBlockingEvent(kind, payload): Promise<EventResponse | null>= — sends blocking_event, returns promise that resolves when server sends event_response or event_cancelled. Returns null if bridge is not connected.
  - =dispose()= — sends =deregister=, closes connection
  - =isConnected(): boolean=
- Reconnection: if connection drops, attempt reconnect with backoff (max 3 attempts, 1s/2s/4s). Don't block session startup on this.
- Heartbeat: send periodic heartbeat every 30s while connected.
- Event response routing: maintain a =Map<eventId, PromiseResolver>= for pending blocking events. When =event_response= arrives, resolve the matching promise. When =event_cancelled= arrives, resolve with null.

** Integration Points

- Initialize in =src/main.ts= or =src/domain/startup.ts= after session is created
- Pass bridge instance to interactive mode via session or mode options
- Bridge is optional — sessions work normally without it (existing TUI-only behavior)
- On session shutdown, call =bridge.dispose()=

** Response Injection

The bridge client needs to be able to resolve blocking selectors/inputs in the interactive mode. Two approaches:

1. *Race pattern*: When =showHookSelector= is called AND a blocking event is emitted, the interactive mode races local input vs bridge response. First to resolve wins.
2. *Callback injection*: The bridge client holds a reference to the active selector's resolve function and can call it directly.

Recommended: Race pattern. The bridge client exposes a =waitForRemoteResponse(eventId): Promise<response>= that the interactive mode races against the local selector. This keeps the bridge decoupled from UI internals.

* Edge Cases

- Socket doesn't exist (server not running): bridge silently disabled, all methods return null/noop
- Socket exists but connection refused: same as above
- Server restarts while client is connected: client detects disconnect, attempts reconnect, re-registers
- Bridge emits event but server never responds (Telegram user ignores it): the local TUI input still works, user can act locally. The bridge promise is cancelled when the local input resolves first.
- Multiple concurrent blocking events: each has unique eventId, all tracked independently
