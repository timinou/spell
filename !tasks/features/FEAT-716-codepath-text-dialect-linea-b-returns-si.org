* Initial Message

Today =§line[A..B]= emits one node per source line. A 50-line range becomes 200 output lines (each wrapped with =LOC#ID  [§line]
  body

=). Agents avoid it and reach for `awk`. Reframe by output shape:

| Form                 | Semantics                       | Output                                  |
|----------------------+---------------------------------+-----------------------------------------|
| =§line[N]=           | one specific line (anchor lookup)| one node, with LINE#ID anchor          |
| =§line[A..B]=        | range = SLICE                   | ONE node, content = lines A..B as text  |
| =§line[..N]=         | head N                          | ONE node, lines 1..N                    |
| =§line[N..]=         | from N to EOF                   | ONE node                                |
| =§line[-N..]=        | tail N (negative anchor)        | ONE node                                |
| =§line[text~="PAT"]= | grep — per-line matches         | per-line nodes (UNCHANGED)              |
| =§line[match="LIT"]= | literal grep                    | per-line nodes (UNCHANGED)              |

Range form == slice == one body. Predicate form == grep == per-line. The grammar already separates these (=Predicate::Range= vs =Predicate::TextMatch=); only the executor conflates them today.

* Implementation sketch
1. Detect when the §line head carries a single =Predicate::Range= (no =TextMatch= / =Compare= / =Flag=)
2. In that branch, build ONE =§slice= (or reuse =§line= kind with a marker on metadata) node whose content is the joined sliced text
3. Negative anchor support: =start = Some(-30)= means "30 lines from EOF"; =end = Some(-1)= means "EOF minus 1"; bounds resolve against =line_index.line_count()=
4. Predicate paths (TextMatch, etc.) remain untouched — keep per-line emission
5. =§line[N]= (single integer, parsed as `Predicate::Ordinal` or similar) keeps single-line LINE#ID anchor — that's the explicit anchor-resolution case for =edit=
