* Initial Message

When the task tool dispatches a tool after another one (for partial sequentiality), it sends a message to the parent thread saying that a job was completed, but not that a previously queued job was started.

* Intention & Purpose
Fix a transparency bug in the `task` tool's batch scheduling.

When a task is dispatched with a `blockers` chain (explicit or implicit via `filesDeps` overlap), the blocked task is held in the TaskTool's internal `readyQueue` and only registered with `AsyncJobManager` *after* its blocker completes. The parent agent has no signal that this auto-promotion has happened: the next `await` call snapshots `manager.getRunningJobs()` once on entry and renders only that snapshot, so the newly-registered job is invisible. The parent concludes the batch is done, then either re-dispatches the work manually or stalls.

Concrete failure observed in session =14d40726c985291f= around 17:29-17:41 UTC: a 4-task batch (TSFix, Prompts, AgentsMd, LegacyDelete) was dispatched with LegacyDelete blocked on TSFix via filesDeps overlap on =packages/coding-agent/src/tools/index.ts=. After TSFix completed, the `await` result said "Still Running (0)" — even though LegacyDelete had just been auto-promoted and was already running. The parent agent re-dispatched LegacyDelete manually, the user replied "it's already dispatching automatically you fucking idiot", and the parent only discovered the running job by =ls=ing the session directory.

This feature gives the parent two correct signals:
1. At dispatch time: explicit count and identity of *queued* tasks waiting on blockers, so the parent knows more work is coming.
2. At await-return time: a "Newly Started" section listing jobs that transitioned from queued to running while the await was blocking, so the parent knows what to await next.

* Context & Narrative
The relevant code paths:

- =packages/coding-agent/src/task/index.ts::TaskTool.execute= (lines ~1020-1235): owns the batch dispatch loop and `scheduleReadyTasks()`. Blocked tasks live in the local `readyQueue` closure, not in `AsyncJobManager`. Dispatch text at line 1222 says "Started ${startedJobs.length} background task jobs" with an `implicitBlockerNote` prefix that only mentions =filesDeps=-derived blockers.
- =packages/coding-agent/src/tools/await-tool.ts::AwaitTool.execute= (lines 62-122): captures =jobsToWatch = manager.getRunningJobs()= once at line 82, races those promises, and renders =#buildResult= over the *original* snapshot. Newly-registered jobs that came online during the wait are never queried.
- =packages/coding-agent/src/async/job-manager.ts::AsyncJobManager.register= (lines 77-158): assigns a fresh =jobId= each time a task is registered. Queued tasks are not pre-registered; they only enter the manager when their blocker's success handler calls =scheduleReadyTasks()= at lines 1133/1161 of =task/index.ts=.
- =packages/coding-agent/src/task/batch-scheduler.ts::buildBatchGraph= (lines 84-123): produces =blockersById= and =implicitBlockers=. The TaskTool currently only forwards =implicitBlockers= into the dispatch =details=, but the same map gives full per-task blocker chains.

* Existing Patterns
- =AsyncJob.startTime= (=async/job-manager.ts= line 22) is set at registration time. Filtering newly-started jobs by =startTime >= awaitInvocationTime= is reliable because the manager assigns it via =Date.now()= on register.
- =manager.getRunningJobs()= (=async/job-manager.ts= line 175) already returns currently-running =AsyncJob= entries with =status === "running"=. Calling it twice — once on entry, once at result-time — is idempotent and cheap.
- =BatchGraph.blockersById= (=task/batch-scheduler.ts= line 39) is already produced and cached on =batchGraph=. Use directly.
- =BatchImplicitBlocker= shape (=task/batch-scheduler.ts= line 31) and =buildImplicitBlockerNote= (=task/index.ts= line 200-208) already render =to=/=from= chains. Mirror that format for queued-task chains in dispatch text.
- =replaceTabs= (=tools/render-utils.ts=) sanitizes job labels for output. Reuse for any new render paths.
- =AwaitToolDetails.jobs: AwaitResult[]= already exists. Append newly-started entries to this array unchanged in shape; consumers receive them via =details.jobs= and can re-await with their =id=.

* Edge Cases
- *Race in result-time snapshot*: a job started by =scheduleReadyTasks()= during the very first millisecond of =await()= might already be in =initialIds=. Handled — =initialIds= filter excludes it from Newly Started.
- *Job started, completed, then evicted, all during the same await*: =AsyncJobManager= retains finished jobs for =DEFAULT_RETENTION_MS= = 5min, so this can't happen in any realistic timing. If it did, =getRunningJobs()= would not list it, =startTime= filter would exclude it from Newly Started; net effect: the job is invisible to the await caller, but =manager.getJob(id)= still resolves it. Acceptable.
- *Multiple awaits race for the same newly-started job*: both will receive it under their own =Newly Started=. Idempotent because the job's =id= is stable; consumers de-duplicate by id if needed.
- *Initial dispatch with all tasks queued behind a synthetic root*: =startedJobs.length === 0= already enters the failure branch at line 1190-1206. Untouched by this change.
- *Cancellation*: if the parent =await= aborts via signal mid-wait, the existing early-return at line 117-119 still fires; with the change, it picks up newly-started jobs queued so far. This is more informative than the current behavior.
- *Concurrency limit reached*: =register()= throws if =runningCount >= maxRunningJobs=. =scheduleReadyTasks()= already wraps =register()= in =try/catch= at line 1177; the queued task transitions to terminal failed status. Newly Started won't show it because it's not running. Correct.
