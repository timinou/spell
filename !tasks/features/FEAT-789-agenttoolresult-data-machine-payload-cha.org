## What it is (and why it's right)
AgentToolResult currently overloads two fields:
- content = DISPLAY channel (human/model-facing text+image blocks)
- details = RENDER-HINT channel (TUI meta lines, stats)

A programmatic consumer (the `execute` PTC-Lisp coprocessor) currently reads structured data via resultToValue's heuristic: prefer `details`, else join `content` text, else an `_images` marker. That heuristic is fragile — it only works for the handful of tools that happen to put a machine-shaped value in `details`, and conflates render hints with payload.

The refactor adds a third, single-purpose field:
- data: D = the machine PAYLOAD channel, required + total (every tool emits it; `null` when purely interactive/side-effecting).

Then resultToValue becomes total and unambiguous: `return result.data ?? null`.

## Why it's a FEAT, not part of any PLAN-32x
Orthogonal to the four hardening items (324 abort, 323 ceiling, 322 backpressure, 325 paging). It touches the cross-package tool contract and EVERY tool + tool test, so it must be its own cutover, not smuggled into a hardening commit.
