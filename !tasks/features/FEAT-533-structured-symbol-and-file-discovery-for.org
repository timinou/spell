* Context

Today =pi-code-graph= exposes only text-oriented graph commands (=status/context/impact/deps/flow/dead_code/clusters/search=). Exact symbol lookup exists only as an internal helper in =crates/pi-code-graph/src/query.rs=, and =search= flattens results to plain text in =crates/pi-natives/src/code_graph.rs=. That is useful for a human, but weak for harness automation and still pushes callers toward =grep= for discovery.

This item adds native structured discovery primitives for symbols and files so the harness can ask the graph for exact/qualified/fuzzy matches with metadata instead of scraping plain text.

* User Workflows

1. A caller asks for symbols matching =CodeTool= and gets structured hits with kind, exported flag, language, path, line, and score.
2. A caller asks for files under a path prefix or suffix and gets structured file hits without regex grep.
3. A caller asks for exact qualified-name resolution and gets one stable answer or an explicit ambiguity/absence result.
4. A caller can still use =code search= for broad lexical/hybrid exploration after symbol/file discovery exists.
5. A later TS wrapper can present compact text while preserving machine-usable =details=.

* Design Decisions

1. Structured result types are the source of truth; pretty text is a renderer, not the transport contract.
2. Exact symbol lookup must prefer qualified names, then unqualified names, then fuzzy search; ambiguity must be explicit.
3. File discovery must not depend on BM25 relevance alone; support deterministic exact/prefix/suffix matching.
4. Preserve existing =search= behavior for broad keyword/hybrid search; do not regress current text workflows.
