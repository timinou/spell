* Scope

**In scope:**
- Hard gate on ~todo_write~ abandonment: ~deferralFupId~ field required when ~status=abandoned~
- Remove ~remove_task~ op entirely — tasks can only be abandoned (never deleted)
- Remove ~status~ field from ~InputTask~ schema — tasks are always created as ~pending~, preventing ~replace~/~add_phase~ bypass of the deferral gate
- Journal status mapping: abandoned to ~BLOCKED~ (not ~DONE~) with ~:DEFERRED_TO:~ property
- Session auto-clear: exclude abandoned tasks (preserve deferral audit trail)
- Session resume: preserve abandoned tasks in ~#syncTodoPhasesFromBranch~ (currently stripped)
- Phase completion: warn about deferred tasks and list FUP IDs
- Pre-filled ~org create~ template in rejection message (hybrid enforcement)
- Plan audit prompt: add deferral focus area
- Plan completion report: require ~[[id:FUP-xxx]]~ links for all deferrals
- ~todo-write.md~ prompt: document ~deferralFupId~, deferral protocol, remove ~remove_task~ docs

**Out of scope:**
- Retroactive FUP creation for past sessions
- FUP ID existence validation (trust the ID — org create is a prerequisite)
- Dashboard bridge changes (nice-to-have, separate follow-up)
- Prompt changes to plan-mode-approved.md for deferral protocol (tool gate is sufficient enforcement)
- ~isPhaseComplete~ logic change — abandoned remains terminal for phase progression
- ~hasUnresolvedBlockers~ logic change — abandoned still resolves blockers

**Boundary rationale:** The deferral gate enforcement is the core invariant. Dashboard rendering and retroactive audits are polish that can follow. The ~isPhaseComplete~ and ~hasUnresolvedBlockers~ behaviors are kept to avoid deadlocks — phases must still progress when tasks are deferred. The reporting (warnings, FUP IDs) compensates for this pragmatic choice.

* Edge Cases

- Task with ~orgItemClosingId~ that is abandoned: the rejection template must warn that the org item lifecycle obligation transfers to the FUP. The ~orgItemClosingId~ should be mentioned in the template body so the agent includes it in the FUP.
- Batch abandonment where some tasks succeed and some fail: if one task in a batch lacks ~deferralFupId~, that specific op is rejected but other ops in the batch still execute (consistent with current behavior where individual ops can fail).
- Task that was ~in_progress~ being abandoned: no special handling beyond the deferral gate — the auto-promotion of next pending task still fires via ~normalizeInProgressTask~.
- Abandoned task that is a blocker for another task: ~hasUnresolvedBlockers~ treats it as resolved. ~formatSummary~ should add a warning when a task becomes unblocked due to an abandoned (not completed) blocker, noting the FUP ID.
- Empty ~deferralFupId~ string: treat as missing — reject.
