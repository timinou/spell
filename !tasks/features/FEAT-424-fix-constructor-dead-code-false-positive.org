* Context
Two related query-layer issues in =crates/pi-code-graph/src/query.rs=:

** Constructor dead-code false positives
=new Foo()= creates a =Calls= edge to the class symbol =Foo=, but NOT to =Foo.constructor= (the method symbol). Since =Foo.constructor= has no inbound edges, =graph_dead_code()= reports it as dead — even when the class is actively instantiated. The smoke output already showed =ProxyMessageEventStream.constructor= flagged as dead.

Fix: two-pronged approach:
1. In the TypeScript extractor, when processing =new_expression=, also emit a synthetic reference to =ClassName.constructor= (so the edge exists in the graph).
2. In =graph_dead_code()=, additionally exclude =Method= symbols named ="constructor"= as a safety net (handles cases where the synthetic edge doesn't resolve, e.g., the class is imported from another file).

** Symbol resolution silently falls back to files
=resolve_symbol()= in =query.rs= tries exact symbol name match, then falls back to =graph_search()= which searches ALL nodes (symbols AND files). If a user asks for =context { symbol: "code.ts" }=, the exact match fails (no symbol named "code.ts"), then graph_search returns the file node — and the query silently returns file-level context instead of an error.

Fix: the fuzzy fallback in =resolve_symbol()= must filter to =GraphNode::Symbol= only. The explicit =resolve_symbol_or_file()= (used by =impact=) keeps its current behavior for commands that legitimately accept either.

* Design Decisions
1. In =collect_references()= in =typescript.rs=, when handling =new_expression=, emit TWO references: one to the class name (=EdgeKind::Calls=, as today), and one to ="{class_name}.constructor"= (=EdgeKind::Calls=). The constructor reference may or may not resolve — if the class isn't in the same file, the indexer won't find the qualified name, but that's OK because decision 2 provides the safety net.
2. In =graph_dead_code()= in =query.rs=, add a filter: skip symbols where =kind == SymbolKind::Method && name == "constructor"=. This handles constructors from imported classes where the synthetic edge didn't resolve.
3. In =resolve_symbol()= in =query.rs=, the fuzzy fallback via =graph_search()= must filter results to only those whose summary =kind != "file"=.
4. No new =SymbolKind::Constructor= variant. Constructors remain =SymbolKind::Method= — adding a new kind would change the extractor, model, serialization, and dead_code filter for no additional benefit beyond what a name check achieves.

** Implementation
1. *typescript.rs* — In =collect_references()=, change the =new_expression= handling:
   #+begin_src rust
   "call_expression" | "new_expression" => {
       if let Some(target) = child.child_by_field_name("function") {
           for name in collect_target_names(target, source) {
               refs.push(ExtractedReference { target_name: name.clone(), edge_kind: EdgeKind::Calls });
               // For new expressions, also reference the constructor method
               if child.kind() == "new_expression" {
                   refs.push(ExtractedReference {
                       target_name: format!("{name}.constructor"),
                       edge_kind: EdgeKind::Calls,
                   });
               }
           }
       }
   }
   #+end_src

2. *query.rs* — In =graph_dead_code()=, add constructor exclusion after the =exported= / =Module= / =Template= check:
   #+begin_src rust
   if symbol.exported
       || matches!(symbol.kind, SymbolKind::Module | SymbolKind::Template)
       || (symbol.kind == SymbolKind::Method && symbol.name == "constructor")
   {
       return None;
   }
   #+end_src
   Note: =SymbolKind= must derive =PartialEq= (it already does).

3. *query.rs* — In =resolve_symbol()=, filter the fuzzy fallback to symbol nodes:
   #+begin_src rust
   exact.or_else(|| {
       code_graph
           .graph_search(query, 10)
           .into_iter()
           .filter(|hit| hit.summary.kind != "file")
           .find_map(|hit| find_node_by_summary(graph, &hit.summary))
   })
   #+end_src
   The =summary.kind= field is a string set to ="file"= for file nodes in =summary_for_node()=.

* Edge Cases
- =new SomeModule.SomeClass()=: The =collect_target_names= for member expressions extracts the property name (=SomeClass=), so the constructor reference becomes ="SomeClass.constructor"=. This matches if the class and constructor are in the same file.
- =new (getClass())()=: Dynamic constructor — =collect_target_names= returns empty for complex expressions. No synthetic edge emitted. This is acceptable.
- Constructors in inherited classes: If =Child extends Parent= and =new Child()= is called, we get edges to =Child= and =Child.constructor=. =Parent.constructor= is not referenced — this is correct (it's =Child='s constructor that's called).
- Symbol with name "constructor" that isn't a TS constructor: Unlikely but possible in other languages. The dead_code filter is TS-specific in practice; Elixir doesn't produce Method symbols named "constructor". Safe.
