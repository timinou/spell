* Scope
- In scope: surface HTML/CSS semantic support through `packages/natives` and `packages/coding-agent` so the code tool can read, navigate, graph, and refactor markup/stylesheets truthfully.
- In scope: expose conservative, high-confidence structural refactors for the operations most useful to an agent: class token rename, id rename, custom property rename, selector body replacement, dead-style removal with proof, and explain-before-edit flows for ambiguous cases.
- In scope: make the prompt/docs/result surface capability-based rather than assuming statement/block languages; HTML/CSS users should understand what the tool can and cannot prove.
- Out of scope: unsafe automatic rewrites when consumer matching is uncertain, bulk utility-framework migrations, or browser-rendered visual verification.

* Edge Cases
- Code-tool renderers must sanitize HTML/CSS result text the same way as every other tool path; previews must not leak raw tabs or overly wide lines.
- Dynamic class concatenation, unknown template expressions, or selector matches crossing unsupported host languages must produce refusal/proof output rather than partial mutation.
- Support detection must not lie when only local semantics are available but graph features are unavailable or stale.
- Operation names must remain structurally coherent; do not add a parallel HTML/CSS-only tool when `code` can express the capability.

* Acceptance Criteria
- The code tool treats HTML/CSS as first-class semantic languages end-to-end.
- HTML/CSS affordances are discoverable in prompts, structured details, and rendered results.
- Conservative refactors succeed for provable cases and refuse ambiguous ones with explicit reasoning.
- Focused coding-agent/native tests lock the user-facing contract and failure modes listed above.
