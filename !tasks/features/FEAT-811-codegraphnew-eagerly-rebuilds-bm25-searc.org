## Context
After BUG-456 (warm-load from disk), the first edge query (`def→`/`ref→`/`call→`) still takes ~21-24s on a 70k-symbol / 217k-edge workspace, vs ~0.5s once memoised. Profiling the load path:

`code_graph_cache::get_or_build_graph` → `cache.load::<GraphCacheEntry>` (bincode deserialize of 21MB) → `CodeGraph::from(entry.graph)` → `CodeGraph::new` → **`bm25_adapter::build_search_index(&persisted)`** which tokenises and indexes all 70k node labels into a BM25 SearchIndex on EVERY construction.

Edge resolution (EdgeResolverImpl) walks the petgraph only — it never queries the BM25 index. ∴ ~20s of the warm-load is search-index work that edge queries never use.

## Proposed improvement
Make the BM25 search_index lazy / optional in CodeGraph:
- Option A: OnceCell<Bm25Index> built on first bm25_search_adapted call, not in new.
- Option B: a CodeGraph::new_without_search constructor used by code_graph_cache (edge path); knowledge-worker search lane keeps eager build.
- Option C: persist the BM25 index alongside the graph so load is deserialize-only.

Option A is cleanest (single type, pay-on-use). Verify the knowledge-worker search lane still warms its index eagerly if it needs sub-second first-search.

## Acceptance
- First edge query on a fresh-cache workspace completes in <3s (deserialize-bound, no BM25 build).
- Search lane behaviour unchanged (or explicitly eager-warmed where needed).
