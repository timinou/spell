* Initial Message

Goal: simple frontend to spell server. a client can connect with a secret token to a fast websocket that can let you connect with the running sessions by that user on that instance (through spell autodiscovery, consolidate the feature by looking at existing usage of similar features).

On the frontend, you can start new plan sessions, you can request a url, etc. that lets you use both xterm.js and, for example, see the pdf generated from a typst requested by a task whose goal was to generate a report.

easy way to setup templates from the frontend, wiht a linear-like command bar. Template 'document', you run it, you get a nice card in your session list, and then it tells you when it has the artifact ready.

* Intention & Purpose
Own server-spawned RPC sessions for the web frontend. Provide a ~WebSessionHub~ that: (a) spawns ~spell --mode rpc~ via the existing ~SessionManager~ but with a web-specific lifecycle, (b) tags each spawned session with ~ownedBy~ (the ~WebIdentity.name~ from the spawning request), (c) registers spawned sessions into the unified ~SocketSessionRegistry~ so they appear next to external CLI sessions in autodiscovery, (d) multiplexes per-session ~RpcEvent~ streams to N subscribers, (e) supports forwarding ~RpcCommand~ from a subscriber back to the right ~RpcClient~.

* Context & Narrative
Two session origins must coexist in one list. External CLI sessions register themselves via the bridge socket and emit ~event_log~ entries. Server-spawned sessions need a sibling registration path so the WS layer queries one source of truth. We extend ~SessionRegistryEntry~ minimally: add ~kind: "external" | "spawned"~, ~ownedBy?: string~, ~templateName?: string~, ~rpcClient?: RpcClient~. ~rpcClient~ is the steering hook for spawned sessions; absent for external ones.

The hub does NOT depend on FEAT-WEB-WS but is consumed by it. It also does NOT depend on FEAT-WEB-TEMPLATE-MANIFEST — template instantiation is owned by FEAT-WEB-TEMPLATE-RUN, which calls ~hub.spawn(...)~.

Scenarios:

2. ~spawn~ emits ~session_added~ to lifecycle listeners.

4. ~send~ on spawned session forwards the command and resolves with the matching response (correlated by ~id~).
5. ~send~ on external session id throws "external sessions are not steerable".
6. ~subscribeEvents~ delivers ~RpcEvent~s emitted by the underlying RpcClient to all subscribers; unsubscribe stops delivery.
7. Two subscribers on the same session both receive each event exactly once (independent listener fanout).
8. RpcClient process exits unexpectedly → hub catches ~error~ event, emits ~session_removed~, broadcasts ~error~ event to subscribers, deregisters from registry.
9. Idle timeout reached → lifecycle expires session; hub deregisters and emits ~session_removed~.
10. ~spawn~ returns synchronously after RPC ready event; ~spawn~ never resolves until ~ready~ is observed (or rejects on timeout).
11. Registry: ~getAll()~ returns spawned + external entries in a stable order (spawned first, then external, by ~startedAt~ asc).

* Edge Cases
- Web enabled but ~socket~ disabled: still construct a SocketSessionRegistry (lazy, no SocketServer). External sessions just won't appear; spawned ones still register. Document this in DOC-WEB.
- Two spawn calls for the same key (race) → SessionManager.getOrCreate already deduplicates; hub treats both as the same session and adds two subscribers if asked.
- Subscribers added after ~spawn~ resolves but before first event → no missed events (RpcClient buffers nothing internally — that's accepted; templates always send the first prompt synchronously after spawn so subscribers attached in the same tick will see ~agent_start~).
- Crash mid-spawn (binary missing, ENOENT) → hub rejects ~spawn~, emits nothing, no registry entry leaked.
- Killing a session that another client is currently sending an ~rpc~ command to → in-flight ~send~ promise rejects with "session terminated".
