* Scope
** In scope
- When the =task= tool spawns a subagent with =todoRef=, automatically include completed predecessor task results in the subagent's context
- Extend =resolveVerificationContext()= in =task/template.ts= to build a predecessor results section
- Predecessor = any task whose ID appears in the current task's =blockers= list AND has =status: "completed"= with a =result= field
- Result summary is truncated (configurable, default 2000 chars per predecessor)
- Parent agent can augment/override via the =assignment= text in the task call
** Out of scope
- Storing results on TodoItem (done in FEAT-B)
- Task tool lifecycle changes (done in FEAT-D)
** Boundary rationale
Result forwarding is a read-only extension of the existing =resolveVerificationContext()= mechanism. It reads from TodoItem.result (set by FEAT-D on completion) and TodoItem.blockers.

* Tests
** File: =packages/coding-agent/test/task/result-forwarding.test.ts= (new)
Scenarios:
1. Task with 2 completed predecessors: subagent context includes both results
2. Task with 1 completed + 1 pending predecessor: only includes the completed one
3. Task with no predecessors (no blockers): no result section injected
4. Predecessor result exceeds 2000 chars: truncated with "[truncated]" marker
5. Result forwarding coexists with verification context (both sections present)

- Truncate each result to MAX_PREDECESSOR_RESULT_CHARS (2000)

* Edge Cases
- Predecessor completed with =result: undefined= (no output): skip it
- Circular blocker references: resolveVerificationContext already handles by looking up IDs, not traversing
- Very large result set (5+ predecessors): cap at 5 predecessors, total budget 10000 chars
