* Scope
In scope:
- Add summary-first staged behavior for broad or weakly scoped grep requests: workspace-wide searches, path-light searches, and pattern sweeps whose first step should be file-hit discovery rather than immediate large content injection.
- Preserve current direct content behavior for already narrow grep calls (explicit file/path/type/glob constraints or obviously focused searches).
- Reuse shared policy classification from `PROJ-047-cross-tool-context-pressure-policy` so transcript/session grep and broad exploratory grep share one policy vocabulary.
- Reduce repeated near-identical grep churn by reusing prior compact summaries when the query/path scope is unchanged and the underlying state has not meaningfully changed.

Out of scope:
- Turning grep into a semantic search tool; `code search`, `ast_grep`, and `lsp` remain the better surfaces for that.
- Forcing staged behavior on tightly scoped grep that already functions as a precise inspection tool.
- Generic workspace caching for all tools; only grep-specific reuse needed for these workflows belongs here.

Rationale:
- `grep:source search` + `grep:other search` together contribute ~14.0% of sampled tokens and ~13.9% of fresh input.
- Many exact grep calls in the review are classic exploration churn: large token cost, tiny visible yield, broad paths, and immediate follow-up searches with slightly refined patterns.
- Fresh-input reduction is the primary optimization objective settled for this plan, and broad grep is one of the clearest input-heavy categories after `read`.

* Tests
Workflows to enumerate and defend first:
1. Workflow 1 — a broad grep returns file-hit counts and representative matches first instead of dumping a large match body.
2. Workflow 2 — a narrow grep (single file, explicit path/glob/type scope, or obviously precise query) still returns direct content results without forced staging.
3. Workflow 3 — transcript/session grep under `.spell` is classified as high-noise and defaults to compact summaries.
4. Workflow 4 — a repeated near-identical broad grep can reuse a compact prior summary when state has not changed, instead of paying the full exploration cost again.
5. Workflow 5 — the staged summary exposes the truthful next-step path so the agent can auto-escalate to a narrower grep or a follow-up read/code tool call.

* Edge Cases
- A grep can be broad by path but precise by pattern; staging should look at both, not only one dimension.
- A narrow grep may still return many matches; do not accidentally stage every high-cardinality precise grep if the user intentionally scoped it.
- Transcript/session grep under `.spell` should stage even when the query itself is precise, because the domain is inherently noisy.
- Reuse logic must not return stale summaries after edits or file changes that could invalidate match sets.
- Representative examples must not lie about omitted matches or file counts.

* Acceptance Criteria
- Broad grep searches become summary-first and reduce fresh-input / turn-count pressure.
- Narrow grep searches preserve direct precision behavior.
- Transcript/session grep defaults to compact summary behavior.
- Repeated broad grep calls can reuse prior summaries when safe.
- Focused tests cover broad-vs-narrow staging, transcript grep handling, repeat-query reuse, and truthful next-step guidance.
