* Problem

The Anthropic streaming contract is one assistant message ≡ one atomic tool batch. The model can't see a =tool_result= mid-message, so it stuffs its entire plan into one turn: =[text, bash(echo ok1), await, bash(echo ok2), bash(ok3)…]=. Tools execute only *after* =streamAssistantResponse= consumes the whole SSE.

Today's =packages/agent/src/agent-loop.ts::streamAssistantResponse= drains the stream to completion. Then =executeToolCalls= runs the batch. If any tool declares =executionMode: "sequential"= (=ask=, =await=, =cancel_job=, =exit_plan_mode=, =browser=), the *whole batch* serializes in source order. The model has already burned tokens speculating about state it can't possibly know (e.g. =echo ok2= after =await= without seeing await's result).

Net effects:
- Wasted output tokens (model babbles past a state barrier)
- Confused operator UX (pending cells appear for tools whose args were generated before barrier state existed)
- Stale model assumptions (the post-barrier text/thinking is reasoning against a fictitious state)

Reference harnesses surveyed (=pi-mono= =packages/agent/src/agent-loop.ts=, =forks/pi=, opencode): none implement a stream barrier. They all drain the SSE then split into sequential/parallel batches. The opportunity is genuinely uncontested.

* Goal

When the streamed assistant message emits =toolcall_end= for a tool whose definition declares =executionMode: "sequential"=, *cut the SSE at that point*:
- close the assistant message with =stopReason: "toolUse"=
- keep only content up to and including the barrier tool block
- abort the upstream SSE (best-effort)
- let =runLoop= execute the trimmed batch and continue with a fresh assistant turn that carries real tool_result context

This enforces a property the autoregressive model cannot enforce itself: *don't generate tokens about a state you don't yet have*.

* Existing Patterns

- =packages/agent/src/agent-loop.ts::streamAssistantResponse= owns the SSE consumer loop. The new behavior lives here, in the switch on =event.type=, branch =toolcall_end=.
- =packages/agent/src/types.ts::ToolExecutionMode= already defines =sequential | parallel=. Five tools opt in: =packages/coding-agent/src/tools/{ask,await-tool,cancel-job,exit-plan-mode,browser}.ts=.
- =packages/agent/src/agent-loop.ts::executeToolCalls= already partitions sequential vs parallel batches at the =records.some(r => r.tool?.executionMode === "sequential")= site. After the cut, the trimmed message hits this exact path — no scheduler change needed.
- =packages/ai/src/types.ts::AssistantMessageEvent= defines the event shape; =toolcall_end= carries =toolCall= with completed =arguments=. Anthropic content blocks stream strictly in order (=content_block_start= → deltas → =content_block_stop=), so cutting at =toolcall_end= leaves a clean, completable message.
- =packages/ai/src/providers/anthropic.ts:725+= already uses an internal =AbortController= (=requestAbortController=) for idle-timeout aborts. The barrier reuses the same pattern: signal cancellation propagates to the SSE.
- =packages/coding-agent/src/session/agent-session.ts= TTSR mechanism (=#handleAgentEvent= ~line 693) shows the abort+inject pattern for stream interruption, but uses =agent.abort()= which sets =stopReason: "aborted"=. The barrier path is cleaner: it sets =stopReason: "toolUse"= directly, no abort fakery.

* User Workflows

1. Model emits =[thinking, bash(ok1), await, bash(ok2)]= in one turn. Barrier cuts at await's =toolcall_end=. Resulting assistant message contains =[thinking, bash(ok1), await]= with =stopReason: "toolUse"=. Tools execute sequentially. Next turn the model sees await's actual result and decides whether =bash(ok2)= still makes sense.
2. Model emits =[text, ask("Should I proceed?"), bash(do_thing)]=. Barrier cuts at ask's =toolcall_end=. =bash(do_thing)= is *never executed* — it was speculation about the user's answer. Next turn proceeds with the real answer.
3. Two sequential tools in same turn: =[await(jobA), await(jobB)]=. Barrier fires at first =toolcall_end= (=await(jobA)=). Trimmed message contains only =[await(jobA)]=. =await(jobB)= will be re-emitted in the next turn if still relevant.
4. Sequential tool is first content block: cut immediately, single-tool batch executes, normal continuation. No regression.
5. Network mid-stream stall during a barrier tool's args: =toolcall_end= never arrives → barrier never triggers → existing stall-retry path handles it normally.
6. Pure-parallel batch (no sequential tool): no =toolcall_end= for a sequential tool fires → full stream consumed as today. Zero behavioral change.
7. Setting =sequentialToolStreamBarrier: "off"=: opt-out for diagnostics / regression testing.

* Edge Cases

- **Provider stream-retry mid-block**: Anthropic provider wipes content on transient stall (=packages/ai/src/providers/anthropic.ts= comment at line 710+). Post-retry the consumer sees fresh =content_block_start= events. The barrier only fires on =toolcall_end= for blocks present *now*, so it cannot trigger on a wiped/dead id. Safe.
- **=interruptMode: "wait"= steering**: orthogonal — steering check runs after each tool, not during stream. Unaffected.
- **Token billing**: provider charges for output generated before abort. Acceptable; net savings come from not paying for *next* batches of stale post-barrier tokens.
- **Lost thinking blocks after the barrier**: model's chain-of-thought after the barrier was reasoning against fictitious state. Discarding it is the *point* — keeping it would corrupt future-turn context.
- **=ttsr= interaction**: TTSR's =agent.abort()= also enters =streamAssistantResponse='s signal-aborted branch. The barrier check runs *before* the signal check inside the toolcall_end branch, but if TTSR aborts during stream the signal-check inside the loop top wins. No conflict.
- **Subagent sessions**: same code path, same behavior. Subagents inherit =sequentialToolStreamBarrier= via =AgentLoopConfig=.
- **Tool resolved via =resolveUnknownTool=**: =context.tools= may not contain the tool definition mid-stream. The lookup misses → fail open (no barrier). Acceptable: deferred-tier tools are uncommon, and this preserves correctness over over-aggressive cutting.
