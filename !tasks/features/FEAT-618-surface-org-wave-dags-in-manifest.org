* Initial Message

the org wave tool should provide the file-level DAG and the subfeature-level DAG, to provide better ways for the implementation agent to orchestrate smartly.

* Scope
- In scope: make `org wave` expose both DAGs in the TypeScript org tool response and append readable DAG sections into the PLAN `* Execution Manifest` when `manifest=true` and `planItemId` is used.
- In scope files: `packages/org/src/tool.ts`, `packages/org/src/types.ts`, `packages/org/test/cmd-wave-manifest-plan.test.ts`, `packages/org/test/cmd-wave-flatten.test.ts`, `packages/org/test/cmd-wave-duplicate-id.test.ts`, and any focused org tool result tests needed for formatting.
- Out of scope: changing `exit_plan_mode` wave extraction semantics, changing `todo_write` task materialization, or adding a new `org` subcommand.
- User-settled decisions: file-level DAG nodes are child item CUSTOM_IDs, not physical paths; subfeature-level DAG nodes are sub-outline CUSTOM_IDs; `file_dag.edges` omit intra-child dependencies; readable DAG sections must be written into the PLAN Execution Manifest; structured response uses explicit `{ nodes, edges }`; `edges[].from` depends on `edges[].to`.

* Existing Patterns
- Current `cmdWave` calls `executeOrg({ command: "computeWaves", items, doneStates: ["DONE"] })`, formats only wave headings via `formatWaveManifest`, and writes via `writeManifestSection`.
- Current manifest format is parsed by `packages/coding-agent/src/tools/exit-plan-mode.ts::extractPlanWaves`, which only consumes `** ... :wave:` headings. New DAG sections must not include the `:wave:` tag.
- Current plan validation treats every `[[id:...]]` in the PLAN body as a child/sub-outline reference. To avoid false validator failures, DAG sections should reference only linked child IDs and declared sub-outline IDs, or use code-form IDs where links are not required.
- Use existing TUI sanitization conventions if rendering changes are required; no raw console logging.

* Tests
- Workflow T1: `org wave category=features manifest=true` returns `file_dag` and `subfeature_dag` in JSON while preserving existing `manifest`, `waves`, `warnings`, and `total_sub_outlines` fields.
- Workflow T2: `org wave manifest=true planItemId=PLAN-*` writes `* Execution Manifest` with wave sections plus readable `** File-level DAG` and `** Subfeature-level DAG` sections, neither tagged `:wave:`.
- Workflow T3: file DAG collapses `FEAT-A::test -> FEAT-B::types` to `FEAT-A -> FEAT-B`, dedupes repeated cross-child edges, and omits `FEAT-A::impl -> FEAT-A::test`.
- Workflow T4: duplicate ID errors from native `computeWaves` still return the exact existing `DUPLICATE_CUSTOM_ID` object and do not write a partial manifest.
- Workflow T5: a PLAN with no linked child items preserves the existing warning-only no-write behavior.
- Verification commands: `bun test packages/org/test/cmd-wave-manifest-plan.test.ts`; `bun test packages/org/test/cmd-wave-flatten.test.ts`; `bun test packages/org/test/cmd-wave-duplicate-id.test.ts`; `bun test packages/coding-agent/test/tools/exit-plan-mode-waves.test.ts` if manifest formatting touches extraction compatibility.
