* Scope
- In scope: add explicit `code` file-lifecycle support for move and delete so those operations no longer live only in `edit` during the migration window.
- In scope: extend the TypeScript schema, tool documentation, result typing/rendering, and native code-buffer bridge so move/delete are first-class `code` file commands with truthful semantics.

- Out of scope: removing the temporary `edit` adapter entirely. That remains the existing follow-up once parity is proven.

* Tests
- Workflow 1: `code delete { file }` deletes an existing text file, returns truthful success details, and invalidates any managed buffer for that path.
- Workflow 2: `code move { file, destination }` moves an existing file, preserves content, invalidates source/destination buffer state, and invalidates filesystem scan caches on both paths.
- Workflow 3: move/delete behave truthfully for fallback text buffers and semantic-capable files.
- Workflow 4: missing source paths, existing destinations, and illegal payload combinations produce explicit errors rather than silent no-ops.
- Workflow 5: tool docs and structured details match the final command surface exactly.
- Workflow 6: `edit`/`code` interoperability remains truthful after move/delete parity lands; no stale-buffer false positives when a follow-up `code` command touches the moved path.

* Edge Cases
- Destination path must be explicit and validated; avoid overloading `content` or declaration-level `rename` semantics.
- Deleting an open buffer must not leave stale buffer entries behind.
- Moving across semantic/fallback extension boundaries must not lie about semantic support after the destination opens again.
- Existing destination handling must be explicit: either reject or replace, but the command contract must state which and tests must lock it down.
