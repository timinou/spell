* Initial Message

Goal: simple frontend to spell server. a client can connect with a secret token to a fast websocket that can let you connect with the running sessions by that user on that instance (through spell autodiscovery, consolidate the feature by looking at existing usage of similar features).

On the frontend, you can start new plan sessions, you can request a url, etc. that lets you use both xterm.js and, for example, see the pdf generated from a typst requested by a task whose goal was to generate a report.

easy way to setup templates from the frontend, wiht a linear-like command bar. Template 'document', you run it, you get a nice card in your session list, and then it tells you when it has the artifact ready.

* Intention & Purpose
Add a new ~web~ block to ~server.kdl~ that configures multiple named bearer tokens. Add a ~verifyWebToken~ guard that maps an inbound ~Authorization: Bearer <secret>~ header (or ~?token=<secret>~ query for WebSocket upgrade) to a stable identity record (~{name, source}~). All other ~/web~ subsystems consume this identity for ownedBy tagging and audit logging.

* Context & Narrative
Today ~server.kdl~ models only HTTP basic-auth for ~/api/*~ and HMAC/bearer for individual ~/trigger/<id>~ goals. The web frontend needs a different auth surface: shared bearer tokens, multiple human identities (Alice, Bob...), one keyspace per deployment, no per-route bypass. The token is sent on the WS upgrade request via ~?token=~ query string (browsers cannot set custom headers on ~new WebSocket()~) and on every plain HTTP /web request via ~Authorization: Bearer~. ~env(...)~ resolution is REQUIRED for the secret value so tokens never live in plaintext KDL.

This item ONLY adds the config schema, parser, types, and the verifier function. Wiring it into routes is done in dependent items.

* Edge Cases
- Token presented but ~web~ not configured → 401 (verifier returns null, route layer maps to 401). Audit log notes "web subsystem disabled".
- Both header and query present → header wins (more explicit).
- Token containing ~:~ or ~/~ → still allowed; we never URL-encode/decode beyond what URLSearchParams does.
- Empty ~Authorization: Bearer~ (whitespace only) → null.
- ~web { token "alice" "env(MISSING, optional)" }~ → resolves to undefined → tokens.alice is dropped with a logger.warn (don't throw — optional ones may be intentionally inactive).
- Identical secrets across two names → both entries kept; ~verifyWebToken~ returns the first lexicographically-sorted match. Documented in code comment as a defensive policy.
