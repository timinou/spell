* Initial Message

Goal: simple frontend to spell server. a client can connect with a secret token to a fast websocket that can let you connect with the running sessions by that user on that instance (through spell autodiscovery, consolidate the feature by looking at existing usage of similar features).

On the frontend, you can start new plan sessions, you can request a url, etc. that lets you use both xterm.js and, for example, see the pdf generated from a typst requested by a task whose goal was to generate a report.

easy way to setup templates from the frontend, wiht a linear-like command bar. Template 'document', you run it, you get a nice card in your session list, and then it tells you when it has the artifact ready.

* Intention & Purpose
Stand up a Vite-built React+TypeScript SPA that becomes the spell frontend. Embed its build output into ~@oh-my-pi/spell-server~ so the daemon serves the SPA at ~/web/~ with no runtime CDN dependency. Wire up authentication (token persisted in ~localStorage~, redirected to a login screen if missing/invalid) and a stable WebSocket client that connects to ~/web/ws~. Provide an empty layout shell (sidebar + main pane) and the auth/ws plumbing the next two items will build on.

* Context & Narrative
The existing dashboard at ~packages/spell-server/src/http/frontend/index.html~ is a single embedded HTML using Preact via esm.sh. Per the design decision, the new frontend is heavier (xterm.js, cmdk, PDF viewer) and benefits from a real bundler. Vite is the standard choice and integrates cleanly with Bun. The build emits a flat ~dist/~ which spell-server slurps at startup (small bundle, ≤ 1 MiB gzipped) into a Map and serves with correct Content-Type. Hashed filenames make caching trivial.

* Edge Cases
- ~web/dist~ does not exist (builder forgot to run) → at startup log a clear warning and serve a hard-coded HTML shell with "Run ~bun run build:web~ first." Do not crash spell-server.
- Token rejected by ~/web/api/sessions~ → ~useAuth~ marks invalid, returns to login. WSClient does not start.
- Browser without WebSocket support → fail gracefully, show banner.
- Two tabs open → each holds an independent WS; both authenticate; both receive broadcast events. Documented as expected.
- Asset path with ~..~ → 400.
- Build hashing: vite default emits ~/assets/index-<hash>.js~; loader stores under exact path.

* Acceptance Criteria
- ~bun run build:web~ produces a working bundle.
- Spell-server launches; ~curl /web/~ returns ~index.html~; ~curl /web/api/sessions~ with valid token returns JSON.
- Browser visit shows login → token entry → empty shell with sidebar placeholder.
- ~bun check:ts~ clean.
- All scaffold tests pass.
