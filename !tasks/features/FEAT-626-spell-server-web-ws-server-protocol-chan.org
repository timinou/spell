* Initial Message

Goal: simple frontend to spell server. a client can connect with a secret token to a fast websocket that can let you connect with the running sessions by that user on that instance (through spell autodiscovery, consolidate the feature by looking at existing usage of similar features).

On the frontend, you can start new plan sessions, you can request a url, etc. that lets you use both xterm.js and, for example, see the pdf generated from a typst requested by a task whose goal was to generate a report.

easy way to setup templates from the frontend, wiht a linear-like command bar. Template 'document', you run it, you get a nice card in your session list, and then it tells you when it has the artifact ready.

* Intention & Purpose
Mount a WebSocket endpoint at ~/web/ws~ on the existing HTTP server. Authenticate with ~?token=~ on upgrade. Define a stable client/server message protocol: list/subscribe sessions, forward RPC commands, route blocking-event answers to external sessions, push artifact-created events filtered by extension, and broadcast registry lifecycle changes.

Provide REST companions under ~/web/api/*~ for stateless lookups (sessions list, templates list, artifacts list, manifest read). All routes share ~verifyWebToken~ from FEAT-WEB-AUTH.

* Context & Narrative
~spell-server~ already creates one ~Bun.serve~ instance in ~http/server.ts::startHttpServer~. The Bun pattern uses ~server.upgrade(req, { data })~ inside ~fetch~ and a sibling ~websocket~ handler. We mirror the ~packages/qml-remote/src/server.ts~ template exactly, but here the WS handler lives co-located with the HTTP handler so a single ~Bun.serve~ owns both.

A WS connection is a per-client multiplexer. The client subscribes to per-session channels with optional filter args (e.g., ~artifactExt: [".pdf"]~). The server pushes events tagged with ~sessionId~ + ~channel~. Lifecycle messages (~session_added~/~_removed~/~_updated~) flow on a global channel everyone sees.

Channels:

Out-of-scope:
- Template execution logic itself (FEAT-WEB-TEMPLATE-RUN owns ~runTemplate(name, params, identity)~). The WS/REST layers call into it.
- Frontend code.

Protocol (canonical):

Client → Server:
- ~{ type: "list_sessions" }~
- ~{ type: "subscribe"; sessionId; channels: Channel[]; artifactExt?: string[] }~
- ~{ type: "unsubscribe"; sessionId; channels?: Channel[] }~ (omit channels = all)
- ~{ type: "rpc"; sessionId; command: RpcCommand }~ (spawned only)
- ~{ type: "answer_blocking_event"; sessionId; eventId; payload: EventResponsePayload }~ (external only)
- ~{ type: "spawn"; templateName?: string; params?: Record<string, unknown>; mode?: string; setupRef?: string; cwd?: string; initialPrompt?: string }~
- ~{ type: "kill"; sessionId }~
- ~{ type: "mint_artifact_url"; sessionId; artifactPath; ttlSec? }~
- ~{ type: "ping" }~

Server → Client:
- ~{ type: "auth_ok"; identity: { name } }~ (immediately on open)
- ~{ type: "session_list"; sessions: SessionSummary[] }~
- ~{ type: "session_added" | "session_removed" | "session_updated"; session: SessionSummary }~
- ~{ type: "rpc_event"; sessionId; event: RpcEvent }~
- ~{ type: "rpc_response"; sessionId; response: RpcResponse }~
- ~{ type: "external_event_log"; sessionId; entry: EventLogEntry }~
- ~{ type: "blocking_event"; sessionId; payload: BlockingEventPayload }~ (mirrored when bridge fires)
- ~{ type: "artifact_created"; sessionId; artifact: ArtifactRef & { ext, mime, sizeBytes, ts, label? } }~
- ~{ type: "artifact_url"; sessionId; url: string; expiresAt: number }~
- ~{ type: "spawn_result"; correlationId?; sessionId }~ (response to spawn)
- ~{ type: "error"; correlationId?; code; message }~
- ~{ type: "pong" }~

Scenarios (WS):
1. Upgrade with valid ~?token=~ succeeds; server immediately sends ~auth_ok~ with the identity name.
2. Upgrade with invalid token → 401; no upgrade.
3. ~list_sessions~ → ~session_list~ with all spawned + external entries.
4. New external session registers via socket bridge → all open WS connections receive ~session_added~ with kind ~"external"~.
5. ~spawn~ → spawn delegated to hub; on success, server replies with ~spawn_result~ (correlationId echoed) and broadcasts ~session_added~.
6. ~subscribe~ to ~"events"~ on a spawned session → subsequent ~rpc_event~ messages arrive on that connection only.
7. ~rpc { command: { type: "prompt", message: "..." } }~ → server forwards to hub; ~rpc_response~ later delivered.
8. Two clients subscribed to same session, only one calls ~rpc~ → both see ~rpc_event~s; only the caller sees the matching ~rpc_response~ (correlated by command ~id~).
9. ~subscribe~ with ~artifactExt: [".pdf"]~ → ~.pdf~ files emit ~artifact_created~; ~.png~ files do not. Case-insensitive.
10. ~subscribe~ with ~ext: ["*"]~ or omitted → all artifacts.
11. ~unsubscribe~ stops further deliveries on those channels.
12. WS close → all subscriptions dropped; no leaks; pending mint_url settles with abort error.
13. ~answer_blocking_event~ on external session forwards to ~SocketSessionRegistry.resolveEvent~. On spawned session, returns ~error~ with code ~"not_supported_for_spawned"~.
14. ~mint_artifact_url~ → server returns ~artifact_url~ with valid signed URL.

Scenarios (REST):
15. ~GET /web/api/sessions~ with valid bearer → JSON list.
16. Without bearer → 401.
17. ~POST /web/api/sessions/:id/artifacts/url~ → JSON ~{ url, expiresAt }~.
18. ~DELETE /web/api/sessions/:id~ → 204; underlying hub.kill called.

* Edge Cases
- Browser cannot send custom headers on ~new WebSocket()~ → ~?token=~ is the canonical path. Header still accepted for non-browser clients (curl, tests).
- Connection drops mid-subscription → cleanup in ~close~ handler removes all listener registrations for that connection. Verified by leak test.
- Sending an ~rpc~ command for an external session → respond ~error~ ~"not_steerable"~ but keep the connection.
- Backpressure: ~ws.send~ with very large arg JSON → if ~ws.readyState !== OPEN~, drop and log; if buffered amount exceeds 4 MiB, drop subsequent events for that connection until below threshold.
- Spawn with templateName when template manifest missing → ~error~ ~"unknown_template"~.
- Two clients spawn the same template concurrently → each gets a distinct sessionId (no dedup).
