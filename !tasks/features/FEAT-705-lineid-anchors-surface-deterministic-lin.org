* Intention & Purpose
Make line anchors copy-pasteable. Tool docs promise `LINE#ID` format (e.g., `5#QW`) so an agent can read a line then reference it in `splice`/`insertBefore` `pos:"5#QW"`. Currently get output shows `<line 5>` with no hash ID, breaking the documented contract.

* Context & Narrative
`crates/pi-code-path/src/dialects/text/axes.rs:28-42` produces NodeRef with `locator: format!("<line {}>", ln)` — no hash ID. The display layer (`packages/coding-agent/src/tools/codepath-result.ts::formatLocator`/`nodeToLocation`) doesn't synthesize one. The kernel-side `pos`/`end` action handlers can already accept `"5#QW"` strings and resolve via content-hash lookup; the missing piece is generating and emitting the IDs at line-render time.

Anchor ID semantics: deterministic per (file, line, line-content). Two-character base32 hash of `line_text` is enough — collisions within a single file are vanishingly rare, and the kernel re-validates the hash before applying the action. Edits earlier in the file that don't touch line 5 leave its anchor stable.

* Edge Cases
- Empty line: `line_anchor_id("")` deterministic value (e.g., `"AA"`)
- Trailing whitespace: hash includes whitespace
- Windows line endings: anchor on bytes between newlines
- pos with no `#ID` suffix (just `"5"`): permitted, no hash validation (backwards-compat)
- Hash collision: documented; user re-anchors via fresh get
