* Scope
- In scope: define the canonical tree-sitter affordance DSL extensions required to make HTML and CSS first-class semantic languages in `pi-code-engine`, with contracts intentionally reusable by HEEx and other host/template languages.
- In scope: add an explicit verification matrix and fixture corpus strategy before implementation so every later item inherits the same semantic truth surface and failure handling rules.
- In scope: specify capability metadata for outline/read/resolve/navigate/edit/graph extraction so downstream `pi-code-graph` and `coding-agent` layers do not invent parallel language knowledge.
- Out of scope: utility-framework semantics, CSS-in-JS, Vue/Svelte/Astro single-file components, and JavaScript-in-`<script>` analysis beyond embedded-region placeholders. Those belong to follow-up work once the core substrate is proven.

* Existing Patterns
- `crates/pi-code-engine/src/language/profile.rs`
  - existing declaration/class/import/export/reference DSL; this item extends that schema instead of adding HTML/CSS special-case walkers.
- `crates/pi-code-engine/src/procedure/mod.rs`
  - activation/selector/transform procedure builder; HTML/CSS affordances must remain declarative here except for tightly-scoped custom transforms.
- `crates/pi-code-engine/src/procedure/rules.rs`
  - rule expressions already leverage generated production/inverse metadata; extend this path rather than hard-coding node-kind checks everywhere.
- `crates/pi-code-engine/build.rs`
  - build-time node-types ingestion; HTML/CSS grammar metadata must flow through the same generator.
- `crates/pi-code-engine/src/outline.rs`, `src/resolve.rs`, `src/navigate.rs`, `src/line_target.rs`
  - current consumers of profile data; the new DSL must serve these paths without language-specific forks except where markup semantics are fundamentally different.
- `crates/pi-code-graph/src/language/generic.rs`
  - graph extraction already consumes engine profiles; this item must publish enough structure for downstream graph reuse.

* Edge Cases
- Repeated anonymous containers must never collapse onto the same symbol name; deterministic disambiguators are required.
- DSL additions must preserve existing TypeScript/Rust/Python/Typst/Markdown/Org/Elixir behavior; regression tests are mandatory where shared code changes.
- Partial parse recovery must surface lowered confidence instead of pretending exact selectors/elements are safe rename targets.
- Embedded-region contracts must keep host and guest byte ranges stable even when delimiters belong to the host language.
- Selector/token matching must distinguish exact semantic tokens from raw substrings; `.btn` and `.btn-primary` are not interchangeable.

* Acceptance Criteria
- One canonical DSL can describe HTML and CSS affordances without introducing a second engine or ad-hoc extractor layer.
- A documented, fixture-backed verification matrix exists before downstream implementation begins.
- Engine tests cover the full workflow and edge-case matrix listed above, including truthful degradation behavior.
- The published contract is explicitly reusable by HEEx rather than Phoenix-specific.
