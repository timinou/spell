* Goal

Make =executeOrg= NAPI function use the same =BufferRegistry= as =executeCodeBuffer=
so org files are managed through the unified buffer system. Org write commands
operate on in-memory buffers with auto-save, eliminating the TS read-modify-write
pattern.

* Current state

- =crates/pi-natives/src/code_buffer.rs= — =static BUFFER_REGISTRY: OnceLock&lt;BufferRegistry&gt;=
- =crates/pi-natives/src/org_buffer.rs= — stateless, re-parses source every call

* Architecture

** Shared registry access

Move the buffer registry static to a shared module or make it accessible from both
=code_buffer.rs= and =org_buffer.rs=:

#+BEGIN_SRC rust
// crates/pi-natives/src/lib.rs or shared module
pub(crate) fn buffer_registry() -> &'static BufferRegistry {
    static REGISTRY: OnceLock<BufferRegistry> = OnceLock::new();
    REGISTRY.get_or_init(|| BufferRegistry::new(language_registry()))
}
#+END_SRC

Both NAPI entry points call =buffer_registry()=.

** New org write commands in =executeOrg=

Add commands that operate on buffered org files:

- =createItem= — open/create buffer, apply create_item TextEdits, save
- =updateItem= — open buffer, apply state/title/body edits, save
- =setProperty= — open buffer, apply set_property edits, save
- =appendNote= — open buffer, apply append_note edits, save
- =editSection= — open buffer, apply section edits, save (replaces current stateless version)

Each write command follows the pattern:
1. Get or open buffer from registry
2. Call pi-org-engine edit function to produce =Vec&lt;TextEdit&gt;=
3. Apply edits via =buffer.edit_batch()=
4. =buffer.save()= (auto-save)
5. Return success response

** Keep stateless read commands

=parse=, =query=, =graph=, =computeWaves=, =nextWave= can remain stateless (parse from
source string) for efficiency — they don't need buffer management. But they should
also work on buffered files when a buffer is already open (avoid re-reading disk).
