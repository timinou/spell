PLAN-315 W4 already added a `subscribe { repo_handle, lanes }` channel
to the knowledge daemon that pushes `index_changed`, `warm_completed`,
`evicted`, `heartbeat`, and `lag` event frames. `MemoryStatusController`
currently polls `peekMemoryProgress` instead of consuming this push
channel, so it pays one RPC round-trip every poll interval and lags
behind real state by up to a full poll period.

** Targets

- `packages/coding-agent/src/modes/controllers/memory-status-controller.ts`
  - subscribe at `start()`; unsubscribe at `stop()`
  - on `warm_completed` → re-render with `warm` status
  - on `index_changed` → re-render with current progress (delta-fold)
  - on `evicted` → re-render with `unavailable`
  - on `lag` → log + fall back to a one-shot peek to resync
- New thin client helper in `packages/coding-agent/src/tools/memory.ts`
  (or `packages/natives/src/knowledge/subscribe.ts`) that wraps the
  underlying `KnowledgeSubscription` (already exists in
  `pi_natives::knowledge_client`).

** Constraints

- Subscription lifecycle MUST match controller lifecycle. Drop on
  controller dispose, on session re-init, on cwd change.
- One subscription per (session, repo_handle). Multi-window / multi-cwd
  sessions need dedup keyed on repo_handle.
- Failure to subscribe (daemon down, capability missing) MUST fall back
  to polling silently — no error in the status line.
- Backpressure: subscription channel is `sync_channel(256)` with
  oldest-drop + `lag` event. On `lag`, the controller MUST resync via
  one-shot peek before resuming event-driven updates.

** Acceptance

- Cold session: status line transitions warming → warm within ~50ms of
  the daemon's `warm_completed` push (vs up to 5s under polling).
- Daemon kill mid-session: subscription error surfaces as fallback to
  poll-mode within 1 reconnect attempt.
- No double-update flicker (push + scheduled poll both firing).
- Subscription teardown leaves no leaked thread, no lingering
  `SubscriptionToken`, no socket fd in `lsof`.

** Difficulty

~3h. Soft because:
- daemon side already implemented (PLAN-315 W4)
- `KnowledgeSubscription` already exists in `pi_natives::knowledge_client`
- protocol frames already defined

Sharp edges:
- lifecycle correctness across session re-init / cwd change
- fallback path when daemon doesn't support subscribe (older daemon)
- avoiding the double-source-of-truth flicker between push and one
  remaining poll
