* ProfileExtractor Design

#+begin_src rust
use pi_code_engine::language::LanguageProfile;

pub struct ProfileExtractor {
    profile: Arc<LanguageProfile>,
}

impl LanguageExtractor for ProfileExtractor {
    fn language(&self) -> SupportedLanguage {
        SupportedLanguage::new(self.profile.id.as_str())
    }

    fn matches_path(&self, path: &Path) -> bool {
        path.extension()
            .and_then(|e| e.to_str())
            .map(|ext| self.profile.extensions.contains(&ext.to_string()))
            .unwrap_or(false)
    }

    fn extract(&self, path: &Path, source: &str) -> Result<ExtractedFile> {
        // 1. Parse source with tree-sitter using profile.ts_language
        // 2. Walk tree, matching nodes against profile.declarations → ExtractedSymbol
        // 3. Walk tree, matching nodes against profile.imports → ExtractedImport
        // 4. For each symbol, collect references by matching profile.references patterns
        // 5. Return ExtractedFile
    }
}
#+end_src

The generic extractor uses the same tree-sitter parsing the old hand-coded extractors used, but reads patterns from the profile instead of hardcoding them.

* Known Divergences

The old TypeScript extractor uses =oxc_resolver= for import path resolution. The profile-driven extractor needs to handle import resolution too. Options:
1. Keep =oxc_resolver= for TypeScript imports (it's already a dependency)
2. Create a generic =ImportResolver= driven by profiles

Recommendation: keep =oxc_resolver= for TypeScript specifically (import resolution is complex and language-specific). The profile's =imports= patterns identify WHERE imports are in the tree; the resolver handles HOW to resolve the specifier to a file path. TypeScript and Elixir each keep their own resolvers — only the EXTRACTOR (symbol/import detection) becomes generic.
