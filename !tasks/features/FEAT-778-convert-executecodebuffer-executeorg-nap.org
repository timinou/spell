* Initial Message

do a deep, critical review of the work just done, and identify any sources of lag or undue TUI renders. the TUI stil feels a bit slow.

* Goal

Stop blocking the JS event loop while Rust does file I/O + parsing
+ diff work in ~executeCodeBuffer~ and ~executeOrg~. Match the
already-correct pattern used by ~executeCodePath~ (BUG-393).

* Diagnosis

Today, both bindings are sync:

#+begin_src rust
#[napi(js_name = "executeCodeBuffer")]
pub fn execute_code_buffer(options: Value) -> Result<Value> {
    match execute_code_buffer_inner(&options) { ... }
}

#[napi(js_name = "executeOrg")]
pub fn execute_org(options: Value) -> Result<Value> {
    Ok(execute_org_catching(&options, execute_org_inner))
}
#+end_src

The JS main thread is held for the entire Rust call (50-500ms typical
for parse/diff/format on real files). Cursor stops blinking, input
buffers, renders stall. User-visible UI hang.

~executeCodePath~ is already correct: returns
~crate::task::Async<Vec<CodePathChunk>>~, runs on the libuv blocking
thread pool, frees the JS event loop for the duration.

Both ~execute_code_buffer_inner~ and ~execute_org_inner~ use
~buffer_registry()~ — the same global state used by the already-async
~executeCodePath~. Thread-safety is already established.

   After:
#+begin_src rust
#[napi(js_name = "executeCodeBuffer")]
pub fn execute_code_buffer(
    options: Value,
    abort_signal: Option<AbortSignal>,
) -> crate::task::Async<Value> {
    let ct = CancelToken::new(None, abort_signal);
    crate::task::blocking("code_buffer", ct, move |_ct| {
        match execute_code_buffer_inner(&options) {
            Ok(value) => Ok(value),
            Err(error) => {
                // (same error-to-JSON path as before)
                Ok(json_response(output, true))
            }
        }
    })
}
#+end_src

   Same pattern for ~execute_org~. Inner functions are unchanged —
   they already take ~&Value~ and return ~Result<Value>~. Just move
   the body into a ~task::blocking~ closure.

   ~abort_signal~ is additive; existing callers can pass ~None~.

* Error semantics (must preserve)

Both sync bindings today *never throw* on Rust errors — they synthesize
a ~json_response(error_payload, true)~ Value. The JS sees a regular
object, often with ~success: false~ or an ~error~ field.

The async version *must* preserve this: never reject the Promise on
Rust errors; always resolve with the response shape. Panics inside
the work closure should still be caught (matching
~execute_org_catching~).

A real Promise rejection only happens for:
- ~AbortError~ when the signal aborts (new behaviour, opt-in)
- Genuine NAPI marshalling failures (already a Promise rejection)

* Thread-safety pre-flight

Spot-check before flipping the switch:
- ~buffer_registry()~ → already used from libuv pool by
  executeCodePath. Thread-safe (RwLock + Mutex).
- ~org_buffer_registry()~ → ditto.
- File I/O: tokio::fs in inner functions? Or std::fs? std::fs is fine
  on the blocking pool; libuv thread is dedicated to this work.

No expected thread-safety issues, but a quick grep for
~thread_local!~ or ~RefCell~ in the inner code paths is the audit.
