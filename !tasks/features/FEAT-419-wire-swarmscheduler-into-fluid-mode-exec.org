* Context

PLAN-173 built =SwarmScheduler=, swarm tools (handoff/spawn-successor), and the =swarmContext= plumbing in =executor.ts=, but no code path actually populates =swarmContext= or uses the scheduler for execution. Fluid mode currently uses a single-agent prompt chain (=session.prompt()=) that manages todo progression manually. The scheduler, blackboard, and swarm tools are inert.

Current execution flow in =executeFluidPlan()= (~line 288 in fluid-mode.ts):
1. Materialize plan into todo groups via =materializeFluidPlanToTodos()=
2. Call =promoteFirstRunnableTask(phases)= to mark initial ready tasks
3. Set todo groups on session
4. Call =session.prompt()= with a single execution prompt
5. The single agent handles all tasks sequentially via todo_write tool calls

Target execution flow:
1. Materialize plan into todo groups
2. Create =SwarmBlackboard= for the swarm run
3. Create =SwarmScheduler= from the materialized DAG
4. Scheduler pump loop dispatches each ready task to =runSubprocess()= with populated =swarmContext=
5. Each subprocess agent receives swarm tools (handoff, spawn-successor)
6. On task completion, scheduler marks done and dispatches next ready batch
7. QML bridge events are preserved throughout

** Design Decisions

1. Keep the single-agent path (=session.prompt()=) for plans with =isSimple= flag (≤2 tasks). This is the existing behavior and works well for simple plans.
2. For multi-task plans, replace =session.prompt()= with a =SwarmScheduler.pump()= loop. Each ready task is dispatched via =runSubprocess()= from =task/executor.ts=.
3. Create =SwarmBlackboard= at the start of =executeFluidPlan()=. Pass it through =swarmContext=. The blackboard persists swarm state as org items under a =swarm= category (this is the existing blackboard API).
4. The =swarmContext= passed to each =runSubprocess()= call includes: =active: true=, =agent= derived from the plan node, =sessionId= from the current session, =currentTaskUri= for the specific task being dispatched, =blackboard= (shared), =scheduler= (shared).
5. The =syncRuntimeStates()= callback (currently used for QML state sync) must be called after each scheduler cycle to update the QML bridge with current DAG state.
6. Error handling: if a task subprocess fails, =scheduler.markFailed(taskUri)= triggers cascade failure. The QML bridge must receive failure events for display.
7. The execution prompt for each subprocess is built from the plan node's task description plus the swarm system prompt (which the executor already injects when =swarmContext.active= is true).
8. Abort signal handling: the scheduler's pump accepts an =AbortSignal=. Wire the existing =signal= from =executeFluidPlan= through to the scheduler.

** Edge Cases
- Plans with deferred agents should not be added to the scheduler DAG.
- If the QML bridge disconnects mid-execution, the scheduler should continue (event routing is best-effort).
- If all tasks fail, the scheduler pump terminates cleanly and the execution snapshot reflects failure state.
- Retry state: the existing retry mechanism (=processFluidEvents= retry loop) must reconstruct the scheduler from persisted todo state, not the original plan.
- The =buildExecutionPrompt()= function currently builds a single prompt for all tasks. For scheduler-driven execution, each subprocess needs a per-task prompt derived from the plan node.

** Existing Patterns to Follow
- =SwarmScheduler.pump(runNode, signal?)= is the async dispatch loop
- =runSubprocess(options: ExecutorOptions)= in =task/executor.ts= is the subprocess launcher
- =FluidExecutionResult= is the return type for =executeFluidPlan=
- =materializeFluidPlanToTodos(plan)= produces ={ groups: TodoGroup[], taskIdByAgentId: Map }=
- =SwarmBlackboard= constructor takes ={ projectRoot, orgConfig, eventBus }=
