* Narrative

Spell's current task dispatch system uses =batch-scheduler.ts=: a static DAG built once from a flat list of tasks with =blockers=, then executed via a pump loop. This works for single-batch dispatch but cannot support interconnected agent swarms because:

1. *The graph is immutable.* Once =buildBatchGraph()= runs, no new nodes or edges can be added. A running agent cannot spawn a successor task or dynamically extend the plan.
2. *Entry points are implicit.* All tasks with zero blockers start together, but there is no concept of "multiple independent sub-DAGs" at the scheduler level -- the scheduler treats the batch as one flat graph.
3. *Readiness is binary.* A task is ready when all its blockers complete. There is no support for artifact-based triggers (e.g., "start when file X exists") or file-dependency overlap detection (e.g., "don't run concurrently with task Y because both modify =parser.ts=").

This item creates the foundational data structure (=MutableDag=) and scheduler (=SwarmScheduler=) that replace the static batch model. Every subsequent swarm feature -- blackboard, handoff, spawn_successor, live result passing -- depends on this scheduler being able to accept mutations at runtime.

The existing =scheduleBatch()= API is preserved as a thin wrapper so all current callers (=TaskTool.#executeSync=, async dispatch) continue working without changes.

* Design Decisions

1. TypeScript owns runtime scheduling (pump loop, concurrency, result collection). Elisp owns persistent graph validation (via =org-fluid-plan= for plans that use org items).
2. =MutableDag<T>= is a generic class parameterized by node payload type =T=. It stores adjacency (=dependentsOf=, =blockersOf=) and supports =addNode()=, =removeNode()=, =addEdge()=, =removeEdge()=. Every mutation runs cycle detection before committing.
3. =SwarmScheduler= wraps =MutableDag= with a pump loop. It exposes =mutate(mutation)= for external callers to inject changes mid-execution. Mutations are queued and applied between pump cycles (not during a running task's callback).
4. Concurrency is isolation-gated: the scheduler accepts an =isolationMode= flag. When active, independent DAG components (detected via union-find from =MutableDag.splitComponents()=) may run concurrently up to =maxConcurrency=. When inactive, only one non-delegated task runs at a time (existing behavior).
5. File-dependency overlap: nodes carry an optional =filesDeps: string[]= field. Two nodes with intersecting =filesDeps= are never concurrently ready, even if they are in different components.
6. Cascade failure propagates to all transitive dependents (existing behavior). Dynamic nodes added after a failure of their dependency are immediately failed.
7. Stagger delay for prompt cache warming is preserved. Applied per launch within a superstep.

class MutableDag<T> {
  addNode(id: string, payload: T, deps?: string[]): void;
  removeNode(id: string, mode: "cascade" | "orphan"): string[]; // returns affected IDs
  addEdge(from: string, to: string): void;
  removeEdge(from: string, to: string): void;
  has(id: string): boolean;
  getPayload(id: string): T | undefined;
  getReady(completed: ReadonlySet<string>, running: ReadonlySet<string>): string[];
  getDependents(id: string): string[];
  getBlockers(id: string): string[];
  topologicalOrder(): string[];
  splitComponents(): MutableDag<T>[];
  get size(): number;
  get roots(): string[]; // nodes with zero in-degree
  // For file-dep overlap:
  setFilesDeps(id: string, files: string[]): void;
  getFilesDeps(id: string): string[];
  hasFileOverlap(idA: string, idB: string): boolean;
}

** =packages/coding-agent/src/task/swarm-scheduler.ts=
The =SwarmScheduler= class. Key API:
#+begin_src typescript
interface SwarmSchedulerOptions {
  maxConcurrency: number;
  signal?: AbortSignal;
  staggerMs?: number;
  isolationMode: boolean;
}

interface SwarmNode<T> {
  id: string;
  payload: T;
  deps?: string[];
  filesDeps?: string[];
  run: (signal: AbortSignal) => Promise<T>;
}

class SwarmScheduler<T> {
  constructor(options: SwarmSchedulerOptions);
  addNode(node: SwarmNode<T>): void; // can be called before or during run
  removeNode(id: string): void;
  run(): Promise<Map<string, SwarmTaskResult<T>>>;
}
#+end_src

*** addNode

- =dag.addNode("c", {}, ["b"]); dag.addNode("d", {}, ["c"]); dag.addNode("e", {}, ["d", "a"])= => forms diamond, no error

*** addNode cycle detection
- Given a->b->c, =dag.addNode("d", {}, ["c"])= then =dag.addEdge("d", "a")= => throws =Error("Cycle detected")=
- Given a->b, =dag.addNode("c", {}, ["b", "a"])= => no cycle, =topologicalOrder() === ["a", "b", "c"]=

*** removeNode
- =dag.removeNode("a", "cascade")= where b depends on a => returns =["a", "b"]=, =dag.has("a") === false=, =dag.has("b") === false=
- =dag.removeNode("a", "orphan")= where b depends on a => returns =["a"]=, =dag.getBlockers("b") === []=
- =dag.removeNode("x", "cascade")= where x doesn't exist => throws =Error("Node x not found")=

*** getReady
- DAG: a(no deps), b(deps: [a]), c(no deps). completed={}, running={} => =getReady() === ["a", "c"]= (both roots)
- completed={"a"}, running={} => =getReady() === ["b", "c"]=
- completed={"a"}, running={"c"} => =getReady() === ["b"]= (c excluded because running)

*** splitComponents
- DAG: a->b, c->d (two disconnected pairs) => =splitComponents()= returns 2 DAGs, one with {a,b}, one with {c,d}
- DAG: a->b->c (single chain) => =splitComponents()= returns 1 DAG with {a,b,c}

*** filesDeps overlap
- =dag.setFilesDeps("a", ["src/parser.ts"]); dag.setFilesDeps("b", ["src/parser.ts"])= => =dag.hasFileOverlap("a", "b") === true=
- =dag.setFilesDeps("a", ["src/parser.ts"]); dag.setFilesDeps("b", ["src/lexer.ts"])= => =dag.hasFileOverlap("a", "b") === false=
- =dag.setFilesDeps("a", [])= => =dag.hasFileOverlap("a", "b") === false= (empty treated as no constraint)

*** topologicalOrder
- Diamond: a->{b,c}->d => order starts with "a", ends with "d", b and c in middle (either order)
- Already tested indirectly above, but verify determinism: same DAG always produces same order

- Tasks a (files: ["src/x.ts"]) and c (files: ["src/y.ts"]), isolation=true => run concurrently

*** Abort
- 3 tasks running, signal.abort() => pending tasks get status "aborted", running tasks receive abort signal

*** Cascade failure
- a fails, b depends on a => b gets status "failed" with error "Predecessor a failed"
- a fails, b depends on a, c depends on b => both b and c fail transitively
