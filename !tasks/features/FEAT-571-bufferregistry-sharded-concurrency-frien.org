* Scope

In: replace `BufferRegistry::buffers: RwLock<HashMap<PathBuf, Arc<Mutex<CodeBuffer>>>>` with `DashMap<PathBuf, Arc<Mutex<CodeBuffer>>>`. Shared-lock reads never block each other; map mutations are shard-local. Per-buffer mutation still serialises via `Arc<Mutex<CodeBuffer>>` (unchanged).

Out: introducing async locks (tokio); changing the public API; per-buffer lock granularity.

* Background

User goal: "super good with being concurrency-friendly within the session". Today a write-lock on the map blocks all opens while one new buffer is inserted; a thundering herd of parallel tool calls (task subagents doing `code read` on 50 files in parallel) serialises unnecessarily.

Sharding the map removes this false contention. Per-file edits remain serialised on the inner mutex (correct).

* Edge cases

- `DashMap::entry` + inner `Arc<Mutex<CodeBuffer>>`: never hold a DashMap shard guard across a `CodeBuffer::open` disk I/O — measure byte reads FIRST, then insert inside the entry closure.
- Deadlock avoidance: do NOT acquire a `CodeBuffer` mutex while holding a DashMap shard lock; release the shard lock before locking the inner mutex.
- Iterator invalidation: `list()` clones snapshots (already the case today).
