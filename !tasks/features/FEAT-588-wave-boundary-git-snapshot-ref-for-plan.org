* Scope

In-scope:
- New module `packages/coding-agent/src/orchestrators/fluid/wave-snapshot.ts` (snapshot create + lookup).
- Hook in `packages/coding-agent/src/tools/todo-write.ts::promoteReadyTasks` (or the applyOps promotion path) to invoke the snapshot at group-boundary transitions for plan-materialized todo groups.
- New git-refs namespace: `refs/spell/plan/<PLAN-ID>/wave-<N>`.
- Surface a `/snapshots` command or agent-facing description in `packages/coding-agent/src/commands/` enumerating active snapshots for the current plan.

Out-of-scope:
- Non-plan-materialized todo groups (free-form user todos not tied to a PLAN item).
- Cross-repo or non-git workspaces.
- Automatic rollback. Snapshot is a restore point; the agent or user decides to use it.
- Replacing the existing `loop/git/checkpoint.ts` mechanism (that is loop-specific; stays orthogonal).

Rationale: in the incident session, Wave 1 (FEAT-577 engine work) completed with passing tests but was not committed. Wave 2 dispatched destructive `quick_task` subagents. When recovery needed `git restore`, HEAD predated Wave 1, so recovery reverted Wave 1 work. A wave-boundary ref would have preserved the working tree as `refs/spell/plan/PLAN-259/wave-1` before Wave 2 started, making `git restore --source=refs/spell/plan/PLAN-259/wave-1` a lossless recovery.

* Existing Patterns

- `packages/coding-agent/src/loop/git/checkpoint.ts::createLoopCheckpoint` uses `$` `git add ${files}` `$` + `$` `git commit` `$` on a side branch. Model the wave snapshot after this but emit to a ref rather than a branch.
- `packages/coding-agent/src/commit/git/index.ts::ControlledGit` wraps git with error-surfaced Bun `$` calls; reuse for ref writes.
- `packages/coding-agent/src/tools/todo-write.ts::promoteReadyTasks` is the single place where pending tasks become runnable. When the freshly-promoted tasks belong to a new group (i.e. all tasks in the prior group are `completed` | `abandoned`), that is the wave boundary.
- `materializePlanWaves` in `packages/coding-agent/src/orchestrators/fluid/plan-to-todos.ts` tags groups with `name` (e.g. "Wave 1 — Engine critical section"). Extend `TodoGroup` to carry the plan item id + wave index so the snapshot can be named deterministically.
- `interactive-mode.ts` calls `session.setTodoGroups(groups, { reset: true })` after approving a plan — the handoff point where snapshot state can be initialized.

Scenarios:

1. *initial-wave snapshot not created prematurely* — plan materialized with 2 waves; no tasks completed yet → no ref written.

2. *wave-1 complete creates wave-1 ref before wave-2 promotion* — all group-1 tasks move to completed; first group-2 task promoted to in_progress → ref `refs/spell/plan/<id>/wave-1` points at current working-tree commit.

3. *dirty tree snapshot includes working changes* — wave-1 completes with uncommitted changes → snapshot commit includes those changes (tree-id distinct from HEAD).

4. *clean tree snapshot points at HEAD* — wave-1 completes with zero uncommitted changes → ref points at HEAD; no new commit object created.

5. *wave-2 completes creates wave-2 ref* — subsequent wave transition writes its own ref without disturbing wave-1.

6. *non-plan groups skipped* — todo group without plan-id metadata → no snapshot.

7. *non-git workspace graceful skip* — working dir is not a git repo → snapshot path noops with a single logger warning, no throw.

8. *ref lookup utility* — `listPlanSnapshots(planId)` returns an array of `{ wave, ref, tree, timestamp }` sorted by wave ascending.

- Exports:
  - `createWaveSnapshot({ cwd, planItemId, waveIndex, logger }): Promise<WaveSnapshotResult>`.
  - `listPlanSnapshots(cwd, planItemId): Promise<WaveSnapshotEntry[]>`.
- `createWaveSnapshot`:
  - Check `git rev-parse --is-inside-work-tree`. If not a repo → warn once and return `{ skipped: "non-git" }`.
  - If working tree clean vs HEAD → `git update-ref refs/spell/plan/<planItemId>/wave-<N> HEAD` → return `{ ref, tree, fromHead: true }`.
  - Else → create a tree snapshot via `git stash create` or `git write-tree` against a temp index built from `git add -A --intent-to-add` (no real commit on HEAD). Then `git commit-tree <tree> -p HEAD -m "spell wave boundary ..."` and `git update-ref refs/spell/plan/<planItemId>/wave-<N> <commit>`. Do NOT advance HEAD.
  - Atomicity: if any step fails, clean up the temp index/tree without leaving dangling refs.

* Edge Cases

- *Concurrent wave transitions* — two children complete simultaneously and both trigger promotion. Guard via `session.waveSnapshots` set; one call wins, others noop.
- *Plan rewrite mid-execution* — if the user calls `todo_write` `replace` to swap groups, snapshot tracker may see waves skipped. Defensive: if a wave-K promotion fires but wave-(K-1) was never completed, skip the snapshot rather than error.
- *HEAD is a tag / detached* — refs under `refs/spell/` are independent of HEAD; no conflict.
- *Ref collisions across plans* — namespace includes `planItemId`; two active plans get distinct refs.
- *Submodules* — ignore submodule content; snapshot only the superproject tree (existing git default).
- *Shallow clones* — commit-tree requires full parent chain; fall back to orphan commit if needed. Refs still usable via `git restore --source`.
- *Merge / rebase rewrites HEAD* — snapshot refs remain valid (pointing at the recorded commit object) until GC. Add a garbage-collection config suggestion in the `/snapshots` output ("refs persist; run `git update-ref -d` to remove").
- *Non-gitignored junk in working dir* — snapshot `--intent-to-add` path captures untracked files too; users who want to exclude should rely on `.gitignore`.
