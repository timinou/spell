* Problem

After a system crash, ~spell recover~ reports skipping large numbers of stale status files (e.g., "Skipped 75 stale status file(s) missing recovery metadata"). These files accumulate indefinitely because:

1. Status files are created early (when niri window ID is discovered) before session info is populated
2. If the process crashes between window ID discovery and session creation, the status file has no ~sessionId~ or ~cwd~
3. ~readCrashed()~ returns these files, ~isRecoverableSession()~ filters them out, but nobody cleans them up
4. The only cleanup for dead-PID files happens in ~readAll()~ (used by niri overview), not ~readCrashed()~ (used by recover)

* Design Decisions

1. Add ~--clean~ flag to ~spell recover~ for standalone stale file cleanup (no recovery, just delete stale files)
2. Auto-clean stale files after recovery completes (always, no flag needed)
3. Add ~cleanStale()~ method to ~StatusFileReader~ in ~packages/desktop-common/src/status-file.ts~
4. Stale = file where PID is dead AND (~sessionId~ or ~cwd~ is missing) — these can never be recovered, safe to delete
5. Print count of cleaned stale files in recovery summary

* Implementation

** Add ~cleanStale()~ to ~StatusFileReader~

#+begin_src typescript
/** Remove stale status files where PID is dead and recovery metadata is incomplete. */
async cleanStale(): Promise<number> {
    const entries = await this.#readStatusFiles();
    let cleaned = 0;
    for (const entry of entries) {
        if (isProcessAlive(entry.data.pid)) continue;
        const hasMetadata =
            typeof entry.data.sessionId === "string" &&
            entry.data.sessionId.length > 0 &&
            typeof entry.data.cwd === "string" &&
            entry.data.cwd.length > 0;
        if (hasMetadata) continue;
        await fs.rm(entry.filePath, { force: true }).catch(() => {});
        cleaned += 1;
    }
    return cleaned;
}
#+end_src

When ~--clean~ is set alone (no other action):
1. Call ~StatusFileReader.cleanStale()~
2. Print "Cleaned N stale status file(s)."

** Auto-clean after recovery

At the end of ~RecoverCommand.run()~, after all recovery is complete:
1. Call ~reader.cleanStale()~ (where ~reader~ is the ~StatusFileReader~ instance)
2. Print "Cleaned N stale status file(s)." if N > 0

This replaces the current "Skipped N stale status file(s) missing recovery metadata." message with an actionable cleanup.

** Handle ~--clean~ early exit

If ~--clean~ is the only flag (no sessions to recover), the command should:
1. Read all crashed files
2. Clean stale ones
3. Report count
4. Exit without proceeding to recovery

If ~--clean~ is combined with recovery, do both: recover sessions AND clean stale files.

* Edge Cases

- Status files with live PIDs must NEVER be deleted by ~cleanStale()~ — only dead-PID + missing-metadata files
- Recoverable files (dead PID + valid metadata) must not be deleted by ~cleanStale()~ — only files without metadata
- File permission errors during cleanup: warn and continue, don't fail the whole command
- Race condition: PID reuse is theoretically possible but negligible in practice (PIDs are large, window IDs are niri-assigned)
