* Problem
=crates/pi-natives/src/code_graph.rs= currently runs fastembed/ONNX Runtime directly in the Bun process via a static =OnceLock<EmbeddingEngine>=. This causes segfaults when the ONNX Runtime's memory operations conflict with Bun's internals.

* Solution
Replace direct =EmbeddingEngine= usage with subprocess communication to the =pi-embedding-worker= binary. All embedding operations delegate to the subprocess via stdin/stdout JSONL.

* Design Decisions
- Remove =EMBEDDING_ENGINE: OnceLock<EmbeddingEngine>= and =get_or_init_engine()= entirely
- Remove =use pi_code_vectors::EmbeddingEngine;= import from code_graph.rs
- Remove =pi-code-vectors= from pi-natives direct dependencies (it's only needed by the worker binary now)
- Keep =pi-code-vectors= as a dependency for type re-exports (=VectorEntry=, =VectorIndex=, =PersistedVectorIndex=, serialization fns) — but NOT =EmbeddingEngine=
- New module: =crates/pi-natives/src/embedding_worker.rs= manages subprocess lifecycle
- Worker subprocess is spawned lazily on first semantic operation
- Worker stays alive for session duration (reused across multiple calls)
- If worker crashes or is not found, semantic features degrade gracefully

* Worker Manager Design
#+begin_src rust
use std::io::{BufRead, BufReader, Write};
use std::process::{Child, Command, Stdio};
use std::sync::Mutex;

/// Manages the embedding worker subprocess lifecycle.
struct EmbeddingWorker {
    child: Child,
    stdin: std::io::BufWriter<std::process::ChildStdin>,
    stdout: BufReader<std::process::ChildStdout>,
}

/// Global worker instance, lazily initialized.
static WORKER: Mutex<Option<EmbeddingWorker>> = Mutex::new(None);

fn with_worker<T>(f: impl FnOnce(&mut EmbeddingWorker) -> napi::Result<T>) -> napi::Result<T> {
    let mut guard = WORKER.lock().map_err(|_| Error::from_reason("worker mutex poisoned"))?;
    let worker = guard.get_or_insert_with(|| spawn_worker());
    f(worker)
}
#+end_src

* Binary Discovery
The worker binary is located using the same candidate path logic as the .node file:
1. =packages/natives/native/pi-embedding-worker= (dev builds)
2. =~/.local/share/spell/natives/<version>/pi-embedding-worker= (compiled binary)
3. =<exec-dir>/pi-embedding-worker= (alongside the binary)

Discovery function checks candidates in order, returns first that exists and is executable. If none found, semantic features are disabled with a clear error message.

** Important: The binary path discovery MUST be implemented in Rust (in =embedding_worker.rs=), NOT in JavaScript. The code_graph.rs runs on a NAPI worker thread and cannot call back into JS. Use these approaches:
- Check =std::env::current_exe()= parent directory
- Check hardcoded platform-specific paths
- Check =PI_EMBEDDING_WORKER= env var override
- Look next to the loaded .node file by reading =/proc/self/maps= or similar

* Graceful Degradation
When the worker is unavailable (binary not found, crashed, failed to initialize):
- =build_semantic_index()= returns an error with message "Embedding worker unavailable: <reason>"
- =code index { semantic: true }= reports the error but completes graph indexing normally
- Hybrid search falls back to BM25-only (existing VectorCacheState pattern handles this)
- The error message includes guidance: "Ensure pi-embedding-worker binary is installed alongside the native addon"
