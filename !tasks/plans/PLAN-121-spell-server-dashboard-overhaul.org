* Context

The spell server at localhost:8787 serves a Preact SPA frontend for the growth project. The frontend renders only a bare goal-status table with raw JSON config dumps.

** Architectural principle: KDL is infrastructure, SQLite is domain state

KDL should define the *shape* of the system — goals, schedules, setups, review policies, state schemas, panels, export targets. Domain data — personas, people, sources, articles — belongs in *state* backed by SQLite. The dashboard reads domain data from the state stores at runtime, not from KDL at config time.

Growth currently violates this: =.spell/data/personas.kdl=, =people.kdl=, =sources.kdl= formalize domain data as KDL config. These files are already *out of sync* with =data/growth.sqlite= (different persona names, different people counts). The KDL data files must be removed; the SQLite DB is canonical.

Spell-server also violates this: =config/data-parser.ts= and =config/data-types.ts= encode domain-specific types (Persona, Person, Source) into the platform layer. The platform shouldn't know about personas. These files must be removed and replaced with a generic state store query API.

** What exists now

*** Infrastructure config (KDL, correctly placed)
The manifest parser handles 8 domain type arrays: panels (2), layouts (1), syncCollections (3), stateSchemas (3), reviewPolicies (1), checkpoints (2), exportTargets (3), notificationRoutes (5). All fully populated in growth's KDL.

*** Domain data (SQLite, correctly placed but dashboard can't access it)
=data/growth.sqlite= has 10 tables: people (1 row), person_sources (4), personas (3), articles (1), article_scores (2), approvals (1), feed_runs (0), exports (2), downstream_jobs (0), downstream_job_attempts (0). Well-designed schema with foreign keys and indexes.

*** Domain data (KDL, wrongly placed — to be removed)
=.spell/data/personas.kdl= (3 personas, different from SQLite), =people.kdl= (4 people, only 1 in SQLite), =sources.kdl= (6 sources, no table in SQLite). These are stale duplicates.

** What's broken

1. =toManifestJson()= only serializes name, version, setups, goals. 8 domain type arrays silently dropped from API.
2. State stores declared in KDL are metadata-only — no runtime SQLite connections, no query API.
3. =data-parser.ts= / =data-types.ts= formalize domain types in the platform (wrong layer).
4. Growth's =.spell/data/*.kdl= duplicates and conflicts with SQLite data.
5. No =sources= table in growth.sqlite for non-person content sources.
6. Frontend has no navigation, no approval queue, no job tracker, no config inspector.

** Key decisions
- *Delete growth's KDL data files.* SQLite is canonical for domain data.
- *Remove data-parser/data-types from spell-server.* Platform doesn't own domain types.
- *Add generic state store query API.* The manifest declares state stores + schemas. The server opens read-only SQLite connections and exposes =/api/state/:storeName/tables/:tableName=.
- *Dashboard reads domain data from state API.* Personas, people, sources, articles — all rendered by querying the state store, guided by stateSchemas from the manifest.
- *Infrastructure config from manifest.* Review policies, checkpoints, export targets, panels, layouts — rendered from =/api/manifest=.
- *Tab navigation.* Goals / Approvals / Jobs / Config.
