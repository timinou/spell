* Context

** Problem

The spell-server's Telegram bot has zero visibility into local TUI sessions running on the same machine. It only manages sessions it spawned itself (via Telegram chat -> RPC). When a local interactive session hits a blocking point (plan awaiting approval, ask tool question, pending action), the user has no way to know unless they're looking at the terminal.

** Approach

Add a Unix domain socket IPC layer between spell-server and coding-agent sessions:

1. *Socket server* in spell-server listening on =~/.spell/server.sock= — accepts connections from local coding-agent sessions, maintains a live session registry.
2. *Bridge client* in coding-agent — connects on startup (best-effort), registers session metadata, emits blocking events (plan approval, ask, pending actions), receives remote responses.
3. *Telegram integration* — =/sessions= command to list all active sessions, notification messages with inline keyboards for blocking events (approve/refine/answer/dismiss), response routing back to originating session via socket.

** Key Design Decisions

- *Unix domain socket* (not HTTP or file-based): bidirectional, real-time, more secure (server controls the communication). The user explicitly chose this over HTTP POST or file beacons.
- *JSON-lines protocol*: same pattern as the existing RPC protocol between spell-server and =spell --mode rpc=. No new serialization format.
- *Race pattern for blocking events*: when a blocking event is emitted, the interactive mode races local TUI input against remote Telegram response. First to resolve wins. This keeps the bridge fully optional — sessions work identically without a server running.
- *Full remote approval*: users can approve, refine, or reject plans directly from Telegram inline keyboards. Not just notifications.
- *All blocking events configurable*: the =session-notifications= KDL block specifies which event kinds trigger Telegram notifications. Defaults to all.
- *Bridge client is best-effort*: if socket doesn't exist (server not running), bridge silently disables. No impact on session operation.
