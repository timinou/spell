* Context
The Telegram bridge in =spell-server= currently handles text, photos, and text documents. Voice messages, audio files, and video notes are silently ignored. This plan adds bidirectional voice support:

- *Inbound*: Voice messages, video notes, and audio documents are downloaded, transcribed via configurable STT (Deepgram or OpenAI Whisper API), and passed as text to the agent.
- *Outbound*: Agent responses can optionally be synthesized to voice via configurable TTS (ElevenLabs or Deepgram Aura) and sent as Telegram voice messages alongside text.
- *Configuration*: A new =voice {}= KDL block in =channels.kdl= with global defaults and per-user overrides. API keys support =env()= resolution.
- *Session control*: A =/voice= command lets users toggle reply mode per-session.

** Key Design Decisions
1. *Provider abstraction*: Both STT and TTS use a provider interface + factory pattern. Adding new providers later is a single-file addition.
2. *No ffmpeg for voice/audio*: STT providers natively accept OGG Opus, MP3, WAV. ffmpeg is only needed for video note audio extraction (MP4 → OGG).
3. *Dual delivery*: Voice replies always include a text message too (searchable, accessible).
4. *Transparent to agent*: Transcription is passed as plain text. The =[Voice]= prefix appears only in the Telegram draft preview, not in the agent prompt.
5. *Graceful degradation*: Missing STT config → friendly error reply. Missing TTS config → text-only replies. Missing ffmpeg → video notes can't be transcribed (but voice messages still work).
6. *Audio document actions deferred*: Saving audio documents to the repo via KDL-defined actions is a follow-up ([[id:FUP-034-audio-document-repo-save-action-via-kdl]]). This plan handles transcription of audio documents but not repo-save actions.
