* Initial Message

thought experiment: now that you can do structural edits to any typst file, and knowing there's a rust crate for SVG output and another for live click in preview, could you imagine a minimal Rust window with WYSIWYG capabilities for Typst files? Integrated in the QML bridge, ideally?

* Context
Spell already has a QML bridge, canvas-style QML component patterns, native Rust extension points, and an in-repo Typst integration draft that assumed WebEngine/WASM preview. This plan intentionally supersedes that direction for the primary editing experience.

The chosen approach is an editing-first, Word/Notion-style Typst editor where:
- QML remains the desktop shell and owns menus, drawers, sidebars, dialogs, and overall window lifecycle.
- A custom native Rust-rendered document surface is embedded into QML for the page/document canvas.
- Typst source remains canonical. The visual surface edits a supported Typst/AST subset directly; there is no persisted visual-schema document format.
- A minimal hidden source/manual mode exists only for recovery and unsupported constructs.
- If interactive native rendering/editing is unavailable, the editor degrades to truthful SVG preview plus reduced editing/recovery paths.
- Linux-first development is acceptable, but the renderer/item seam must not dead-end cross-platform support.

Key repo evidence informing this plan:
- `packages/qml/src/qml-bridge.ts`, `packages/qml/bridge/windowmanager.h`, and `packages/coding-agent/src/tools/canvas.ts` establish QML as the existing window shell and control plane.
- `domain/growth/src/qml/panels/EditorPanel.qml` is the nearest existing editor shell scaffold.
- `domain/growth/specs/deep-dive/typst-integration.org` is prior art to reuse or explicitly supersede where it assumes WebEngine/WASM as the primary path.
- `crates/pi-code-engine/src/language/mod.rs` already includes Typst language support.

The recommended implementation sequence is foundation first: native surface and contracts, then source mapping/edit engine, then the visual QML shell, then template/asset/agent workflows, then fallback/export/verification hardening.
