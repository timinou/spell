* Context

The user's recent plan-mode transcript revealed three concrete defects in the org orchestration layer that must be fixed together because they share a contract:

1. The native engine's wave computation reads the :BLOCKERS: property (comma-split), but the repo writes :DEPENDS: (space-separated). Result: every running of "org wave" puts every item in wave 0, completely ignoring declared dependencies. The user's transcript above shows this directly.
2. Sub-outline CUSTOM_ID auto-prefixing is incomplete. The rewriter rejects the empty-left "colon colon suffix" form, and the cmdUpdate paths for section= and append= bypass the rewriter entirely. The user had to use bash + sed to repair files left in a broken state ("CUSTOM_ID: ::slug"). That manual cleanup is the antipattern they called out.
3. Sub-outline headings are not first-class: they nest inside OrgItem.children in the engine and never reach the wave graph; they also lack the ITEM TODO keyword so they cannot participate in state tracking. The user's stated requirement: waves must be about sub-outlines (FEAT-XXX::task-slug), and sub-outlines must carry the ITEM prefix, "fully representative of the work".

The settled design decisions (recorded via the planning ask):

1. Engine-side: extract_items_from_buffer flattens sub-outlines into the returned Vec — one source of truth, every consumer benefits.
2. Engine-side: OrgItem.blockers() reads :DEPENDS: first (space or comma), falls back to :BLOCKERS: — fixes top-level waves AND new sub-outline waves in one stroke.
3. Auto-inject ITEM keyword on sub-outline headings at create/update time, parallel to the existing CUSTOM_ID auto-prefix.
4. org wave with manifest=true AND planItemId=<PLAN-ID> walks linked children, emits the formatted Execution Manifest, AND writes it directly into the PLAN body via editSection. The text is also returned to the LLM caller so it can confirm the write.
5. PLAN body MUST carry both top-level [[id:FEAT-X]] links (for discovery and lifecycle tracking) AND sub-outline [[id:FEAT-X::slug]] entries inside the manifest.

This PLAN orchestrates six child items in five waves to deliver these decisions end-to-end.

Chicken-and-egg note: decision 5 is not enforceable by the CURRENT validator (validatePlanItem cannot resolve sub-outline [[id:]] links). FEAT-606 is the child item that teaches the validator to accept both link shapes. The initial PLAN body uses top-level links only; as part of FEAT-605's acceptance, "org wave --manifest=true --planItemId=<this-PLAN>" regenerates the Execution Manifest at sub-outline granularity and writes it back in place. This is the first PLAN that will exercise the new manifest flow end-to-end.
