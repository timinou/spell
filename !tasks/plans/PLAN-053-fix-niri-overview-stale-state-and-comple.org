* Context

The niri overview (compositor-level window overview) renders a snapshot of the
current todo phases and tasks. Two bugs make it unreliable:

1. *Stale snapshot*: The niri controller reads =ctx.todoPhases= from the interactive
   mode's cached field. This cache is updated by an async event handler that hasn't
   finished when the niri listener fires (session =#emit()= does not await async
   listeners). The authoritative data in =session.getTodoPhases()= is already correct
   at that point.

2. *Missing-blocker = blocking*: The niri controller's inline blocker resolution
   treats missing refs (=!dep=) as blocking. The canonical =hasUnresolvedBlockers=
   treats them as resolved. After auto-clear removes a completed blocker task, all
   dependents flip to "blocked".

3. *Completed tasks vanish*: After auto-clear (default 60s delay), completed tasks
   are spliced from the phase data and empty phases are filtered out. No count or
   summary remains in the niri overview.

Approach: Fix the stale read and blocker semantics first (BUG-045), then add
per-phase completed-count tracking in the session and render it in the niri overview
(BUG-046).

Key decisions:
- The niri context =todoPhases= getter switches from interactive mode cache to
  =session.getTodoPhases()= (authoritative, sync)
- Cleared-completed counts are tracked per phase ID in the session as a
  =Map<string, { name: string; count: number }>=
- The =replace= op triggers a count reset via an optional =reset= parameter on
  =setTodoPhases=
- The niri overview renders completed counts in phase headers and preserves
  fully-cleared phases as dimmed summary lines
