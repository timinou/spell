* Context
** Problem
Plan execution currently maps 1 org item = 1 todo task. When a plan has FEAT-001 with 5 implementation steps and FEAT-002 with 5 steps, the executor works through FEAT-001 entirely before starting FEAT-002. But many steps across items are independent (e.g., type definitions for both features could be written in parallel). This limits parallelizability of the todo_write task list.

** Approach: Wave-Based Decomposition
Introduce "manifest waves" -- a plan-level concept where the Execution Manifest groups cross-item parallel tasks into named waves. Each wave contains implementation steps from multiple org items that can execute concurrently. Waves execute sequentially (wave N depends on wave N-1 completion for the same org item).

This is DISTINCT from "dependency waves" (the existing =org-next-wave.el= runtime concept that computes which org items are ready based on inter-item dependency state).

*** Org-native encoding
- Within child items: implementation steps use standard org heading tags for wave assignment (=:foundation:=, =:core:=, =:verify:=)
- In Execution Manifest: wave headings tagged =:wave:= group cross-item parallel tasks
- Entry format: =- [[id:ITEM-ID]] Step description= (standard org list items with id links)

*** Extraction pipeline
- Primary: new elisp MCP tool =org-extract-plan-waves= using org-element AST
- Fallback: TypeScript =extractPlanWaves()= via =parseOrgHeadings()= for when Emacs isn't running
- Data flows: exit-plan-mode -> ExitPlanModeDetails.waves -> #approvePlan -> template context -> executor

*** Backward compatibility
- Plans without =:wave:= headings work exactly as before (waves field is null/undefined)
- Executor prompts use Handlebars ={{#if waves}}= conditional -- non-wave plans get current behavior
- All existing tests continue to pass unchanged

** Key Design Decisions
1. Two distinct wave concepts: "dependency wave" (runtime, org-next-wave.el) vs "manifest wave" (static, plan decomposition)
2. Org-native encoding using standard heading tags -- no custom syntax
3. Primary extraction via elisp (org-element), TypeScript fallback for robustness
4. Multiple tasks can share orgItemId -- each triggers two-phase verification independently; org state transition done once at completion protocol end
5. Cross-wave deps auto-generated by executor: wave N task for orgItemId X blocks on wave N-1 task for same orgItemId
6. Also wires existing cmdWave()/cmdGraph() stubs to their elisp MCP tools (opportunity fix)
