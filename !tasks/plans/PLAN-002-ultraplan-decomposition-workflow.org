* Initial Message

Change the ultraplan's prompt and stuff to favour creating PROJ, FEAT, and BUG files and to use the DRAFT->PLAN to orchestrate between those files, and make sure you explicitly ask all the questions you can before you record each file, and that you run Metis before you start creating Org files, so that all that is written are detailed instructions, and all options have been decided upon. Ask me as many questions as possible

* Problem

The current ultraplan workflow creates a single monolithic DRAFT item containing everything: problem statement, approach, sub-tasks, verification. On approval, the body is copied verbatim into a PLAN item. This has three problems:

1. *No structured decomposition.* The PROJ, FEAT, and BUG categories exist in org config but sit empty. All work lives in a flat PLAN body. There's no way to track individual work items across plans or query them independently.

2. *DRAFT duplication.* Every approved plan exists twice: once as a DONE DRAFT, once as a DOING PLAN with identical content. The DRAFT category adds overhead with no value.

3. *Insufficient questioning.* The agent often makes assumptions about scope, error handling, and categorization rather than asking the user. Quality gates (Metis/Momus) run too late or too narrowly.

* Design Decisions (all confirmed with user)

** Removal of DRAFT category
- PLAN items are created directly in the =plans= category. No intermediate DRAFT step.
- =finalizePlanDraft()= is replaced with =approvePlan()= that transitions PLAN from INIT→DOING.
- Settings =org.planDraftCategory= and =org.planDraftState= are kept in schema (backward compat) but ignored by new code.
- Existing DRAFT files on disk are left as-is (become orphaned).

** New INIT state
- INIT = "Initiative" — used for PLAN (orchestrator) items.
- ITEM = used for child tasks within each initiative.
- TODO keywords become: =[INIT, ITEM, DOING, REVIEW, DONE, BLOCKED]=.
- State transitions for INIT mirror ITEM: =INIT → [DOING, BLOCKED]=, plus =INIT → REVIEW → DONE=.
- STATE_TRANSITIONS in defaults.ts is dead code (never enforced at runtime), but we update it for documentation.

** Child items in PROJ/FEAT/BUG categories
- Agent creates child items in their respective categories (PROJ for multi-feature/infra work, FEAT for single features, BUG for fixes).
- Agent proposes categories and asks user to confirm the full breakdown before creating any items.
- Children are created with state: ITEM.
- PLAN body references children via =[[id:CHILD-CUSTOM-ID]]= org-mode links.

** Dynamic categories from config
- Available categories (excluding plans, drafts, sessions) are read from org config at template render time.
- Passed to plan-mode-active.md as structured data via Handlebars =#each=.
- Agent sees the list and picks appropriate categories for each child item.

** Org-mode [[id:...]] links
- PLAN body uses =[[id:FEAT-001-add-auth]]= style links to reference children by CUSTOM_ID.
- A new =extractIdLinks()= utility in =packages/org/src/= parses these links.
- =exit_plan_mode= uses this parser to validate child references exist.

** PLAN body format
- Narrative context section (problem, approach, decisions)
- Structured execution manifest: ordered list of child references with dependencies
- Example:
  #+begin_example
  * Context
  Background and key decisions...

  * Execution Manifest
  1. [[id:FEAT-001-add-auth]] (depends: none, effort: 2h)
  2. [[id:FEAT-002-add-middleware]] (depends: FEAT-001, effort: 1h)
  3. [[id:BUG-001-fix-token-refresh]] (depends: FEAT-001, effort: 30m)
  #+end_example

** Creation order
- Children first → collect IDs → create PLAN with [[id:...]] references in body.
- The prompt template must enforce this order explicitly.

** Questioning workflow
- Agent explores codebase, asks questions progressively (scope boundaries, acceptance criteria clarity, error handling, testing approach as SHOULD checklist).
- Metis runs on requirements + codebase context.
- Agent addresses Metis gaps with more questions if needed.
- Agent proposes breakdown (titles, categories, scope) to user.
- Daedalus validates the proposed decomposition (before items are created).
- User confirms the breakdown.
- Agent creates child items, then PLAN.

** Quality gates (ultraplan only)
- Gate 1: Metis — requirements gap analysis (unchanged).
- Gate 2: Daedalus (NEW) — decomposition validation. Runs BEFORE items are created. Validates: category fitness, scope boundaries, dependency ordering, effort estimates.
- Gate 3: Momus — plan quality review (existing, enhanced). Now validates PLAN + all child items.

** /plan vs /ultraplan
- Both use the new flow (direct PLAN creation, no DRAFT).
- /plan: explore → ask → propose → create items → PLAN → exit.
- /ultraplan: explore → ask → Metis → more questions → propose → Daedalus → user confirm → create items → PLAN → exit → (Momus via approval UI).

** Approval flow
- =exit_plan_mode= accepts PLAN CUSTOM_ID (required when org enabled).
- Validates PLAN item exists and has [[id:...]] child references in body.
- On approval: transitions PLAN INIT→DOING. Children stay ITEM.
- Execution session behavior with children is OUT OF SCOPE (follow-up).

** Backward compatibility
- =org.planDraftCategory= and =org.planDraftState= settings remain in schema, ignored by new code.
- =drafts= category stays in DEFAULT_ORG_CONFIG temporarily (can be removed in a future cleanup).
- Existing DRAFT files on disk are orphaned but accessible via direct file reads.
