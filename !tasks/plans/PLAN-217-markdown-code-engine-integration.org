* Initial Message

looking at the typst and org integrations to pi-code-engine, what would you want to implement for your markdown usage to be a delight?

* Context

The pi-code-engine provides structural code intelligence (outline, read, edit, navigate) driven by tree-sitter grammars and language profiles. Currently supports TypeScript, Rust, Python, Typst, and Elixir. Markdown files (~.md~) fall through to plain text with no structural understanding.

This plan makes markdown a first-class language in the code engine by:
1. Extending the declaration/profile system to support document languages where names and bodies aren't simple AST fields
2. Adding a tree-sitter-markdown grammar and markdown language profile with section-as-declaration semantics
3. Building a procedure DSL transform layer so languages can register custom edit operations declaratively
4. Proving the extension point works across languages with Typst promote/demote procedures
5. Adding tool result injection so agents learn about language-specific operations on first use

** Key Decisions

1. ~DeclarationPattern~ extended with ~NameExtractor~ (Field, ChildField, ChildText, Literal) and ~BodyExtractor~ (None, Field, AfterChild) — enables document languages
2. ~ClassLikePattern~ extended with ~ClassBodyExtractor~ (Field, Direct) — sections have direct child members
3. Markdown sections are declarations (kind: "section"), nested sections are class-like members. Symbol resolution: ~"Installation.Prerequisites"~
4. Frontmatter is a declaration with ~NameExtractor::Literal { name: "frontmatter" }~
5. Procedure DSL gets a declarative ~Transform~ enum with ~Custom(fn)~ escape hatch (documented as DSL improvement flag — its existence signals the DSL should eventually express that pattern)
6. Resolution 2 for markdown: heading tree + content type annotations (paragraph/code block/list counts) + symbol paths for drill-in
7. Tool result injection: first code tool result on a new language appends a concise operations guide. Per-language, per-session
8. Block grammar only — inline grammar (bold/italic/links) not needed for section-level operations
9. No extract-code-block operation — res 2 metadata + normal read with offset/limit covers this
