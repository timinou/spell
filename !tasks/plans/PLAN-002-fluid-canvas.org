* Goal

Replace ~spell --qml~ with ~spell --canvas [name]~. Keep existing chat canvas as ~--canvas chat~. Build a new ~fluid~ canvas (default) that takes a single text prompt, decomposes it into a DAG of agent tasks via a planning agent, and executes them reactively via a queue-based scheduler. Each agent's output fills a queue; downstream agents that subscribe to it become ready and are dispatched. Agents stream live output to their own panel, and the planning agent declares which agents produce persistent canvas components.

* Queue-Based Execution Model

Each agent has exactly one output queue. Agents declare which queues they subscribe to (via ~dependsOn~). The scheduler dispatches an agent when *all* its subscribed queues have data. Concurrency is bounded by a configurable semaphore (default 5).

#+begin_example
analyze \u2500\u2500\u252c\u2500\u2500 extract-findings \u2500\u2500 fix-issues
           \u2502
           \u2514\u2500\u2500 extract-metrics  \u2500\u2500 dashboard (canvasOutput: table)
#+end_example

\"Waves\" are emergent: agents with no deps start immediately; their completion unlocks subscribers, which start immediately (up to concurrency limit). No explicit wave iteration.

For fan-out (one agent's output consumed differently by multiple agents), the planning agent creates lightweight \"splitter\" nodes \u2014 regular agents with trivial extraction tasks. This keeps the model simple: one output per node, always.

When an agent completes, its full ~SingleResult~ (output text, exit code, duration, tokens) is passed as structured context to all dependent agents.

Agents with ~canvasOutput~ declared in the plan produce persistent canvas components (markdown, table, diff, etc.) when they complete. This is how the interface adapts: the planning agent controls what the user sees.

* Key Technical Decisions

| Decision | Choice | Rationale |
|---|---|---|
| ~--qml~ | Removed entirely | No external consumers, one concept one representation |
| Execution model | Queue-based reactive scheduler | Waves are emergent, not pre-computed; naturally handles fan-out |
| Fan-out | Splitter nodes (composition) | One output per node; no multi-port complexity |
| DAG module | New in coding-agent, purpose-built | Swarm-ext not a dep; only ~dependsOn~ needed |
| Module location | ~src/orchestrators/fluid/~ subfolder | Groups dag, queue-scheduler, event-router, orchestrator, types |
| Planning agent tools | Configurable via ~settings.fluidFastPlan~ | Better plans with tools, fast option for quick tasks |
| Concurrency | Configurable via ~settings.fluidConcurrency~, default 5 | Semaphore in scheduler |
| Canvas output | Declared per-agent in FluidPlan (~canvasOutput~ field) | Planning agent controls UI layout |
| Panel creation | Two-phase (create \u2192 confirm \u2192 start) | Prevents event loss from late panel creation |
| Event drain | 100ms setInterval with reentrancy guard | Prevents UI freeze when parent agent idle |
| Iterative planning | Phase 2 (not this plan) | Single-intent first, add re-planning later |
| Mock strategy | Constructor injection (~runAgent~ option) | Avoids module-level mock leakage |
| Multi-publishing | Composition (splitter nodes) | Keeps core model simple, no multi-port agents |

* Critical Risk: EventBus Drain

Drain is coupled to parent agent turn lifecycle (sdk.ts:1775). In fluid mode the parent is idle while subagents work. Without active draining, P1 queue fills at 100 entries and blocks. FluidOrchestrator owns a 100ms drain timer with reentrancy guard (~#draining~ boolean) to prevent overlapping drain() calls. ~drain()~ awaits handlers sequentially; reentrancy guard prevents handler interleaving.
