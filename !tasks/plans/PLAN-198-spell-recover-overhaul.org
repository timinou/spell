* Context

~spell recover~ has three issues:

1. *Empty windows*: Ghostty ~+new-window~ IPC does not reliably forward the ~-e spell -r <sessionId>~ command to the new window. The window opens with a default shell prompt instead of the recovered spell session. This affects Ghostty 1.3.0 and is caused by multi-argument forwarding bugs in the ~+new-window~ IPC path.

2. *Stale file accumulation*: Status files without recovery metadata (~sessionId~, ~cwd~) accumulate indefinitely (75+ files observed). These are created when spell crashes before session creation completes. The recover command warns about them but never cleans them.

3. *No fallback*: When automatic recovery fails silently (window opens but command doesn't execute), the user has no actionable next step. Status files are deleted after "successful" IPC delivery, so retry is impossible.

** Approach

- Switch from ~-e <args...>~ to ~--command=<full cmd>~ format for Ghostty IPC (more robust single key-value serialization)
- Add ~--direct~ flag to bypass IPC entirely (standalone Ghostty processes)
- Always print manual fallback commands after recovery
- Add ~--clean~ flag for standalone stale file cleanup
- Auto-clean stale files after every recovery run

** Key Decisions

1. Use ~--command=spell -r <id>~ (single k=v) instead of ~-e spell -r <id>~ (multi-arg)
2. Add ~--title=<label>~ to windows for identification
3. ~--direct~ flag launches standalone ~ghostty~ processes (no IPC)
4. ~--clean~ flag removes dead-PID + missing-metadata status files
5. Auto-cleanup runs after recovery (no flag needed)
6. Manual commands always printed after recovery as fallback
