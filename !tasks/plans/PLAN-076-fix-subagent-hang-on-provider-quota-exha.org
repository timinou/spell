* Context

Three user sessions appeared hung for 30+ minutes because delegated task subagents hit a provider usage-limit error (=usage_limit_reached= from OpenAI Codex). The subagent's =AgentSession= correctly classified the error as retryable and entered auto-retry with 30-minute backoff (=QUOTA_EXHAUSTED_BACKOFF_MS=). The retry behavior itself is correct — the problem is that the user had zero visibility into what was happening.

** Root Cause (UX gap, not logic bug)

The main session TUI already renders retry state beautifully: =event-controller.ts= shows a spinner with "Retrying (1/3) in 30s... (esc to cancel)". But subagent sessions running inside the task tool don't forward their retry state to the parent:

1. =AgentSession= emits =auto_retry_start= / =auto_retry_end= as session events via =#emitSessionEvent()=
2. The task executor subscribes only to agent-loop events (=session.subscribe()=), not session events
3. Session-level retry events never reach the =AgentProgress= object
4. The parent TUI shows "Running background task..." with no error/retry context
5. =await= reports "Still Running" with no indication the subagent is blocked on retry

** Approach

Bridge the retry session events from subagent sessions into the task progress pipeline:

1. Add retry state fields to =AgentProgress= type
2. In the task executor, listen for session retry events and update progress
3. Forward subagent progress in async task mode (currently =onUpdate= is =undefined=)
4. Render retry state in TUI task progress and =await= output

** Key Decisions

- *Keep retry behavior as-is.* The 30-minute backoff for quota exhaustion is intentional. Provider accounts may switch; quotas may reset. Users can abort retrying subagents if they don't want to wait.
- *No changes to =createSubagentSettings()= or =#handleRetryableError()=.* The fix is purely UX surfacing.
- *Fix async progress forwarding as part of this.* The async task path passes =onUpdate = undefined= to =#executeSync=, which means NO subagent progress reaches the parent during execution. This is a pre-existing gap that makes retry surfacing impossible without also fixing the forwarding.
