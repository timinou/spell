* Problem (error class E4 — the only one that CORRUPTS state)

A PTC-Lisp program that does effectful work then errors leaves PARTIAL EFFECTS:
```clojure
(tool/create "a.txt" ...)   ; committed to disk
(tool/edit "b.rs" ...)      ; committed to buffer
(boom)                       ; error → program "discarded" but a.txt + b.rs ALREADY landed
```
The program reports failure, so the agent may retry → double-apply. This is
"alive-and-scary #1" in specs/beam-orchestrator/07-execute-substrate-status.md and
the deferred "D3-txn" in 06-execute-substrate.md. It is the worst class because it
silently corrupts the repo; W1 psettled + W1b preflight removed the two COMMON
producers (mid-batch fan-out failure; typo-after-effects) but the general case is open.

* Verified current behavior (why this is real, not theoretical)

- In `beam/ptc_runtime/lib/ptc_runtime/peer.ex` (handle_call {:tool_call,...}, ~L187)
  each tool call dispatches over the wire to Node and the effect COMMITS IMMEDIATELY.
  There is no enlistment, no envelope. A later error cannot unwind earlier commits.
- The affordance D3 builds on EXISTS at single-edit granularity:
  `BufferRegistry.edit_transaction(session_id, path, code_paths, fn)` in
  crates/pi-code-engine/src/buffer.rs, with `ClientMessage::Intent` conflict detection
  and journaling (see crates/pi-code-engine/tests/coord_transaction.rs:
  edit_transaction_surfaces_peer_conflict_on_overlapping_intent,
  edit_transaction_emits_journal_entry_on_success). pi-edit-broker
  (crates/pi-edit-broker/) is the coordination server.
- WHAT'S MISSING: a PROGRAM-SPANNING envelope — "enlist every edit/create this program
  makes; commit them atomically iff the program reaches its end; discard all on error."
  That is FEAT-638 MultiIntent/MultiCommit at program scope (referenced in 06 D3-defer).

* Design: BEGIN…COMMIT/ROLLBACK around a program

```
execute program start → open a transaction scope (session_id = the execute's owner)
  each (tool/edit ...)/(tool/create ...) → ENLIST into the scope's intent set
                                            (stage the buffer mutation, do NOT commit)
  program reaches end successfully        → MultiCommit: apply all staged intents
                                            atomically (the broker already detects
                                            overlapping-intent conflicts per-path)
  program errors / fail-signal            → discard scope: zero intents land
```

Decisions to make explicit in this plan (so impl needs no clarification):
- D3.1 Scope boundary = one execute program (NOT a session; bindings persist across
  executes but a transaction does not). A multi-execute "transaction" is out of scope.
- D3.2 Read tools (find/org-query/memory) are NOT enlisted — they read live state
  mid-program as today. Only write-effect tools (effects.ts `write` tag:
  edit/create/org-set/etc.) enlist. Reuse the effects.ts taxonomy — do not re-derive.
- D3.3 Conflict semantics: if at COMMIT time the broker reports a peer conflict on an
  enlisted path (another session committed the same span first), the WHOLE program's
  commit fails with a typed PeerConflict result — nothing lands, agent re-runs. This
  reuses the existing edit_transaction conflict path, lifted to the multi-intent set.
- D3.4 Non-buffer effects (bash with side effects, network) CANNOT be rolled back.
  Decision: the transactional lane covers BUFFER/FS edits via the broker ONLY. A
  program that mixes (tool/bash {non-read}) with edits is REJECTED at preflight with
  "transactional lane covers edits/creates; side-effecting bash cannot enlist —
  split the program". Honest boundary, not a false promise of total rollback.
- D3.5 Partial-commit visibility: the cost meter (D-7) reports enlisted-vs-committed
  counts in execute details so the agent sees "5 edits staged, all committed" or
  "5 staged, 0 committed (PeerConflict on b.rs)".

* Tests

- A program that creates A, edits B, then errors → NEITHER A nor B lands (the
  decisive partial-effect test). Re-run after fixing → both land.
- A program that creates A, edits B, succeeds → both land atomically; journal shows
  one MultiCommit.
- Concurrent execute commits an overlapping span first → the program's commit fails
  PeerConflict, nothing lands, typed result.
- Read tools mid-program see live state (not staged) — reads are not enlisted.
- A program mixing side-effecting bash + edit → rejected at preflight.

* MECHANISM CORRECTION (post-investigation, 2026-06-11)

Investigation (agent://7-TxnSubstrate) found the plan's core mechanism assumption
is WRONG for the actual write path:

- ASSUMED: stage `(tool/edit)`/`(tool/create)` writes via
  `BufferRegistry.edit_transaction` + broker `MultiCommit`.
- ACTUAL: the Spell `edit`/`create` tools BYPASS pi-code-engine entirely \u2014 they
  call the kernel (`executeCodePath` \u2192 pi-natives) which writes DIRECTLY to disk.
  The broker `MultiIntent`/`MultiCommit` protocol (stubbed-ready in
  crates/pi-edit-broker) coordinates pi-code-engine BUFFER edits across SESSIONS
  \u2014 a different axis. The ptc write tools never touch it.

- FOUND INSTEAD: `edit.ts` (lines 214-335) ALREADY implements strict
  snapshot/rollback \u2014 snapshot every target file before ops, restore on failure \u2014
  at SINGLE-tool-call granularity. This is exactly D3's needed primitive, at the
  wrong SCOPE.

CORRECTED MECHANISM: D3 = program-scoped snapshot/rollback at the DISPATCH layer.
Lift edit.ts's strict-transaction snapshot/restore from single-call to
whole-program scope:
- a TransactionScope (Node) opens per execute program;
- each write-effect tool call captures its touched files' BEFORE-state (first
  touch only, deduped) into the scope;
- program SUCCESS \u2192 commit = no-op (writes already durable), clear snapshots;
- program ERROR/fail-signal \u2192 rollback = restore all snapshots in REVERSE.
This is optimistic-apply + rollback (writes land, then revert on error), NOT
deferred-commit (nothing-on-disk-until-success). The deferred-commit IDEAL needs a
staging VFS the write tools route through \u2014 which does not exist \u2014 so it is a
documented future refinement, not the MVP. Optimistic-apply + rollback FULLY kills
E4 (the create-edit-boom program leaves the repo clean) with one narrow residual:
a hard Node-process crash mid-program before rollback runs \u2014 addressed by a
snapshot-set journal (W3) for crash-recovery, strictly better than today (where
EVERY error leaks partial effects).

exec_id threading: `client.ts:313` carries exec_id but uses it only for the abort
signal; it does NOT reach `onToolCall`. D3 must thread exec_id into the dispatcher
so a tool call binds to its program's TransactionScope.

SEPARATED OUT: the Rust broker MultiIntent/MultiCommit work (concurrent PROGRAMS
committing the same file) is a real but DIFFERENT concern from E4 partial-effects.
Filed as its own item; not on the E4 critical path.
