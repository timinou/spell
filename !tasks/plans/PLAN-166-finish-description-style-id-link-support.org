* Context

PLAN-164 fixed two =[[id:...]]= regex extractors (strict in
=packages/org/src/id-links.ts=, loose in

=extractPlanWaves= and several cosmetic nits in the test files touched
by PLAN-164.

** Root cause (finding #1)

=packages/coding-agent/src/tools/exit-plan-mode.ts= line 65 contains a
wave-entry parser regex that also hard-codes the double close bracket
after the target:

#+begin_src typescript
const entryRe = /^\s*-\s+\[\[id:([^\]]+)\]\]\s+(.+)$/;
#+end_src

This regex is used by =extractPlanWaves= to parse Execution Manifest
wave entries into structured =PlanWave[]= data consumed by todo
auto-init. Description-form entries never match, so all wave entries
are silently dropped when the plan author uses description links. The
=extractIdLinks= path still recognises the child references (that was
PLAN-164's fix), so plan validation passes — but the waves structure
ends up with zero entries per wave, producing hollow todo phases at
execution time.

** Scope

- Correctness fix for =extractPlanWaves= with TDD-first tests
  (addresses findings #1 and #2) — tracked in the child BUG item.
- Cosmetic cleanup in two test files from PLAN-164 (addresses findings
  #3, #4, #5) — tracked in the child FUP item.

** Approach

Same pattern as PLAN-164:
- Regex EXTENSION (not rewrite) with an optional non-capturing
  description segment: the pattern =(?:\[[^\]]*\])?= inserted between
  the target's closing bracket and the link's final bracket.
- Capture group shape preserved exactly: group 1 = orgItemId, group 2
  = step text after the link.
- TDD: failing tests first, then regex edit, then verify.
- Writer (=formatWaveManifest=) stays plain-form only. Reader
  (=extractPlanWaves=) becomes lenient. Postel's law.

** Key decisions

1. Split into two child items by concern:
   - BUG (=#A=, 30m) for correctness + TDD tests (findings #1, #2)
   - FUP (=#C=, 10m) for cosmetic cleanup (findings #3, #4, #5)
   No DEPENDS — the two children touch disjoint files and can run in
   any order or in parallel.

2. Regex EXTENSION (not rewrite) preserves the capture shape and keeps
   all 7 pre-existing =extractPlanWaves= tests green unchanged.

3. Do NOT unify the three id-link extractors (=extractIdLinks=,
   loop-ingestion =parser.ts= regex, =extractPlanWaves= =entryRe=).
   They have different target grammars and different tail requirements
   (global flag vs anchored line parse with step capture).

4. Do NOT touch =formatWaveManifest= or
   =packages/org/test/wave-manifest.test.ts=. The writer still emits
   plain-form only; that test documents the WRITER contract. Only the
   READER gets lenient.

5. TDD order: 3 new failing tests in =exit-plan-mode-waves.test.ts= →
   verify failures → single-line regex edit in =exit-plan-mode.ts=
   line 65 → verify all 10 tests pass → =bun check:ts= clean (no new
   type errors; pre-existing errors in unrelated files documented in
   PLAN-164 stay unchanged).

6. Cosmetic FUP: three targeted edits. Two blank-line insertions and
   one string-literal simplification. No semantic changes. File bytes
   written to disk in the spec-ingestion test MUST stay byte-identical
   across the Finding #5 edit.

Note: this PLAN body intentionally uses plain-form =[[id:...]]= links
only (no description form) in its Execution Manifest. Rationale: the
=extractPlanWaves= bug this plan fixes is currently present in =main=,
so if this plan itself used description-form wave entries, its wave
extraction at =exit_plan_mode= time would fail. Since this plan uses a
flat manifest (no =:wave:= headings), =extractPlanWaves= returns
=undefined= anyway and =extractIdLinks= handles child reference
extraction (PLAN-164 already made that path description-form-aware).
Using plain form in the manifest is robust regardless.
