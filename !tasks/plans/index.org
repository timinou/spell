** Context
User reported `spell` aborting with SIGABRT after a native panic:
`crates/pi-org-engine/src/buffer.rs:147:32: start byte index 258 is out of bounds` while parsing content beginning with a PLAN org file frontmatter. Investigation found the native org parser computes `frontmatter_end` with `line.len() + 1` for every `source.lines()` line. When a file-level org item contains only `#+` frontmatter lines and no final newline/body, `.lines()` omits the nonexistent newline but the parser still adds one, causing `frontmatter_end > source.len()` and then a panicking slice `source[frontmatter_end..]` when `include_body=true`.

Current repo evidence:
- `crates/pi-org-engine/src/buffer.rs:120-150` contains the faulty `frontmatter_end += line.len() + 1` and body slicing.
- `crates/pi-natives/src/org_index.rs:224-233` builds org index entries with `include_body=true`, so the boundary bug can be hit by plan validation/index resolution.
- `packages/org/src/native-ops.ts::findItemById` uses native `orgIndexResolve` with `includeBody: true`.
- `packages/coding-agent/src/plan-mode/plan-validation.ts::validatePlanItem` depends on `resolvePlanItem`/`findItemById` for PLAN and child item validation.
- `crates/pi-natives/src/org_buffer.rs::execute_org` currently maps ordinary errors to JSON, but does not contain native panics before they cross NAPI.

Settled decisions:
1. Fix the invariant in the native parser first; the boundary calculation must be byte-accurate and must not exceed `source.len()`.
2. Add Rust parser tests and native parse/index tests before implementation.
3. Add org bridge panic containment at the NAPI boundary as defense-in-depth, without using a production-only fake command.
4. Add a coding-agent plan-validation regression proving a frontmatter-only PLAN file without trailing newline returns normal validation issues instead of aborting.
5. Do not delete, move, or migrate existing org task files as part of the implementation.
