* Initial Message

kk look online what code-specific vector embeddings do and how that could help with the `code search` task

* Context
** Problem
The =code search= subcommand uses BM25 over symbol names and file paths. It cannot find code
by intent, natural language, or semantic similarity — only by exact or tokenized name matches.
When the agent needs to find "rate limiting logic" but the function is called =throttle()=,
the current search misses entirely.

The industry consensus (April 2026) is that hybrid search (BM25 + vector embeddings + graph
structure) outperforms any single approach. Augment Code demonstrated +6 points on SWE-bench Pro
purely from better context retrieval. Cursor showed 12.5% accuracy improvement from hybrid
retrieval. Sourcegraph's Cody converged on combining code graph (SCIP) + keyword + semantic
search. Pure vector RAG for code underperforms structural retrieval alone — the structural
side (graph edges, AST, LSP) is already strong in Spell, so vectors supplement rather than replace.

** Approach
Add local vector embeddings to =pi-code-graph='s search, using =fastembed-rs= for ONNX inference
in Rust. The architecture:

1. *New crate* =pi-code-vectors= — embedding model lifecycle (jina-code-v2 via fastembed),
   AST-aware code chunking with contextualized text, vector index with brute-force cosine search
2. *Hybrid search* in =pi-code-graph= — RRF fusion of BM25 + cosine results, then graph-aware
   re-ranking that boosts nodes adjacent to top results via structural edges
3. *Integration* through =pi-natives= N-API bindings with =--semantic= opt-in flag, coding-agent
   wiring for the agent to use semantic search

** Key Decisions
1. Model: =jina-embeddings-v2-base-code= (137M params, 768 dims, 8K context, Apache 2.0, code-specific)
2. Inference: =fastembed= crate (ONNX via =ort=), fully local, zero API calls
3. Separate crate: =pi-code-vectors= isolates the ONNX/ML dependency from =pi-code-graph=
4. Feature-gated: =pi-code-graph= depends on =pi-code-vectors= behind =semantic= cargo feature
5. Opt-in: =code index --semantic= downloads model (~500MB) on first use, builds vectors alongside graph
6. Hybrid scoring: Reciprocal Rank Fusion (RRF, k=60) — proven, parameter-light
7. Graph re-ranking: boost direct neighbors (callers/callees/importers) of top-5 results
8. Storage: =.spell/graph/workspace-vectors.bin= alongside graph cache, fingerprint-validated
9. Brute-force cosine: sufficient for <50K symbols, sub-10ms per query
10. Graceful degradation: no vectors -> pure BM25 (zero regression for users who don't opt in)

*** Deviations
- *Cyclic dependency resolved*: Plan specified =pi-code-vectors= depends on =pi-code-graph= for graph types. This creates a cycle (pi-code-graph -> pi-code-vectors -> pi-code-graph). Resolved by moving =chunking.rs= from =pi-code-vectors= into =pi-code-graph= behind the =semantic= feature gate. =pi-code-vectors= is now a pure embedding/vector-index crate with zero graph dependency. This is architecturally cleaner: chunking is graph-specific logic that translates graph data into text for embedding.
- *=fastembed= API differences*: Plan used =InitOptions= and =query_embed()=; actual fastembed v5 uses =TextInitOptions= and requires =&mut self= for =embed()= with no separate query API. Wrapped =TextEmbedding= in =Mutex= for thread safety.
- *=OnceLock::get_or_try_init=* is unstable (nightly-only); replaced with manual =get()= + =set()= pattern.
- *pi-code-engine formatting*: =cargo fmt= fixed pre-existing formatting drift in =pi-code-engine= (not caused by this plan).
