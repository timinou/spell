Can you leanly improve/change the decomposition steps of plans and ultraplans to fully support these? As in: you remove Daedalus (just don't activate it anymore), but instead you create the org files, and the org subtasks can depend on each other and other file CUSTOM_IDs, and the execution manifest is built from there, and there is a way to spin several agents that will then also spin agents so that there are several threads, that are coordinated through the main agent? * Context

** Problem
Plan execution currently has three separate paths:
1. *Plan mode*: =exit-plan-mode.ts= extracts PlanWave from execution manifest -> =plan-mode-approved.md= instructs agent to create =todo_write= phases -> agent manually works through phases, spawning task subagents
2. *Loop system*: manifest tickets -> =TicketLifecycleManager= -> =getReadyTickets= -> agent execution
3. *Fluid orchestrator*: =FluidPlan= (agents + dependencies) -> =QueueScheduler= with concurrency -> parallel agent dispatch

These paths duplicate scheduling logic, have inconsistent org lifecycle management, and limit parallelism. The plan-mode execution is single-threaded (one agent working through waves sequentially), with no support for multiple independent workstreams executing simultaneously.

** Approach
Unify plan execution onto the FluidOrchestrator as the single execution engine:
- *Elisp-first*: New =org-fluid-plan= MCP tool in Elisp reads org items, builds dependency graph, detects connected components via union-find, emits FluidPlan JSON. All graph algorithms in Elisp with ERTs.
- *Multi-component execution*: Disconnected components in the dependency graph are auto-detected. Each component gets a coordinator agent session that manages its sub-DAG independently.
- *OrgFluidBridge*: Bridge layer connects FluidOrchestrator events to org state transitions (ITEM->DOING->DONE). Post-execution hooks handle audit state, design history, plan completion.
- *Direct FluidOrchestrator invocation*: After plan approval, system invokes FluidOrchestrator directly instead of injecting =plan-mode-approved.md= prompt. No manual agent execution.
- *Advisory Daedalus*: Daedalus becomes purely advisory (non-blocking), runs AFTER org items are created on the real DAG. No user confirmation of decomposition.

** Key Decisions
1. *FluidPlan source*: Elisp MCP tool auto-converts org items -> FluidPlan JSON. Agent writes org items, system builds execution plan.
2. *Coordinator type*: Full agent sessions always (lightweight prompt for simple cases <=2 items).
3. *Org lifecycle*: Hooks in FluidOrchestrator via OrgFluidBridge. =completePlanItem= (currently dead code) wired into post-execution hooks.
4. *todo_write*: Stays passive for manual tracking. Coordinator sessions get their own todo_write instances.
5. *Abort cascade*: Independent — failed coordinators don't affect others.
6. *Migration strategy*: Big bang — implement everything, cut over, delete old paths.
7. *FluidOrchestrator interface*: OK to break, refactor to org-native, update all consumers.
8. *Elisp boundary*: All graph algorithms (topological sort, cycle detection, connected components) in Elisp. Loop system callers (metis-builder, momus-builder) migrate to MCP calls.

*** Deviations

1. *File-backed plan fallback preserved*: =plan-mode-approved.md= and =PlanWave= types were NOT deleted as originally planned. They remain for file-backed plans (org disabled) which still use the legacy prompt-injection execution path. The new FluidOrchestrator path handles all org-backed plans.

2. *Loop system caller migration deferred*: =metis-builder.ts= and =momus-builder.ts= were not migrated from direct =org-depend.ts= imports to MCP calls. These builders are defined but not actively called by the loop system. Migration is premature until these are wired into production use.

3. *=org-compute-waves.el= not deleted*: Retained because =org wave= CLI command (=org-next-wave.el=) still references it. Removing it would break the existing =org wave= command.

4. *Coordinator subprocess execution*: Instead of spawning a full =runSubprocess= in-process agent session per coordinator, the implementation uses =session.prompt()= with synthetic prompts. This is simpler and avoids the complexity of managing parallel in-process agent sessions, while still achieving the stated goal of FluidOrchestrator-based execution.
