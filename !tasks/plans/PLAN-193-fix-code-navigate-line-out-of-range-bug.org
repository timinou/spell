* Context

The =code navigate= command fails with "buffer error: line out of range" when the LLM passes both =line: N= (top-level) and =target: { line: 0 }= (schema-default fill). This was initially observed on Typst files but affects all languages.

** Root cause

The TypeScript code tool's argument flattening unconditionally overwrites =options.line= with =params.target.line= when the value is =0= (because =0 !== undefined= is =true=). The Rust =node_at()= function then rejects line =0= as out-of-range.

** Approach

Two fixes, ordered by priority:

1. Guard =target.line= flattening in =code.ts= to skip zero values (truthiness check, matching =node_type= pattern)
2. Replace wasteful =buffer.source().lines().count()= in =navigate.rs= with =rope.len_lines()=, eliminating an unnecessary full-file String allocation and fixing a latent off-by-one for trailing-newline files

** Key decisions

- Use truthiness check (=if (params.target.line)=) rather than explicit => 0= comparison -- matches the existing =node_type= pattern and is sufficient since line is 1-indexed
- Adjust =rope.len_lines()= result for trailing newlines rather than using =str::lines().count()= -- avoids O(n) allocation, makes navigate consistent with =buffer.info().line_count=
