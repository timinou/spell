* Initial Message

* Initial Message

Spell has been using CPU like crazy recently. Investigation found three compounding causes:

1. A zombie session at 71.9% CPU for 5 days, holding 6 fds pointing to a deleted pty — the controlling terminal was closed but spell kept rendering into the void.
2. Streaming assistant messages allocate O(content × tokens) Markdown instances per turn — HeapHelper GC threads hold a steady 14% during turns.
3. Even idle sessions sit at 0.5–9% CPU due to a fan-out of independent polling timers (OSC11 every 2s, multiple heartbeats, daemon health probes, per-spinner =setInterval=, etc.) that never stop or adapt.

Plus: the TUI render path force-invalidates the Container cache on every frame, so the existing differential cache is dead code.

User scope: focused purely on making the TUI feel responsive and reduce CPU/memory. *Hibernate is out of scope.*

* Problem

Three intertwined classes of waste, each verified against current code:

** Class A — pty-loss spin
=Terminal.#safeWrite= in =packages/tui/src/terminal.ts= flips =#dead= only on synchronous throw. Pty hangup emits an async =error= event on =process.stdout=; no listener catches it. No =process.stdin.on('end'|'close')= either. No liveness probe. SIGHUP doesn't help because spell processes are commonly reparented to =systemd --user=. Net effect: =#osc11PollTimer= and the render loop keep writing into a closed fd forever.

** Class B — streaming rebuild
=AssistantMessage.updateContent= in =packages/coding-agent/src/modes/components/assistant-message.ts:120-170= calls =#contentContainer.clear()= then rebuilds every child (=new Markdown=, =new Text=, =new Spacer=) for the *full accumulated message* on every streamed chunk. =Markdown=' s lex cache is per-instance, so each rebuild also re-lexes the whole growing message via =marked.lexer=.

** Class C — render coalescing defeats itself
=TUI.#executeRender= calls =this.markTreeDirty()= before every render, resetting =Container.#dirty= and =#cachedLines= across the entire subtree. The cache that =Container.render= consults is therefore always cold. The =Component.invalidate= → ancestor =Container= propagation is also missing — leaf changes don't bubble up the parent chain.

** Class D — polling fan-out
At least 7 distinct =setInterval= sources fire on a baseline idle session (OSC11 poll, cursor heartbeat, session-bridge heartbeat, ManagedDaemon health, AsyncJobManager watchdog, LSP idle check, web-session processInfo). None of them adapt: OSC11 keeps polling even after the answer is known; heartbeats fire on a fixed cadence rather than on idle silence; per-=ToolExecution= spinners create one timer each.

* Goal

For the *active session*:
- Streaming turn CPU on main thread: 30–70% → 10–25%
- HeapHelper aggregate GC: ~14% → <3%

For the *idle session*:
- Steady-state CPU: 0.5–9% → <0.5%
- Active timerfds per session: 7+ → ≤3
- Renders per second with N concurrent spinners: 12.5 × N → 12.5

For *resource hygiene*:
- Zombie sessions (pty-deleted, >24h old): observed 1+/week → 0

Lock these in with CI invariants that fail loudly on regression.

* Non-goals

- *Hibernate / suspend / persistent revival* — explicitly out of scope for this plan.
- Reworking viewport/cursor positioning — recent fixes are the truth there.
- Replacing the =marked= markdown lexer — only its invocation pattern is wrong.
- Per-component dirty-tree rewrite — work with the existing =#dirty= model, just stop overwriting it.
- React-style virtual-DOM diffing — keep the existing line-diff for actual changes.
- Resource caps / circuit breakers — not the bottleneck.
