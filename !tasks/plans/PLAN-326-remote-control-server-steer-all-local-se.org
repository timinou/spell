* Intent

One server, running anywhere on this machine, controls *all* live spell sessions through an
easy web interface. Sending a message from the web to a running terminal session must act
*exactly* as if the user had typed it in that terminal. Config lives in =../spell-remote-example=.
No auth/permissions work for now (Firezone local network handles that later).

* Current reality (post-exploration)

The =packages/spell-server= package already is an HTTP+WebSocket server with web-token auth,
a unified session registry (external CLI sessions + server-spawned RPC sessions), a React SPA
(=packages/spell-server/web=), an artifact watcher, templates, and the Telegram bridge.

Sessions ALREADY connect to one global server at =~/.spell/server.sock= via
=SessionBridgeClient= (=packages/coding-agent/src/session-bridge/client.ts=). So the
"interconnected sessions that know each other through sockets" substrate EXISTS.

** The core gap

External (terminal/TUI) sessions can only:
- register (pid/cwd/mode/project)
- answer *blocking events* (ask / plan_approval / hook_*) — Q&A round-trips
- emit low-fi =event_log= summaries (opt-in)

They CANNOT receive a free-form steering message. =WebSessionHub.send()= explicitly throws
"not steerable" for external sessions; =ws/server.ts= only routes =rpc= to spawned sessions and
=answer_blocking_event= to external ones. There is no terminal-input injection path.

∴ The #1 user requirement (send a message to a running terminal session as if typed) is
unimplemented. Everything else (transcript, status, mobile) is presentation on top.

* Architecture

Make terminal sessions *first-class steerable* by extending the EXISTING socket — not a new
transport. The socket becomes bidirectional for real input, not just Q&A.

#+begin_src
web composer ──WS{type:rpc, command:{type:prompt|steer|abort,...}}──▶ WebSubsystem.#dispatch
                                                                         │ external? 
                                                                         ▼
                                                       SocketSessionRegistry.injectMessage(sid, payload)
                                                                         │ writes frame
                                                                         ▼
                                       session.connection ──{type:inject_input}──▶ SessionBridgeClient
                                                                         │ onInjectInput
                                                                         ▼
                                       InteractiveMode.injectRemoteInput(text, mode)
                                                                         │
                                                                         ▼
                                       session.prompt(text, {streamingBehavior:steer|followUp})
                                       ≡ identical to a terminal keystroke submit ✓
#+end_src

Transcript mirror: external sessions push a richer =event_log= (user msg, assistant text,
tool start/end) so the web renders what the terminal shows; the registry keeps a ring buffer
backfilled on subscribe. (We deliberately reuse =event_log=, not a second channel.)

** Design invariants

1. ONE steering surface. A web =prompt= to an external session and to a spawned session take the
   same =BridgeRpcCommand= shape; the hub dispatches by session kind. No parallel API.
2. Injection is exactly =session.prompt= — same queueing, steer/follow-up, history, persistence.
   No bespoke message path that could drift from terminal behavior.
3. The socket stays line-delimited JSON; new frames are additive + back-compatible (old TUIs
   that don't understand =inject_input= simply never receive one).
4. Server already global via =~/.spell/server.sock=; "one server controls all" needs no new
   discovery — only that every TUI keeps connecting (it does).
