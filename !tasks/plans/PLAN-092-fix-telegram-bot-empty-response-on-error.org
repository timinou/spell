* Context

The Telegram bridge bot replies with "Assistant completed without a text response" when the agent encounters any error during prompt handling. This affects all error paths: missing model, missing API key, LLM auth failure, rate limiting, or any LLM error that produces =stopReason=error=.

Root cause: three interacting defects in the bridge's RPC event handling:

1. =ResponseStreamer= (=packages/telegram-bridge/src/bridge/rpc-to-telegram.ts=) only collects text from =text_delta= / =text_end= assistant events. When the LLM errors, the error info is in =message_end='s message payload (=errorMessage=, =stopReason=), but the streamer ignores the payload.

2. When =session.prompt()= throws (no model/API key), =rpc-mode= outputs ={ type: "response", success: false, error: "..." }=. The streamer ignores =type: response= entirely. Additionally, =rpc-client= (=packages/telegram-bridge/src/rpc/rpc-client.ts=) only resolves =promptCompletion= on =agent_end= / =turn_end=, so a failed prompt command causes a 5-minute hang.

3. The bridge's =RpcEvent= types (=packages/telegram-bridge/src/rpc/types.ts=) define =message_end= without a message payload, hiding the error data that the RPC process actually sends.

Approach: widen the =RpcEvent= types, handle error responses in =rpc-client=, surface errors in =ResponseStreamer=, and add test coverage.

Key files:
- =packages/telegram-bridge/src/rpc/types.ts= — RPC event type definitions
- =packages/telegram-bridge/src/rpc/rpc-client.ts= — prompt completion resolution
- =packages/telegram-bridge/src/bridge/rpc-to-telegram.ts= — ResponseStreamer
- =packages/telegram-bridge/src/bot/bot.ts= — message handler wiring (read-only, for context)
- =packages/coding-agent/src/modes/rpc/rpc-mode.ts= — RPC mode prompt handling (read-only, for context)
