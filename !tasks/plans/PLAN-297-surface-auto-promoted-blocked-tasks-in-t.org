* Initial Message

When the task tool dispatches a tool after another one (for partial sequentiality), it sends a message to the parent thread saying that a job was completed, but not that a previously queued job was started.

[[id:FEAT-671-surface-auto-promoted-blocked-tasks-in-t]]

* Context
The `task` tool's batch dispatch holds blocked tasks in a closure-local `readyQueue` (see =packages/coding-agent/src/task/index.ts= line 1026, =scheduleReadyTasks=). They become real `AsyncJobManager` jobs only when their blocker's success handler re-runs the scheduler. The `await` tool snapshots `manager.getRunningJobs()` once on entry (=packages/coding-agent/src/tools/await-tool.ts= line 82) and renders only that snapshot. Auto-promoted jobs are therefore invisible to the parent agent: it sees "Still Running (0)" and concludes the batch is over.

Concrete failure: session =14d40726c985291f= 17:29-17:41 UTC. Batch =[TSFix, Prompts, AgentsMd, LegacyDelete (filesDeps blocker on TSFix via index.ts)]= dispatched. After TSFix completed, =await= reported batch done. Parent agent re-dispatched LegacyDelete manually. User: "it's already dispatching automatically you fucking idiot". Parent had to =ls= the session dir to discover =31-LegacyDelete.jsonl= already running.

Two complementary signals fix this:
1. *Dispatch-time*: enumerate queued tasks with their blocker chains (extending the existing `implicitBlockerNote` pattern to all blockers, not just filesDeps-derived ones).
2. *Await-return-time*: a "Newly Started" section listing jobs that came online between the await call and result, computed via diff of the running-jobs snapshot using `AsyncJob.startTime` filtering.

Out of scope: pre-registering queued tasks as first-class jobs in =AsyncJobManager= (would require adding a =queued= status to =SubagentOutcome= and updating web dashboard, =jobs://= URI, event log; defer).
