* Context

Org wave and graph commands return near-empty results because 97% of items (672 of 688) use the file-level format (~#+CUSTOM_ID:~, ~#+STATE:~ frontmatter) which the Elisp tools do not support. The Elisp ~org-mcp--collect-full-items-from-file~ and ~org-mcp--collect-graph-nodes-from-file~ only scan for heading-level items (~* STATE Title~ with ~:PROPERTIES:~ drawer).

The only item visible to wave/graph was a phantom test fixture (~TSK-001-test~) leaking from a ~#+begin_example~ block — org-element treats ~* ITEM~ at column 0 as a headline regardless of block context.

Additional issues discovered:
- ~INIT~ state missing from ~org-tasks-todo-keywords~
- ~org-tasks--find-directory~ looks for ~@tasks~ but the directory is ~!tasks~
- Full org-element parsing of 672 files exceeds the 30s MCP timeout

** Approach

Add a lightweight frontmatter parser (~org-tasks--parse-file-frontmatter~) to ~org-tasks.el~ that extracts item metadata from ~#+KEY: value~ lines without ~org-element-parse-buffer~. Wire it into wave and graph node collection as a fast-path. Keep heading-level scanning for sub-outline support.

** Key decisions
- Fast-path: regex-based ~#+KEY:~ scanner reads first 2KB of each file, handles 97% of items in <1ms per file
- Slow-path: ~org-element-parse-buffer~ used only for the 16 files with heading-level items
- Both paths produce the same alist shape — downstream wave/graph logic unchanged
- ERT tests validate both paths and mixed scenarios
