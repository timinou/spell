* Context

The current failure came from the native structured edit path rejecting more than one unique file root in a single `edit` request:
- `crates/pi-natives/src/code_buffer.rs::resolve_edit_path(...)` collects every recursive `targetId` file root and hard-errors unless there is exactly one.
- `packages/coding-agent/src/tools/code.ts::primaryFileForOperations(...)` also bakes in the same hidden assumption by looking only at `operations[0].targetId`.

Settled decisions for implementation:
1. Keep one mutation representation: extend existing `code edit` / native `executeCodeBuffer { command: "edit" }` instead of adding a parallel multi-file command.
2. Both the public `code` tool and the direct native API must accept requests spanning multiple root files.
3. Persistence semantics are best-effort, not atomic across files. Each file remains transactionally edited within itself, but a later file may fail after earlier files have persisted successfully.
4. Direct native `edit` auto-saves by default, even though only the public `code` tool performs LSP-based formatting.
5. The public `code` tool must preserve its current formatting-before-save behavior by using the native multi-file contract in staged mode, then formatting/saving per file best-effort.
6. Successful persisted edits must still leave buffers usable for `undo` / `redo` while the buffers remain open.
7. Result normalization, preview UI, docs, and examples must cut over to grouped per-file outcomes/diffs so callers see the truth.

Recommended approach:
- Native layer (`pi-natives`) grows grouped multi-file edit execution with aggregate per-file results and default auto-save + staged opt-out.
- Public `code` tool consumes that aggregate contract, performs per-file formatting and persistence, and renders grouped per-file previews/results.
- No shim, no second command, no silent single-file fallback.
