** New discovery (2026-05-03): The 404 from better-ccflare is masked as "Connection error." because better-ccflare v3.4.27 sets ~Content-Encoding: gzip~ on error responses without actually gzip-compressing the body. bun's ~fetch()~ auto-decompresses based on the header → ~ZlibError~ → Anthropic SDK wraps as ~APIConnectionError("Connection error.")~. Confirmed via: (1) curl -v showing ~Content-Encoding: gzip~ + ~Content-Length: 140~ on uncompressed JSON body, (2) bun ~fetch()~ against better-ccflare 404 endpoint throwing ~ZlibError~, (3) Anthropic SDK error.ts:106 defaulting to "Connection error." message. Fixing the double /v1/ URL is the primary fix; the gzip encoding issue is upstream (better-ccflare) but warrants a followup workaround (~Accept-Encoding: identity~ or error response handling).

*** Root Cause Analysis

1. *Double /v1/*: Anthropic SDK internally prefixes baseURL with /v1/messages. streamBetterCcflare appended /v1 to baseURL, producing /v1/v1/messages. better-ccflare returned 404.

2. *Auth fallback*: serviceProviderMap only resolved ANTHROPIC_AUTH_TOKEN. Users with standard ANTHROPIC_API_KEY had no auth header sent. Added ANTHROPIC_API_KEY as fallback (ANTHROPIC_AUTH_TOKEN still preferred).
