** Settled Decisions
1. External provider-backed `code_search` stays separate; this cutover is only about repo-local search/discovery.
2. `grep` becomes the sole agent-facing repo-local search surface; overlapping `code` discovery commands are cut over in the same change rather than left as a parallel API.
3. `grep` gains an explicit raw-text escape hatch and a semantic-local mode; auto-routing may only prefer semantic lookup when the query is symbol/path-like and the request is not obviously a regex-oriented raw-text search.
4. Raw-text grep on supported code files must enrich output with exact declaration `targetId` when the match is on the declaration line, otherwise an enclosing `scopeTarget` / `scopeTargetId`.
5. Model-visible grep output, not only hidden `details`, must surface the IDs needed for one-hop follow-up into `code edit` / `code read`.
6. Existing FEAT-559 broad/narrow/noise behavior remains binding; semantic folding must compose with it instead of bypassing it.

** Brief Tradeoff Analysis
- Keep `code` search commands and merely add grep metadata:
  - ✓ lowest risk
  - ✗ leaves two repo-local search surfaces, so the current code→grep churn remains partly structural
- Replace grep with a new repo-search tool:
  - ✓ clean separation on paper
  - ✗ violates the user request and duplicates prompt/tool routing again
- Fold repo-local semantic lookup into grep, preserve explicit `rawText`, and remove overlapping `code` discovery commands:
  - ✓ one search surface, targetId-ready output, aligns with observed session behavior
  - ✓ uses existing targetId substrate from PROJ-048 instead of inventing new IDs
  - Risk: auto-routing can misclassify regex-heavy requests if the semantic/rawText boundary is too loose
- ∴ Recommended approach: grep-centered cutover with strict raw-text escape hatch and targetId/scopeTarget enrichment.

** Recommended Approach
- Phase 1 — lock the grep contract and failing tests first: semantic-local lookup, explicit `rawText`, targetId/scopeTarget output, and jq-derived regression workflows.
- Phase 2 — enrich raw-text grep results on supported code files with exact declaration `targetId` or enclosing `scopeTarget` using the existing stable target-ID machinery.
- Phase 3 — add semantic-local grep mode backed by existing code-buffer/search infrastructure.
- Phase 4 — remove overlapping agent-facing `code` discovery/search commands and update prompts/tests so repo search is taught through grep only.
- Phase 5 — verify that the old code→grep two-step flows can now be expressed as single-hop grep workflows without regressing FEAT-559 broad/noise handling.
