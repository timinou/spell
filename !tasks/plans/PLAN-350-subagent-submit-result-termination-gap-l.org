* Goal

make loop/anomaly conditions visible to the orchestrator in real time instead of only
discoverable via post-hoc transcript archaeology — via a structural fix to the
underlying data model, not additional scattered checkpoints on top of the existing
unsynchronized state.

* Non-goals

* Structural design
** Why a checkpoint-list-of-patches is the wrong shape
The executor's "is this subagent done" question is answered today by five
unsynchronized variables (`terminating`, `submitResultCalled`, `abortSignal.aborted`,
`abortReason`, `submitResultItems[]` used as if it were a single-value slot). Adding
more independently-placed checks on top of that (a hard gate here, a budget cap
there, a detector somewhere else) doesn't remove the race between them — it relocates
it, which is exactly why the prior fix attempt (`3-SubagentExecutorFixes`, above)
already tried that shape and the same failure recurred. The fix has to change the
data model these five variables are approximating, not add a sixth.

** S1 — Collapse lifecycle to one enum, one authority
Replace `terminating` + `submitResultCalled` + `abortSignal.aborted` + `abortReason`
(4 variables, 3+ read sites, no shared source of truth) with one
`SessionLifecycle: "running" | "closing" | "closed"` field on the executor's
per-subagent state. Every site that currently reads one of the old four booleans
reads this instead. Scheduling another turn while `closed` becomes inexpressible by
the type, not merely checked-against at each call site.

** S2 — `submit_result`'s terminal call is not a tool call
Every other tool (bash/edit/find) correctly returns control to the model to decide
what happens next. A terminal `submit_result` has no "next" — that's its entire
purpose. Today, acceptance still goes through the same async tool round-trip as any
other tool, so the model regains a turn afterward exactly like it would after
`bash` — that mismodeling is the direct cause of "700 more calls after success."
Fix: resolving the terminal cell (S3) synchronously ends the generation stream
itself — no further completion request is issued for that session. This removes the
"calls after acceptance" failure class by construction: there is no turn left in
which to make another call, not an abort signal racing to catch one in time.

** S3 — Split the result store: checkpoint log (multi-valued) vs terminal cell (single-assignment)
Preserves the freedom to submit several results — by design, per explicit direction
to keep that freedom — via an honest type split instead of one array used for two
purposes at once (a log AND a single answer, "last write wins" by accident).

New envelope shape (schema-safe — lives in the envelope, never inside a dispatch's
own declared `data` shape, so it can never collide with a caller's output schema).
Field is named `keep_going`, not `final`, so the DEFAULT (omitted) behavior reads
unambiguously as false — an agent that says nothing is NOT asking to keep going:
#+BEGIN_SRC typescript
result: {
  data?: T
  error?: string
  keep_going?: boolean   // NEW — sibling of data/error. The SOLE authority on
                          // terminal vs checkpoint. Omitted/false = terminal
                          // (resolves `terminal`, ends the session). true = this is
                          // a checkpoint, session continues — unconditionally.
}
#+END_SRC

Rule: `keep_going` is the single, sole authority on session continuation — no other
field overrides it in either direction. `keep_going` omitted OR `false` → terminal:
this call resolves `terminal` and ends the session, WHETHER OR NOT `error` is also
set (an unrecoverable failure report is exactly the normal terminal case — `error`
just fills the terminal cell's error slot instead of its data slot). `keep_going:
true` → checkpoint, session continues, unconditionally — including when `error` is
also present: a subagent legitimately reporting "this specific approach failed, I'm
trying something else" is a real, useful checkpoint, not a contradiction to reject.
`error` is descriptive payload content in either case, never a second control-flow
trigger — deliberately NOT allowed to silently override an explicit `keep_going:
true`, since that would just reintroduce the "two variables that can disagree"
problem S1 exists to remove.

Zero migration cost: ~87% of existing dispatches are already correctly single-shot
and never set `keep_going`, so they keep working exactly as today with no
prompt/schema change. `keep_going: true` is the ONLY way to opt into checkpoint
semantics — an explicit, affirmative ask to continue, and by design that assertion
is trusted over any other field.

Executor state becomes two honestly-typed stores instead of one overloaded array:
#+BEGIN_SRC typescript
checkpoints: CheckpointRecord[]   // append-only; every keep_going:true call
                                  // (error or data, doesn't matter which). Genuinely
                                  // multi-valued — no invariant violated, because
                                  // nothing here was ever pretending to be THE answer.
terminal: Result | null          // compare-and-swap, write-once. First call with
                                  // keep_going omitted/false locks it (error or data
                                  // payload, either is a valid terminal shape). Any
                                  // submit_result call after `terminal` is set is a
                                  // hard rejection ("session already resolved"), not
                                  // a silently-recorded overwrite.
#+END_SRC

Note (important framing, not a caveat to bury): the prevalence audit found ZERO
existing legitimate uses of `submit_result` as a multi-final/progress-report
channel. The only multi-call *legitimate* bucket found (2-8 calls per session) was
schema-REJECTION-then-retry (`isError: true`, not accepted, then corrected) —
unrelated to deliberate checkpointing. `keep_going`/checkpoints is a forward-looking
capability being added by deliberate choice, not a fix recovering a usage pattern
that was already silently relied upon.

** S4 — Observability is a live projection of S2+S3, not a bolted-on heartbeat
`checkpoints` for a long-running subagent doubles as its own heartbeat content:
`jobs://<id>` reads the SAME `checkpoints`/`terminal` state the executor already
maintains, live, not a separately-built mechanism exposing otherwise-private closure
variables. One structural decision (an honest, publicly-shaped data model) resolves
both the termination bug and the "4h23m of total silence" visibility gap in one
motion, rather than requiring a second, unrelated heartbeat mechanism.

** S5 — Checkpoint-stream anomaly detector (bounded backstop, not primary defense)
Scope: watches ONLY the `checkpoints` bucket (never `terminal` — a single
compare-and-swap write has nothing to detect). Enforces (a) a hard cap on total
`keep_going: true` checkpoints per session (e.g. 20) and (b) a payload-similarity
heuristic — consecutive checkpoints that are byte-identical to the prior one, OR
differ from it only by an incrementing counter/suffix — derived directly from the
prevalence audit's observed subtypes (incrementing-counter spam, verbatim-repeat,
both must OR together since a real incident can drift between them, as seen in the
DockData file). This heuristic applies regardless of whether a checkpoint carries
`data` or `error` — a subagent spamming `keep_going:true` + incrementing `error`
strings is the same failure shape as spamming `data`.

Critically: the ORIGINAL incident (`plan204Full`'s `{"a1":true}` … `{"ww50":true}`)
cannot recur in this shape at all, independent of whether S5 ever fires — call #1 had
no `keep_going` field, defaults to terminal, resolves `terminal`, locks it; call #2 is
a hard structural rejection under S3, full stop. S5 is a backstop for subagents that
deliberately set `keep_going: true` and then never resolve `terminal`, not the
primary defense for the incident that started this investigation.

** S6 — Discipline-gate exhaustion escalates to parent
When a subagent's yield-reminder hits its max-attempts ceiling
(`agent-session.ts` ~L3977-4060), surface that fact in the task dispatch result
returned to the orchestrator, instead of the child silently giving up. Confirmed gap:
yield-reminder behavior today is byte-identical at every `taskDepth` — no escalation
path exists at any depth. Kept as its own item because it is orthogonal to the
`submit_result` lifecycle fix (S1-S4): a subagent can exhaust its discipline
reminders without ever touching `submit_result`.

** S7 — General cross-tool "looping" discipline
A new discipline type (`config/discipline.ts`): last-N tool calls of the same name
with near-identical/incrementing arguments → forced interrupt ("you appear to be
looping — stop, resolve the block or submit your best honest partial result now").
Kept as its own item because S1-S5 only cover `submit_result` — a subagent could
still loop on `bash` or `edit` with no natural terminal/checkpoint split to lean on.
This is the generic version of S5's heuristic, for every other tool.

** Wall-clock ceiling and schema default (folded into acceptance below, not separate waves)
Two small, uncontroversial additions ride along with the above rather than standing
as separate waves: (a) a per-subagent-session wall-clock limit, checked each dispatch
loop tick, as an orthogonal safety net for a subagent that is checkpointing
genuinely-slowly rather than looping; (b) a default-on minimum schema when a dispatch
declares none, so a trivial single-key payload (`{"ww1":true}`-shaped) still fails
validation loudly instead of passing through an unconstrained `Record<string,Any>`.

* Acceptance criteria
1. A `submit_result` call with `keep_going` omitted or `false` resolves `terminal`
   and synchronously ends the subagent's generation stream — regardless of whether
   `data` or `error` is set — a test asserts no further completion request is issued
   and any subsequent tool call (including another `submit_result`) is hard-rejected
   with "session already resolved," not silently accepted.
2. A `submit_result` call with `keep_going: true` appends to `checkpoints` and does
   NOT terminate the session — regardless of whether `data` or `error` is set on
   that call (an "attempt failed, trying another approach" checkpoint is valid) — a
   test asserts the subagent can continue working and later resolve `terminal`
   normally by omitting `keep_going` (or setting it false) on a later call.
3. `jobs://<id>` polling mid-run returns the live `checkpoints` array and current
   `terminal` state (null until resolved) — test or manual verification against a
   long-running background dispatch with at least one checkpoint emitted.
4. A synthetic subagent that sets `keep_going: true` indefinitely without ever
   resolving `terminal` is capped at the configured checkpoint limit (e.g. 20) and
   forced to resolve — test asserts termination well before 700 calls.
5. A synthetic checkpoint stream with byte-identical or incrementing-counter-only
   payloads (in `data` or `error`) triggers S5's detector within the cap, flagged
   distinctly from a normal multi-checkpoint completion.
6. Dispatch with no declared `schema` still rejects a trivial single-boolean-key
   `data` payload.
7. `bun run --parallel check:ts check:rs` clean; existing executor/submit-result/
   discipline test suites pass unmodified except where intentionally updated for the
   new lifecycle/checkpoint model.

* Waves (suggested build order)
S1 (lifecycle enum) and S3 (checkpoint/terminal split) are the foundation — build
together first, since S2's synchronous-halt behavior depends on both existing. S2
(synchronous halt) follows immediately once S1+S3 land — this is the change that
actually eliminates the incident class. S4 (jobs:// live projection) is nearly free
once S3 exists — sequence right after. S5 (checkpoint anomaly detector) and the
wall-clock/schema additions are independent, bounded backstops — parallel-safe with
S4 or with each other. S6 (discipline escalation) and S7 (generic cross-tool loop
discipline) are both independent of S1-S5 and of each other — parallel-safe at any
point.

** Delegated-verdict reliability (methodology note)
4 of 13 delegated explore-agent verdicts in this audit were wrong when checked against
exact payload distribution/adjacency (`2-AiStreamingFixes`, `215-FixMachineHelpersTestCluster`,
`29-Feat703PolyphonyFaithfulPreview`, `30-Feat700WebhookSecrets`) — all caught and
overturned before they could corrupt the design. Two failure patterns identified:
(1) reasoning from surrounding session narrative/context instead of sampling the
actual tail-end payload bytes; (2) mistaking "real work exists somewhere in this
file" for "real work is adjacent to the suspect calls," without checking tool-call
POSITION/ADJACENCY. Required discipline for any future audit of this shape: exact
payload distribution counts (`sort | uniq -c` over extracted payloads) and explicit
adjacency checks, not narrative inference.

** Design deviations from the original write-up (both discussed and agreed with user)
1. `error` does NOT force terminal unconditionally \u2014 `keep_going` is the SOLE,
   unconditional authority in both directions (final design, per explicit user
   correction mid-session).
2. Field renamed `final`\u2192`keep_going` so the omitted/default case reads as "not
   asking to continue" without requiring the reader to already know the default
   (per explicit user request).
3. The tool-layer write-once lock originally sketched for S3 was REMOVED during
   implementation \u2014 it would have broken the pre-existing legitimate
   gate-verification retry flow (BUG-354). The single-assignment CAS instead
   lives at the EXECUTOR layer (`submitResultTerminal`), which is
   gate-verification-aware; the tool layer just reports `keepGoing`/`haltsLoop`
   accurately per call. `haltsLoop` (synchronous, in the agent loop) is what
   actually prevents runaway re-calls, not a tool-level lock.
4. Added `lastGateRejectedSubmission` (not in the original design write-up) after
   discovering during implementation that gate-rejected terminal claims need
   separate tracking from `submitResultTerminal` \u2014 required to keep BUG-354's
   `gate_failed` outcome and structuredResult-preservation-on-rejection working

*** S6 design correction (from evidence)
Original sketch: "escalate discipline-gate EXHAUSTION to the parent." Evidence shows
the more common and more actionable case is different: **the reminder-injection
itself can push a near-context-limit session over the edge**, causing an
unrecoverable crash that reads identically to "subagent silently gave up." Revised
S6 scope, two parts:
1. Before injecting a yield-reminder, check remaining context budget; if the
   reminder would push the request near/over the model's context limit, either
   compact/summarize first or skip the reminder and fail-honest immediately with a
   distinct outcome (e.g. `"context-exhausted-before-reminder"`) instead of
   silently emitting an unanswerable request that 400s.
2. Regardless of cause, a session that dies without ever getting a chance to call
   submit_result after entering the reminder flow should render a DISTINCT outcome
   from generic `submit-result-missing"/"failed"/"aborted"` \u2014 e.g.
   `"reminder-flow-crashed"` \u2014 carrying the actual underlying error (context
   limit, provider 400, etc.) so the parent can tell "crashed while trying to
   respond" apart from "chose not to respond."
3. Separately: `todo_write({tasks:[]})` immediately following a yield-reminder
   (clearing ALL todos in one call, not completing them) is a distinguishable gate-
   gaming signal worth flagging on its own \u2014 add a lightweight check: if the
   open-work guard's incomplete-count drops to 0 via a single wholesale-clear call
   (not a sequence of individual completions) immediately after a reminder fired,
   annotate the outcome so it's visible to review, even if not blocked outright.

** S7 evidence: real, severe, cross-repo instances found
Built a precise detector (python, not naive tool-name counting): for every subagent
transcript, extract the ordered sequence of non-submit_result tool calls
(name + arguments, `_i`/`intent` stripped as free-text noise), and find the longest
run of BYTE-IDENTICAL consecutive calls. Ran across all ~15k files.

Initial pass flagged high-volume single-tool sessions (e.g. 130 consecutive `find`
calls) \u2014 verified these are FALSE POSITIVES: every `find` target and `_i` was
distinct, substantive, real exploration (confirms naive same-tool-name counting is
the wrong basis for S7, argument-identity is required).

Byte-identical-argument detection found genuine, severe loops:

| `6-runtimeFoundation.jsonl` | `git log --all --oneline -- "lib/agentmaker/conversations/conversation_gate.ex" \| head -5` | 316 identical calls, lines 386\u21921040 of 1043 (~60% of the entire session) |

*** S7 design correction (from evidence)
Original sketch: "last-N tool calls same name with near-identical/incrementing args
\u2192 forced interrupt." Evidence supports this but sharpens the basis:
1. Detection MUST be on (tool name + full normalized argument set), not tool name
   alone \u2014 the false-positive check above (130 distinct `find` calls, all
   legitimate) proves same-tool-high-volume is not a usable signal by itself.
2. Byte-identical-argument repetition (not just "near-identical/incrementing") is
   the dominant real pattern found here \u2014 simpler and cheaper to detect than the
   incrementing-counter heuristic S5 needed for `submit_result` (because there's no
   analogous "the model is manufacturing distinct-looking keys" pressure on a tool
   like `bash`/`find` \u2014 it just re-issues the identical call).
3. A useful refinement given the git-log-loop cases specifically: if the repeated
   call is a READ-ONLY inspection command (git log/show/diff, grep, find, cat) with
   no WRITE tool call (edit/bash-mutating-command/git commit) interleaved anywhere
   in the surrounding window, that's a strong "waiting for a state change I'm not
   causing" signal \u2014 worth a slightly lower threshold than a generic repeat, since
   the audit shows it's a real, specific, recurring antipattern (2 independent
   instances of the identical `git log ... | head` shape).
4. Threshold: legitimate heavy tool use in this dataset (backdesk `bash grep`
   sessions, verse `find` exploration) topped out with fully DISTINCT arguments
   every call, never repeating identically even once in the sampled cases \u2014
   suggests a conservative threshold (e.g. 5-8 byte-identical consecutive calls,
   mirroring S5's window) has low false-positive risk, consistent with S5's finding
   for `submit_result`.

** Net effect on the follow-up plan
S6 and S7 remain correctly scoped as separate work from S1-S5 (confirmed: neither
touches `submit_result` lifecycle at all), but both designs are now evidence-driven
rather than speculative:
- S6 targets a context-overflow-during-reminder crash (the dominant real cause of
  "died without submit_result" in this dataset) with a distinct outcome value, not
  a generic "escalate exhaustion" mechanism that would rarely fire (evidence: true
  exhaustion never observed even once in ~15k transcripts).
- S7 targets byte-identical consecutive tool calls (the dominant real pattern found,
  cheaper to detect than incrementing-counter matching), with an optional
  read-only-with-no-interleaved-write refinement for the specific "polling a state
  I'm not causing" antipattern observed twice independently.
