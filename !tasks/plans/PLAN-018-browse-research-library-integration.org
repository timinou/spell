* Context

** Problem

The browse mode (~spell --canvas browse~) has a working findings panel and inline finding cards, but findings only enter the system when the agent explicitly sends a ~customType='finding'~ message. Most research happens through ~web_search~ (returns SearchSource[]), ~fetch~ (returns scraped content), and ~code_search~ (returns CodeSearchSource[]) tool calls -- none of which surface in the findings panel or research library. The user cannot see the research being built in real time unless the agent cooperates.

** Approach

Hybrid auto-creation + agent-driven curation:
- *web_search*: every SearchSource automatically becomes a finding (sourceType='search', curated=false)
- *code_search*: every CodeSearchSource becomes a finding (sourceType='code_search', curated=false)
- *fetch*: URL tracked as uncurated finding automatically; agent can promote noteworthy fetches via explicit custom message (curated=true)
- FindingsPanel gets Curated/All toggle -- curated by default, All shows everything including background fetches
- Dedup by normalized URL in findings panel; enrichment merges later data into existing finding
- Search results grouped under collapsible headers in chat flow
- Fetched content viewable in a dedicated ContentViewer panel tab (document type, with markdown rendering, search, copy)
- Each finding card shows source type icon (search/fetch/code/browser/agent)
- Browse-mode system prompt supplement teaches agent to emit findings for noteworthy fetches

** Key Design Decisions

1. *Batched finding emission*: BrowseEventMapper emits ~{type:'findings_batch', findings:[], searchGroup?:{query}}~ for web_search -- avoids 10+ rapid bridge messages and provides natural search grouping boundary. map() signature stays ~Record<string,unknown> | null~ (no breaking change). Additional events emitted via onAdditionalEvent callback.
2. *Start-end correlation*: mapper maintains ~Map<toolCallId, {toolName, args}>~ from tool_execution_start to retrieve query/URL at tool_execution_end (args not available on end event)
3. *Per-tool extraction*: web_search/code_search iterate sources arrays; fetch produces exactly one finding from URL. All three guard against isError, missing details, and error fields before extracting.
4. *QML ListModel arrays*: all array-typed fields use newline-delimited strings (tagsText pattern) or JSON strings (sourcesJson) -- QML ListModel cannot store native arrays
5. *Content store*: fetched content bodies stored in BrowseContentStore.js (imported by BrowseShell), keyed by tabId, LRU-evicted at 10 entries -- avoids 50KB strings in ListModel
6. *Three-way panel visibility*: BrowseShell chat/browser/document via tabType field on browserTabsModel entries
7. *Persistence without content*: findings metadata persisted in QSettings (excludes contentBody to stay under size limits), content re-fetched on demand
8. *Enrichment without timeline*: merge data on dedup (update excerpt, set enriched badge), but clickable interaction timeline deferred to [[id:FEAT-050-finding-enrichment-timeline-visualizatio]]

** Showcase Use Case
User says "research quantum computing". Agent runs web_search -> 10 SearchSource findings automatically appear in FindingsPanel (All mode) and chat (collapsible search group). Agent fetches 3 promising URLs -> they appear as fetch findings in All mode. Agent marks 2 as noteworthy via sendCustomMessage -> those 2 appear in Curated mode. User clicks a fetched finding -> ContentViewer tab opens with rendered markdown. User clicks "Open in browser" -> live browser tab opens.
