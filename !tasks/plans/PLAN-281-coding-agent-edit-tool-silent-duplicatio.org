Root-cause analysis (verified against transcript + source):

The `edit` tool in hashline mode accepts `op:"replace"` with only `pos` (or only `end`) and a multi-line `lines` array. The contract treats pos-only replace as exactly one-line replace — the multi-line payload gets spliced in place of the single anchor line, and the rest of the originally-intended region survives directly below the inserted payload. Visual effect: duplicated content. The session shows three such calls on `workbench_live.ex`, producing a ~33-line duplicated `<Surface>…</Surface>` subtree and a broken HEEx tree. The agent self-diagnosed only after inspecting the resulting diff; the tool itself never warned.

Contributing factor on the same session: the agent tried `code edit` first with `targetId="...left_pane_component.ex::AgentmakerWeb.Admin.Workbench.LeftPaneComponent"` (a valid deeply-nested Elixir `defmodule`), got `Symbol '…' not found. Available: []`, and fell back to the text `edit` tool. Restoring the structural edit path on deeply-nested Elixir modules removes the fallback that exposes the text-edit contract gap.

Settled design decisions:
1. Safety policy = strict fail. pos-only or end-only `replace` with `lines.length !== 1 && lines.length !== 0` MUST be rejected pre-mutation. No autocorrect, no span promotion, no warning-then-apply. Matches the precedent set by PLAN-261 / BUG-289.
2. Failure classification lives in the existing `HashlineAnchorError` taxonomy with a new `"span_mismatch"` variant and `HashlineSpanMismatchError` subclass — not a generic `Error`, not mixed into `HashlineMismatchError`.
3. Rejection happens in `resolveEditAnchors` (pre-apply), not inside `applyHashlineEdits`, so the rejection mirrors `MissingHashlineAnchorError`/`MalformedHashlineAnchorError` placement and keeps the apply path free of shape validation.
4. Field names stay: `pos` and `end` remain. The fix is description clarity, not a rename. Schema description strings and `hashline.md` both state explicitly that `lines.length` does not set the span and that `pos` alone means single-line replace.
5. Prompt update ships one counterexample in the `<examples>` section next to the existing range-replace example, so the model sees the failure shape inline rather than only after triggering it at runtime.
6. Elixir resolver failure is a separate child item (not a new scope creep into the hashline bug). It carries the structural-edit-path restoration that closes the fallback route to the text-edit failure mode.
7. Full cutover: once the runtime gate lands, no compatibility escape hatch remains. The taxonomy is invariant across hashline-mode edit calls.
8. Native binary staleness hypothesis for the Elixir resolver failure is explicitly in scope for investigation (per memory summary "Pin native binary rebuild" pitfall); if it is the root cause, fix extends the staleness detection surface rather than inventing a new resolver path.
