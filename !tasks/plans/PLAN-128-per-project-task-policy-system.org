* Context

** Problem
Tasks created during planning have no automatic gate enforcement based on their nature. Frontend tasks get dispatched without journey test requirements, API tasks without contract test requirements. The planner and executor must manually remember to set gates — and they don't. In the hotelcomm session (FEAT-063, -065, -067), all three frontend tasks were created with DEPENDS relationships but zero gates for journey tests or self-documenting code.

** Approach: Layer-Based Task Policies
A two-level config (project + mode) that:
1. Declares the project's layer vocabulary (what ~:LAYER:~ values mean in this project)
2. Associates gates and contextual guidance per layer
3. Auto-injects those gates at every task creation point in the pipeline

Config lives in two places:
- ~.spell/task-policies.yml~ — project-level defaults
- Mode frontmatter ~taskPolicies~ field — mode-specific overrides (mode wins by name)

** Key Decisions
- LAYER matching, not content/tag matching — ~:LAYER:~ on org items is the primary signal
- Sub-outline items (~FEAT-001::implement-ui~) can carry their own ~:LAYER:~ property, overriding parent's LAYER. This allows a single feature to span layers (e.g., frontend UI + API endpoint).
- Hard + soft enforcement: gates are auto-injected (block completion without verification), AND policy text is injected into prompts and subagent context for guidance
- Explicit gates always take precedence over policy defaults — the agent can override
- ~layers:~ in the config file defines the vocabulary AND provides descriptions shown to the planner

** Config Schema
#+begin_example
# .spell/task-policies.yml
version: 1
layers:
  frontend:
    description: "LiveView pages, components, browser interactions"
  api:
    description: "REST/GraphQL endpoints, request/response contracts"
policies:
  - name: frontend-journey-tests
    match:
      layer: frontend
    gates:
      gateLlm: "Journey tests covering complete user flow..."
      gateCmd: "mix test test/journey/"
    inject: |
      Write journey tests in test/journey/.
#+end_example

** Execution Pipeline
The LAYER property flows through four stages:
1. Planning: prompt shows layers + policies → planner sets ~:LAYER:~ on org items and sub-outline items
2. Approval: ~extractPlanWaves~ enriches wave entries with resolved LAYER from org item properties (sub-outline checked first, parent as fallback)
3. Auto-init: ~planWavesToTodoPhases~ carries ~layer~ into ~TodoItem~ → ~TodoWriteTool~ auto-injects gates
4. Dispatch: task dispatch passes ~layer~ to auto-roster → ~TodoWriteTool~ auto-injects gates → subagent receives gate requirements + policy inject text
