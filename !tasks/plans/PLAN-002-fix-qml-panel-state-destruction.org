* Initial Message

bro when i do `spell --qml` and the chat opens and I write sth and I click on Dashboard then Chat, the chat reinitialises. Reproduce the bug manually then in the test files and give me your root cause analysis and directions for fixing

* Problem

When using ~spell --qml~, typing a message in the Chat panel and switching to Dashboard then back to Chat loses all messages. The chat reinitialises with empty state on every panel switch.

* Root Cause

~shell.qml~ uses a single ~Loader~ (id: ~panelLoader~) with a reactive ~source~ binding tied to ~root.activePanelIndex~:

#+begin_src qml
Loader {
    id: panelLoader
    source: {
        var panel = root.panels[root.activePanelIndex]
        if (panel && panel.path) return panel.path
        return Qt.resolvedUrl("panels/ChatPanel.qml")
    }
}
#+end_src

When ~activePanelIndex~ changes, the ~source~ binding re-evaluates. The Loader destroys the old component entirely (including its ~messagesModel~, ~isStreaming~, ~tokenCount~, scroll position, etc.) and creates a fresh one from the new source. QML Loader is designed for lazy loading, not tab-like switching.

** What gets destroyed
- ~ChatPanel.messagesModel~ (ListModel) — all chat history
- ~ChatPanel.isStreaming~ / ~tokenCount~ / ~modelName~
- ~DashboardPanel.agentStatus~ / queue depths / orchestrator list
- ListView scroll position in any panel
- Any input text in progress

** Existing test documents the bug
~panel-lifecycle.test.ts~ has a test "panel switch destroys chat state" that asserts ~count == 0~ after a round-trip switch. This test documents the wrong behavior — it should assert state preservation.

* Fix: Replace Loader with Repeater of Loaders backed by ListModel

** Architecture

Replace the single ~Loader~ with a ~Repeater~ that creates one ~Loader~ per panel. All Loaders stay alive simultaneously. Only the active panel's Loader is visible.

Use ~ListModel~ (not a JS array) for the panels collection. ListModel supports incremental operations (~append~, ~remove~, ~set~) that don't cause the Repeater to destroy and recreate all delegates. A JS array would cause full Repeater re-creation on every ~panels = nextPanels~ assignment (panel add/remove), losing state for all panels — defeating the purpose.

** Key structural change

#+begin_src qml
// BEFORE: single Loader, destroys on switch
Loader {
    id: panelLoader
    source: root.panels[root.activePanelIndex].path
    onLoaded: root.flushPendingForActivePanel()
}

// AFTER: Repeater of Loaders, all stay alive
ListModel { id: panelsModel }

Item {
    id: panelContainer
    anchors.fill: parent

    Repeater {
        id: panelRepeater
        model: panelsModel
        delegate: Loader {
            anchors.fill: parent
            source: model.path || ""
            visible: index === root.activePanelIndex
            onLoaded: {
                if (index === root.activePanelIndex)
                    root.flushPendingForActivePanel()
            }
        }
    }
}
#+end_src

** Why ListModel matters

~addOrReplacePanel~ and ~removePanelById~ currently reassign the entire ~panels~ array:
#+begin_src javascript
panels = nextPanels  // New array reference → Repeater destroys ALL delegates
#+end_src

With ListModel:
#+begin_src javascript
panelsModel.append(panel)    // Adds one Loader, existing ones untouched
panelsModel.remove(idx)      // Removes one Loader, existing ones untouched
panelsModel.set(idx, panel)  // Updates in-place, Loader re-evaluates source binding
#+end_src

** Active panel accessor

Replace all ~panelLoader.item~ references with a function:
#+begin_src qml
function getActivePanelItem() {
    var loader = panelRepeater.itemAt(activePanelIndex)
    return loader ? loader.item : null
}
#+end_src

Internal code (~forwardToActivePanel~, ~flushPendingForActivePanel~) uses this function. Tests access via ~root.getActivePanelItem()~.

** onActivePanelIndexChanged flush is now safe

The old single-Loader design had a race: ~onActivePanelIndexChanged~ fired before the Loader loaded the new panel, so ~panelLoader.item~ was the old component. That's why it was removed (previous session fix).

With Repeater, each panel has its own Loader. ~panelRepeater.itemAt(newIndex)~ correctly returns the target panel's Loader. If it's already loaded, flush succeeds immediately. If it's loading for the first time, ~onLoaded~ handles the flush. So ~onActivePanelIndexChanged~ can be restored:

#+begin_src qml
onActivePanelIndexChanged: flushPendingForActivePanel()
#+end_src

* Risks and mitigations

** ListModel property access syntax differs from JS array
Sidebar delegates use ~modelData.icon~ (JS array) vs ~model.icon~ (ListModel). Mechanical change but easy to miss one. Mitigation: grep for ~modelData~ after refactor.

** Repeater delegate index stability
ListModel incremental ops preserve Repeater delegate identity. When ~panelsModel.remove(idx)~ is called, delegates at higher indices shift down. If ~activePanelIndex~ pointed to a higher index, it must be adjusted — ~removePanelById~ already does this.

** All panels loaded in memory
With Repeater, all panels are simultaneously loaded (not just the active one). For 2-3 panels this is negligible. If panel count grows large, consider ~active: index === root.activePanelIndex || loaded~ pattern to lazy-load but keep alive once loaded.

** Message routing to inactive panels becomes possible
With all panels alive, messages COULD be forwarded to inactive panels directly (instead of queuing/dropping). This is explicitly NOT in scope — keep existing routing semantics. Future enhancement opportunity.
