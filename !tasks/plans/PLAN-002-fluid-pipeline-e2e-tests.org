* Problem

Three disconnected test layers exist for fluid canvas mode:

1. *EventBus + orchestrator tests* (=fluid-drain.test.ts=, =fluid-event-pipeline.test.ts=): Test EventBus -> FluidEventRouter -> =bridge:outbound=. No QML. Verify event ordering and drain timing.
2. *QML journey tests* (=fluid-shell-states.test.ts=, =fluid-shell-agents.test.ts=): Launch QML headlessly via =QmlTestHarness= (offscreen). Events injected directly via =journey.agentSends()= -> =harness.sendMessage()=, bypassing EventBus entirely.
3. *No full-pipeline test* exists that wires EventBus drain timer -> FluidEventRouter -> =bridge:outbound= -> =harness.sendMessage()= -> QML state transition.

The drain timing bug just fixed was structurally uncatchable by either layer because:
- Layer 1 verifies events reach =bridge:outbound= subscribers when drained, but never touches QML
- Layer 2 verifies QML responds to events, but bypasses the drain mechanism entirely

This gap means the agent cannot autonomously verify that event timing works end-to-end. It can only assert on internal state (EventBus queue depth, subscriber callbacks) or QML state (via direct injection), never both together.

* Approach

Write a single end-to-end test file that wires real =EventBus= + real =FluidEventRouter= + real =QmlJourney= using the production drain pattern. Not a framework. The =bridge:outbound= -> =sendMessage()= wiring is 3 lines of glue code.

The production wiring pattern (from =fluid-mode.ts= lines 49-55):
#+BEGIN_SRC typescript
const eventRouter = new FluidEventRouter(eventBus);
const bridgeUnsub = eventBus.subscribe("bridge:outbound", (raw: unknown) => {
    // In production: bridge.sendMessage("fluid-shell", raw)
    // In test: harness.sendMessage(raw as Record<string, unknown>)
    void journey.agentSends(raw as Record<string, unknown>);
});
#+END_SRC

This gives the test the exact same event delivery path as production, with events flowing through the real priority queue, real drain timer, real coalescing, and real FluidEventRouter mapping.

** Key design decisions

- *Factory function, not class.* Production wiring is ~8 lines of glue. A class adds indirection without earning it. A =setupFluidPipeline()= function returning ={ eventBus, router, journey, startDrain, stopDrain, teardown }= is transparent.
- *No visual regression.* Golden screenshots are fragile across Qt versions and font rendering. State assertions via =evaluate()= + =expectText()= are more reliable. Screenshots remain available via =harness.screenshot()= for ad-hoc debugging.
- *No real subprocesses.* FluidOrchestrator accepts a =runAgent= callback. Mock it with controlled timing. The pipeline test verifies wiring from orchestrator events through drain through QML rendering. Subprocess execution is orthogonal.
- *Retry-based assertions only.* Total latency from enqueue to QML state change is 100-250ms (drain interval + bridge round-trip + QML event loop). Use =journey.waitUntil()= exclusively, never assert on timing.
- *Bidirectional testing.* Production has a round-trip: QML emits events (=prompt=, =cancel_execution=) back via bridge events, which =processFluidEvents()= dispatches. The test must verify this loop.
- *One =beforeAll= per describe.* QmlTestHarness spawns a real bridge process (cold start 1-3s). Start once, reset QML state between tests.
- *Extract helper at DRY=2.* If a second test file needs the same setup, extract ~50 lines to =test/helpers/fluid-pipeline.ts=. Not before.

interface FluidPipeline {
    eventBus: EventBus;
    router: FluidEventRouter;
    journey: QmlJourney;
    // Start/stop the 100ms drain timer (same pattern as production)
    startDrain(): void;
    stopDrain(): Promise<void>;
    // Full cleanup in production ordering
    teardown(): Promise<void>;
}

async function setupFluidPipeline(): Promise<FluidPipeline> {
    const eventBus = new EventBus();
    const router = new FluidEventRouter(eventBus);
    const journey = await QmlJourney.launch("FluidShell.qml");

    // Wire bridge:outbound -> QML (production pattern from fluid-mode.ts)
    const bridgeUnsub = eventBus.subscribe("bridge:outbound", (raw: unknown) => {
        void journey.agentSends(raw as Record<string, unknown>).catch(() => {});
    });

    // Drain timer management (same pattern as executePlan)
    let draining = false;
    let timer: NodeJS.Timeout | undefined;
    // ... (real implementation with reentrancy guard)

    return {
        eventBus, router, journey,
        startDrain() { /* start setInterval 100ms */ },
        async stopDrain() { /* clearInterval + flush */ },
        async teardown() {
            // Production ordering: stop drain -> dispose router -> unsub bridge -> teardown harness
            await this.stopDrain();
            router.dispose();
            bridgeUnsub();
            await journey.teardown();
        },
    };
}
#+END_SRC

Critical: =teardown()= must enforce the production cleanup ordering from =fluid-mode.ts= finally block:
1. Stop drain timer + flush
2. =router.dispose()= (stop subscribing to FLUID_EVENT_CHANNEL)
3. =bridgeUnsub()= (stop forwarding to QML)
4. =journey.teardown()= (kill bridge process)

* What this enables for agent autonomy

With this infrastructure in place, the agent can:

1. *Verify full event flow headlessly*: enqueue events exactly as production code does, verify QML responds exactly as the user would see
2. *Test timing-sensitive behavior*: drain timer intervals, coalescing, reentrancy -- all exercised through the real pipeline, not mocked
3. *Test user interactions*: click Cancel, submit prompts, retry failed agents -- and verify the event round-trip through EventBus and back to QML
4. *Take screenshots at any point*: =journey.screenshot("planning-state.png")= captures the QML rendering for visual inspection when needed
5. *Never be blocked by environment*: all of this runs in =QT_QPA_PLATFORM=offscreen= mode, no display required
