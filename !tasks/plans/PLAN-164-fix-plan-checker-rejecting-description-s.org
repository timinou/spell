* Context

=exit_plan_mode= and =spec-ingestion= both fail to recognise org's valid
description-style id link syntax — the form with two bracket pairs where the
second pair holds a description. A PLAN whose =* Execution Manifest= uses
that form is rejected with "PLAN item ... must include at least one child
reference" even though description links are valid org and render correctly
in Emacs and elsewhere.

Root cause: two TypeScript id-link extractors hard-code the trailing
double-close-bracket with no allowance for the description form.

- =packages/org/src/id-links.ts= (canonical strict, used by =exit_plan_mode=
  via =extractIdLinks=) — requires two close brackets immediately after the
  strict CUSTOM_ID capture group.
- =packages/coding-agent/src/loop/ingestion/parser.ts= (loose, used by
  loop-ingestion validator) — requires two close brackets immediately after
  the loose target capture group.

The elisp extractor =org-fluid-plan--extract-plan-child-ids= already uses a
single trailing close bracket and correctly handles both forms, so no elisp
change is needed.

Approach: extend each regex with an optional non-capturing description
segment between the target's closing bracket and the link's final bracket.
The strict extractor's CUSTOM_ID grammar stays unchanged (lowercase and
malformed ids still rejected); the loop extractor's loose grammar stays
unchanged. TDD: add failing tests in both packages first, then apply both
regex fixes together. Do NOT unify the two extractors — they intentionally
have different target grammars.

Key decisions:
1. Fix both extractors in one change (same root cause, partial fix would
   leave loop ingestion silently dropping description links).
2. Regex extension, not rewrite — preserves existing negative test cases and
   sub-outline-id handling.
3. No elisp edit. No prompt or doc edit.
4. TDD order: Phase 1 tests fail, Phase 2 test fails, Phase 3 both regexes
   patched, Phase 4 =bun check:ts= clean.

Note: this PLAN body intentionally avoids writing any literal
description-form id link in its prose so that the (fixed) extractor cannot
mistake illustrative text for child references. The concrete failing example
and the expected regex shapes live in the child item
