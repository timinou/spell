* Initial Message

make 'code edit' able to write new files (show me how). forbid edit and write usage if the file is supported by code edit. propose improvement to make code edit excellent.

* Context
Tooling note: the current `org` tool does not accept `INIT` and only supports `ITEM`, `DOING`, `DONE`, `BLOCKED`, `CANCELLED`, and `REVIEW`. This orchestration record is therefore stored as `ITEM` and should be treated as the plan-mode `INIT` equivalent for handoff.

User request: make `code edit` able to write new files, show the exact API shape, forbid `edit` and `write` usage when the file is supported by `code edit`, and propose one improvement that would make `code edit` excellent.

Repository facts verified before planning:
- `packages/coding-agent/src/tools/code.ts` currently forwards `command:"edit"` to native `executeCodeBuffer(...)` and auto-saves after successful `edit` / `undo` / `redo`.
- `crates/pi-natives/src/code_buffer.rs` currently routes file-local commands through `buffer_registry().open(&path)`, so a missing file fails before edit begins.
- `crates/pi-code-engine/src/buffer.rs` implements `CodeBuffer::open()` with `fs::metadata(path)?` + `fs::read(path)?`; `CodeBuffer::save()` writes the buffer path to disk but does not itself establish missing-file creation semantics.
- `packages/coding-agent/src/patch/index.ts` (`edit`) and `packages/coding-agent/src/tools/write.ts` (`write`) currently lack any block against code-supported extensions.
- `packages/coding-agent/src/prompts/tools/code.md` documents only existing declaration/body edits; `packages/coding-agent/src/prompts/system/system-prompt.md` still presents `edit`/`write` as generic fallback tools.

** Settled Decisions
1. New-file support will use explicit `code edit { file, operation: "create", content }`.
2. `operation:"create"` is missing-file only and whole-file only in v1. If the path exists, error and point callers to `replace` / `replace-body`. Reject unrelated targeting fields (`symbol`, `line`, `patches`, `edits`) for truthfulness.
3. Supported-file gating will use the same NAPI-supported extension set that `code` already uses today. Extract a single source of truth in TypeScript rather than duplicating extension lists.
4. Create must preserve structural-engine semantics rather than delegating to `write`: keep buffer history/diff/undo coherent, then run the existing formatter-before-save path, then persist.
5. Create should preserve current write ergonomics by creating missing parent directories before save.
6. `edit` and `write` will hard-error on supported files with actionable replacement examples; no silent auto-reroute.
7. Proposed excellence improvement: make `code edit` failures self-recovering by returning structured recovery hints (closest declarations / suggested next commands) for target-resolution and patch-match failures.

** Recommended approach
Tradeoffs considered:
- Explicit `operation:"create"` vs dedicated `command:"create"`: explicit op keeps all file mutations under one mental model and reuses existing `command:"edit"` plumbing.
- Explicit `create` vs implicit missing-file `replace`: explicit is better because missing-file creation is a materially different operation with different validation and error cases.
- Runtime hard-block vs prompt-only guidance for `edit`/`write`: runtime hard-block is required; otherwise the policy can be bypassed and source-of-truth remains ambiguous.

Recommendation:
1. Build native create support first (`pi-code-engine` + `pi-natives` + `code.ts` + result/docs/tests).
2. Then cut over supported-file `edit`/`write` calls to hard errors using a shared support detector and matching prompt docs.
3. Keep the excellence work as a follow-up after the cutover so the mandatory path is correct before optimizing failure recovery.

** How the caller should use it after implementation
Create a new supported file:
#+begin_src json
{
  "command": "edit",
  "file": "src/new-module.ts",
  "operation": "create",
  "content": [
    "export function newModule() {",
    "  return 42;",
    "}"
  ]
}
#+end_src

Expected behavior:
- Missing supported file → created, formatted if formatter exists, then saved.
- Existing file → actionable error telling the caller to use `replace` / `replace-body` instead.
- Calling `write` on `src/new-module.ts` or `edit` on other supported-code files → actionable error pointing at `code edit`.
