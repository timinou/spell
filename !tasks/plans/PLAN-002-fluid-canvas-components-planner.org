* Problem

Two areas block fluid canvas maturity:

1. *Canvas component gaps.* The =component-gaps.md= doc identified 5 missing components. Three are resolved (LayoutContainer, StatusIndicator, LogStream). Two remain: a reusable *ProgressBar* canvas block and a *syntax-highlighted CodeBlock*. Without a CodeBlock, all agent code output is rendered as unstyled plain text via =Text.MarkdownText=, which has no token-level coloring. Without a ProgressBar canvas block, agents cannot emit live structured progress.

2. *Planner quality.* The planner prompt is generic (86 lines, 3 examples). No guidance on task granularity, anti-patterns, or canvasOutput usage. DAG validation is structural only (cycles, missing deps) -- no checks for empty task descriptions, excessive agent count, or invalid canvasOutput types. No semantic validation exists.

* Approach

Two phases, each independently shippable.

*Phase 1 (components + structural validation):*
- Add =CodeBlock= canvas component using TS-side tokenization (shiki) into pre-rendered HTML, displayed via =Text.RichText= in QML. No C++ changes. The block data schema is ={ language: string, code: string, html: string }=. TS layer populates =html= before sending to QML.
- Add =ProgressBar= canvas component as a *static display* block only. Shows a completed ratio or labeled bar. NOT live-updating (the current =canvas_output= event fires only on agent completion; streaming canvas updates are a separate feature in DRAFT-009-fluid-structured-agent-progress-events). Block data: ={ value: number, max?: number, label?: string }=.
- Register both as planner-emittable types: update =CanvasOutputType= union, =canvasOutputSchema=, ContentBlock.qml dispatch, and planner prompt simultaneously.
- Extend =validateDag()= (rename to =validatePlan()=) with: non-empty task descriptions, agent count cap (warn >12), valid canvasOutput types against the TS enum.

*Phase 2 (planner prompt + semantic validation):*
- Improve planner prompt with 5 concrete heuristics and richer examples.
- Add semantic validation as inline LLM call (NOT a subprocess -- use the =ai= package directly with a cheap/fast model). Runs within the planning phase latency (hidden inside "Planning..." UI state). On rejection: re-invoke planner with critique as context, max 1 retry. On second failure: emit =plan_error=.
- Wire into =executePlan()= between =runPlanningAgent()= return and =executeFluidPlan()= call.

* Key decisions

- *CodeBlock highlighting: TS-side tokenization.* Shiki produces HTML; QML renders =Text.RichText=. No C++ QSyntaxHighlighter. Block data carries both raw =code= and pre-rendered =html= so QML stays pure display. Language detection falls back to "text" if unknown.
- *ProgressBar: static only.* Live-updating canvas blocks requires a new =canvas_update= event type which is out of scope (belongs in structured-progress-events PROJ).
- *Both new types are planner-emittable.* They get added to the =CanvasOutputType= union, schema, prompt, and QML dispatcher atomically. =code= for when the planner wants an agent to produce syntax-highlighted output. =progress= for summary bars in completion results.
- *Semantic validation: inline, not subprocess.* Direct LLM call avoids subprocess startup latency. Runs during planning phase. Max 1 re-plan attempt.
- *Rename validateDag -> validatePlan.* One function, one validation pass, one error list. No parallel validation paths.

** ITEM Improve planner prompt
:PROPERTIES:
:EFFORT: 1h30m
:END:

File: =src/prompts/agents/fluid-planner.md=

Add 5 heuristics:
1. Each task should be completable by a single agent in one session.
2. Target 2-8 agents. Use more only when tasks are genuinely parallelizable.
3. Use =canvasOutput= only for output meant for human review (not intermediate data).
4. Each task description must state what the agent should produce, not just what it should do.
5. Prefer wide DAGs (parallelism) over deep chains (sequential bottleneck).

Add anti-patterns section:
- Don't create a single agent for everything (defeats the purpose).
- Don't create > 12 agents for a simple task (overhead exceeds benefit).
- Don't chain agents when they could run in parallel.
