User request: `org wave` should provide both the file-level DAG and the subfeature-level DAG so the implementation agent can orchestrate more intelligently.

Settled design decisions:
1. File-level DAG nodes are child item CUSTOM_IDs (`FEAT-*`, `BUG-*`, etc.), not physical org file paths.
2. File-level DAG edges are produced by collapsing sub-outline dependency edges to parent child IDs and omitting intra-parent edges.
3. Subfeature-level DAG nodes are canonical sub-outline CUSTOM_IDs (`PARENT::slug`) included in the wave input.
4. DAG edge direction matches existing native graph semantics: `from` depends on `to`.
5. `org wave` exposes DAGs in structured JSON as explicit `{ nodes, edges }` fields.
6. When `manifest=true` and `planItemId` is set, `org wave` writes readable DAG sections inside the PLAN `* Execution Manifest` after wave sections.
7. DAG headings must not use the `:wave:` tag; only wave headings are executable task waves for `exit_plan_mode`.
8. Existing outputs (`manifest`, `waves`, `warnings`, `total_sub_outlines`) and duplicate-ID error contracts remain compatible.

Repository facts verified during planning:
- `packages/org/src/tool.ts::cmdWave` currently calls native `executeOrg({ command: "computeWaves" })`, formats only wave headings with `formatWaveManifest`, and writes through `writeManifestSection`.
- `crates/pi-org-engine/src/graph.rs` already has `DepEdge`, `GraphResult`, `WaveResult`, `compute_waves`, duplicate-ID checking, and existing edge semantics where `from` is blocked by `to`.
- `crates/pi-natives/src/org_buffer.rs::cmd_compute_waves` serializes native `WaveResult` directly.
- `packages/coding-agent/src/tools/exit-plan-mode.ts::extractPlanWaves` reads only `** ... :wave:` headings and ignores other `**` headings.
- Memory note used: `memory://root/memory_summary.md` warns Rust API changes may hit native binary staleness; verification must rebuild/check native paths truthfully.

Recommended approach:
- Extend native `WaveResult` with DAG fields once, then pass those fields through the TS org tool and manifest formatter. This keeps the dependency graph source of truth in native graph code and avoids reconstructing divergent DAG semantics in TypeScript.

Out of scope:
- No new org subcommand.
- No change to `nextWave` eligibility.
- No change to approved task materialization beyond preserving/communicating DAG context.
- No compatibility shim with reversed edge direction.
