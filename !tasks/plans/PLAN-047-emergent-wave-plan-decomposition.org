* Context
** Problem
Plan execution maps 1 org item = 1 todo task. Implementation steps within items are invisible to the task scheduler. When FEAT-001 and FEAT-002 each have 5 steps, the executor serializes them entirely, even though cross-item steps are often independent. This limits parallelizability.

** Approach: Emergent Waves from Topological Sorting
Waves are NOT hand-crafted by the planner. Instead:
1. Implementation steps within org items become individually addressable via sub-outline CUSTOM_IDs (=PARENT-ID::sub-slug= format, e.g., =FEAT-001::define-types=)
2. Steps declare dependencies via =:DEPENDS:= property referencing other sub-outline IDs
3. The system topologically sorts the dependency graph and the resulting layers ARE the waves
4. The org tool auto-assigns =:WAVE: N= properties and generates a skeleton Execution Manifest
5. The planner fills in descriptions; the executor creates wave-based todo lists with cross-item parallelism

** Key Design Decisions
1. Sub-outline CUSTOM_ID format: =PARENT-ID::sub-slug= (=::= separator). Globally unique by parent prefix.
2. Consolidate BLOCKER to DEPENDS everywhere (elisp already uses DEPENDS; TS code uses BLOCKER. Unify.)
3. Waves emerge from topological sort of sub-outline dependency graph. Planner does NOT manually assign waves.
4. Emacs is hard dependency. No TypeScript fallback for wave computation. Elisp computes everything.
5. Full recompute on write: when DEPENDS changes, rebuild entire category dependency graph and recompute WAVE properties.
6. =orgItemId= becomes non-gating (lineage). New =orgItemClosingId= is gating (triggers verification).
7. ALL plans use wave-structured Execution Manifest. Not optional. Flat manifests deprecated.
8. Meta-planning is recursive: the plan's own Execution Manifest uses wave format.
9. cmdWave/cmdGraph wiring is separate PROJ for elisp consistency.
