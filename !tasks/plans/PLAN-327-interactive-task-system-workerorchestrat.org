* Goal

Turn the task system from fire-and-forget delegation into a *live, bidirectional* delegation surface:
- a subagent can ask the orchestrator a question mid-run (an in-task tool, sibling to ~report_finding~)
- the orchestrator LLM routes the answer: always back to the originator, plus any sibling tasks it judges relevant (fan-out)
- transport rides the existing in-process ~EventBus~ (the broker)
- ~todoRef~ -> ~ref~ (required, nullable), accepting both roster ids and ~org://~ URIs
- the whole dialogue is visible in the TUI and the spell-server web/Telegram surface

* Grounding facts (verified in repo, 2026-06-09)

- Subagents run **in-process**: ~executor.ts::runSubprocess~ is a misnomer -- it calls ~createAgentSession()~ + ~session.prompt()~ in the *same* Bun process. The "subprocess" framing is historical. => a live channel to a running worker needs **zero IPC**; it is a shared-memory ~EventBus~ subscription.
- ~EventBus~ already carries ~task:subagent:event~, ~task:subagent:progress~, ~swarm:*~, ~todo:*~ channels (~task/types.ts~, ~utils/typed-event-map.ts~).
- ~subprocessToolRegistry~ (~task/subprocess-tool-registry.ts~) is the precedent: a tool registers ~extractData~ / ~shouldTerminate~ / ~renderInline~ / ~renderFinal~; the parent reads emitted JSONL tool events into ~progress.extractedToolData[tool][]~. ~report_finding~ (~tools/review.ts~) is the reference impl -- it pushes structured data **up** but has **no reply path**. The ask-tool is its twin *with* a reply path.
- Context-init today: parent writes ~context.md~ (compact summary via ~formatCompactContext~) once per batch; ~renderTemplate~ merges ~context~+~assignment~; ~resolvePredecessorResultsContext~ injects blocker outputs into dependents.
- Async exists: ~async.enabled~ + ~session.asyncJobManager~; ~index.ts~ already routes a batch to background jobs when ~asyncEnabled && agent.blocking !== true~. Worker turns are uninterruptible (one ~await provider.completion()~); injection only at turn boundaries / tool-call resolution.
- ~SwarmBlackboard~ persists coordination as **real org items** (~appendItemToFile~). Org plan dir = ~!tasks/plans/~, category ~plans~.
- Dead code: ~swarmEnabled~ block in ~task.md~ -- ~swarmEnabled~ never passed to ~renderDescription~.

** CORRECTION — answer mechanism is /btw-style context fork, NOT async turn

Earlier draft assumed the orchestrator takes a live turn to answer (needing async batches, risking deadlock R2). The user pointed at how ~/btw~ works: ~BtwController~ forks a side ~streamSimple~ over a snapshot of the session context (~systemPrompt~ + ~getCompactContext()~), answers, and NEVER mutates the main loop. Applied here:

- The answer is generated by forking the parent session's context snapshot, with ~toolChoice~ forced to ~answer_subtask~. No live orchestrator turn. ∴ the orchestrator can be blocked in ~await taskBatch~ (normal blocking ~task~ call) and STILL answer. R2 deadlock + async dependency both eliminated.
- ~TaskTool~ already holds the parent ~ToolSession~ (~this.session~), which exposes ~eventBus~, ~modelRegistry~, ~model~, ~getSystemPrompt()~, and ~getCompactContext()~ ("compact conversation context for subagents, excludes tool results, system prompts") — the exact /btw snapshot surface. * Primitives

** P1 -- ask_orchestrator tool (in-task only)

Mirror of ~report_finding~: registered in ~subprocessToolRegistry~, injected ONLY into subagent toolsets (never the root agent). Schema:
- question: string -- the ask
- blocking: boolean -- D1: park vs ack-and-continue
- scope_hint?: string -- worker's guess at who else cares (advisory; orchestrator decides)
- _i: string -- intent, per house convention

Behaviour:
- blocking=true -> the tool's ~execute~ returns a Promise that resolves when the orchestrator's answer arrives on this worker's inbox topic. Worker parked at a clean tool boundary; no mid-completion interrupt.
- blocking=false -> returns immediately ~{acknowledged, questionId}~; answer delivered as a developer-role message on the worker's NEXT turn (pull-inbox, P3).

** P2 -- broker topics (extend SwarmEventMap)

- task:ask:raised    { runId, questionId, fromTaskId, fromSessionId, question, scopeHint?, blocking }
- task:ask:answered  { runId, questionId, answer, recipients: string[] }   // recipients = task ids
- task:ask:cancelled { runId, questionId, reason }

~raised~ emitted by the ask-tool; orchestrator-side listener consumes it. ~answered~ emitted after the orchestrator composes the reply; per-worker inbox routers filter by membership in ~recipients~.

** P3 -- per-worker inbox

Each running subagent session owns a bounded inbox (mirrors 315 ~sync_channel(256)~ + lag-drop from AGENTS.md knowledge-daemon). Two drains:
- blocking ask -> the awaiting tool-call promise is the consumer (direct resolve when questionId matches).
- non-blocking / unsolicited broadcast -> drained at the TOP of each worker turn, injected as a developer message ~[orchestrator -> you] re: <q>: <answer>~. Eventually-consistent; never interrupts an in-flight completion.

** P4 -- orchestrator-side answer pump (D3)

Batch is async => orchestrator live. A ~task:ask:raised~ event becomes a first-class interrupt surfaced into the orchestrator's loop (reuse the user /btw injection path). Orchestrator answers naming recipients; a deterministic relay emits ~task:ask:answered~. Originator auto-added to recipients if the LLM omits it (D2 invariant enforced in CODE, not prompt).

** P5 -- ref resolver (D4)

Replace ~taskItemSchema.todoRef~ with ~ref: string | null~ (required key). Resolver:
- null -> no linkage (explicit, valid)
- /^task-\d+/ or roster id -> findTask(groups, ref)  (current todoRef path)
- /^org:\/\// -> org engine lookup -> gates + predecessor wiring from the org item

Keeps ~resolveVerificationContext~ + ~resolvePredecessorResultsContext~ working for both shapes. ~org://~ unlocks durable cross-session linkage.

* Event flow -- blocking ask, fan-out to 2 of 3

batch[task1,task2,task3] dispatched async -- orchestrator stays live
  task1 -- ask_orchestrator{blocking:true, q:"which error type?"}
           (task1 parks at tool boundary) -- emit task:ask:raised
  orchestrator loop <- interrupt (P4)
  orchestrator: "use AppError; relevant to task1 & task3"
           -- emit task:ask:answered{recipients:[task1,task3]}
  task1 inbox <- resolve parked promise -- answer returned as tool result
  task3 inbox <- queued -- injected as developer msg on task3's next turn
  task2 -- unaffected (not a recipient)
  TUI + server <- subscribe task:ask:* -- render Q/A thread under the batch

* Open questions / risks

- R1 (cost): every question = one orchestrator turn (D2). Knob: per-batch ~maxAsks~ budget; over budget -> ask-tool returns "ask budget exhausted, decide yourself".
- R2 (deadlock): blocking ask while orchestrator itself blocked. D3 (async batch) is the structural fix -- verify orchestrator is never simultaneously parked awaiting the same batch it must answer.
- R3 (ordering): two workers ask near-simultaneously; orchestrator answers serially. Inbox is per-worker (no cross-talk), but the orchestrator's turn must drain ALL raised asks before yielding, else stragglers wait a full cycle.
- R4 (context bloat): broadcast answers append to recipients' contexts. Keep answers terse; consider a ~data://~ pointer for long answers (URI-as-currency strength).
- R5 (prompt vs code invariants): "originator always receives" and "drain all asks before yield" enforced in CODE, not prompt.

* Non-goals

- No new out-of-process transport (in-process EventBus suffices -- key insight).
- No human-in-loop answering this round (Telegram seam noted, not built).
- No change to DAG scheduler semantics; asks are orthogonal to blockers.
