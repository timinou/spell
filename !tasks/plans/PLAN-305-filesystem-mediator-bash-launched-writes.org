* Initial Message

look at brush and tell me how it manages file writes

* Problem
Bash-spawned writes (sed -i, python script.py, go build, npm install)
bypass the existing intent/commit coordination layer because they touch
files directly. Multi-spell coordination only works when all writers go
through the broker socket. Goal: make this universal.

* Solution shape
Per-repo FUSE mount, owned by a new pi-edit-broker-fs daemon. Spawned
and supervised by pi-edit-broker using the same fork+setsid+pidfile
pattern that already exists. Mount-over-self so users see ONE folder.
All filesystem syscalls in the repo route through the daemon, which
translates them into the existing intent/commit protocol against the
coordination broker.

* Non-goals
- Replace existing intent/commit protocol -- extend it
- Block writes by default -- mediate, observe, journal; rejection is opt-in
- Sandbox semantics -- this is a coordination layer, not a security boundary
- Windows support in v1 -- Linux + macOS only

* Architecture (final, after broker code review)
The existing pi-edit-broker already owns:
- multi-spell coordination via Unix socket
- intent/commit/multi-txn protocol
- daemonization (fork+setsid+pidfile+probe)
- grace-period exit
- journal replay for crash recovery
- session reaper

The new pi-edit-broker-fs daemon extends this same pattern:
- per-repo singleton (pidfile at $XDG_RUNTIME_DIR/spell/fs-<repo-hash>.pid)
- spawned & supervised by pi-edit-broker via the existing spawn helper
- mounts FUSE over the real repo path (mount-over-self with O_PATH lower_fd)
- translates each kernel call to existing Intent/Commit RPCs
- holds a synthetic SessionId per writing process (synthesised from /proc pid)

Multi-spell-instance protection lives at three layers:
  L1 kernel: single FUSE mount per repo, kernel serializes per-inode
  L2 fs-daemon: per-inode write queue (parking_lot::Mutex)
  L3 broker: existing intent/commit protocol arbitrates across sessions

The broker is unchanged in Phases 0-4. Phase 5 is the only PR that
modifies pi-edit-broker's own code (adds the supervision hook).

* Phase 7 -- memory + CPU hardening (gate: perf benchmarks)

Targets:
- Read passthrough: zero-copy via splice(2) when both fds are pipe-able;
  fall back to read+write
- Write hot path: bytes -> lower fd direct; journal entry queued on
  bounded channel; batched fsync every 16ms or 64 entries
- Pre-image snapshots: content-addressed (blake3) store in
  $XDG_CACHE_HOME/spell/snapshots/; dedup across files; LRU-evicted
- Snapshot skip threshold: 16 MB default (metadata-only journal entry)
- Inode table: dashmap<u64, InodeState>, lock-free reads
- io_uring opt-in for lower fd batch I/O (cfg gated)
- Daemon RSS budget: 32 MB steady-state, hard cap 128 MB
- Per-call latency budget: p50 < 50 us, p99 < 500 us for hot ops

Benchmarks (criterion):
  B7.1   sequential read 1 GB: throughput within 5% of ext4 baseline
  B7.2   sequential write 1 GB: within 10% of ext4 baseline
  B7.3   1000 small files create+write+close: throughput
  B7.4   tar extract of linux kernel source tree: total time
  B7.5   make -j8 on a real C codebase: total time
  B7.6   git clone --depth=1 inside mount: total time
  B7.7   RSS over a 24h soak with random workload: bounded
  B7.8   p99 latency of FUSE openat under load

Memory tests:
  M7.1   leak check (valgrind-style: track InodeState allocations across
         100k open/close cycles)
  M7.2   bounded queue back-pressure when journal flush slow
  M7.3   handler thread pool sized to ncpus, not unbounded
