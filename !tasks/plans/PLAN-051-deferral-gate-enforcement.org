* Context

** Problem

During plan execution, the coding agent can abandon todo tasks freely by setting ~status: "abandoned"~ via ~todo_write~. This causes deferred work to be silently forgotten. In session ~14a837d85a75458c~ (PLAN-048), the agent abandoned tasks 10, 15, and 16 with just a ~notes~ field — no FUP org items were created, no structured tracking exists, no audit trail. The completion report mentioned deferrals in prose, but nothing structured survived for follow-up.

Three systemic escape hatches exist:
1. ~update~ op with ~status: "abandoned"~ — no gate, sails through at line 424 of ~todo-write.ts~
2. ~remove_task~ op — silently deletes tasks with zero validation
3. ~replace~/~add_phase~ ops — can create tasks pre-~abandoned~ via the shared ~StatusEnum~ in ~InputTask~

** Approach

Hard gate enforcement at the ~todo_write~ tool level. When ~status=abandoned~, a ~deferralFupId~ field is REQUIRED — the tool rejects without it and provides a pre-filled ~org create~ template. All bypass paths are closed:
- ~remove_task~ op is removed entirely
- ~status~ field is removed from ~InputTask~ (tasks always created as ~pending~)
- ~abandoned~ can only be reached via the ~update~ op with ~deferralFupId~

Supporting changes:
- Journal maps abandoned to ~BLOCKED~ (not ~DONE~) with ~:DEFERRED_TO:~ property
- Session auto-clear and resume preserve abandoned tasks (audit trail)
- Phase completion warns about deferred tasks with FUP IDs
- Plan audit and completion report prompts require FUP references

** Key Decisions

1. Scope: ALL abandoned tasks require FUP (not just org-linked)
2. No escape hatch: every abandonment creates a FUP. If work is irrelevant, FUP is created and marked DONE immediately
3. Enforcement: hard rejection (not soft warning). Two-step flow: agent creates FUP via ~org create~, then passes ~deferralFupId~ to ~todo_write~
4. Journal: ~BLOCKED~ status (not ~DONE~). ~#+TODO~ line: ~ITEM DOING BLOCKED | DONE~
5. ~isPhaseComplete~ unchanged — abandoned remains terminal for phase progression (avoids deadlocks). Compensated by warnings listing FUP IDs
6. ~hasUnresolvedBlockers~ unchanged — abandoned still resolves blockers (same deadlock avoidance reason)
7. Batch abandonment allowed — multiple tasks can share one FUP ID
8. No retroactive enforcement
9. ~remove_task~ op removed entirely — tasks can only be abandoned, never deleted
10. FUP content: full self-contained context (title, reason, original task content/details, source org item link, acceptance criteria, sub-outline steps) so follow-up sessions can execute without reading the original plan
