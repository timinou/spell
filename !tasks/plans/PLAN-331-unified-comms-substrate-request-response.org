* Goal

Collapse Spell's FOUR parallel "a process needs an answer from elsewhere" mechanisms onto ONE transport-agnostic request/response substrate, so:
- a *spawned* (RPC) agent CAN answer a blocking event (today: hard-rejected ~not_supported_for_spawned~)
- ~task:ask:*~ subagent dialogue is observable server-side (web/Telegram) for FREE — same frame as blocking events
- the wire is modelled on the most mature existing pattern (PtcRuntimeClient JSON-RPC-2.0/NDJSON) so a future BEAM orchestration move is wire-compatible, not a 4-protocol translation
- dead swarm comms code (blackboard/handoff/spawn-successor) is removed (parallel-impl cleanup)

NON-GOAL this plan: instance↔instance peer/federation. That is a SEPARATE follow-on plan, viable only once this substrate proves out. (User decision 2026-06-09.)

* Grounding facts (verified in repo, 2026-06-09)

Four request/response mechanisms exist today, at four maturity levels:

| mechanism | file | transport | answer channel | maturity |
|-----------|------|-----------|----------------|----------|
| BlockingEvent | ~spell-server/socket/*~, ~web/ws/*~ | unix socket, JSONL | ✓ ~resolveEvent~ socket write-back (EXTERNAL sessions only) | live |
| AskBroker ~task:ask:*~ | ~coding-agent/task/ask-broker.ts~ | in-process shared object | ✓ parked Promise (in-process only) | live, tested (PLAN-327) |
| RPC stdio | ~spell-server/rpc/rpc-client.ts~ | child stdout JSONL | ✗ ~not_supported_for_spawned~ (web/ws/server.ts ~line 353) | live |
| PtcRuntimeClient | ~coding-agent/tools/ptc-runtime/client.ts~ | NDJSON, JSON-RPC 2.0 | ✓ id-correlated, bidirectional, per-call cancel, init-replay | MOST mature |

- ~EventBus~ (P0–P3 priority queue) is an OBSERVATION layer (drop-oldest, no delivery guarantee) — NOT a comms substrate, by design. Keep it as the observation tap.
- ~src/swarm/{blackboard,handoff-tool,spawn-successor-tool}.ts~: zero callers, zero tests, never registered. The "tried but never tested" comms attempt. AskBroker superseded it. DEAD.
- ~packages/swarm-extension/~: live + tested, but ORTHOGONAL (standalone YAML pipelines, filesystem comms, heavyweight subprocesses). Do NOT unify — different problem.
- BEAM today = execute-sandbox (~ptc_runner~) + Expert LSP ONLY. No plan to move orchestration/comms onto BEAM. ∴ a TS substrate is SAFE (BEAM won't obsolete it) and forward-aligned IF it mirrors the PtcRuntimeClient wire.

* The key insight — the primitive already exists, split across two files

#+begin_src
PtcRuntimeClient  ⊃  Transport{writeLine,onLine,onClose,close}  +  pending:Map<id,{resolve,reject}>  +  nextId
                     └─ the WIRE: id-correlated parked-promise over an abstract pipe. Transport is ALREADY the extraction seam.

                     └─ the SEMANTICS: request/response policy on top of a wire.

  Transport impls: in-process | child-stdio | unix-socket | (future) BEAM | (future) peer.
#+end_src

** Preliminary wire-extraction design (answers the "own folder?" question)

YES — the wire extracts cleanly. ~Transport~ is already an interface in client.ts decoupling correlation from the physical pipe. Proposed home:

#+begin_src
packages/coding-agent/src/comms/            ← new folder, single responsibility = the wire
  transport.ts        Transport interface (lifted verbatim from ptc-runtime/client.ts)
  request-broker.ts   RequestBroker: nextId + pending<id,{resolve,reject}> + per-call AbortSignal
                        + bidirectional reentrant-request handler + transparent-replay hook
  envelope.ts         { v, id, kind: "request"|"response"|"event", correlationId?, method?, params?, result?, error? }
                        (JSON-RPC-2.0-shaped, house style from PtcRuntimeClient + knowledge daemon {protocol_version})
  transports/
    in-process.ts     direct function-call Transport (for AskBroker's current zero-IPC case)
    child-stdio.ts    wraps a child's stdin/stdout (RPC path)
    (socket.ts later) unix-socket Transport (spell-server external path) — W3 may stub, full in follow-on
#+end_src

Responsibility split keeps PtcRuntimeClient as a CONSUMER of comms/ (it adds catalog/execute/tool_call semantics on top), and AskBroker becomes a consumer too. Neither owns the wire.
