** Settled Decisions
1. The plan uses one deduplicated recursive request shape: `code edit { operations: [{ targetId, actions: [...], children?: [...] }] }`.
2. `targetId` is graph/code-engine backed, stable across tool surfaces, and includes file roots in the same namespace as semantic symbols.
3. `content` remains the canonical replacement payload; patch semantics move into an action kind such as `findAndReplace` instead of remaining a separate top-level operation family.
4. Operations may contain nested child symbol work; target references appear once per node, and ordered actions execute sequentially inside that node.
5. Hard cutover only: remove old `create` / `patch` / `replace-body` / `replace` shapes from prompts, validation, callers, and results in the same change. No aliases.
6. Plan/output truth matters too: if org wave/manifests cannot truthfully represent the new dependency DAG, the implementation may remediate that tooling gap in-scope rather than leaving planning inconsistent.

** Brief Tradeoff Analysis
- Recursive node schema vs flat normalized graph:
  - Recursive nodes preserve deduplication while remaining legible to agents and humans.
  - Flat normalized records are easier for generic tooling but duplicate coordination data in practice and are harder to author by hand.
- Recursive node schema vs full entity tables:
  - Entity tables maximize normalization but impose unnecessary ceremony for a tool call payload.
  - The tool contract should be deduplicated by default, not database-shaped.
- ∴ Recommended approach: recursive node schema with stable `targetId` references.
