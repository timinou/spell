* Initial Message

I want to set up task policies in kdl with a command when I enter a new repository. like some sort of onboarding thing. what could that look like? finish with your completed summary

* Context

** Problem
Spell has no onboarding story. When you enter a new repo, there is no =spell init=. Task policies — one of the most powerful features (automatic gate injection per layer) — require manually creating =.spell/task-policies.yml= with an undocumented YAML schema. Domain selection requires a separate =.spell/domain.json=. Configuration is scattered across multiple files with no unified entry point.

** Approach: spell.kdl as the project manifest
Introduce =spell.kdl= at the project root as the single entry point for project configuration. It replaces =.spell/domain.json= (domain selection) and =.spell/task-policies.yml= (policy definitions) with a unified KDL file that reads like documentation:

#+begin_src kdl
domain "coding"
import "spell.coding.typescript"

policy "api-quality" layer="api" {
    gate-commit true
    gate-cmd "bun test"
    verify-cmd "tsgo"
}
#+end_src

Three lines gets you full policies. The =import= system uses dot-namespaced references (=spell.coding.typescript=, =spell.growth.default=) to pull in built-in template files that provide default layers and policies for common project types.

=spell init= becomes the entry point — detects the project's language, frameworks, and actual toolchain (test runner, type checker, linter), picks the right template, and generates =spell.kdl= with real gate commands from the detected toolchain.

** Key Decisions
- *File location*: =spell.kdl= at project root (not inside =.spell/=) — visible, version-controlled, like =package.json= or =Cargo.toml=
- *Import namespace*: dot-notation (=spell.coding.typescript=) — module-style, extensible
- *Merge semantics*: imports provide base layers/policies; local declarations override by name (reuses existing =mergePolicies= logic)
- *Backward compat*: =spell.kdl= → =.spell/task-policies.kdl= → =.spell/task-policies.yml= fallback chain. Existing YAML configs keep working.
- *Domain deprecation*: =spell.kdl= =domain= node replaces =.spell/domain.json=. domain.json still works but logs a deprecation warning.
- *Detection scope*: Smart toolchain detection (test/check/lint commands) for coding projects only. Growth and other domains get template defaults.
- *Partial implementation*: A prior session created =task-policies-kdl.ts= (KDL parser), =init-cli.ts= (basic init), =commands/init.ts= (CLI class), and registered the init command in =cli.ts=. The executor should build on this, not start from scratch. =@bgotink/kdl= is already a dependency.

** What This Makes Possible
- *Zero-config onboarding*: =spell init= → working policies in seconds
- *Template ecosystem*: =spell.coding.typescript=, =spell.growth.default=, eventually user-defined templates
- *Single source of truth*: One file tells you everything about how spell is configured for this project
- *Smart gates*: Policies reference the project's actual test/check commands, not placeholders
- *Domain-aware*: Growth projects get content/analytics/outreach layers; coding projects get frontend/api/data layers
- *Composable*: Import a base template, override what you need, done
