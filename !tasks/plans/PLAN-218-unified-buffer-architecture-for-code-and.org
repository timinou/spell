* Context

The coding agent has two completely separate file editing systems that should be one:

1. *Code tool*: TypeScript → NAPI → Rust =pi-code-engine= (CodeBuffer with Rope + tree-sitter + dead LoroDoc CRDT). Buffer-managed, in-memory edits, explicit save. Supports TS, Rust, Python, Typst, Elixir.

2. *Org tool*: TypeScript =org-reader.ts= (line-state-machine parser) + =org-writer.ts= (line-array mutator) + partial Rust =pi-org-engine= (tree-sitter parser for 3 commands: editSection, graph, waves). No buffer management — reads from disk every time, writes via atomicWrite.

This causes:
- Duplicate parsers (TS line-state-machine AND Rust tree-sitter for the same org files)
- Fragile line-based text manipulation instead of structural AST edits
- No shared buffer state between code and org operations
- Dead CRDT adding failure modes to code edits (LoroDoc never merges, mirrors rope byte-by-byte)
- Global Mutex blocking all buffer operations across files

** Settled design decisions

1. *CRDT removal*: Strip LoroDoc from CodeBuffer. Undo/redo already works via separate History struct.
2. *Per-buffer locking*: =BufferRegistry= holds =RwLock<HashMap<PathBuf, Arc<Mutex<CodeBuffer>>>>= instead of =Mutex<BufferRegistry>=.
3. *Shared buffer registry*: Both =executeCodeBuffer= and =executeOrg= NAPI entry points share the same BufferRegistry static.
4. *Crate structure*: =pi-org-engine= depends on =pi-code-engine=, uses CodeBuffer for parsing, keeps domain logic (query, graph, item extraction).
5. *NAPI entry points*: Separate functions (=executeCodeBuffer=, =executeOrg=) sharing one BufferRegistry.
6. *TS elimination*: =org-reader.ts= and =org-writer.ts= die. =tool.ts= becomes thin adapter calling native ops.
