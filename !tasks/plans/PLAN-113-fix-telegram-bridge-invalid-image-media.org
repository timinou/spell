* Context
Telegram's file download API returns =application/octet-stream= as =Content-Type= for photo files. After the previous fix ([[id:BUG-133-telegram-bridge-imagecontentref-type-mis]]) aligned field names, image uploads now reach the Anthropic API but with an invalid =media_type= value. The API rejects any value outside ={image/jpeg, image/png, image/gif, image/webp}=.

The fix adds magic-byte detection and media type normalization in the Telegram bridge's =collectImages= function (=packages/spell-server/src/telegram/bridge/telegram-to-rpc.ts=). This is the right fix location because:
- The bridge is the entry point where external (untrusted) Content-Type headers arrive
- The Anthropic provider's unsafe cast (line 306 in =anthropic.ts=) is a separate concern — it should never receive invalid types from internal callers
- Magic-byte detection is robust: even if Telegram changes Content-Type behavior, the bytes are authoritative

Approach: TDD. Write failing tests for pure functions first, then implement, then wire in and add integration test.

Key files:
- =packages/spell-server/src/telegram/bridge/telegram-to-rpc.ts= — source of the bug, receives the fix
- =packages/spell-server/test/telegram/bridge.test.ts= — test file
- =packages/coding-agent/src/utils/mime.ts= — reference for magic byte signatures (do not modify)
- =packages/ai/src/providers/anthropic.ts= line 306 — the unsafe cast (out of scope for this plan)
