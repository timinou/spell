Why did Metis fail repeatedly?

* Context
The repeated “Metis failed” behavior in session `14ab6894eaa2d281` was a layered failure, not one defect. First, the session never launched a real `metis` agent; it substituted delegated `plan` and `oracle` subagents. Second, both delegated sessions died before the first tool call with Anthropic `401 Invalid bearer token`, so the failure happened at model startup, not during analysis. Third, the task layer rewrote that startup failure into a misleading missing-`submit_result` warning, which hid the real cause and made repeated failures look like a Metis/planning defect.

Recommended approach:
- Repair Anthropic delegated-session credential invalidation / refresh so a known-bad bearer token is not reused.
- Preserve the real pre-submit startup failure in task results instead of collapsing it into the generic missing-`submit_result` warning.
- Add constrained delegated-model fallback that only walks the already-allowed candidate list implied by agent/settings patterns; do not broaden into unrelated provider roulette.

Key decisions:
- Auth repair is isolated in `packages/ai` and lands before task-layer fallback.
- Failure surfacing is a separate task-layer fix so auth defects remain diagnosable even when fallback is unavailable.
- Fallback only applies to startup-time auth/provider-availability failures and only across pre-resolved allowed candidates.
- Adjacent quota/retry work already exists in `BUG-075-subagent-sessions-hang-30-minutes-on-pro` and `BUG-076-async-task-errors-not-surfaced-to-user-d`; this plan focuses specifically on auth-invalid startup failures and truthful fallback behavior.
