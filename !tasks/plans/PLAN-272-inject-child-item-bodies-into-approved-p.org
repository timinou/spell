* Context

When a PLAN item is approved via `exit_plan_mode`, the fresh executing session receives only the PLAN's own body (via `planContent` in `plan-mode-approved.md`) and a bare Execution Manifest with `[[id:…]]` links. Every linked FEAT/BUG/FUP body must be re-fetched by the executing agent via `org get` before it can act; when waves auto-seed todos, each `TodoItem.details` is empty so `task … todoRef` auto-derives a one-liner assignment — sniper-pattern fails.

`validatePlanItem` (at `packages/coding-agent/src/plan-mode/plan-validation.ts:163`) already loads every linked child's `{id, file, body, properties}` into `resolvedChildren: Map<string, ResolvedPlanChildItem>` for layer resolution, then discards the map. This plan plumbs that existing data through to:
1. The approved-plan prompt template via a new `## Child Item Specifications` section (FEAT-601-inject-linked-child-org-bodies-into-appr).
2. The `TodoItem.details` of each wave-seeded todo via a new sub-outline slicer (FEAT-602-seed-todos-from-waves-with-owning-child).
