* Context
`org wave` and `org graph` are failing recurrently in plan mode with `Emacs MCP error -32603: Internal error`.

Verified root causes in the current repo state:
- `packages/emacs/src/daemon.ts` caches Emacs sessions by `hash(projectRoot + sessionId)` and ignores `socketPrefix`, so org callers can reuse the code-intelligence daemon instead of starting an org daemon.
- The reused `spell-emacs-*` daemon only exposes code tools; a direct socat call in this session returned `Tool not found: org-next-wave`.
- `packages/org/src/tool.ts` still uses one-shot `emacsSessionPromise` / `orgClientPromise` caching, so org-side startup failures do not get the circuit-breaker + lazy-restart semantics already implemented in `EmacsSessionManager`.
- `packages/org/test/tool-wave-graph.test.ts` currently encodes a false contract: `category` resolves to a directory path and `no args` forwards empty args, even though the Elisp handlers are file-oriented and child items live in separate `.org` files.
- `packages/coding-agent/src/prompts/system/plan-mode-active.md` explicitly tells the planner to run `org wave` on a category, so the implementation and the planning prompt are out of sync.

Recommended approach
- Fix the daemon identity boundary first by scoping session caching by daemon flavor (`socketPrefix` or equivalent).
- Keep `EmacsSessionManager` as the lifecycle abstraction. It is not a thin `ManagedDaemon` wrapper; it owns warmup result ingestion, lazy restart, coalescing, and cooldown behavior. Reuse it for org callers instead of bypassing it.
- Add a dedicated org session manager path for org MCP consumers (`OrgTool`, `ExitPlanModeTool`, and any touched shared org-client entry point).
- Repair `wave`/`graph` so category / no-arg calls resolve to a truthful org target set that matches plan-mode usage across multi-file categories, then lock that behavior down with both TS tests and new ERT coverage.
