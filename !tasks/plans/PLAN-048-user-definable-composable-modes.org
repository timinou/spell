* Context

** Problem

Spell's modes (plan, ultraplan, design, audit, loop) are hardcoded in TypeScript with fixed prompts, fixed tool restrictions, and fixed lifecycle behavior. Non-technical cofounders (sales/marketing) cannot customize what the agent focuses on during planning or auditing, cannot add domain context that persists across sessions, and cannot create new workflow modes for their specific needs.

** Approach

Introduce a ~.spell/modes/<name>/MODE.md~ configuration system that makes modes fully user-definable and composable:

1. *MODE.md format*: YAML frontmatter (structured config) + markdown body (prompt content parsed by ~##~ headings into named sections: Context, Instructions, Focus Areas, Examples, and phase-specific sections for loop integration).

2. *Composition via extends*: Single-parent inheritance. ~extends: plan~ merges parent config with child overrides. Child frontmatter wins for scalars, replaces arrays, deep-merges objects. Body sections concatenate (parent then child).

3. *Hybrid migration*: Built-in modes keep their TypeScript lifecycle code AND gain MODE.md-like prompt definitions in ~packages/coding-agent/src/modes/definitions/~. User modes with ~extends: plan~ inherit the prompt definition; the TS lifecycle code handles enter/exit/guards.

4. *Wave-based execution*: Plans created within user-defined modes support the wave decomposition system. Mode configs can customize the execution prompt (~plan-mode-approved.md~) that drives wave-based todo initialization.

** Key Decisions

- *Directory-per-mode*: ~.spell/modes/<name>/MODE.md~ (not flat files), supports QML overlays and reference docs.
- *Discovery*: Project-level (~.spell/modes/~) and user-level (~~/.spell/agent/modes/~). Project overrides user.
- *Tool control*: ~tools.allow~ or ~tools.deny~ (mutually exclusive) resolved through extends chain.
- *TODO integration*: Phase templates, starter tasks, gate presets. Wave-derived phases override ~todo.phases~ when waves exist.
- *State transitions*: Simple/chained/nested. Context policies: fresh/carry/summarize.
- *Canvas*: Companion windows (~ui.canvas~). Canvas-primary (~ui.primary: 'canvas'~) routes output to canvas.
- *Loop*: Phase prompts customizable via ~## Plan Phase~ etc. Pipeline hardcoded. Dashboard monitoring first.
- *Audit*: ActiveModeState variant. Custom focus/maxDepth/escalation.
- *Execution*: ~plan-mode-approved.md~ gets ~{{#if modeExecutionInstructions}}~ extension points.
- *exit_plan_mode to exit_mode*: ~{{exitToolName}}~ provides indirection. User modes extending plan run extractPlanWaves.

- *FEAT-129 (Canvas Integration) BLOCKED*: Canvas spawning and canvas-primary routing require QML bridge infrastructure. Core mode system works without it. The ~ui.canvas~ and ~ui.primary~ frontmatter fields are defined in types but not wired at runtime.
- *Context policies runtime*: The ~contextPolicy~ field (fresh/carry/summarize) is defined in types and parsed but runtime execution (compaction, session clearing) is deferred. The infrastructure (mode stack, afterComplete) is in place.
- *Full chained transition runtime*: afterComplete field is parsed and persisted. The transition dispatch at mode exit (checking afterComplete and entering next mode) is scaffolded but not fully wired.
- *Starter task instantiation*: todo.phases are defined in types and parsed. The prompt instructions for wave-based todo initialization exist. Automatic pre-population of todos on mode activation is deferred.
- *Exit tool rename*: exit_plan_mode was NOT renamed to exit_mode. The plan called for this but it would break the existing tool contract. Instead, the tool uses ~{{exitToolName}}~ template indirection which already provides the abstraction.
