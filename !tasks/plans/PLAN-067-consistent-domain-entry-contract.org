* Context
** Problem
Domain startup semantics are currently inconsistent across the available entry paths. Today the codebase has at least three distinct knobs: domain selection (=--domain= or =.spell/domain.json=), surface selection (=--canvas=), and the default root command. The user expectation for this follow-up is explicit: selecting the growth domain should auto-open the growth UI on interactive startup, yet the CLI also needs one obvious canonical command for starting a domain directly.

** Recommended approach
Adopt one contract:
- Domain selection (=--domain growth= or project =.spell/domain.json=) controls *which domain is active*.
- For interactive sessions, an active domain may choose a preferred UI surface; for growth this means auto-opening the domain UI when a display is available.
- If no display is available, interactive startup falls back to the normal TUI instead of failing.
- Explicit domain entry becomes =spell domain <name>=, with =spell growth= as a convenience alias for the growth domain.

This keeps policy selection, startup routing, and user-facing commands aligned instead of leaving each path to imply different behavior.

** Key decisions
- =spell domain growth= is the canonical explicit command; =spell growth= is a convenience alias.
- =--domain growth= and =.spell/domain.json= keep identical runtime semantics; the CLI flag only overrides which domain is active.
- Growth auto-opens its domain UI only for interactive sessions with a graphical display.
- No-display interactive runs fall back to the TUI; =-p= and =--mode rpc= remain non-UI.
