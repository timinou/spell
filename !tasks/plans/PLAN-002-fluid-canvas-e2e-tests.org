* Product Promises

The fluid canvas feature makes these user-facing promises:

1. ~--canvas~ flag defaults to ~fluid~; ~--canvas chat~ routes to existing QML shell
2. ~--canvas invalid~ produces a clear error message
3. FluidShell.qml launches and shows a centered text input field
4. User types a prompt, presses Enter -> it reaches TS as ~{type: \"prompt\", text}~
5. Planning state shows a loading indicator (\"Planning...\")
6. After plan completes, agent panels appear for each agent in the DAG
7. Agent panels show state transitions: pending -> ready -> running -> completed/failed
8. Agent stream text appears in panels during execution
9. Canvas outputs (markdown, table, diff, tree, log) render in panels after completion
10. QueueInspector shows progress (X/Y agents completed)
11. Failed agents show failure state (red indicator)
12. Failed dependencies cascade -- downstream agents are marked failed
13. Execution complete state is shown
14. Plan errors show an error message and allow recovery (re-prompt)
15. Settings ~fluid.concurrency~ and ~fluid.fastPlan~ are respected

* Discovered Bugs (fix alongside tests)

** BUG-1: FluidShell.qml never handles ~fluid:plan_error~

~FluidShell.qml~ ~onMessageReceived~ checks for ~fluid:plan_start~, ~fluid:plan_complete~, ~fluid:execution_complete~, and agent events. There is *no case* for ~fluid:plan_error~.

Meanwhile, ~fluid-mode.ts~ emits ~fluid:plan_error~ on 3 error paths via the event router.

*Impact*: If the planning agent fails, the user sees the BusyIndicator forever. The shell is stuck in ~planning~ state with no recovery path.

*Fix* (4 concrete steps in ~FluidShell.qml~):

1. Add ~property string lastError: \"\"~ to the root ApplicationWindow properties.
2. In ~onMessageReceived~, add a case for ~fluid:plan_error~:
#+begin_src javascript
if (payload.type === \"fluid:plan_error\") {
    root.lastError = payload.error ? String(payload.error) : \"Planning failed\"
    root.state = \"input\"
    return
}
#+end_src
3. Add a ~Text~ element in the input state ~ColumnLayout~ (below the ~TextField~, above the ~Button~) that shows ~lastError~ in ~SpellTheme.error~ color, ~visible: lastError.length > 0~, with ~wrapMode: Text.WordWrap~.
4. Clear ~lastError~ at the start of ~submitPrompt()~: ~root.lastError = \"\"~.

- File: ~packages/coding-agent/src/modes/qml/FluidShell.qml~

** BUG-2: ~canvas_output~ events arrive after ~execution_complete~

In ~fluid-mode.ts~, ~orchestrator.execute()~ resolves *after* ~QueueScheduler~ emits ~execution_complete~ (line 61 of queue-scheduler.ts). Then ~fluid-mode.ts~ loops over results and enqueues ~canvas_output~ events. The QML side transitions to ~state='complete'~ on ~execution_complete~, but canvas outputs arrive later.

*Impact*: \"Execution complete\" banner flashes before canvas output panels render. The drain timer is already stopped in the ~finally~ block, so events may stall.

*Fix* (3 concrete steps):

1. In ~fluid-orchestrator.ts~, modify the ~onEvent~ callback inside ~execute()~ to intercept ~agent_state_change~ events with ~state === \"completed\"~. Look up the node in ~plan.agents~ by ~agentId~. If the node has ~canvasOutput~ and the event has a ~result~, enqueue a ~canvas_output~ event on ~FLUID_EVENT_CHANNEL~ immediately after forwarding the state_change:
#+begin_src typescript
onEvent: event => {
    this.#eventBus.enqueue(FLUID_EVENT_CHANNEL, event, Priority.P1);
    // Emit canvas_output right after completed state_change, before execution_complete
    if (event.type === \"agent_state_change\" && event.state === \"completed\" && event.result) {
        const node = plan.agents.find(a => a.id === event.agentId);
        if (node?.canvasOutput) {
            this.#eventBus.enqueue(FLUID_EVENT_CHANNEL, {
                type: \"canvas_output\",
                agentId: event.agentId,
                outputType: node.canvasOutput.type,
                title: node.canvasOutput.title,
                content: event.result.output,
            }, Priority.P1);
        }
    }
},
#+end_src
2. Remove the for-loop in ~fluid-mode.ts~ (lines ~102-116) that emits ~canvas_output~ after ~orchestrator.execute()~ returns. This loop would now double-emit.
3. Remove the now-unnecessary ~await eventBus.drain()~ call that followed that loop.

- File: ~packages/coding-agent/src/orchestrators/fluid/fluid-orchestrator.ts~
- File: ~packages/coding-agent/src/modes/fluid-mode.ts~
