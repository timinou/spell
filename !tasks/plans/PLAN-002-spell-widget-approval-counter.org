* Problem

The Spell widget in DankMaterialShell shows a combined ~actionableCount~ for ~needs_input~ and ~pending_approval~, but ~pending_approval~ never actually appears because of a bug in spell's niri status notification.

** Bug: ~pending_approval~ status is never written to disk

In ~packages/coding-agent/src/modes/interactive-mode.ts~, the plan approval flow sets ~isPendingApproval = true~ (line 1039), then awaits ~showHookSelector~ (line 1040), then sets it back to ~false~ (line 1041).

The niri controller (~packages/niri/src/controller.ts~) learns about state changes via ~context.subscribe()~, which wraps ~session.subscribe()~ — a listener on ~AgentEvent~ emissions from the agent session. But after setting ~isPendingApproval = true~, no session event fires (the agent is paused waiting for the selector). The niri controller never sees the change, so ~pending_approval~ is never written to ~\~/.spell/status/<id>.json~.

Contrast with ~needs_input~: that status is derived from ~onInputCallback~ which is set when the session's main loop yields, coinciding with agent events. And ~isAwaitingHookInput~ (hook selectors during streaming) works because events keep flowing while streaming. ~pending_approval~ is the one case where the flag is set at a quiet moment with no events.

** Root cause

~NiriOverviewContext.subscribe~ only fires on ~AgentEvent~ from the session. Interactive-mode-level state changes (~isPendingApproval~, and potentially ~isAwaitingHookInput~ in non-streaming scenarios) have no notification path to the niri controller.
