* Context
Post-implementation audit (cycle 1) of PLAN-085 found 5 defects. The most critical: =ResponseStreamer.done= can hang forever when the RPC lifecycle fails before emitting terminal events, blocking cleanup in both the main message flow and =/btw=. Additionally, every message leaks an event listener on the shared RPC client, respawned sessions lose the Telegram system prompt, and photo/document-only messages are silently dropped despite the bridge already supporting them.

** Approach
Test-first: each bug-fix item writes failing tests that demonstrate the defect, then implements the fix to make them pass. Three items, two waves.

1. *Wave 1* (sequential — shared =bot.ts=): BUG-090 writes tests for =cancel()=/=offEvent()= and the finalize-throw scenario, then implements. BUG-091 writes tests for respawn prompt propagation, then implements =CommandContext= changes + message guard loosening.
2. *Wave 2*: BUG-092 writes message handler integration tests that verify already-fixed behavior (should pass immediately).

** Key Decisions
- =ResponseStreamer= gets a public =cancel(): void= that idempotently resolves =done=. Callers use it in catch/finally paths. =#finalize()= and the error handler use try/finally so =#doneResolve()= always runs.
- =RpcClient= gets =offEvent(callback)= for listener removal. The message handler stores its listener ref and removes it after the streaming cycle.
- =telegramPrompt= moves into =CommandContext= so all command handlers (including =respawnSession=) have access. This simplifies =createMessageHandler= from 3 params to 1 (=cmdCtx=).
- The message guard is loosened: messages with =text=, =photo=, or =document= are accepted. Other message types (stickers, voice, etc.) pass to =next()=.
- =createMessageHandler= is exported for direct testing. Tests verify the wired pipeline: mock context → process manager → streamer → reply.
