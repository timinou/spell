* Context

The =emacs_code= tool provides structural code intelligence via an Emacs daemon running treesit + combobulate. It's a powerful complement to LSP — operating directly on AST structure for any tree-sitter supported language without needing a language server. However, it's currently underused due to several issues:

1. *Limited built-in language coverage.* Only 15 languages are hardcoded across three separate tables (grammar sources in pi-prelude.el, extension→lang and extension→mode in pi-treesit.el). Adding a new language requires editing all three files.

2. *No introspection or management commands.* There's no way to see what languages are available, which grammars are installed, or install new ones at runtime.

3. *Low tool priority.* Classified as "standard" tier (same as fetch, web_search) and ordered near the bottom of the tool list, after org.

4. *Sparse description.* The one-liner description doesn't convey capabilities or differentiation from LSP.

** Approach

Adopt a recipe-based language system adapted from [[https://github.com/renzmann/treesit-auto][treesit-auto]] (GPLv3, compatible with our license). This replaces three hardcoded tables with a single recipe list covering 50+ languages. We extract only the recipe data (grammar URLs, extensions, modes, dependencies, ABI compat revisions) — not treesit-auto's mode-remap or interactive installation logic, which our daemon architecture handles differently.

Add =languages= and =install_grammar= subcommands so the agent can introspect and extend language support at runtime.

Promote to core tier and improve the description.

** Daemon management audit result
Both emacs_code and org tools share the same daemon infrastructure: =EmacsSessionManager= (circuit breaker, lazy restart, concurrent-call coalescing) → =ManagedDaemon= (postmortem registration, health timer, graceful shutdown, socket probe). Two previous bugs (isAlive check, session recovery) are already DONE. The emacs_code daemon management is on par with the org tool. No gaps found.

** How to make emacs_code more prominent (meta-information)
The tool's prominence is controlled by several levers:
- *Tier* (TOOL_TIERS in tools/index.ts): "core" tools get full descriptions; "standard" get full; "specialized" get compact one-liners. Promoting to "core" ensures the description is always shown.
- *BUILTIN_TOOLS ordering* (tools/index.ts): Dict iteration order determines prompt ordering. Moving emacs_code earlier puts it closer to the top of the tool list the agent sees.
- *Description quality* (tool.ts): The description string is what the agent reads in its system prompt. A better description = better tool selection by the agent.
- *System prompt rules*: The AGENTS.md "Procedure" section and tool precedence rules can mention emacs_code. The current system prompt mentions LSP and ast_grep but not emacs_code.
