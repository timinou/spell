* Problem

The QML integration test suite proves protocol compliance in isolation but does not prove that ~spell --qml~ works as a user experience. Specifically:

- Messages are never verified through shell.qml's Loader routing
- Typing/clicking is tested in isolated ChatPanelTestHarness, never through the production shell
- The pending message queue (last-write-wins per panel) is never exercised
- Armed tool round-trips (_tool/_rid) are never triggered
- Error conditions (Loader failure, malformed messages) are never tested
- Panel lifecycle (add/remove/replace, state destruction on switch) is never verified

Two gaps are acknowledged as structurally untestable with current infrastructure:
- Daemon/socket mode (production uses Unix socket; tests use stdio)
- Multi-client bridge (requires daemon mode)

* Metis Findings (incorporated)

** Panel state is NOT preserved — Loader destroys components
The ~Loader~ uses a reactive ~source~ binding. When ~activePanelIndex~ changes, the old component is destroyed entirely. ChatPanel's ~messagesModel~ is gone. Gap #3 must test destruction, not preservation.

** Pending queue is last-write-wins, not FIFO
~pendingPanelMessages[panelId] = payload~ overwrites previous. Only the LAST ~dashboard_update~ per panel survives. Tests must verify overwrite semantics.

** Armed tools require 6-hop UI chain
~Loader → ChatPanel → ListView → MessageDelegate → AssistantBubble → MarkdownContent → CodeBlock~. Build incrementally: first verify render, then attempt click. Capture rendering failures as distinct from tool invocation failures.

** No reset protocol in shell.qml
~reset()~ only works with ChatPanelTestHarness. Shell tests use evaluate-based cleanup between tests or fresh journey instances.

** Non-dashboard messages to inactive panels are silently dropped
Only ~dashboard_update~ is queued. All other types are lost when their target panel is inactive.

* Momus Review Fixes (incorporated)

** F1: Armed tools save button is fire-and-forget (no _rid)
~onCodeSaveRequested~ sends ~{_tool:"write", path, content}~ with NO ~_rid~. The ~_rid~ pattern only exists on ~onLinkActivated~ for file:// links: ~{_tool:"read", _rid:"preview-"+Date.now(), path}~. Test #2 (save button) verifies fire-and-forget. Test #3 (_rid round-trip) uses ~evaluate()~ to trigger ~bridge.send~ directly, bypassing the rendering chain.

** F2: shell-chat-input reduced to 2 tests (not 4)
~chat-input-interaction.test.ts~ already covers all 4 scenarios (type+Return, click send, abort, empty input) via ChatPanelTestHarness. shell-chat-input only adds value by proving input works through the shell Loader. Two tests suffice: (1) type+Return → prompt event, (2) abort button during streaming → abort event. "Empty input blocked" and "prompt in messagesModel" are already proven.

** F3: resetShell() needs waitUntil confirmation
After setting ~activePanelIndex = 0~, must wait until ~panelLoader.item~ is non-null and has ~messagesModel~ before clearing. Add ~waitUntil~ loop + settle. Document that resetShell only works when resetting TO chat panel (index 0).

* Test Isolation Strategy

Each test file creates ONE ~QmlJourney~ in ~beforeAll~, tears down in ~afterAll~. Between tests, evaluate-based cleanup with confirmation:

#+begin_src typescript
async function resetShell(journey: QmlJourney): Promise<void> {
  // Reset to chat panel (index 0)
  await journey.evaluate("root.activePanelIndex = 0");
  // Wait until Loader has loaded ChatPanel and item is ready
  await journey.waitUntil(async () => {
    const hasItem = await journey.evaluate<boolean>(
      "panelLoader.item !== null && typeof panelLoader.item.messagesModel !== 'undefined'"
    );
    return hasItem || null;
  }, 2000);
  // Now safe to clear chat state
  await journey.evaluate("panelLoader.item.messagesModel.clear()");
  await journey.evaluate("panelLoader.item.isStreaming = false");
  // Clear pending queue
  await journey.evaluate("root.pendingPanelMessages = ({})");
  await journey.settle(50);
}
#+end_src

Note: resetShell only works when resetting TO chat panel (index 0, ChatPanel.qml). If the active panel is something else, the messagesModel/isStreaming clears target the wrong panel type.

For tests that mutate the panel list (add/remove), use a nested ~describe~ with its own journey.

#+begin_src typescript
async focusInput(): Promise<void> {
  const elements = await this.observe();
  const textEdit = elements.find(e => e.className.startsWith("QQuickTextEdit"));
  if (textEdit) {
    await this.clickId(textEdit.id);
    return;
  }
  const flickable = elements.find(e => e.className.startsWith("QQuickFlickable"));
  if (!flickable) throw new Error("No TextEdit or Flickable found for input focus");
  await this.clickId(flickable.id);
}
#+end_src

*submitPrompt(text):* Type a message and press Return. Sets up waitForBridgeEvent BEFORE pressing Return to avoid race. Returns captured prompt payload.
#+begin_src typescript
async submitPrompt(text: string): Promise<Record<string, unknown>> {
  await this.focusInput();
  await this.#harness.type(text);
  await this.#harness.settle(this.#settleMs);
  const eventPromise = this.#harness.waitForBridgeEvent(
    e => e.type === "event" && (e as any).payload?.type === "prompt",
    5000,
  );
  await this.#harness.press("Return");
  const ev = await eventPromise;
  await this.#harness.settle(this.#settleMs);
  return (ev as any).payload;
}
#+end_src

*expectPanelActive(id):* Retry-based assertion on active panel id.
#+begin_src typescript
async expectPanelActive(id: string): Promise<void> {
  await this.#harness.waitUntil(async () => {
    const activeId = await this.evaluate<string>(
      "root.panels[root.activePanelIndex].id"
    );
    return activeId === id || null;
  }, this.#assertTimeout);
}
#+end_src

*waitUntil(fn, timeout):* Expose harness waitUntil for resetShell and custom assertions.
#+begin_src typescript
async waitUntil<T>(fn: () => Promise<T | null | false>, timeout?: number): Promise<T> {
  return this.#harness.waitUntil(fn, timeout ?? this.#assertTimeout);
}
#+end_src

* Gaps NOT Covered (infrastructure limitations)

- *Daemon/socket mode*: Production uses Unix socket to persistent daemon. Tests use stdio+offscreen. Protocol is identical but connection lifecycle (reconnect, state snapshot) is untestable without a real daemon.
- *Multi-client*: Bridge daemon supports multiple concurrent socket clients. Requires daemon mode to test.
- *Visual rendering fidelity*: Offscreen mode renders but does not display. Screenshots exist but visual layout verification (colors, alignment, overflow) requires human review or pixel comparison.
- *Hot reload*: ~QmlBridge~ watches files and calls ~reload()~. Requires filesystem watch integration test with real file changes.
