In that session and in a few others, running momus leads to \n\n being added instead of new lines. Can you trace why?

* Context

** Problem
When the LLM uses =org update= with =section= to revise plan items (especially after Momus
review), the body parameter contains literal =\n= characters instead of actual newlines. This
produces org files with =\n= text on a single line instead of properly formatted multi-line
content.

Two independent bugs compound to create the observed behavior:

1. *LLM generates literal =\n= in JSON tool call arguments* — The plan-mode prompt example
   (line 67 of =plan-mode-active.md=) shows the body as a single-line string with =\n=
   separators. The LLM mimics this pattern and double-escapes the =\n= in JSON, producing
   literal backslash-n in the string value. The =formatOrgResult= fallback using
   =JSON.stringify= reinforces this pattern in tool results.

2. *Emacs section edit does not replace sub-headings* — The =org-tasks--edit-section-headline=
   function in replace mode only deletes text before the first sub-heading, then inserts the
   new body. When the new body contains sub-headings (which it always does for plan sections),
   they get inserted before the existing sub-headings, creating duplication. Combined with
   Bug 1 (literal =\n=), the entire new body becomes a single long line with =\n= text
   followed by the original properly-formatted sub-headings.

** Approach
Four targeted fixes, ordered by impact:

1. *Body normalization in org tool* (critical) — Convert literal =\n= / =\t= to real newlines/tabs
   before any consumer sees the args.
2. *Section edit full replace* (critical) — In replace mode, delete the entire section content
   including sub-headings, not just the preamble.
3. *Prompt example cleanup* (preventive) — Remove =\n= from the body example in the plan-mode
   prompt.
4. *formatOrgResult cleanup* (secondary) — Replace JSON.stringify fallback with human-readable text.
