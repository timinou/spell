* Context

** Problem
~atomicWrite~ in ~packages/org/src/atomic-write.ts~ uses a deterministic tmp path (~${filePath}.tmp~).
When two concurrent async operations target the same org file, they share the same ~.tmp~ path.
The interleaving that causes ENOENT:

1. Op A writes content-A to ~X.org.tmp~
2. Op B overwrites ~X.org.tmp~ with content-B
3. Op A renames ~X.org.tmp~ -> ~X.org~ (succeeds, but moves B's content — silent corruption)
4. Op B renames ~X.org.tmp~ -> ~X.org~ — ENOENT because ~.tmp~ is already gone

This affects all org write paths: ~appendItemToFile~, ~applyItemMutations~, ~setPropertyInFile~,
~initCategoryDir~, and ~writeJournal~. The plan-mode system prompt explicitly encourages parallel
~org create~ via task subagents (plan-mode-active.md line 219), making concurrent writes a normal path.

Beyond ENOENT, concurrent read-then-write cycles cause silent data loss: two operations read the
same file state, compute independent mutations, and the second write overwrites the first.

Additionally, ~generateId~ in ~cmdCreate~ scans files for max sequence numbers non-atomically.
Two concurrent creates in the same category can generate duplicate sequence numbers. (This is
directly observable: the BUG items in this plan both got sequence number 001.)

** Approach
Three-layer fix, all within ~packages/org/~:

1. *Unique tmp paths*: Change ~atomicWrite~ to use ~${filePath}.${crypto.randomUUID().slice(0, 8)}.tmp~.
   Add try/finally to clean up orphan tmp files on failure.

2. *Per-file write serialization*: Add in-process ~AsyncMutex~ + ~KeyedMutex~ (~Map<string, AsyncMutex>~).
   Wrap ~appendItemToFile~, ~applyItemMutations~, ~setPropertyInFile~ with per-file locks.

3. *Per-category ID serialization*: In ~cmdCreate~, wrap ~generateId~ + ~appendItemToFile~
   in a per-category-path mutex so sequence scan + file write are atomic.

** Key decisions
- In-process mutex (not filesystem locks). Sufficient because org tool runs single-process.
  The existing ~packages/coding-agent/src/config/file-lock.ts~ uses fs-level mkdir locks but
  that's heavier than needed and would add cross-package dependency.
- ~AsyncMutex~ uses Promise-chain pattern with ~Promise.withResolvers~, matching project conventions.
  The existing ~Semaphore~ in ~packages/coding-agent/src/task/parallel.ts~ is count-based, not
  a fit for serialization.
- Journal writes (~writeJournal~) are already best-effort with try/catch — unique tmp fix alone
  is sufficient; no mutex needed since journal files are session-scoped and full-rewrite.
- ~initCategoryDir~ race is benign (both writes produce identical content) — unique tmp fix
  alone is sufficient.
- Lock ordering is always category -> file (never reversed). ~cmdCreate~ acquires category lock,
  then ~appendItemToFile~ internally acquires file lock. No other code path reverses this.

** Edge cases the fix must handle correctly
1. *Lock release on error*: If locked function throws, lock MUST release. Permanent block = all
   subsequent ops on that key hang forever. ~withLock~ must use try/finally.
2. *Nested lock no-deadlock*: ~cmdCreate~ holds category lock, calls ~appendItemToFile~ which
   acquires file lock. Lock ordering is consistent (category -> file). No reverse path exists.
   ~cmdUpdate~/~cmdNote~/~cmdSet~ acquire only file lock, never category lock.
3. *Null-return operations release promptly*: ~applyItemMutations~ returns null when item not found.
   Lock must release immediately, not hold while fallback scan continues.
4. *Orphan tmp cleanup*: Unique tmp suffixes mean failed writes leave uniquely-named orphans.
   ~atomicWrite~ finally block must unlink the tmp file if rename didn't succeed.
5. *Different-key parallelism preserved*: ~KeyedMutex~ must not accidentally serialize different
   file paths or different category paths.
