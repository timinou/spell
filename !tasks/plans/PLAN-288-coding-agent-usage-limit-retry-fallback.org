* Context
User reported that provider 429 errors in session =14cc69946fb52683= create a 30 minute retry window. Investigation found:
- The coordinator root log starts/awaits child jobs; provider errors are in child logs under the session artifact directory.
- Current wave-5 examples: =37-W5ToolKbProofsDock.jsonl= and =38-W5DeleteDeadRuntime.jsonl= each recorded Kimi =429 rate_limit_error= around 19:35/19:36.
- Earlier wave-2 proof: child logs =9-W2PreservePortBindings.jsonl=, =11-W2NotificationsRewrite.jsonl=, =12-W2MappingTestsAndService.jsonl=, =13-W2MappingEditorUi.jsonl=, =15-W2DockAttachAndUi.jsonl=, =16-W2KbUploadTests.jsonl=, and =17-W2BenchmarkRemoveFakeDefault.jsonl= show attempt 1 around 15:09 and attempt 2 around 15:39.
- Code chain: =AgentSession.#handleRetryableError= → =parseRateLimitReason= → =calculateRateLimitBackoffMs= → =AuthStorage.markUsageLimitReached= → =abortableSleep(delayMs)=.
- Parser misses snake-case =rate_limit_error= and then sees provider prose containing =quota=, producing =QUOTA_EXHAUSTED= → 30m.
- Subagents currently do not have a policy boundary preventing long usage-limit sleeps.

Settled design decisions:
1. Explicit 429 rate-limit tokens (=rate_limit_error=, =rate_limit_exceeded=, =rate-limit=, =rate limit=, “too many requests”) classify as =RATE_LIMIT_EXCEEDED= before quota prose.
2. True billing-cycle/quota exhaustion remains =QUOTA_EXHAUSTED= for credential-blocking semantics.
3. Subagents must never sleep 30m for provider usage-limit/quota errors.
4. Runtime order for subagents: same-provider credential rotation → configured fallback model role → short capped transient retry → fail fast for quota/unknown exhaustion.
5. Fallback model selection is role-based/configured, not arbitrary first available model.
6. Top-level interactive sessions preserve existing long quota wait behavior unless a future user request changes it.
