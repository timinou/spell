* Context
Problem:
- Current spill behavior is effectively tuned for very large outputs (`DEFAULT_MAX_BYTES = 50 KB`, `tools.artifactSpillThreshold = 50`), so many test runs, git inspection commands, and remote status/log calls stay inline long enough to leak into the next LLM request.
- `.local/token-usage/token-usage-review.data.js` shows the target bash leak classes (`tests`, `git inspection/staging`, `remote logs/status`) account for ~40.8M / 73.9M bash shared tokens and ~496k estimated input-leakage tokens across 30 recent sessions (~16.5k input tokens per session on average).
- Existing code already has the right primitives — session artifacts, `artifact://` routing, `wrapToolWithMetaNotice()`, `OutputSink`, and bash-side internal URL expansion — but the defaults and trigger model are too lenient.

Settled design decisions:
1. Lower the default spill policy aggressively for non-precision tools: spill at 2.5 KB or 50 lines; keep 1 KB / 50 lines inline on success.
2. Preserve a slightly larger failure inline budget: 5 KB / 120 lines after spill.
3. Keep precision inspection/edit/query tools exempt from the low-spill default: `read`, `grep`, `org`, `find`, `code`, `lsp`, `ast_grep`, `ast_edit`.
4. Reuse existing `artifact://` follow-up workflows instead of inventing a second analysis path.
5. Add a bash-only explicit per-call override `lenientSpill` with a visible warning; no sticky session toggle.
6. Unify wrapper-level and streaming-tool spill behavior so the legacy 50 KB shell defaults stop bypassing the intended policy.
