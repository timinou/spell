* Context

The =code outline= tool crashes with =Symbol's function definition is void: t= on any
Elixir (.ex/.exs) file. Two separate bugs in ~packages/emacs/elisp/pi-treesit.el~:

1. *Paren mismatch* in ~pi-treesit-declaration-kind~ (lines 366-367):
   The outer cond catch-all ~(t type)~ is accidentally inside the =call= clause body.
   When the =call= branch matches (all Elixir files), it evaluates ~(t type)~ as a
   function call, crashing because =t= has no function definition.

2. *Arguments field lookup* in ~pi-treesit-declaration-name~ (~line 300):
   Uses ~treesit-node-child-by-field-name node \"arguments\"~ but tree-sitter-elixir does
   not assign a field name to the =arguments= child (it has =field=nil=). Returns nil
   for all Elixir nodes, producing empty outlines even after the paren fix.

Additionally, 3 pre-existing ERT tests (yaml, toml, json) in ~test-outline.el~ fail due
to ~let~ vs ~let*~ scoping — they reference a binding before it's available.

*** Deviations

Additional bugs discovered and fixed during implementation:
1. *Paren mismatch in pair branch* (pi-treesit-declaration-name line 287): The =pair= cond clause was missing its closing paren, causing =table=, =call=, and catch-all branches to be parsed as part of the =pair= body. This was the root cause of declaration-name returning nil for ALL non-pair types that follow the pair branch (including Elixir call nodes). Fixed by adding the missing close paren.
2. *YAML block_node not in unwrap list* (pi-treesit--top-level-nodes-children): YAML =block_mapping_pair= nodes are inside =block_node= which wasn't being unwrapped. Added =block_node= to the unwrap list and to the allowed grandparent types in the =block_mapping_pair= name check.
3. *TOML table children not returned*: Table node was returned but its child =pair= nodes were not. Added a keep-and-unwrap mode for =table= nodes using named children only.
4. *TOML pair key field missing*: tree-sitter-toml =pair= nodes have no =key= field name (unlike JSON). Added fallback to first named child.
5. *Markdown let/let* scoping*: Same let->let* bug existed in the markdown test.
