** Settled Decisions
1. Start with full product-surface HTML + CSS support, not HEEx-first and not broad-SFC-first. HTML/CSS become first-class semantic languages; HEEx reuses the host/guest substrate next.
2. Extend the existing engine DSL instead of adding parallel HTML/CSS-specific walkers. The design center is: one affordance vocabulary → many languages.
3. CSS v1 covers plain CSS selectors, custom properties, cascade/override reasoning, `@media`, `@supports`, and `@keyframes`. Utility frameworks are explicit follow-up work.
4. Graph semantics should gain first-class style nodes/edges and confidence/provenance instead of overloading everything onto generic reference edges.
5. Refactors stay conservative by default. Provable class/id/custom-property renames and proof-backed dead-style removal may mutate; uncertain selector/cascade cases must explain and refuse.
6. The test suite must be impeccable: fixture-driven, cross-layer, regression-focused, and explicit about degradation/ambiguity. Every item includes required workflows and edge cases in its body.
7. `org wave` was run during planning, but the current tool output did not isolate this session’s subset cleanly; the execution waves below mirror the explicit child-item `DEPENDS` DAG for this plan’s items.

** Recommended Approach
- Phase 1: define the affordance DSL, capability model, and fixture matrix before any HTML/CSS implementation.
- Phase 2: make HTML locally semantic with reusable embedded-region contracts for downstream CSS and future HEEx.
- Phase 3: make CSS locally semantic and graph-aware across HTML consumers, with conservative dead-style and token tracing.
- Phase 4: surface the new capabilities through the code tool, native bridges, prompts, result typing, and conservative refactor flows.
- Phase 5: only after core verification, expand outward to HEEx-full semantics, utility frameworks, and broader template hosts.
