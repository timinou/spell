* Intent

A declarative terminal UI for SpellAgent (PLAN-344) that lets you (1) type a new
chat/mission and (2) watch EVERYTHING happening inside the run — and *inside the
insides* of the model: turn → llm (reasoning) → tool → (if the tool is a
sub-agent) its own nested run → its turns → … arbitrarily deep.

The whole UI is DSL design. Three borrowed ideas, fused:
  - Surface DSL (DjinnUI): screen = data; ONE render contract; generic renderer
    never branches on pane type — type logic lives in the pane.
  - Mirror DSL (Djinn LiveView): a pane declaratively MIRRORS a slice of a
    source-of-truth into its local view-model, `when:`-gated, re-evaluated after
    every update batch.
  - ExRatatui (callback runtime): `mount/render/handle_event/handle_info`;
    render returns `[{widget, rect}]`; non-blocking DirtyIo; TextInput/Textarea
    for the composer; Table/Gauge/BarChart/Chart for aggregates.

The synthesis (the headline): a pane COLOCATES the PtcRunner traces it reflects
with how it renders them — `events/0` (subscribe) + `project/2` (the mirror) +
`view/1` (render), one module, one screenful.

* Verified ground truth (file-checked 2026-06-18 — do not re-litigate)

** The model's interior already exists as a telemetry span forest
`PtcRunner.SubAgent.Telemetry` emits, all prefixed `[:ptc_runner, :sub_agent]`:
  - `[:run,  start|stop|exception]`  agent, status, step
  - `[:turn, start|stop]`            turn, program, result_preview, prints, tokens
  - `[:llm,  start|stop]`            messages, response (raw reasoning), token deltas
  - `[:tool, start|stop|exception]`  tool_name, args, result
  - `[:compaction, :triggered]`      single emit, messages_before/after
EVERY event carries `span_id` (8-hex) + `parent_span_id` (nil at root). Nested
spans link parent→child → the events form a FOREST. That forest IS "inside the
insides": a tool whose impl is a sub-agent emits its own nested `[:run,…]` subtree
linked by parent_span_id. Recursion is free — no special code.
(beam/ptc_runner-vendored/lib/ptc_runner/sub_agent/telemetry.ex)

** Prior art that aggregation works on the forest
`PtcRunner.TraceLog.Analyzer.summary/1` already folds events → counts/tokens/
durations (count_events, extract_tokens). Aggregates are a different REDUCER at
the same `project/2` seam, not a new construct.
(beam/ptc_runner-vendored/lib/ptc_runner/trace_log/analyzer.ex)

* The DSL surface (authoring target)

#+BEGIN_SRC elixir
defmodule SpellAgent.Tui.Inspector do
  use SpellAgent.Tui.Surface

  surface do
    title  "spell · live inspector"
    layout :three_column                       # transcript | span-forest | detail
    composer :prompt, on_submit: &SpellAgent.Session.run/1
  end

  pane :transcript, region: :left,   component: Tui.Panes.Transcript
  pane :tree,       region: :center, component: Tui.Panes.SpanTree, focusable: true

  pane :detail, region: :right do
    mirror :span, from: {:selected, :tree}     # follows the cursor in :tree
    view fn %{span: span} -> [{Paragraph.new(SpanFmt.detail(span)), :fill}] end
  end
end
#+END_SRC

A colocated built-in pane:

#+BEGIN_SRC elixir
defmodule SpellAgent.Tui.Panes.Transcript do
  use SpellAgent.Tui.Pane
  events [[:turn, :stop], [:run, :stop]]       # dirty-filter: only these wake it
  def project(forest, _),
    do: %{turns: Store.turns(forest), final: Store.final_return(forest)}
  def view(%{vm: %{turns: ts, final: f}, rect: r}),
    do: [{List.new(Enum.map(ts, &TurnFmt.line/1) ++ [FinalFmt.line(f)]), r}]
end
#+END_SRC

* Aggregates — pressure-test PASSED (same contract, zero new concepts)

A pane is events/0 → project/2 → view/1. project/2 is an ARBITRARY fold over the
forest: transcript folds → list of turns; an aggregate folds → a number /
histogram / group-by. Same seam. Findings that became contract invariants:
  1. project/2 returns ANY shape (forest → term()), never assume rows.
  2. view/1 emits ANY widget; renderer never branches → aggregates just pick
     Table/Gauge/BarChart.
  3. SCOPE is the only new thing aggregates surface, and it's already expressible
     by WHICH source you mirror: `from: :span_forest` (whole run) vs
     `from: {:selected, :tree}` (selected subtree, recomputed as the cursor
     moves). ⇒ an aggregate can be LIVE-SCOPED to your navigation with no new
     primitive. Drilling "inside the insides" and aggregating over what you
     drilled into are the SAME `from:`.
Caveat (perf, not DSL): whole-forest recompute is O(spans)/batch — fine for a
session; if it bites, Store keeps incremental tallies BEHIND project/2 (an
optimization, invisible to the DSL). That hideability is itself proof the seam
is right.

Example aggregate pane:

defmodule SpellAgent.Tui.Panes.TokenMeter do

  def project(f, _), do: %{by_turn: Store.tokens_by_turn(f), ratio: Store.ctx_ratio(f)}
  def view(%{vm: vm, rect: r}), do: [{BarChart.new(vm.by_turn), r}]

* Spark entities (match repo convention: args:[:name], identifier::name, target: schema struct)

  - @composer  name, on_submit (fun/1, required)
  - @mirror    name; from (event-suffix | named derived source | {:selected,pane});
               when (fun/1, gates re-eval); collect (:last|:list|:tree); default
  - @pane      name; region (:left|:center|:right|:full); component (module) XOR
               view (fun/1); focusable; entities: [mirrors: [@mirror]]
  - @surface_section  title, layout; entities: [@composer]
Transformer → `__surface_config__/0` → %Surface{panes, composer, layout} =
the compile-time contract, tested directly (DjinnUI §10 pattern) — no runtime.

* Runtime modules

** Store (GenServer)
attach_many to all sub_agent events → cast → upsert %Span{} keyed by span_id,
linked by parent_span_id. start opens (t0,kind,meta); stop closes (t1, merge
meta, status); exception → status:error. After each cast, broadcast
{:store_updated, fired_suffixes} to subscribed App. Derived accessors: forest/0,
turns/1, final_return/1, tool_spans/1, tokens_by_turn/1, subtree/2 (for selected).

** Projection (the mirror reconciler)
For each pane: if `when:` open AND the pane's events/0 intersect fired_suffixes,
run project(forest, assigns) → cache vm; else keep cached. (Mirror's
reconcile-after-every-batch, re-keyed from LV lifecycle to telemetry batches.)

** App (ExRatatui.App, callback runtime)
state = %{config: Inspector.__surface_config__(), focus, cursor (per-pane),
composer_buf, vms}. mount: subscribe to Store. handle_info({:store_updated,…}):
re-project dirty panes, re-render (coalesced ~30fps tick to absorb bursts).
render/2: Layout.split by layout, call each pane.view, concat [{widget,rect}].
handle_event: Tab cycles focus; arrows move focused pane cursor → re-derive
{:selected,…} mirrors; Enter in composer → Task.start(on_submit, [buf]) so the
new mission's telemetry streams back into the Store; never blocks the BEAM.
UI state (focus/cursor) lives in App, NOT the Store (model SoT stays replayable).

* Open decisions (cheap, stated)
- Inline `view:` fn vs component module: default panes to MODULE form (reuse +
  testable); reserve inline for one-off detail (DjinnUI's extract-when-reusable).
- Cursor/focus = App state, never Store (else record/replay breaks).
- Render cadence: re-render on {:store_updated} + ~30fps cap (a chatty turn emits
  dozens of events/ms; uncapped redraw wastes the NIF boundary).
- ex_ratatui NIF download is network/precompiled; the SPIKE's risky core (1-4)
  needs neither — only the App (5) needs the dep.
