* Context

** Problem
The loop system is a state-machine-driven orchestration engine for multi-iteration plan-code-review cycles, but it operates on a single flat =taskContent= string. Specs are only used for validation and drift detection -- they are never decomposed into trackable work items. There is no manifest concept, no per-ticket tracking, no integration with ultraplanning (Metis/Momus), and no pre-launch approval flow. The gap between the existing loop infrastructure and a spec-driven workflow is substantial but bridgeable: the building blocks (spec parser, org sync, gate system, domain system, plan-code-review cycle, ultraplan agents) exist but are disconnected.

** Approach
Transform the loop system into a spec-driven orchestration engine across 4 phases:

1. *Core Foundation*: Manifest data model, =manifest_building= state in kernel, org-native persistence, org-depend property parser, Emacs tooling extensions, ticket lifecycle management.
2. *Tooling*: Replace =loop_start= with =loop_prepare= + =loop_launch= (breaking change). Manifest building system prompt. Enhanced iteration prompts with full manifest context for agent-directed ticket selection.
3. *Integration*: Metis gap analysis on specs before manifest creation (mandatory). Momus validation on manifest before launch (mandatory). Automatic gate derivation from acceptance criteria and GATE_* properties. Layered gate system (per-ticket, per-iteration, per-manifest). Spec drift auto-replan with manifest merge.
4. *UX*: QML manifest viewer canvas for monitoring. Enhanced TUI manifest approval summary.

** Key Design Decisions

*** Manifest as org
- =manifest.org= orchestration sheet + individual ticket =.org= files in =.local/!tracks/loops/{loopId}/manifest/=
- Use org tool and Emacs extensions for ergonomic manifest management
- Persistence hierarchy: event log (truth) -> checkpoint (optimization) -> org items (visibility)

*** org-depend conventions
- =:BLOCKER:= property with IDs (entries that must be DONE first)
- =:TRIGGER:= property with =ID(KEYWORD)= expressions (actions on completion)
- Custom: =:GATE_CMD:=, =:GATE_ARTIFACT:=, =:GATE_LLM:= for gate hints
- Added to original spec/task org files, not duplicated

*** New loop states
- Add =manifest_building= between =idle= and =planning=
- State machine: idle -> manifest_building -> planning -> iterating -> ...
- =manifest_building= has relaxed tool restrictions (read-only workspace + exploration + org writes + test/check)

*** Breaking API change
- Remove =loop_start= tool entirely
- New =loop_prepare= (spec ingestion + manifest building trigger) + =loop_launch= (start iterating on approved manifest)
- =loop_done= extended with =completedTickets= and =activeTickets= fields

*** Hybrid ticket lifecycle
- Loop transitions tickets to DOING when iteration starts on them
- Agent transitions tickets to DONE when satisfied
- Loop verifies via per-ticket gates before accepting DONE
- org keywords: (no state) -> ITEM -> DOING -> DONE, plus BLOCKED, HOLD

*** Layered gates
- Per-ticket: derived from acceptance criteria + GATE_* properties, fire on ticket completion
- Per-iteration: domain gates (existing behavior)
- Per-manifest: validation gates on loop completion

*** Agent-directed ticket selection
- Plan phase receives full manifest state (all tickets, states, dependencies, findings)
- Agent picks which tickets to work on next based on dependency order and state
- LLM decides when a ticket is "large" enough to spawn a child loop

*** Spec drift response
- Auto-pause on drift detection
- Re-parse changed specs, merge into manifest preserving completed tickets
- User approval for replan (respects auto-approve settings)
- Git commit with =🔄 loop(replan): ...= message

*** Pre-launch flow
- =loop_prepare= triggers =manifest_building= state
- Agent runs Metis (mandatory), builds manifest via org tool, runs Momus (mandatory)
- User approves via =/loop launch= or auto-approval callback
- Transitions to =planning= and iteration begins
