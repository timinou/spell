# W6.5 review wave — PLAN-315

## Summary
Two HIGH-confidence `this`-binding bugs in `browser-component.ts` make the memory-browser panel non-functional the moment any non-meta key is pressed and again on Esc-driven close. Both bugs share the same root cause: tab methods are extracted from the receiver and invoked unbound, but every tab implementation relies on `this` (private-field access). One P2 race in `since-tab.ts` when the user toggles the 24h/7d window during an in-flight fetch. The other items from the brief (Alt+M decoding, cwd resolution, dispose chain, cross-tab nav race, smoke tests) checked clean or are not bugs against the W6 spec. Recommendation: **gap-fix before next wave** — without the fix, the panel cannot be exercised.

## Findings

### HIGH-1 (P1, confidence 0.98) — Tab `handleInput` invoked unbound, throws on every key
- **File:line**: `packages/coding-agent/src/modes/components/memory-browser/browser-component.ts:49-52`
- **Code**:
  ```ts
  const handler = this.#tabs[this.#activeTab].handleInput;
  if (handler) handler(data);
  this.#opts.onRequestRender();
  ```
- **Repro**: Press Alt+M to open the browser, press `j` (or any nav/printable key) on the default Search tab. Execution enters `MemorySearchTab.handleInput` with `this === undefined` (class methods are strict). The first statement `if (this.#disposed) return;` performs a private-field read on `undefined` and throws `TypeError: Cannot read properties of undefined (reading '#disposed')`. The same TypeError fires for every tab (`MemoryGraphTab`, `MemoryRecentTab`, `MemorySinceTab` — they all guard on `this.#disposed` first). Net effect: every key except `Tab`/`Shift+Tab`/`Esc` (handled at the container level) throws; the panel is unusable.
- **Fix sketch**:
  ```suggestion
  		// Delegate to active tab
  		this.#tabs[this.#activeTab].handleInput?.(data);
  		this.#opts.onRequestRender();
  ```
  The optional-call form on the receiver expression preserves `this` binding. (Side note: the indentation of the existing three-line block is also off — extra leading tabs vs. the surrounding scope.)
- **Confidence rationale**: pure JS semantics, mechanically reproducible by reading the two files. No spec interpretation needed.

### HIGH-2 (P1, confidence 0.98) — `dispose()` calls each tab's dispose without `this`, throws on Esc-close
- **File:line**: `packages/coding-agent/src/modes/components/memory-browser/browser-component.ts:104-111`
- **Code**:
  ```ts
  dispose(): void {
      if (this.#disposed) return;
      this.#disposed = true;
      for (const tab of this.#tabs) {
          const d = (tab as unknown as Record<string, unknown>).dispose;
          if (typeof d === "function") (d as () => void)();
      }
  }
  ```
- **Repro**: Open the browser, press `Esc`. `MemoryBrowserComponent.handleInput` calls `this.#opts.onClose()`, which calls `browser.dispose()` (see `selector-controller.ts:835-839`). `dispose()` extracts each tab's `.dispose` into a bare reference `d` and calls `d()` — `this` is `undefined`. Every tab's `dispose()` body starts with `this.#disposed = true`, which is a private-field write on `undefined` → `TypeError`. The first tab in the array (`MemorySearchTab`) throws before reaching the rest, leaving timers (`#debounceTimer`) and graph/recent/since tabs un-disposed and the selector overlay in a partially-torn-down state.
- **Fix sketch**:
  ```suggestion
  	dispose(): void {
  		if (this.#disposed) return;
  		this.#disposed = true;
  		for (const tab of this.#tabs) {
  			(tab as TabPanel & { dispose?: () => void }).dispose?.();
  		}
  	}
  ```
  Calling `obj.dispose?.()` (method invocation on the receiver) preserves `this`. Cleaner alternative: add `dispose?(): void` to the `TabPanel` interface in `types.ts` and drop the cast.
- **Confidence rationale**: same JS semantics as HIGH-1; both bug sites destructure a method out of its receiver. Trivial repro path.

### HIGH-3 (P2, confidence 0.85) — Since-tab window toggle races concurrent fetches
- **File:line**: `packages/coding-agent/src/modes/components/memory-browser/since-tab.ts:175-178` (`handleInput` space branch) and `:38-62` (`#refresh`)
- **Code**:
  ```ts
  if (data === " ") {
      this.#window = this.#window === "24h" ? "7d" : "24h";
      this.#refresh();
  }
  ```
  `#refresh()` has no guard against concurrent invocation, no AbortController, and no sequence number — it just `await memorySince(...)` then `this.#result = result`.
- **Repro**: Open the Since tab, press `Space` twice in quick succession while the first fetch is in flight (`memorySince` ends up dispatching through `dispatchMemoryAction`, which hits an RPC/daemon path; under load this is racy). Two `#refresh()` promises are active. If fetch #2 (the most recent window) resolves first and fetch #1 (the now-stale window) resolves second, fetch #1's result overwrites `#result` and `#combined`. The render header still says `[24h]` (because `#window` reflects the last keypress), but the listed added/modified entries belong to the 7d window. UI is inconsistent until next refresh.
- **Fix sketch**:
  ```suggestion
  	async #refresh(): Promise<void> {
  		const seq = ++this.#refreshSeq;
  		this.#loading = true;
  		this.#error = null;
  		this.#onRequestRender();

  		try {
  			const ms = this.#window === "24h" ? 24 * 60 * 60 * 1000 : 7 * 24 * 60 * 60 * 1000;
  			const ts = new Date(Date.now() - ms).toISOString();
  			const result = await memorySince(this.#repoRoot, ts);
  			if (this.#disposed || seq !== this.#refreshSeq) return;
  			this.#result = result;
  			this.#buildCombined(result);
  			this.#selectedIndex = 0;
  			this.#loadedOnce = true;
  			this.#loading = false;
  			this.#onRequestRender();
  		} catch (e) {
  			if (this.#disposed || seq !== this.#refreshSeq) return;
  			this.#error = String(e);
  			this.#loading = false;
  			this.#onRequestRender();
  		}
  	}
  ```
  with a new `#refreshSeq = 0` private field. (Or guard with `if (this.#loading) return;` at the Space branch — simpler but loses the latest-window-wins semantics if the user holds Space.)
- **Confidence rationale**: race is provable from the source; user-visible impact is bounded (UI label vs. data mismatch, recoverable by pressing Space again). Reported as P2 to reflect the bounded impact.

## Non-findings (filtered)

- **Brief item 1 ("`handler` `this` bug")** → escalated to HIGH-1 above (and the dispose mirror at HIGH-2).
- **Brief item 2 (dispose lifecycle)** → modulo HIGH-2's broken invocation, each tab's `dispose()` body correctly sets `#disposed` and search-tab additionally `clearTimeout`s its debounce timer. All async callbacks (`memorySearch`, `memoryAbout`, `memorySince`) re-check `if (this.#disposed) return;` after `await`. Once HIGH-2 is fixed, lifecycle is correct.
- **Brief item 3 (cross-tab nav race on Graph)** → `MemoryGraphTab.setFocus` checks `this.#disposed` on both success and error paths after `await memoryAbout(...)`. Safe.
- **Brief item 4 (Recent tab never re-loads)** → `MemoryRecentTab.activate()` only fetches when `!#loadedOnce`. The W6-research spec at `!tasks/plans/plan-artifacts/PLAN-315/W6-research.md:454-456` describes Recent as "lists episodes from memorySince() with far-past ts" without a refresh requirement. Drift, not a bug. Could file as FUP if product wants a refresh affordance.
- **Brief item 5 (Since-tab Space race)** → escalated to HIGH-3.
- **Brief item 6 (Alt+M decoding)** → `matchesKey` (crates/pi-natives/src/keys.rs:798-802) decodes `alt+m` legacy as `[0x1b, 'm']` (2 bytes); `escape`/`esc` matches only the 1-byte `0x1b`. The `CustomEditor.#handleInputInner` orders `alt+m` interception (line 105-108) before the `escape` fallback (line 148-156), so there is no cross-handler ambiguity. Inside the browser, the panel checks `escape`/`esc` first; `\x1bm` (2 bytes) cannot match either, so Alt+M re-pressed while the panel is open is silently consumed by tab handlers without closing the panel. Acceptable.
- **Brief item 7 (smoke test for `MemoryBrowserComponent` lifecycle)** → No `memory-browser.test.ts` exists under `packages/coding-agent/test/`. Searched `W6-research.md` and `PLAN-315.md` — no acceptance line mandates a TS smoke test for W6. The research doc's task acceptance items are render/cycle/integration, not "tests added". Without a written spec requirement, this is a coverage gap, not a contract violation. Strongly recommend a smoke test be added alongside the HIGH-1/HIGH-2 fix — exactly the scenario that test would catch.
- **Brief item 8 (`as` casts in `actions.ts`)** → All four wrappers do `result as { ... }` then `data.foo ?? defaultValue`. The `??` fallback covers undefined; shape mismatch beyond that would surface at render time. Style smell, not a bug.
- **Brief item 9 (`activate()` no-op on SearchTab)** → `MemorySearchTab.activate()` actually re-triggers search when `#query.length > 0` (search-tab.ts:30-34). Spec satisfied.
- **Brief item 10 (`showMemoryBrowser` cwd)** → `getProjectDir()` from `@oh-my-pi/pi-utils` is already used in `selector-controller.ts:98,178,195`. Returns a real path or throws — consistent with sibling selectors.
- **W6-research drift** — Two design items in the research doc are missing from the implementation: (a) "2s poll interval for Since tab (start in constructor, cancel in dispose)" — the implementation is one-shot+manual-toggle; (b) "Preview pane from memoryAbout() for selected hit" on Search tab — not implemented. Neither is a logic bug; they're scope reductions. Worth FUP-ing if product expects them.

## Recommendation
**Gap-fix needed before next wave.** HIGH-1 and HIGH-2 together leave the panel unusable: keypress throws (HIGH-1), Esc-close throws (HIGH-2). Both are one-line fixes in `browser-component.ts`. HIGH-3 is a follow-up nice-to-have. A smoke test that mounts `MemoryBrowserComponent`, drives one keypress, then disposes would have caught HIGH-1 and HIGH-2 — add one alongside the fix.
