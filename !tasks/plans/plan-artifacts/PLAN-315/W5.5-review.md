## Findings

### HIGH-1: AGENTS.md describes Inprocess mode as having "silent RPC errors" — Inprocess never attempts RPC

- **File**: `.spell/AGENTS.md:28`
- **What**: The documented "Escape hatch" paragraph says: "In this mode, RPC errors are silent (the old behaviour); in the default `Daemon` mode, RPC errors are propagated as query failures."
- **Why it fails**: In `Inprocess` mode, the code at `recall_engine.rs:330-332` reads `WorkerMode::Inprocess => { /* Skip RPC entirely — use in-process WarmEngine. */ }` — RPC is never attempted. There are no RPC errors to be silent about. The "old behaviour" (pre-W5) did attempt RPC and silently fell through on failure; the new `Inprocess` path skips RPC altogether. The document describes a behaviour that does not exist, which will mislead future developers about the execution path in Inprocess mode.
- **Confidence**: HIGH — the code path is unambiguous (`Self::Inprocess => {}`, no RPC call before the WarmEngine section), and the doc's phrasing directly contradicts it.
- **Fix**: Replace "In this mode, RPC errors are silent (the old behaviour)" with "In this mode, RPC is bypassed entirely; queries are served directly from the in-process `WarmEngine` (no daemon socket is contacted)."
  - Proposed patch to `.spell/AGENTS.md` line 28:
    ```
    - Escape hatch: set `PI_KNOWLEDGE_WORKER=inprocess` to bypass the daemon socket and fall back to the in-process `WarmEngine`. Useful for CI, offline development, and tests. In this mode, RPC is bypassed entirely; queries are served directly from the in-process `WarmEngine` (no daemon socket is contacted). In the default `Daemon` mode, RPC errors are propagated as query failures.
    ```

## Non-findings (filtered)

- `read_worker_env()` filters `PI_KNOWLEDGE_WORKER=inprocess` from transport resolution, but the fall-through to `PI_EMBEDDING_WORKER` means a user with only `PI_KNOWLEDGE_WORKER=inprocess` set (no legacy var) still ends up spawning a subprocess worker via `acquire()` → `worker_candidates()`. This is *intentional*: Inprocess mode skips the daemon RPC but still needs the embedding subprocess for vector index building. Only a documentation-design consideration, not a bug.
- `MockWorkerEnv` in `code_graph.rs:539` uses `reset_for_tests()` but not `reset_worker_mode_for_tests()`. This is safe because code_graph tests never call `worker_mode()`; they only use `embed_batch` / `embed_query` which route through the transport cache (separate `WORKER` OnceLock).
- `SocketEnv` in `embedding_worker.rs` socket tests similarly omits `reset_worker_mode_for_tests()`. Safe for the same reason — socket tests don't touch `worker_mode()`.
- `daemon_mode_propagates_rpc_failure` reaches the `knowledge_capable() == false` error path (not the `query_via_rpc` error path), because the nonexistent `PI_EMBEDDING_WORKER` path causes `acquire()` to fail in `EmbeddingWorker::spawn`. This is a correct path; the test assertion `err.contains("PI_KNOWLEDGE_WORKER=inprocess")` matches both error strings.

## Recommendation

One doc fix needed before W6 lands. The code is otherwise sound: dispatch logic is correct, all test fixtures properly isolate env state, no third-party call sites bypass the mode check, and the fail-loud behaviour matches the intent. The AGENTS.md fix is a one-line edit in `.spell/AGENTS.md:28`.
