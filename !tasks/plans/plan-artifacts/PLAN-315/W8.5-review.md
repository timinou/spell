# W8.5 review wave — PLAN-315

## Summary

W8 commit `1197e32f3` lands three artefacts: a `BenchPayload` event +
`publish_bench_event` helper in `pi-knowledge-worker/src/subscribe.rs`,
a 339-line bash harness `scripts/perf/plan315-n10.sh`, and a methodology
appendix in `W8-perf.md`. The Rust changes are clean: BenchPayload
serialises to `bench_payload` matching the existing `tag="event",
rename_all="snake_case"` convention, `publish_bench_event` follows the
exact `publish_warm_completed` pattern (lookup via `EventRegistry`,
drop-oldest with lag counter), and both new tests assert delivery (not
just no-panic). However the bash harness is **deeply broken at the
instrumentation layer**: it sends a JSON shape the daemon does not
accept, the RSS sampler runs *after* the load phase, the search-latency
gate is dominated by Python startup overhead per query, and the
PASS/FAIL emitter silently passes any `N/A` value. The
`W8-perf.md` claim that push delivery is "measured via the integration
test" is a documentation lie — the test asserts delivery within a 1 s
timeout, not P99 latency over N samples.

**Recommendation: gap-fix needed before next wave.** Several of the
seven advertised gates produce numbers, but those numbers are not
measurements of what the gate documents.

## Findings

### HIGH-1 · Harness sends `cmd`/`repo`/`query`; daemon expects `command`/`repo_root`/`repo_handle`/`text`

`scripts/perf/plan315-n10.sh:118-128, 144-157, 169-181, 192-205`
together with `crates/pi-knowledge-worker/src/main.rs:61-122`.

The Command enum is tagged `#[serde(tag = "command", rename_all =
"snake_case")]`. Every JSON request the harness emits uses the key
`cmd` instead of `command`, and supplies fields under the wrong names:

```python
# Open  — harness sends:
{'request_id': 1, 'cmd': 'open', 'repo': 'session-1'}
# daemon expects:
{'command': 'open', 'repo_root': '<absolute path>'}

# Search — harness sends:
{'request_id': 3, 'cmd': 'search', 'query': 'gamma', 'repo': 'session-1'}
# daemon expects:
{'command': 'search', 'repo_handle': '<from open response>', 'text': 'gamma'}
```

`process_line_with_conn` (main.rs:486-499) peeks `"command"` to dispatch
subscribe/unsubscribe, finds none, and falls through to
`process_line` → `serde_json::from_str::<Command>` → returns
`Response::Err { error: "malformed JSON or command: …" }`. Every
"search" the harness times is therefore the daemon JSON-parse + reject
path, never an actual search. The script `> /dev/null 2>&1` discards
the error body, so the silent failure is invisible. The `memory.search
P99` column on the gate table is **not search latency** — it is
"`python3 -c` cold-start + AF_UNIX RTT + daemon serde error".

Fix sketch:
```python
req = json.dumps({'request_id': 1, 'command': 'open',
                  'repo_root': str(sess_path)}).encode() + b'\n'
# capture handle:
handle = json.loads(resp)['repo_handle']
# search:
req = json.dumps({'request_id': 3, 'command': 'search',
                  'repo_handle': handle, 'text': 'gamma'}).encode() + b'\n'
```

Confidence: **VERY HIGH** — the serde tag, RecallQuery fields
(`crates/pi-knowledge-core/src/recall.rs:89-105` — `text: Option<String>`,
no `query`), and `Command::Open { repo_root: PathBuf, … }` are all
directly verifiable in this tree.

### HIGH-2 · `emit_gate` reports ✅ PASS on `N/A` measurements

`scripts/perf/plan315-n10.sh:251-258, 273`.

```bash
emit_gate() {
  local name="$1" target="$2" measured="$3" pass="$4"
  local status="❌ FAIL"
  if awk -v m="$measured" -v p="$pass" 'BEGIN{exit !(m+0 <= p+0)}' 2>/dev/null; then
    status="✅ PASS"
  fi
  …
}
```

When no per-session log accumulates (e.g. the daemon rejects every
request, or the corpus generator aborts), the percentile helpers return
the literal string `N/A` (line 240-244). `awk` then coerces
`"N/A"+0 → 0`, the test `0 <= 45` is true, and the gate row reports
`memory.search P99 (ms) | ≤ 50 | N/A | ✅ PASS`. A failed measurement
masquerades as a passing gate.

Fix sketch:
```bash
emit_gate() {
  local name="$1" target="$2" measured="$3" pass="$4"
  local status="❌ FAIL"
  case "$measured" in
    ''|N/A|NA) status="⚠ NO DATA" ;;
    *)
      if awk -v m="$measured" -v p="$pass" 'BEGIN{exit !(m+0 <= p+0)}'; then
        status="✅ PASS"
      fi
      ;;
  esac
  printf "| %s | %s | %s | %s |\n" "$name" "$target" "$measured" "$status" >> "$REPORT_FILE"
}
```

Confidence: **VERY HIGH** — reproducible by `awk 'BEGIN{print "N/A"+0}'`
(prints `0`).

### HIGH-3 · RSS sampler runs *after* the workload, not during it

`scripts/perf/plan315-n10.sh:195-219`.

Section 8 spawns 10 background query sessions and `wait`s for ALL of
them to finish. *Then* section 9 starts the RSS sampler:

```bash
# section 8 — kicks off 10 client sessions
for i in $(seq 1 10); do ( … 100 queries … ) & done
wait               # ← blocks until every query session is done

# section 9 — RSS sampler starts only now
( for _ in $(seq 1 30); do ps -o rss=… -p "$DAEMON_PID"; sleep 2; done ) > rss-samples.log &
sleep 62
```

By the time the sampler runs, the daemon has been idle for the full
sampling window. The recorded peak is the post-workload steady-state
RSS, not the working-set peak under N=10 load. Gates 2 (`per-session
RSS`) and 3 (`total RSS`) therefore do not measure what they advertise.

Fix sketch: start the RSS sampler **before** kicking off the query
phase, then `wait`/`kill` it after the queries finish:

```bash
( for _ in $(seq 1 90); do ps -o rss= -p "$DAEMON_PID" 2>/dev/null || true; sleep 1; done ) \
  > "${WORK_DIR}/rss-samples.log" &
SAMPLER_PID=$!
# … queries …
wait                            # query sessions
kill "$SAMPLER_PID" 2>/dev/null || true
```

Confidence: **VERY HIGH** — pure control-flow inspection.

### HIGH-4 · `TOTAL_RSS_MB` is `per-session × 10` for a single shared daemon

`scripts/perf/plan315-n10.sh:222-232`.

```bash
PEAK_RSS_KB=$(awk '{print $1}' rss-samples.log | sort -n | tail -1)
PEAK_RSS_MB=$(awk -v k="$PEAK_RSS_KB"  'BEGIN{printf "%.0f", k/1024}')
PER_SESSION_RSS=$(awk -v k="$PEAK_RSS_KB" 'BEGIN{printf "%.0f", k/1024}')   # ← full daemon
TOTAL_RSS_MB=$(awk -v k="$PEAK_RSS_KB"   'BEGIN{printf "%.0f", k*10/1024}') # ← 10× of full daemon
```

There is **one** daemon process serving all 10 sessions; the sampler
records only `DAEMON_PID`. So `PEAK_RSS_KB` is already the total RSS
across N=10. `PER_SESSION_RSS = peak/1024` therefore reports the full
shared-daemon RSS as the per-session number (over-attribution), and
`TOTAL_RSS_MB = peak × 10 / 1024` over-counts the total by 10×.

A 500 MB daemon serving 10 sessions would render as
`per-session 500 MB ❌ FAIL` *and* `total 5000 MB ❌ FAIL` — when the
real per-session footprint is ~50 MB and the real total is 500 MB.

Fix sketch:
```bash
TOTAL_RSS_MB=$(awk -v k="$PEAK_RSS_KB" 'BEGIN{printf "%.0f", k/1024}')
PER_SESSION_RSS=$(awk -v k="$PEAK_RSS_KB" 'BEGIN{printf "%.1f", (k/1024)/10}')
```

Confidence: **VERY HIGH** — single daemon spawn at line 162, only
`DAEMON_PID` sampled at line 213.

### HIGH-5 · Cold warm-up gate documents "12k symbols ≤ 90 s" but harness opens 1 session

`scripts/perf/plan315-n10.sh:133-156` and `:271`.

The cold measurement section is:
```bash
COLD_START=$(date +%s%N)
# python3 -c … open 'session-1' …          # ← only session-1
COLD_END=$(date +%s%N)
COLD_MS=$(( (COLD_END - COLD_START) / 1000000 ))
…
emit_gate "cold warm-up (ms, 12k symbols)" "≤ 90000" "$COLD_MS" "80000"
```

Each session has 1,200 .org items (corpus generator at lines 105-128
loops `seq 1 10` × `seq 1 1200`), so opening session-1 warms 1,200
symbols. The gate is labelled "12k symbols" but the measurement is
for 1.2k. Either the corpus per session needs to be 12 k items, or all
ten sessions need to be opened before stopping the timer.

Fix sketch:
```bash
COLD_START=$(date +%s%N)
for i in $(seq 1 10); do
  python3 -c "import json,socket; s=socket.socket(socket.AF_UNIX,socket.SOCK_STREAM); \
    s.connect('${SOCK}'); \
    s.sendall((json.dumps({'command':'open','repo_root':'${WORK_DIR}/session-${i}'})+'\n').encode()); \
    s.makefile('r').readline(); s.close()"
done
COLD_END=$(date +%s%N)
```

Confidence: **VERY HIGH** — corpus shape and warm-up code are both
in-tree.

### HIGH-6 · `emit_gate` "target" column is decoupled from the actual pass threshold

`scripts/perf/plan315-n10.sh:265-271`.

```bash
emit_gate "libpi_natives.so size (MB)"     "≤ 92.5"  "$SIZE_MB"         "90.0"
emit_gate "per-session RSS peak (MB)"      "≤ 100"   "$PER_SESSION_RSS" "90"
emit_gate "total RSS N=10 (MB)"            "≤ 1587"  "$TOTAL_RSS_MB"    "1400"
emit_gate "memory.search P99 (ms)"         "≤ 50"    "$P99_SEARCH"      "45"
emit_gate "cold warm-up (ms, 12k symbols)" "≤ 90000" "$COLD_MS"         "80000"
```

The 2nd arg is what the report prints in the "Target" column. The 4th
arg is what `awk m <= p` actually evaluates. They are different on
**every gate**. A `libpi_natives.so` measured at 91 MB renders as
`Target ≤ 92.5 | Measured 91 | ❌ FAIL`, contradicting itself in the
same row. The implicit tighter "internal budget" is nowhere
documented in `W8-perf.md`.

Fix sketch: collapse to one threshold; if a defensive margin is
desired, encode it as an explicit `BUDGET=` constant and render both
columns from the same value:

```bash
LIBPI_BUDGET=92.5
emit_gate "libpi_natives.so size (MB)" "≤ ${LIBPI_BUDGET}" "$SIZE_MB" "$LIBPI_BUDGET"
```

Confidence: **VERY HIGH** — direct inspection of the call sites.

### HIGH-7 · Push delivery gate is documented as measured but is not

`!tasks/plans/plan-artifacts/PLAN-315/W8-perf.md` "Methodology notes"
("Push delivery measured via `publish_bench_event` Rust integration
test, not by the bash harness directly") + the only added test
(`crates/pi-knowledge-worker/src/subscribe.rs:514-541`,
`bench_payload_delivers_on_subscribed_channel`).

That test subscribes once, publishes one BenchPayload, asserts the
frame arrives inside a 1-second `recv_timeout`, and checks the
`emitted_at_ms` field is non-zero. It does **not** sample N
iterations, does **not** record receipt timestamps, does **not**
compute any percentile. There is no other bench binary in
`crates/pi-knowledge-worker/benches/`. The harness's own methodology
appendix admits this in its next paragraph ("A dedicated bench binary
… *should be added*"). So gate 6 ("push delivery P99 ≤ 500 ms") has
**no measurement anywhere in the tree** — but the public methodology
text says it is measured. Mark it `DEFERRED` like cg_search, or land
the bench binary.

Fix sketch:
```bash
emit_gate_stub "push delivery P99 (ms)" "≤ 500" \
  "DEFERRED — bench binary not yet authored; bench_payload delivery test asserts arrival only"
```

Confidence: **VERY HIGH** — both files are present in the diff;
neither contains percentile machinery for BenchPayload.

### HIGH-8 · Per-query `python3 -c` spawn dominates `memory.search` latency

`scripts/perf/plan315-n10.sh:181-205`.

The per-query inner loop is:
```bash
for q in $(seq 1 100); do
  T0=$(date +%s%N)
  python3 -c "import json,socket,sys; …connect/send/recv/close…" > /dev/null 2>&1 || true
  T1=$(date +%s%N)
  echo $(( (T1 - T0) / 1000000 )) >> "$LOG"
done
```

Each measurement runs `T1-T0` around a freshly forked `python3`
interpreter: process spawn + interpreter init + module imports
(`json`, `socket`, `sys`) + connect + send + readline + close. On a
warm Linux box `python3 -c 'pass'` alone is ~25–40 ms; with imports
it climbs to 40–60 ms. The 50 ms search-P99 gate is therefore
unreachable by construction even if daemon search were 0 ms. (See
also HIGH-1 — the daemon never actually searches anyway, so the
"measurement" today is pure startup + JSON-reject.)

Fix sketch: hold one Python process per session for the full query
phase and emit timing per query from inside the loop:

```bash
python3 -u <<'PY' > "$LOG" &
import json, socket, time, sys, os
sess = os.environ['SESS']
sock = os.environ['SOCK']
s = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM); s.connect(sock)
f = s.makefile('rw')
f.write(json.dumps({'command':'open','repo_root':f'/work/{sess}'})+'\n'); f.flush()
handle = json.loads(f.readline())['repo_handle']
for q in range(110):
    t0 = time.perf_counter_ns()
    f.write(json.dumps({'command':'search','repo_handle':handle,'text':'gamma'})+'\n'); f.flush()
    f.readline()
    t1 = time.perf_counter_ns()
    if q >= 10:                                   # discard priming
        print((t1 - t0)//1_000_000)
PY
```

Confidence: **VERY HIGH** — startup cost of `python3 -c` with imports
is widely documented and trivially measurable; the script
unambiguously brackets `T0`/`T1` around the whole spawn.

### HIGH-9 · `Open` response is never read, so no `repo_handle` flows into `Search`

`scripts/perf/plan315-n10.sh:144-157, 169-205`.

Even setting aside HIGH-1, the open snippet does:
```python
resp = s.makefile('r').readline()
s.close()                          # ← response discarded
```

Subsequent search commands hard-code `'repo': '${sess}'` (with the
wrong key name, but even after fixing to `'repo_handle'`, they
substitute the session directory name, not the daemon-allocated
handle returned by `Open`). `Command::Search` requires the exact
`repo_handle: String` produced by `repo_cache::open(...)` (main.rs
line 268), which is an opaque, FNV-style identifier — not the
session directory name. With the schema fixed but the handle still
mis-supplied, every search would return
`Response::Err { error: "unknown repo_handle …" }`.

Fix sketch: parse `resp` JSON, extract `repo_handle`, thread it into
every downstream request:
```python
import json
handle = json.loads(resp)['repo_handle']
…
{'command':'search', 'repo_handle': handle, 'text':'gamma'}
```

Confidence: **HIGH** — driven by reading `repo_cache::open` and
`Command::Search` shape; the harness clearly does not capture or
forward any handle.

## Non-findings (filtered)

- `Event` enum doc-comment ("/// Per-(repo_handle, lane) subscriber
  registry. / subscribe; the registry fans out …") was edited to delete
  "Multiple connections may", leaving the second line dangling. Doc nit,
  not a logic bug.
- `bench_payload_emitted_at_ms_within_recent` (subscribe.rs:519-541) uses
  the global `registry()` singleton rather than a fresh `EventRegistry`.
  Cross-test contamination is bounded by the unique `"fnv:ts"` repo key
  and the `delta < 3000` assertion is loose enough to absorb scheduler
  jitter; not flake-prone in practice.
- P99 awk helpers (`int(c*p)`) are off by one rank vs the strict
  nearest-rank definition: with N=1000 they return the 990th
  zero-indexed value (rank 991) rather than the 990th (rank 990). The
  effective bias is <0.1 percentile and dwarfed by HIGH-1/HIGH-8.
- `XDG_RUNTIME_DIR="${WORK_DIR}"` inline-export is fine for daemon
  socket use (daemon takes `--socket` directly; XDG only matters for
  `default_runtime_dir`).
- `cleanup()` trap on `EXIT INT TERM`: SIGKILL cannot be trapped (noted
  in script header) — acceptable trade-off.
- Hardware fingerprint (kernel/CPU/RAM/date) is captured in the report
  header per spec.
- No `$RANDOM` use; iteration counts fixed (10 sessions, 1200 items,
  10+100 queries) — reproducibility intent met.
- Report file path uses `W8-perf-run-${EPOCH}.md`, so it cannot collide
  with the committed `W8-perf.md`.
- `BenchPayload` wire-format check: serde tag is `event`,
  `rename_all="snake_case"` → variant emits `"event":"bench_payload"`,
  which is exactly what test 1 asserts. ✓
- `publish_bench_event` follows the `publish_warm_completed` pattern
  faithfully (lookup via `registry().publish`, drop-oldest +
  per-sink lag counter handled by `LaneEvents::publish`). ✓

## Recommendation

**Gap-fix needed before next wave.** The W8 commit's *Rust* changes are
ship-ready: BenchPayload, `publish_bench_event`, and the two unit tests
all behave as documented. The *bash harness*, however, does not
measure the gates it advertises (HIGH-1, HIGH-3, HIGH-4, HIGH-5,
HIGH-8, HIGH-9), silently passes missing data (HIGH-2), and the
`W8-perf.md` methodology section overstates what is actually measured
(HIGH-7). Recommend: keep the Rust commit, treat the harness as
scaffolding, and either (a) fix HIGH-1/2/3/4/5/8/9 plus the methodology
text in a follow-up commit, or (b) explicitly mark gates 2/3/4/6/7 as
DEFERRED in `W8-perf.md` and track the harness rewrite in FUP-089
alongside the cg_search-corpus TODO.
