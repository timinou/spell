** Problem

Commit =fe63fe88f= (2026-04-05 17:37:19, PLAN-148) introduced a regression. The shared =resolveOpenAICacheParams()= helper now sends =prompt_cache_retention: "24h"= to the Codex provider when =cacheRetention= defaults to ="long"=. The standard OpenAI Responses API (=api.openai.com=) accepts this parameter. The Codex API at =chatgpt.com/backend-api= does NOT:

#+begin_example
Codex error event: Unsupported parameter: prompt_cache_retention (code=invalid_request_error)
#+end_example

=invalid_request_error= is not in =CODEX_RETRYABLE_EVENT_CODES=, so the subagent exits immediately with code 1. Every =task= tool dispatch that resolves to a Codex model (e.g. =openai-codex/gpt-5.3-codex-spark=) fails — the subagent session completes in ~7 seconds with 0 tool calls.

This was the exact failure mode observed in session =14aefc4e23125900= (2026-04-05 17:41:06): all three Wave 1 subagents + one retry all died within 7-8 seconds with the identical error.

** Approach

The existing Codex request normalizer (=transformRequestBody= in =request-transformer.ts=) already strips parameters that the chatgpt.com API does not support (=max_output_tokens=, =max_completion_tokens=, lines 154-155). The fix adds =delete body.prompt_cache_retention= to the same block. The TypeScript type definition stays; only the runtime value is stripped before transmission. =prompt_cache_key= is NOT stripped (the chatgpt.com API accepts and benefits from it).

3. No change to =openai-codex-responses.ts= — the spread call is correct.
