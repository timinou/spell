* Context

** Problem
Plan execution has three disconnected paths:
1. *Legacy prompt-injection* (/plan, /ultraplan): Agent receives full plan via synthetic prompt. Agent manually initializes todo_write from wave structure. Agent drives execution, manually calls ~org update~ for lifecycle transitions. This path is reached when ~fluidPlan~ is missing or org is disabled.
2. *FluidOrchestrator path* (interactive-mode): When ~fluidPlan~ is available, ~#executeViaFluidOrchestrator~ creates a DAG scheduler. But every agent runs via ~await this.session.prompt()~, which serializes through one session (AgentBusyError guard). todo_write is completely bypassed. OrgFluidBridge transitions org items via events. Despite having a concurrent QueueScheduler, execution is sequential.
3. *Canvas fluid-mode* (QML): A planner agent decomposes a prompt into a FluidPlan. FluidOrchestrator dispatches agents via ~runSubprocess~ (real parallelism). QML visualizes DAG progress. No org items, no todo_write. Shares the FluidOrchestrator class but nothing else.

The result: three code paths doing variations of the same thing, with different levels of completeness, and no shared execution model.

** Approach: Agent-Driven Model (Model B)
The main agent session receives the full plan and drives execution via todo_write. FluidOrchestrator becomes a plan compiler/validator, not an executor.

*** Flow
1. Plan compiled → FluidPlanWithComponents (org-fluid-plan MCP or planner agent)
2. ~fluidPlanToTodoPhases()~ converts FluidPlan → TodoPhase[] (auto-init, one phase per wave per component)
3. Session pre-populated with todo phases before agent starts
4. Agent receives plan prompt with "todos are pre-populated, you may modify them"
5. Agent executes via todo_write state machine: mark in_progress → work → mark completed
6. Agent uses ~task~ tool for parallelism (subagents with ~todoRef~)
7. todo_write hooks auto-transition org items: in_progress → DOING (orgItemId), completed → DONE (orgItemClosingId)
8. Plan-level completion when all phases done

*** Key Decisions
- *Model B selected*: Agent drives execution, orchestrator advises. Agent sees whole plan, makes judgment calls about parallelization, can adapt mid-execution.
- *todo_write is the universal control plane*: In both /plan and canvas paths.
- *Org transitions are automatic*: Triggered by todo_write status changes, not manual ~org update~ calls or OrgFluidBridge events.
- *Auto-init with agent flexibility*: System converts FluidPlan → TodoPhases. Agent can modify structure before/during execution.
- *Canvas converges*: Uses the same FluidPlan → TodoPhases → agent execution pipeline. QML visualization adapts to receive events from the new model.
- *Coordinators kept*: For multi-component plans, coordinators use todo_write internally.

** What FluidOrchestrator Module Becomes
A *plan compilation and validation library*: types, DAG utilities, wave computation, plan-schema, event-router. Not an execution engine — that role moves to todo_write + agent + task tool.
