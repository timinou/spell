1. **What**: PLAN-213 was marked `DONE` even though a required verification command (`bun check:ts`) did not pass.  
   **Where**: `!tasks/plans/PLAN-213-code-tool-error-envelope-and-language-gu.org`, state line at top and completion section around `** Completion [2026-04-12]` / `*** Verification`.  
   **Why**: This breaks the plan completion contract: downstream reviewers cannot tell whether the change itself is fully verified or merely believed safe despite a failing required gate.  
   **Effort**: small

2. **What**: The unresolved `bun check:ts` blocker is documented, but there is no linked follow-up org item/FUP tracking that remaining work.  
   **Where**: `!tasks/plans/PLAN-213-code-tool-error-envelope-and-language-gu.org`, `*** Deviations` section near the end.  
   **Why**: The verification blocker is now easy to lose. If the repo-wide check must be green for release confidence, this leaves the failure unowned and untraceable.  
   **Effort**: trivial

3. **What**: The new guard message says “Use the read tool for non-code files,” but it also fires for unsupported code languages, not just non-code files.  
   **Where**: `packages/coding-agent/src/tools/code.ts`, unsupported-extension branch around the new guard near `FILE_COMMANDS` / `SUPPORTED_EXTENSIONS` check.  
   **Why**: This is slightly misleading. A caller trying an unsupported code language is told the file is “non-code,” which can push the model toward the wrong fallback behavior and obscure the real limitation (“unsupported by code tool”).  
   **Effort**: trivial

4. **What**: There is no automated JS-level integration test for the real Rust→NAPI→TypeScript unsupported-language path; the TS suite still mocks `executeCodeBuffer`.  
   **Where**: `packages/coding-agent/test/tools/code.test.ts`, new guard/error tests around the block added near the existing error-handling tests.  
   **Why**: Rust unit tests cover the wrapper and the manual check covers one end-to-end case, but there is no automated contract test across the actual package boundary. A future regression in the NAPI bridge or JS wrapper could slip through without failing the TS test suite.  
   **Effort**: small

5. **What**: `SUPPORTED_EXTENSIONS` is now a second source of truth for language support and can drift from the native engine.  
   **Where**: `packages/coding-agent/src/tools/code.ts`, `SUPPORTED_EXTENSIONS` constant near the top of the file.  
   **Why**: When native language support changes, the code tool can silently reject files the engine already supports, or vice versa. That creates a hard-to-notice contract mismatch at the tool boundary.  
   **Effort**: medium
