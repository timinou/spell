* Context

The current =code= file engine and =pi-code-engine= language registry support TypeScript, Rust, Python, Typst, Markdown, Org, and Elixir, but =pi-code-graph= defaults to only TypeScript + Elixir. The graph also duplicates language extraction logic in bespoke extractors, which creates drift against =crates/pi-code-engine/src/language/mod.rs= and makes language expansion expensive.

This item establishes a declarative graph-extraction core that treats =pi-code-engine= =LanguageProfile= as the canonical source for declarations, class/member hierarchy, imports, exports, and generic reference patterns. The goal is parity of language coverage, not full parity of language-specific semantic richness. Language-specific import resolution and semantic edge enrichment remain explicit extension hooks.

* User Workflows

1. A caller runs =code index= in a Rust, Python, Typst, Markdown, Org, TypeScript, or Elixir workspace and gets graph coverage instead of silent language drop-off.
2. A caller runs =code status= and sees file/symbol counts that reflect every language the =code= tool already accepts.
3. A later feature can add new graph queries without rewriting per-language extraction from scratch.
4. A maintainer adding a new language to =pi-code-engine= has one canonical schema to extend instead of two divergent stacks.

* Design Decisions

1. Use =LanguageProfile= as the declarative schema for baseline graph extraction.
2. Build a generic extractor that emits declarations, member relationships, imports, exports, and generic references from engine profiles.
3. Keep import resolution pluggable per language; do not force a fake universal resolver.
4. Keep edge enrichment pluggable per language/domain; baseline parity may emit more =References= edges before richer =Calls/Inherits/Renders/TypeParameterOf= enrichment exists.
5. Preserve stable qualified-name rules per language and document them in code comments/tests.
