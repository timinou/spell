* Scope
In scope:
- Extend validation and test coverage so plan mode enforces execution usability, not only structural completeness.
- Cover child-item TODO-outline `ITEM` headings, PLAN-level implementation guidance requirements, manifest/heading expectations, and balanced prompt regression checks.
- Update validation and prompt tests around `exit_plan_mode`, prompt rendering, and wave extraction where needed.

Out of scope:
- Rewriting the planning prompt contract itself; covered by sibling prompt-contract item.
- Approved-plan orchestration wording and todo/task execution semantics; covered by sibling orchestration item.
- Runtime execution behavior changes unrelated to plan validation or prompt tests.

Rationale: the repo already validates many org invariants (`EFFORT`, `PRIORITY`, `LAYER`, `CUSTOM_ID`, `DEPENDS`, acyclic sub-outline graphs), but it still allows plans that are structurally valid while being too thin for direct execution. This item hardens the validator and tests so the new execution-first planning contract remains enforceable.

- Existing invariant style to reuse: focused contract tests with exact failure-path assertions instead of smoke tests.

* Tests
Workflows that must be enumerated up front:
- Workflow 1: `exit_plan_mode` rejects child items whose implementation sub-step headings omit `ITEM` TODO outline keyword.
- Workflow 2: `exit_plan_mode` rejects PLAN items that keep context and manifest links but omit the new required implementation-oriented PLAN heading(s) or equivalent execution instructions.
- Workflow 3: prompt rendering tests fail if wording regresses to findings-heavy / execution-thin guidance.
- Workflow 4: wave extraction and plan parsing still work when new PLAN-level implementation headings are added.
- Workflow 5: balanced plans with rich rationale plus explicit execution headings are accepted.

Test files / scenarios:
- `packages/coding-agent/test/tools/exit-plan-mode-validation.test.ts`
  - add failing fixtures for missing `ITEM` heading keyword and missing PLAN-level implementation guidance

  - add acceptance / rejection cases for the new PLAN body contract
- `packages/coding-agent/test/tools/exit-plan-mode-waves.test.ts`

* Edge Cases
- Rich plans that add new PLAN headings must still keep `Execution Manifest` parseable and wave extraction stable.
- Child items may include non-implementation headings; enforcement should target implementation sub-step headings, not unrelated prose headings.
- Backward-compat flat manifests may still parse, but plan-mode-created artifacts should satisfy the stricter contract.
- Failure messages must stay explicit enough for plan authors to fix the org artifact quickly.

* Acceptance Criteria
- `exit_plan_mode` rejects child items missing `ITEM` TODO-outline implementation headings.
- `exit_plan_mode` rejects PLAN items that remain findings-rich but execution-thin under the new contract.
- Wave parsing remains stable when new PLAN-level implementation headings are present.
- Prompt and validation tests fail on regression and pass for balanced execution-first plans.
- Validation errors remain concrete and actionable, naming the missing invariant rather than failing generically.
