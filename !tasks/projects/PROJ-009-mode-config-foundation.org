* Initial Message

I want to make my sales and marketing cofounders more able to use spell by e.g. being able to create .spell/<something> files that e.g. customise the behaviour of plan, ultraplan, and audit. What can you propose?

* Scope

**In scope:**
- ~ModeConfig~ type definition + ~ModeConfigFrontmatter~ schema
- Mode capability type in discovery system (~capability/mode.ts~)
- Discovery from ~.spell/modes/<name>/MODE.md~ (project ~.spell/modes/~ + user ~~/.spell/agent/modes/~)
- Body section parser: split markdown body by ~##~ headings into named sections (Context, Instructions, Focus Areas, Examples)
- Extends chain resolver with cycle detection (single-parent only)
- Frontmatter validation schema
- Project/user precedence (project overrides user, same as skills)
- Deep merge semantics for extends chain (child overrides parent for scalars, arrays replace, objects deep-merge)
- Tool allow/deny resolution through extends chain

**Out of scope (handled by downstream items):**
- Prompt injection into existing templates (FEAT: Mode Prompt Injection)
- Slash command registration and mode activation (FEAT: Mode Activation + Runtime)
- Lifecycle generalization / ActiveModeState (FEAT: Mode Lifecycle Generalization)
- Canvas/QML UI loading (FEAT: Canvas Integration)

**Boundary rationale:** This is the pure data model and parsing layer. It produces loaded, validated, resolved ~ModeConfig~ objects that all downstream features consume. No runtime behavior changes, no prompt changes, no tool registration. Strict separation ensures the foundation is testable in isolation.

* Edge Cases

- *MODE.md with BOM*: Strip UTF-8 BOM before parsing (existing ~parseFrontmatter~ should handle this).
- *MODE.md with frontmatter but empty body*: Valid — ~sections~ all undefined, ~custom~ empty map.
- *Extends target = built-in name*: Resolves against ~modes/definitions/plan.md~ etc., not user .spell/modes/plan/.
- *Multiple .spell/modes/ in ancestor dirs*: Walk up like skills, closest to cwd wins, deeper ancestors ignored for same name.
- *Unknown frontmatter fields*: Warn via logger, don't fail. Forward compatibility for future extensions.
- *MODE.md updated while session active*: Modes are loaded once at startup (same as skills). Changes require session restart.
- *Directory without MODE.md*: Silently ignored during discovery.
- *MODE.md with only body (no frontmatter)*: Derive name from directory name, all frontmatter defaults apply.
