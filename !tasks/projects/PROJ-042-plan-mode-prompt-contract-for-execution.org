* Scope
In scope:
- Rework the planning prompt contract so PLAN artifacts remain high-context but become execution-first for fresh execution sessions.
- Update planning-facing prompt surfaces that define what a good plan must contain: `packages/coding-agent/src/prompts/system/plan-mode-active.md`, `packages/coding-agent/src/prompts/system/plan-mode-subagent.md`, and any directly-coupled prompt assertions in prompt-template tests.
- Introduce explicit PLAN-level implementation guidance requirements in addition to `* Context`, `* Verification`, and `* Execution Manifest`.
- Require child-item implementation sub-step headings to use TODO-outline form with `ITEM` plus `:CUSTOM_ID:` / `:DEPENDS:`.

Out of scope:
- Changing the org storage model or category layout.
- Removing or shortening rationale-heavy sections (`Scope`, `Existing Patterns`, `Tests`, `Edge Cases`, findings/rationale in PLAN `Context`).
- Planner execution handoff prompts and runtime orchestration wording beyond the surfaces listed above; covered by sibling child item.

Rationale: recent plans are structurally valid but often over-index on exploration findings and critical files, leaving a fresh execution agent to reconstruct the actual implementation path. This item fixes the plan contract at the prompt layer without reducing plan resolution.

- Spec anchor: `specs/plan-mode-prompt-guidance-2026.md` — canonical findings, bias diagnosis, and target behavior.

- Existing conventions to preserve: org-native decomposition, `org wave`, `:CUSTOM_ID: CHILD::suboutline-id`, test-first ordering, self-contained fresh-session handoff.

* Edge Cases
- Plans with rich architectural findings but weak manifests must now be considered incomplete; prompt wording should make this explicit.
- Smaller tasks must not be forced into shallow or lower-resolution plans; they may have fewer workstreams, but each still needs executable steps.
- TODO-outline `ITEM` headings must not break test-first ordering guidance; tests still precede implementation where applicable.
- Prompt updates must not accidentally imply that rationale sections are optional or should be compressed.

* Acceptance Criteria
- Rendered planning prompts explicitly distinguish high-context findings from execution instructions.
- Child implementation examples use `** ITEM ...` headings while preserving `:CUSTOM_ID:` / `:DEPENDS:` structure.
- Rendered plan-mode guidance requires PLAN-level implementation instructions beyond a flat or wave-based manifest.
- Planning subagent guidance requests implementation-ready output, not only critical files.
- Prompt tests fail if planning regresses back to findings-heavy but execution-thin output.
