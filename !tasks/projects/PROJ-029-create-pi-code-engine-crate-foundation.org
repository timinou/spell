* Context: Why This Crate Exists

The =code= tool in Spell currently has two backends: (1) an Emacs daemon for file-local operations (outline, read, navigate, edit) and (2) a Rust =pi-code-graph= crate for cross-file graph operations (context, impact, deps, flow, etc.). The Emacs path has latency (socat + JSON-RPC per call), requires an Emacs 29+ daemon with tree-sitter, and duplicates language understanding: Elisp defines declaration patterns in =pi-treesit.el= while Rust defines its own extractors in =pi-code-graph/src/language/=.

We are building =pi-code-engine= as a new Rust crate that replaces the Emacs backend entirely for the =code= tool. It will own all file-scoped code intelligence: buffer management, outline, read, navigate, structural edits, and language profiles. The existing =pi-code-graph= crate will be refactored to depend on =pi-code-engine= for language profiles and symbol extraction, eliminating its duplicated TS/Elixir extractors.

The canonical design document is =specs/pi-code-engine-spec.md=. Read it fully before starting any implementation.

* Goal

* Design Decisions (All Binding on Implementation)

1. Crate location: =crates/pi-code-engine/=
2. Pure Rust library — no NAPI, no Emacs, no JS. NAPI bindings live in =pi-natives= and are a separate item.
3. Language profiles are the single source of truth for all language understanding. One profile drives outline, navigate, graph extraction, structural edits.
4. Profiles have two parts: (a) a runtime-loaded YAML/JSON definition specifying declarations, imports, exports, references, separators; (b) build-time generated production rules from tree-sitter =node-types.json= files.
5. Built-in profiles for 4 languages: TypeScript/JavaScript (shared profile), Rust, Python, Elixir.
6. =LanguageRegistry= holds all loaded profiles. Profiles are matched by file extension. Registry is created once, shared via =Arc=, immutable after construction.
7. Production rules follow the combobulate pattern: each node type maps to its named fields and the child types valid in each field. Inverse rules map child type → possible parent types. These are used by the Procedure DSL (separate item) and for validating structural edits.
8. =build.rs= generates production rules from grammar crates' =node-types.json= files at compile time. The generated code lives in =$OUT_DIR= and is included via =include!=.

** =crates/pi-code-engine/build.rs=

This script reads =node-types.json= from each tree-sitter grammar crate and generates Rust code.

How to find =node-types.json=: Each tree-sitter grammar crate bundles this file. The path depends on the crate — typically at the crate's source root or in a =src/= subdirectory. Use the =DEP_TREE_SITTER_<LANG>_DIR= env var if the grammar crate sets it via cargo:rustc-link-search, otherwise locate it via the crate's manifest directory.

Strategy that works reliably:
1. Use =std::env::var("OUT_DIR")= to get output path
2. For each grammar, try to find =node-types.json= by searching the grammar crate's source directory (use =pkg_config= or hardcode known relative paths from the crate source)
3. If found: parse JSON, generate Rust constants
4. If not found: generate empty constants with a compile-time warning (=println!("cargo:warning=...")=)

Generated file format for each language:

#+begin_src rust
// Generated by build.rs from tree-sitter-typescript/node-types.json
// DO NOT EDIT

use std::collections::HashMap;

pub fn production_rules() -> HashMap<&'static str, (&'static [&'static str], &'static [(&'static str, &'static [&'static str])])> {
    // Maps node_type -> (unnamed_children, [(field_name, [child_types])])
    let mut rules = HashMap::new();
    rules.insert("if_statement", (
        &[] as &[&str],  // unnamed children
        &[
            ("alternative", &["else_clause"] as &[&str]),
            ("condition", &["parenthesized_expression"]),
            ("consequence", &["statement"]),
        ] as &[(&str, &[&str])],
    ));
    // ... more rules
    rules
}

pub fn inverse_rules() -> HashMap<&'static str, &'static [&'static str]> {
    // Maps child_type -> [parent_types]
    let mut rules = HashMap::new();
    rules.insert("else_clause", &["if_statement"] as &[&str]);
    // ...
    rules
}

pub const ALL_TYPES: &[&str] = &["if_statement", "function_declaration", ...];
pub const SUPERTYPES: &[&str] = &["expression", "statement", "declaration", ...];
#+end_src

The =node-types.json= schema (from tree-sitter docs):
- Array of objects, each with: =type= (string), =named= (bool), =fields= (object mapping field name → {types, required, multiple}), =children= (same shape), =subtypes= (array of {type, named})
- Nodes with =subtypes= are supertypes (abstract, never appear in real tree)

#+begin_src rust
use std::collections::HashMap;
use serde::{Deserialize, Serialize};
use crate::language::LanguageId;

/// A complete language profile driving outline, navigate, graph extraction, and structural edits.
#[derive(Debug, Clone)]
pub struct LanguageProfile {
    pub id: LanguageId,
    pub extensions: Vec<String>,
    pub declarations: Vec<DeclarationPattern>,
    pub class_like: Vec<ClassLikePattern>,
    pub imports: Vec<ImportPattern>,
    pub exports: Vec<ExportPattern>,
    pub references: Vec<ReferencePattern>,
    pub separators: Vec<String>,
    /// Build-time generated. Maps node_type → (unnamed_children, [(field, [child_types])]).
    pub production_rules: ProductionRules,
    /// Build-time generated. Maps child_type → [parent_types].
    pub inverse_rules: InverseRules,
    /// All known node types for this language.
    pub all_types: Vec<String>,
    /// Abstract supertypes (never in real parse tree, used in rule expansion).
    pub supertypes: Vec<String>,
    /// tree-sitter Language object for creating parsers.
    pub ts_language: tree_sitter::Language,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct DeclarationPattern {
    pub node_types: Vec<String>,
    pub name_field: String,
    pub kind: String,
    #[serde(default)]
    pub body_field: Option<String>,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ClassLikePattern {
    pub node_type: String,
    pub body_field: String,
    pub member_types: Vec<String>,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ImportPattern {
    pub node_type: String,
    pub specifier_field: String,
    #[serde(default)]
    pub is_type_only: bool,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ExportPattern {
    pub node_type: String,
    pub visibility: String,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ReferencePattern {
    pub node_type: String,
    pub exclude_parent_types: Vec<String>,
}

/// Production rules: node_type → field definitions.
pub type ProductionRules = HashMap<String, ProductionRule>;
pub type InverseRules = HashMap<String, Vec<String>>;

#[derive(Debug, Clone, Default)]
pub struct ProductionRule {
    pub unnamed_children: Vec<String>,
    pub fields: HashMap<String, Vec<String>>,
}

/// YAML-loadable profile (subset — no production rules, those are generated).
#[derive(Debug, Deserialize)]
pub struct ProfileYaml {
    pub language: String,
    pub extensions: Vec<String>,
    #[serde(default)]
    pub declarations: Vec<DeclarationPattern>,
    #[serde(default)]
    pub class_like: Vec<ClassLikePattern>,
    #[serde(default)]
    pub imports: Vec<ImportPattern>,
    #[serde(default)]
    pub exports: Vec<ExportPattern>,
    #[serde(default)]
    pub references: Vec<ReferencePattern>,
    #[serde(default)]
    pub separators: Vec<String>,
}

/// Load a profile from YAML string. Production rules must be attached separately.
pub fn load_profile_yaml(yaml: &str) -> crate::error::Result<ProfileYaml> {
    serde_yaml::from_str(yaml).map_err(|e| crate::error::CodeEngineError::Profile(e.to_string()))
}
