* Scope
In scope:
- Replace the current top-level `code edit` mutation fanout (`create`, `patch`, `replace-body`, `replace`, plus duplicated `file`/`symbol`/`line` targeting) with one deduplicated recursive schema centered on stable graph/code-engine target IDs.
- Make `code edit` accept one canonical top-level request shape: `operations: [...]`, where each node names one `targetId`, one ordered `actions: [...]` list, and optional nested `children: [...]` for sub-symbol work.
- Treat file roots as first-class targets in the same ID namespace as semantic symbols so whole-file create/replace and symbol-level edits share one reference model.
- Keep `content` as the canonical replacement payload and move current patch semantics into a dedicated action kind (for example `findAndReplace`) instead of a separate top-level operation family.
- Preserve only truly distinct semantic transforms as action kinds (`rename`, `wrap`, `kill`, `move`, `clone`, token renames, etc.), not as duplicated target-selection APIs.
- Cut over internal callers, prompts, result typing, diagnostics, task/subagent emission, native bridge types, and focused tests in the same change. Hard cutover only: no aliases, shims, or mixed-mode contracts.
- If required to make plan execution truthful, remediate the org tooling gap around sub-outline wave/manifests as part of the implementation sequence rather than hand-waving around it.

Out of scope:
- Broad code-graph feature expansion unrelated to stable edit target IDs.
- Adding new edit semantics not already represented by the current code tool family.
- Preserving external backward compatibility for the removed `create` / `patch` / `replace-body` / `replace` shapes.
- General AST rewrite redesign outside the `code` tool contract.

Rationale:
- The observed task-subagent bug is a schema smell, not an Elixir/path support problem: duplicated top-level operation shapes let callers emit invalid combinations like `operation: "create"` plus read defaults such as `resolution`.
- The settled design direction is deduplication by default: one target reference type, one recursive operation tree, one content-writing surface, one cutover.
- Stable graph-backed target IDs are required so nested operations can reference symbols uniformly across read/navigation/edit flows instead of oscillating between `file`, `symbol`, and `line` entry points.

* Edge Cases
- File-root target IDs must remain stable for missing-file create without requiring a pre-existing symbol record.
- Nested child operations must fail truthfully when a parent replacement invalidates child byte ranges or ownership assumptions.
- Legacy payloads may appear partially normalized by wrappers; rejection logic must detect mixed old/new fields and explain the canonical repair path.
- `findAndReplace` / patch-like actions must stay scoped to the resolved target and reject ambiguous matches rather than broadening silently.
- Result renderers and failure classifiers must not leak stale references to removed operations such as `create` or `replace-body`.
- Stable target IDs must survive language-specific declaration forms (nested methods, exported wrappers, markdown sections, HTML/CSS tokens where supported) without collapsing unrelated symbols together.
- If org-wave support is touched, the change must not corrupt existing category-wide wave behavior while adding truthful item/sub-outline planning support.

* Acceptance Criteria
- One canonical recursive `code edit` schema exists and is used across prompts, tool validation, native bridge types, and internal callers.
- File roots and semantic symbols share one stable `targetId` namespace that supports whole-file and nested symbol edits.
- The old top-level `create` / `patch` / `replace-body` / `replace` shapes are removed from the public contract and rejected truthfully when used.
- Task/subagent emission no longer produces malformed create payloads or duplicated target fields.
- Focused verification passes for the touched layers, at minimum the exact package/crate tests selected above plus `bun check:ts` and `bun check:rs` if the implementation crosses both TypeScript and Rust.
- If org-wave remediation is needed, execution manifests can truthfully reflect the intended dependency DAG instead of collapsing to a misleading file-level stub.
