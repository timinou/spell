** Wire ExitPlanModeTool to call org-fluid-plan
:PROPERTIES:
:CUSTOM_ID: FUP-012-fluid-orchestration-wiring-prerequisi::wire-exit-plan-mode
:END:

~ExitPlanModeTool.execute()~ currently extracts waves via ~extractPlanWaves()~ but never calls the ~org-fluid-plan~ MCP tool to build ~FluidPlanWithComponents~. The ~fluidPlan~ field in ~ExitPlanModeDetails~ is always undefined.

Fix:
- In ~exit-plan-mode.ts~, after resolving the PLAN item and extracting child IDs, call the Emacs MCP tool ~org-fluid-plan~ with ~{plan_id: params.itemId}~
- Parse the JSON response into ~FluidPlanWithComponents~
- Set ~details.fluidPlan~ in the return value
- The interactive-mode ~#approvePlan~ already passes ~details.fluidPlan~ through, and ~#executeViaFluidOrchestrator~ already checks for it

** Add sub-plan validation
:PROPERTIES:
:CUSTOM_ID: FUP-012-fluid-orchestration-wiring-prerequisi::sub-plan-validation
:END:

~validatePlan~ is called only on the top-level coordinator plan. Sub-plans passed to coordinator nodes skip validation entirely. An 80+ node sub-plan inside one coordinator receives no cycle detection, no dependency integrity check.

Fix: Run ~validatePlan~ on each component's sub-plan in ~FluidOrchestrator.execute()~ before wrapping in coordinator nodes.

Files: ~packages/coding-agent/src/orchestrators/fluid/fluid-orchestrator.ts~, ~packages/coding-agent/src/orchestrators/fluid/dag.ts~

** Configure concurrency limits
:PROPERTIES:
:CUSTOM_ID: FUP-012-fluid-orchestration-wiring-prerequisi::concurrency-limits
:END:

No global subprocess concurrency cap across coordinator nodes. Multiple concurrent coordinators can each spawn parallel agents. With 98 nodes and concurrency=5 per coordinator, this could create many concurrent API calls.

Fix:
- Make ~MAX_RECOMMENDED_AGENT_COUNT~ configurable via settings (~fluid.maxAgents~) or suppress for legitimate large plans
- Consider a shared semaphore for subprocess spawning across coordinators
- Use ~fluid.concurrency~ setting (already exists, default 5) but verify it applies to coordinator-spawned subprocesses too

Files: ~packages/coding-agent/src/orchestrators/fluid/fluid-orchestrator.ts~, ~packages/coding-agent/src/orchestrators/fluid/queue-scheduler.ts~

* Edge Cases
- org-fluid-plan MCP call fails (Emacs not running): fall back to wave-based execution or error gracefully
- Sub-outline CUSTOM_IDs not found: org-fluid-plan emits warnings, partial plan still executes
- Deferred nodes with downstream dependents: dependents should still execute (deferred counts as completed)
- Coordinator subprocess crash: QueueScheduler marks node failed, propagates to dependents

* Acceptance Criteria
- ~spell --canvas fluid~ with an org plan containing [[id:...]] links produces a FluidPlan via org-fluid-plan
- Plan approval flow populates fluidPlan in ExitPlanModeDetails
- FluidOrchestrator executes the plan (not legacy prompt injection)
- FUP items with deferred flag are skipped during execution
- Coordinator agents receive full body context for sub-outline nodes
- Sub-plans are validated before execution
