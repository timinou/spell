* One-line

A dashboard tile that holds a saved PTC-Lisp WRITE program (a codemod), shows
"would change N files" as a live drift signal whenever the dashboard is open, and
applies it transactionally with one click (or auto, if armed).

* Why this is the anchor use case

This is the purest expression of W4-write's value: a transform stops being a
one-shot command and becomes a DURABLE, RE-APPLICABLE object. The dev keeps the
codemod; it watches the repo; it tells them when the repo has drifted away from the
shape the codemod enforces; applying it is one safe, atomic action. It is the case
that justifies the whole "program as a value" thesis.

* The grounded scenario (concrete, end to end)

A repo migrated its logger: `oldLog(x)` → `logger.info(x)`. New code occasionally
reintroduces `oldLog` (muscle memory, copy-paste, merges). The dev wants a STANDING
guard, not a one-time sweep.

They author the codemod once as a stored write program:

```clojure
;; title: "migrate oldLog → logger.info"
;; mode: write
(->> (tool/find {:target "src/**/*.ts::§call[name=oldLog]"})
     (map (fn [hit]
            (tool/edit {:operations
              [{:target (str (get hit "path") "::" (get hit "symbol"))
                :action {:kind "replace" :find "oldLog" :content "logger.info"}}]})))
     (count))                       ; returns N files changed
```

They save it as a tile on their project dashboard. From then on:

** State A — repo is clean (no oldLog anywhere)
The tile renders calm: "migrate oldLog → logger.info · ✓ no drift". The visible-refresh
dry-run found 0 matches → 0 writes → nothing to do. No noise.

** State B — drift appears (someone reintroduced oldLog in 3 files)
Next time the dashboard is OPEN, the tile's visible-refresh dry-run runs the program
read-only (D3 captures the writes, force-rolls-back), and the tile renders:
"migrate oldLog → logger.info · ⚠ would change 3 files" with the file list on hover
and an [Apply] affordance.

** State C — the dev clicks [Apply] (interactive intent)
The program runs for real, transactionally. The tile renders the structured txn
outcome: "✓ committed 3 files (foo.ts, bar.ts, baz.ts) · 14:32". If the program had
errored mid-run, D3 rolls back and the tile shows "↩ rolled back — program failed:
<reason>, repo unchanged". Either way the repo is never half-migrated.

** State D — the dev arms autoWrite (background-tick intent, opt-in per tile)
For a codemod they fully trust, they flip the tile's "auto-apply" toggle. Now even a
background tick (dashboard closed) applies the transform and APPENDS a visible audit
line to the tile's history: "✓ auto-committed 2 files · 03:14". Never silent.

* Architecture (step by step)

1. STORAGE. A tile persists a StoredProgram (program text + mode:"write" + title +
   optional signature) plus tile-local UX state: { autoWrite: boolean,
   lastOutcome?: TxnOutcome, lastRunAt?: number, history: AuditLine[] }. Storage host
   is the dashboard/canvas tile model (confirm the exact store; likely the org item's
   PROPERTIES drawer or a canvas window's bridge state, mirroring how W4-read tiles
   store their :program block).

2. REFRESH (visible). When the dashboard is open and the tile refreshes, the host
   calls `executeTool.runStored(stored, { intent: "visible-refresh" }, context)`. Per
   FUP-112, a write program under visible-refresh runs as a DRY RUN: the program
   executes, D3 captures the writes, then force-rolls-back even on success. The result's
   `details.transaction` = { outcome: "dry-run", files: N, paths: [...] }. The tile
   renders the drift signal from that (N>0 → "would change N", N=0 → "no drift").

3. APPLY (interactive). The [Apply] button calls
   `runStored(stored, { intent: "interactive" })`. The write executes for real;
   `details.transaction` = { outcome: "committed" | "rolled-back", files, ... }. The
   tile renders the outcome and appends an audit line.

4. AUTO (background). If `tile.autoWrite` is set, a background tick calls
   `runStored(stored, { intent: "background-tick", autoWrite: true })` → writes for
   real, records the outcome to the tile's history (visible on next open). If autoWrite
   is NOT set, a background tick is INERT (per FUP-112) — the tile keeps its last known
   state, costs nothing.

5. The host NEVER constructs the rollback logic — it only reads `details.transaction`
   and renders. All atomicity lives in D3; all mode/intent logic lives in FUP-112; this
   UC is purely presentation + the per-tile autoWrite toggle.

* UX (taste)

```
┌─ migrate oldLog → logger.info ──────────────[⚙]─┐
│  ⚠ would change 3 files                          │   ← visible-refresh dry-run
│  foo.ts · bar.ts · baz.ts                        │
│  ┌─────────┐  ┌──────────────┐                   │
│  │ Apply   │  │ ⏻ auto-apply │  last: 14:02 ✓2   │   ← Apply = interactive
│  └─────────┘  └──────────────┘                   │      toggle = arm autoWrite
└──────────────────────────────────────────────────┘
```
- Calm by default: 0 drift → a single ✓ line, no buttons clamor.
- The drift count is the headline; the file list is secondary (hover/expand).
- [Apply] is primary only when drift>0; greyed when clean.
- "auto-apply" is a deliberate, sticky per-tile toggle with a visible armed state (a
  filled indicator) so the dev always knows which tiles can mutate unattended.
- Every real write (interactive or auto) leaves a timestamped audit line; the tile's
  history is one expand away. Discard/rollback outcomes are shown with equal weight to
  commits (a failed apply must not look like a no-op).
- Colour: drift = warning amber (actionable, not alarming red); committed = success
  green; rolled-back = neutral with a clear "repo unchanged" reassurance.

* Tests

- visible-refresh on a drifted repo → tile shows "would change N", repo UNCHANGED
  (dry-run actually rolled back).
- visible-refresh on a clean repo → "no drift", 0 writes.
- interactive Apply → repo changed, txn outcome "committed", audit line appended.
- a program that errors mid-apply → "rolled-back", repo unchanged, failure surfaced.
- background-tick, autoWrite OFF → INERT (no run, no cost, tile state unchanged).
- background-tick, autoWrite ON → writes for real, audit line recorded.

* Acceptance

A saved codemod tile shows live drift while the dashboard is open without mutating,
applies atomically on click with a visible committed/rolled-back outcome, and only
mutates on a background tick when explicitly armed — every real write leaving an audit
line.
