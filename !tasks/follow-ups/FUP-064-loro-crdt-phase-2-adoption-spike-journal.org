** Writeup must answer these questions
:PROPERTIES:
:CUSTOM_ID: FUP-064-loro-crdt-phase-2-adoption-spike-journal::writeup-coverage
:END:
1. Does Loro's =LoroText= expose the =op[]= granularity our journal already assumes (insert/delete at byte offsets, encoded as a compact op sequence)?
2. What is Loro's document identity model? Does it fit per-file repo-scoped coordination, or does it require a single root doc?
3. What is the serialized op size for typical edits (a method rename, a 100-line insertion) versus our current structural-diff size? Include concrete measurements from Loro docs or a quick =cargo add= scratch crate outside the workspace.
4. What is Loro's conflict model for overlapping concurrent edits on the same byte range? Is block-on-conflict still possible, or does Loro force merge-always semantics?
5. How does Loro integrate with tree-sitter boundaries? Can we still attribute edits to CodePath nodes after merge, or does character-level concurrent merge dissolve that attribution?
6. What is Loro's GC/snapshot story? Does it handle long-lived repos with millions of historical ops?
7. What is the Rust API stability commitment? Version pinning risk.
8. Licensing: is Loro's license compatible with ours (check workspace =LICENSE=).
9. What is the minimal shim to make the existing journal forward-compatible without breaking existing readers?
