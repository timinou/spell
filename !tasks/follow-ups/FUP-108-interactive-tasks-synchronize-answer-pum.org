** R1 \u2014 broker.close() races in-flight answer fork (P2)
~askBroker?.close()~ runs synchronously after ~scheduleBatch~ resolves, but the answer pump is fire-and-forget (~void (async () => { ... broker.answer() })()~). If the batch resolves while a fork is still streaming, close() clears ~#pending~ and the in-flight ~broker.answer~ later no-ops (answer silently dropped, warn-logged). Conversely a delivery can land into a session whose ~finally~ is about to ~dispose()~.
Fix sketch: track in-flight fork promises on the broker; ~close()~ should await pending forks (bounded timeout) before resolving-cancelled. Or have the pump register an AbortController the broker signals on close.

** R2 \u2014 isolated worktree teardown race (P2, conf 0.4)
Isolated subagents get followUp delivery identically; a late non-blocking answer could start a turn referencing a worktree being torn down in ~cleanupWorktree~. Compounds R1 + the (now-fixed) revival issue. The ~session.isStreaming~ delivery guard added in wave-2 triage mitigates the common case (idle worker won't revive), but a worker streaming AT teardown time is still a window.
Fix sketch: gate delivery additionally on \"worker not in teardown\"; or drain/await deliveries before cleanup.

Both are timing windows, not common-path. The wave-2 triage already fixed the two P1s (fork-rejection deadlock; non-blocking revival via isStreaming guard) and redesigned D6 to be turn-safe (answeredLog in result text instead of mid-turn history mutation).
