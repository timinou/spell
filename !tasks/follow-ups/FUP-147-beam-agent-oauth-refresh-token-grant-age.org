* Why deferred
The Anthropic subscription token in agent.db is a 1-YEAR token (verified: expires
2027-05-07), so v0 never needs to refresh during normal use. SpellAgent.OAuth.maybe_refresh/2
currently returns a near-expiry token unchanged with a warning.

* What to build
- Implement the refresh-token grant in SpellAgent.OAuth:
  POST https://api.anthropic.com/v1/oauth/token
  body {grant_type: "refresh_token", client_id: "9d1c250a-e61b-44d9-88ed-5944d1962f5e",
        refresh_token: <refresh>}. Response {access_token, refresh_token, expires_in} →
  new expires_ms = now_ms + expires_in*1000 - 300_000.
- Decide write-back policy: v0 keeps the refreshed token IN MEMORY to avoid clobbering
  the parallel TS Spell's agent.db. For a long-lived BEAM agent, persisting back is needed.
  Options: (a) write to agent.db with an UPDATE (must match TS Spell's row format + updated_at);
  (b) a separate spell_agent-owned credential store. Prefer (a) if the formats stay compatible —
  one source of truth — but verify the TS AuthStorage round-trips what we write.

* Acceptance
- A mock token endpoint test: expired cred -> ensure_fresh/0 performs the grant -> returns a
  non-expired cred with the new access token.
- If write-back chosen: a refreshed token is readable by a fresh SpellAgent.Credentials.load/1
  AND does not break TS Spell's reader (manual cross-check).

- packages/ai/src/utils/oauth/anthropic.ts (TS refresh flow + client_id, base64-wrapped)
- packages/ai/src/auth-storage.ts (how TS persists refreshed tokens to agent.db)
