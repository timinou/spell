* Context (follow-up to BUG-462)

BUG-462 (commit 2f0548a1e) turned `type_error` from a dead end into a recoverable
error for ONE curated case: `(contains? <string> <string>)` →
"For strings use (includes? s sub) or (index-of s sub)". The mechanism is a
per-builtin/per-arg-shape clause table, `specific_type_error/2`, in
`beam/ptc_runner-vendored/lib/ptc_runner/lisp/eval/helpers.ex`, consulted by
`type_error_for_args/2` (~helpers.ex:90) before falling back to
`generic_type_error/2` (~helpers.ex:109, the bare "invalid argument types: …").

This is the same affordance the excellent `unbound_var` path already provides
("Did you mean: starts-with?" / ".substring") — but for type mismatches.

* The opportunity

Add new `specific_type_error/2` clauses as real collisions are observed in live
`execute` use. Candidate next entries (verify each is real before adding):
- `(get <list> k)` shape errors → point at `(nth coll i)` / `(first …)`.
- `(assoc <list> …)` / `(update <list> …)` → vector-vs-list idioms.
- numeric ops on strings → `(parse-long s)` / `(parse-double s)` first.

* Non-goals (deliberate)

Do NOT build a blanket type-inference / coercion-suggestion engine. The curated
per-case table is intentional: each clause is a verified, high-signal idiom
collision, matching the codebase's style and the `unbound_var` suggestion engine.
Speculative clauses that never fire (see FUP-134, conj) are the failure mode to
avoid.

* Acceptance

Each added clause: (a) cites a real observed friction, (b) suggests the correct
idiom, (c) has a test in nil_poison_test.exs proving it fires AND that the correct
typed call still works (no false positive).
