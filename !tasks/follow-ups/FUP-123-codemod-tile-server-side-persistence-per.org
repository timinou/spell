* DECIDED ARCHITECTURE (supersedes the original SQLite+server-scheduler sketch below)

Decided 2026-06-11 with the user (refining-question pass). See decision memory
DEC-tile-persistence-architecture--org-item-. Four locks:

1. SCHEDULER = SPLIT. The pi-knowledge-worker daemon IDLE-EXITS after 30min by design
   (crates/pi-knowledge-worker/src/main.rs:9 + accept_loop exits when idle>=idle_secs, to
   not pin RAM) → it CANNOT fire a 3am nightly tick. So this FUP builds ONLY persistence +
   browser-driven "tick while panel open". The unattended-3am scheduler is split out to
   FUP-129 (needs an always-on host: OS timer / systemd-timer one-shot, NOT the daemon).

2. PROGRAM lives in a memory playbook :program block (FUP-115), referenced by id. A tile
   stores program_ref=playbook-id, NOT inline program text. One program, many wirings by
   ref (solves FUP-121 identity). FUP-115 is a soft dependency — until it ships, a tile MAY
   fall back to inline program text, but the schema carries program_ref as the forward path.

3. PERSISTENCE = SPLIT by lifecycle (record has two halves, opposite storage needs):
   - TILE CONFIG (low-churn, declarative) = an ORG ITEM with a PROPERTIES drawer.
   - TILE HISTORY (high-churn, event-log) = a memory EPISODE per run + last-outcome cached
     as a property on the org item for fast render.
   ∴ NO new storage backend. (spell-server SQLite stays read-only; not reopened writable.)

4. owner+project columns BOTH present → per-operator now, per-project-shared later (sharing
   flag deferred). This maps to the user's "save into a note/episode, promote" instinct.

* What gets written (exact)

** Tile config — an org item (category: follow-ups or a new `tiles` category — decide at impl)

```
* Codemod: migrate oldLog -> logger.info
  :PROPERTIES:
  :CUSTOM_ID:    FUP-123-codemod-tile-server-side-persistence-per::TILE-a1b2
  :OWNER:        alice            ; operator token
  :PROJECT:      /code/ora/spell  ; cwd/project key
  :PROGRAM_REF:  PB-migrate-oldlog ; -> memory playbook id (FUP-115); inline fallback ok
  :MODE:         write
  :AUTOWRITE:    t                ; the arm toggle (trust signal)
  :SCHEDULE:     0 3 * * *        ; for FUP-129's unattended half; unused here
  :LAST_OUTCOME: committed        ; cached for fast render
  :LAST_FILES:   4
  :LAST_RUN_AT:  2026-06-11T03:00
  :END:
```

Queryable: "armed tiles for project X" = org-query property filter AUTOWRITE=t PROJECT=X.

** Tile history — a memory episode per run (KG timeline)

On each run (interactive or browser-tick), append a memory episode:
`note "tile TILE-a1b2 <intent> <outcome> <files> [paths]"` with about=[TILE-a1b2 org id],
involved=[program_ref]. The episode store is the durable bounded timeline (KG handles
retention). The org item caches ONLY the last outcome (3 properties above) for render
without a KG query.

* Build scope (this FUP — persistence + browser-tick only)

1. ORG TILE STORE (coding-agent): helpers to create/read/update a tile org item via the
   existing org tool surface (PROPERTIES drawer read/write). owner+project keyed. A list
   query for the web UI: tiles WHERE project=current. NB use the agent's existing org file
   locking — tiles may be written by a browser action AND (later) a scheduler.

2. HISTORY = memory episode (coding-agent): on every run, write one episode; update the
   org item's LAST_OUTCOME/LAST_FILES/LAST_RUN_AT cache properties. Bounded by KG retention,
   not a hand-rolled 50-cap.

3. WEB UI wiring (spell-team-chat + spell-server): the CodemodTilePanel reads/writes tiles
   via a NEW REST surface (GET/PUT /web/api/tiles → coding-agent org-tile-store). localStorage
   becomes the OFFLINE FALLBACK, not the source of truth. The run_stored RPC path is unchanged.
   Browser-driven tick: the existing on-open visible-refresh + interactive Apply stay; this
   just persists their outcomes server-side instead of per-browser localStorage.

4. NO unattended firing here. autoWrite ARMS a tile and persists; nothing fires it on a
   schedule yet — FUP-129 owns that. Document this clearly in the tile UI ("armed; auto-runs
   when the scheduler ships").

* Tests

- Create a tile → an org item with the PROPERTIES drawer round-trips (owner/project/program_ref/
  mode/autoWrite); a second read returns identical config.
- A run appends a memory episode AND updates the org item's LAST_OUTCOME cache; the panel
  renders last-outcome from the cache without a KG query.
- List tiles for project X returns only X's tiles (owner+project filter).
- Arming (autoWrite=t) persists to the org item and survives reload (server-side, not just
  localStorage); a second operator on the same project sees the tile (per-project read path
  present even if sharing-write is deferred).
- Offline (server unreachable) → localStorage fallback still renders the last-known tiles.

* Acceptance

Tile configs persist as org items (git-tracked, org-queryable, owner+project keyed), run
history persists as memory episodes with a last-outcome cache on the org item, and the
team-chat panel reads/writes server-side with localStorage as offline fallback. No new
storage backend. Unattended scheduled firing is explicitly OUT (FUP-129).
