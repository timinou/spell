* Scope
~packages/coding-agent/src/modes/fluid-mode.ts~ and ~packages/coding-agent/src/orchestrators/fluid/~ currently use ~materializeFluidPlanToTodos~ and ~fluidPlanToTodoPhases~ to map FluidPlan DAG nodes into todo phases, then dispatch tasks separately.

After task-tool auto-roster + DAG scheduling lands, fluid mode can potentially use the same unified dispatch path by sending tasks with ~phase~ and ~blockers~ and letting auto-roster create/manage todos.

Analysis must cover:
- Fluid orchestrator retry behavior and interaction with todo state transitions
- Canvas output handling via ~canvasOutput~ on ~FluidAgentNode~
- Event lifecycle compatibility across ~FluidEvent~ types
- Runtime tracking correctness for ~taskIdByAgentId~ mapping

Deferred intentionally: current fluid-mode flow is stable, and auto-roster can ship without this unification.

* Acceptance Criteria
- Fluid mode uses the same task dispatch path as agent-driven work
- ~plan-to-todos.ts~ utilities remain available but are no longer the primary consumer path
- Fluid-mode retry logic remains correct with auto-roster-created items
- Canvas output handling behavior is preserved
