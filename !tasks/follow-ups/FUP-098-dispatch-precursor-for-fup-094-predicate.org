* DISCOVERY: SemanticBackend is dormant (2026-05-26)

Empirical investigation of the live ``find`` surface against HEAD =827429c24= revealed the findings are symptoms of a single underlying gap, not six independent gaps. The actual root cause:

** =type_resolver= module has ZERO call sites outside its own tests.

#+begin_src
$ grep -rln "type_resolver::dispatch" crates/pi-natives/src/
(no output)

$ grep -rln "SemanticBackend\|CompositeSemanticBackend\|hover_dual" crates/pi-natives/src/
crates/pi-natives/src/code_path/type_resolver.rs   ← only itself
#+end_src

PLAN-319 W3 built ``type_resolver::dispatch``, ``dispatch_hover``, ``SourceSelector``, ``HoverDual``, ``HoverOutcome``, the full smart-merge — and shipped it as a library nobody calls. The walker (``code_path/code_resolver/walker.rs``) still uses the *old* text-based ``#hover`` path:

#+begin_src rust
// walker.rs:163-185
if q.name == "hover" {
    let decl_text = &src[node.start_byte()..node.end_byte()];
    let sig_end = hover_signature_end(decl_text);
    // ...text-only signature extraction, no SemanticBackend
}
#+end_src

For any other qualifier (``#signature``, ``#type_definition``, ``#inlay``, ``#diagnostics``):

#+begin_src rust
// walker.rs:218
nref.diagnostics.push(Diagnostic {
    variant: DiagnosticVariant::UnsupportedOperation,
    message: format!("unknown qualifier '{}'", q.name),
    span:    None,
});
#+end_src

So the live behaviour is:
- ``#hover`` → text-based signature (no smart-merge, no LSP)
- ``#signature`` → 'unknown qualifier'
- ``#type_definition`` → 'unknown qualifier'
- ``#inlay`` → 'unknown qualifier'
- ``#diagnostics`` → 'unknown qualifier' (file-level: FsResolver also rejects)
- ``#hover_inferred`` → 'unknown qualifier' (silent because walker emits the diagnostic but the calling code suppresses it on missing qualifier? — that's a separate path; net: `[§empty]`)
- ``[source=graph|semantic|both]`` → parses (as Predicate::Attribute) but **never consulted** because dispatch isn't called
