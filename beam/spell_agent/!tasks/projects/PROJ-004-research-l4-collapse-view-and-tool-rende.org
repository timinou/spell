* The boundary this dissolves
LOOKING vs ACTING. Today (PLAN-009 v1) a slot's :render is PURE: view/ + lens/ +
harness/ read-queries over injected data, NO side-effecting tool/. This layer
removes that wall: a widget can BE a live tool call. The interface stops being a
view of state and becomes an active surface that queries and acts as it renders.

* Premise
v1 keeps view/ pure for safety (a render must not loop, cost, or mutate). That is
a deliberate boundary, not a law of the design. The render contract is
"node -> placement subtree"; nothing structural forbids a pane whose :render
performs effects.

* The move
A pane whose render is live:
  {:type "pane" :slot "pane/callers"
   :render "(view/list {:items (map :name (tool/find {:target (str (harness/cursor-id) \" def->\")}))})"}
Now "show callers of the symbol under my cursor" is a LAYOUT, not a workflow.
"Show the diff of the file I am hovering" is a pane. The codebase is queried AS
the UI renders; acting on it is the same gesture as looking at it. The render
clock and the effect system merge.

* Why it is reachable
- view/ builders and tool/ already coexist in the same PtcRunner.Lisp sandbox;
  the only thing stopping it is the deliberate tools-map restriction in the slot
  runner. Removing the restriction is a one-line policy change — the DANGER is
  why it is research, not the difficulty.

* The danger (this is the whole point of the layer being deep)
- A render with effects can: loop (render triggers a tool that changes state that
  triggers a re-render), cost real money/time per frame, and MUTATE (tool/edit in
  a render = the UI edits the codebase by being displayed).
- The frame clock is fast; effects on the frame clock are catastrophic without
  governors.

* What it needs before it is safe to even prototype
- A render-effect CAPABILITY tier: which tools may appear in a render (read-only
  query tools yes; mutating tools NEVER, or only behind explicit user gesture).
- A per-frame effect BUDGET (cost ceiling, call-count cap) enforced by the slot
  runner.
- Memoization/debounce so a stable cursor does not re-run tool/find every frame
  (PROJ caching from PLAN-009 Fork D applies; here it is mandatory not optional).
- Loop/fixpoint detection (shared with PROJ-001's render/reason loop).

* Open questions
- Is the right primitive "effects in render" at all, or "a render that DECLARES a
  data dependency the runtime satisfies once and caches" (a reactive cell, like a
  LiveView assign) — which gives the same UX (live callers pane) WITHOUT effects
  on the frame clock? The reactive-cell framing may dissolve the danger entirely:
  the pane declares `needs (tool/find ...)`, the runtime runs it on cursor-change
  (keystroke clock, debounced) and injects the result as data/. Then render stays
  pure and the boundary moves rather than vanishes. STRONGLY PREFER exploring
  this framing first.
- This is arguably where "the interface IS the agent" terminates: no line between
  inspecting the codebase and operating on it.

* Security/cost notes (FUP-track — but here security is load-bearing, not secondary)
- tool/edit (or any mutator) in a render is the highest-risk idea in the whole
  vision. If prototyped, START read-only-tools-only, behind the reactive-cell
  framing, with a hard per-frame budget. File the capability-tier + budget as a
  blocking prerequisite FUP before any mutation is allowed.

* Acceptance (reactive-cell framing, the safe form)
- A pane declares a data dependency on a read-only query keyed by the cursor; the
  runtime satisfies it on cursor-change (debounced), injects as data/, render
  stays pure; the "live callers pane" works with zero per-frame effects.

* Design of Record — Reactive Cells (the safe form)   :design:

Adopted framing: REACTIVE CELLS (spec's strongly-preferred form). Render stays
pure; the looking/acting boundary RELOCATES from "render vs workflow" to
"declare vs resolve". Effects never touch the frame clock.

** Core symmetry (the design in one line)
A hole is a PURE cell: deps -> value, FRAME clock, ZERO tools (HoleResolver, W3).
A reactive cell is an EFFECTFUL hole: deps -> value, SLOW clock (reproject /
keystroke / store-update), READ-ONLY tools, async + cached.
Same HoleDiff dependency machinery (W6). Different clock + capability tier.

Existing seams reused (nothing new invented at the substrate level):
- HoleResolver (lib/spell_agent/tui/hole_resolver.ex)  — pure frame-clock host, zero tools.
- Reaction.Ptc (lib/spell_agent/tui/reaction/ptc.ex)   — off-frame host w/ tools map + fail-safe; the model for the cell resolver.
- HoleDiff (lib/spell_agent/tui/hole_diff.ex)          — changed_keys/2 + per-hole dep tracking; the trigger.
- DataBag.build (lib/spell_agent/tui/data_bag.ex)      — the data/* injection point; cells merge here.
- reproject (app.ex:342) + handle_info({ref,result}) (app.ex:365) — the slow clock + async-task completion path.

** Syntax — declare-and-reference (render never sees the effect)
Declare (a named data dependency, resolved off-frame):
  (cell/define {:name    "callers"
                :query   (tmpl:: (tool/find {:target (str ~(get data/ui :cursor-id) " def->")}))
                :debounce 80})
Reference (an ORDINARY pure hole; render does not know it is live):
  (layout/set {:slot "pane/callers"
    :source (tmpl:: {:type "list"
                     :items [~@(map (fn [c] (get c :name)) data/callers)]})})

The :query is itself a frozen tmpl:: — its ~holes are deps on OTHER data/* keys.
When HoleDiff.changed_keys sees data/ui change, the cell re-resolves on the slow
clock and writes data/callers. The render hole ~…data/callers stays pure,
zero-tools. Cursor moves -> callers pane updates -> ZERO per-frame effects.

** The four governors (security is load-bearing here, not secondary)
1. Capability tier: cells get a NEW, SEPARATE read-only tools map (find/get/
   hist-queries/harness-reads). Mutators (edit/create/bash-write) NEVER
   registered. Render holes keep their zero-tools map untouched. (Inverts the
   spec's "remove the restriction" into "add a narrower one".)
2. Async + debounced: resolve runs in a Task (mirrors the mission {ref,result}
   path at app.ex:365), coalesced on cursor quiescence. Off the frame clock AND
   off the synchronous reproject path.
3. Memoized: HoleDiff reuse — deps unchanged -> the tool never re-runs.
4. Loop guard: static cycle check at cell/define — a cell may not depend on a
   data/* key it writes (shared concern w/ PROJ-001 render/reason loop).

** Syntax decision (fork resolved)
Chose `cell/define` (prelude verb, peer of the existing keymap/define-reaction)
over (a) folding into layout/set metadata, (b) a new reader sigil ~!.
Rationale: mirrors the shipped reaction vocabulary, keeps declaration separate
from layout (single responsibility), adds no reader-level surface. Open: an
implicit-lift form (render hole ~(tool/find …) auto-promoted to a cell) is more
magical but removes the explicit declare; deferred unless requested.

** The honest reactive idiom (discovered + documented)
A cell's trigger MUST flow through data/* (the dep set is extracted from
data/<key> leaves in the quoted query). An out-of-band gaze read (harness/
cursor-id) has no data/* dep -> resolves once, never live. Combine the data/*
trigger with the read for computation:
  (quote (let [_ (get data/ui :cursor)] (harness/descendants {:id (harness/cursor-id)})))
