NOTE [2026-06-30]: ABANDONED — scoped on a faulty premise (honesty correction, not a deferral of real work).

The W3 premise was that intra-pane navigation round-trips to_ui→react→from_ui per keystroke (a derived %Ui{} marshalled both ways). VERIFIED FALSE by tracing the actual data-flow:
- Keystroke path: App.handle_key_event → Keys.dispatch({intent}, state.ui, forest) → %Ui{} → reproject. Keys.dispatch is %Ui{}→%Ui{}, PURE, no tree.
- to_ui appears on ZERO keystroke-path call sites (only harness/* tools + layout_registry.reset).
- from_ui is a ONE-DIRECTIONAL gaze→tree projection, written once per reproject (event) + once per render — not a both-ways per-keystroke round-trip.
- ∴ state.ui is the CANONICAL gaze; the tree's gaze-tags are the derived projection. The inverse of the moduledoc framing.

Applying playbook "Don't mirror canonical state in a side-struct" (the wrapped-vs-dissolved test: count round-trips on the event path = 0): retiring %Ui{} would force deriving it on-demand via to_ui for the 168-test reaction algebra, INTRODUCING the per-keystroke round-trip W3 claimed to remove. Net-negative churn across 17 test files. Correct move = do not execute.

W1 (Tree/SplitSpec) + W2 (path lenses + lens/update) were genuine measured wins and ship. The one small real redundancy found while verifying (render_tree vs sync_layout_gaze double from_ui) is filed as FEAT-031 (low priority, non-structural).
