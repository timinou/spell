* Initial Message

Let's pick up the multi-session cockpit UI. How would it be implemented and done using the Spell BEAM agent principles, and what could it look like? Maximum beam lisp usage. Include your methodology for the implementation

* Summary

Deliver FEAT-044 parts 3-5 (the live concurrent-session view + human-facing steering) the BEAM-Lisp-maximalist way: the cockpit is NOT a new Elixir app module (that is the SessionBrowser mistake, repeated bigger) — it is a `body`-slot LAYOUT VALUE (a `.ptc` program the agent authors) projecting one new bounded data binding. Elixir grows by ~1 materializer + 1 transport read; the mind (data) grows by 2 `.ptc` files + a `human/*` verb namespace. Every visual decision — grid breakpoints, card content, status colors, "doing now" line, ordering — is a PTC expression the agent edits live, no recompile.

Doctrine: Elixir = body (materialize `data/sessions`, bound cost, fall back). BEAM Lisp = mind (arrange, project, navigate, steer). Friction today = the concurrent view would be body-logic doing a mind's job.

* Design (the maximalist shape)

** 1. One new body primitive — SpellAgent.Tui.Cockpit.sessions/1 (the ONLY genuinely new read-Elixir)
Read-only, bounded, best-effort materializer. Unions `SessionRegistry.lineage/0` (live meta) with per-session `DataBag.snapshot_from` (content) into `[map]`, each row string-keyed for PTC. Reads the shared Hist substrate (no pid attach — the FUP-006-preferred read-through path). Bounds: `@max_sessions 12` (atom/render floor), `@snapshot_turns 3` (bounded content per card). Per-row try/rescue so one sick session degrades that card only. Injected as `data/sessions` in DataBag exactly like `data/forest`/`data/vms`, on the existing refresh clock.

** 2. The cockpit layout — priv/tui/cockpit_layout.ptc (the deliverable's heart, pure data)
Rides the `body` slot. Projects `data/sessions` into an N-up responsive grid of per-session cards via PURE PTC: `grid-cols` breakpoints (1→1,2-4→2,5-9→3,>9→4), `session-card` (a focusable `view/pane` whose border/glyph reflect live status), `grid` geometry (`view/split` math over n). `:tags {:focus-session id :drilled bool}` on the body node carry cockpit state (tags-on-tree, no new %Ui{} field). Compiled fallback floor = a 1-column session-id list, snapshot-tested (never-brick).

** 3. Navigation — the session-grid focus ring is lens/ ops (NO new nav code)
`cockpit/next-session` = `(lens/retag-focus tree :next)`; `cockpit/drill` = set body `:drilled`+`:focus-session`; `cockpit/back` = clear `:drilled`. Authored as `keymap/define-reaction` (data), bound via `keymap/bind` (data) — rebindable/redefinable. Drill-in REUSES the single-session default layout unchanged (that session's snapshot as `data/forest`) → the existing inspector IS the drill view, for free. One render path.

** 4. human/* — the mind surface for steering (parts 4-5)
A `Namespace.Spec` in the catalog (Wave-1 pattern), addressing a session by id, analogous to `black/*` for agents:
- `human/list` → `SessionRegistry.lineage/0` (lineage subtree as data)
- `human/watch {id}` → set body drill tags (= the drill reaction, callable)
- `human/spawn {intent, tools?, budget?}` → `Spawn.create(owner: :human)` — routes App.submit through the ONE gateway (closes part 4: human-started sessions get uniform lineage)
- `human/interrupt {id}` → cooperative interrupt signal at the turn boundary (the loop/continue `check_termination` seam) — the ONE part needing new invariant design (see FUP)
- `human/adopt {id}` → re-parent an orphaned child to `:human` (registry meta update)

* Failure ladder (never brick the surface)
- `Cockpit.sessions/1` raises → `data/sessions` = last-good cache → `[]`
- cockpit `.ptc` raises/bad shape → last-good cockpit tree → compiled 1-col fallback (snapshot-tested)
- a single session snapshot fails → that card shows "(snapshot unavailable)", others unaffected (per-row rescue)
- registry down → `lineage/0` → `[]` → "(no live sessions)", never crash

* Boundaries → FUPs
- Cross-session is read-through-store (sub-second refresh-clock lag), NOT pid-attach/telemetry (heavier, deferred to FUP-006 lineage).
- `human/interrupt` invariant design (forced-interrupt-mid-NIF-edit partial-write risk) → its own oracle-gated FUP (filed as FUP-035).
- Multi-node stays out (FUP-020/021).

* Acceptance
