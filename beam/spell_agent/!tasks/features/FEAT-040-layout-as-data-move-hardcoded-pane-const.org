* Summary
The layout is architected as a homoiconic tree (layout/* verbs) but the DEFAULTS remain hardcoded Elixir: pane width constraints (3-pane 34/30/36, 2-pane 45/55) and a pane_module dispatch table in default_layout.ex. For a system whose thesis is "the surface is editable data," the default layout itself should be BEAM Lisp data the agent can read and rewrite. Define it in BEAM Lisp.

* Evidence
- lib/spell_agent/tui/default_layout.ex:~L77-82 hardcoded constraints; L62-67 hardcoded pane_module dispatch (adding a pane needs a recompile despite harness/declare-pane existing for runtime panes).

* Design
- Express the default layout as a PTC/data value (a layout tree literal in priv/, loaded at boot), the same shape layout/set produces — so the "native fallback" and an agent-authored layout are the SAME kind of value (no special Elixir default).
- The pane_module dispatch becomes a registry entry (tie into the PaneRegistry that harness/declare-pane already uses), so a declared pane and a built-in pane resolve through one table.
- Keep a compiled last-good fallback (never-brick-the-surface): if the data layout fails to load, fall back to a minimal native default.

* Acceptance
- The default layout is a data value (BEAM Lisp / priv), editable without recompiling; the agent can read it via layout/show and rewrite it via layout/set.
- Built-in and runtime-declared panes resolve through one registry.
- A broken data layout degrades to a safe native default, never a crash.
