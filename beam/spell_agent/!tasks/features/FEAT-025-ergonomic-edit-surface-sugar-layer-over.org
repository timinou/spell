SPIKE (design only — not yet implemented). Answers the open design question from PLAN-020: "should edit operations use s-expr syntax `(edit path :op :args)` or plain data structures?"

* Resolution

NOT either/or. **Plain data is the ground truth; s-expr is a thin authoring skin that desugars to it.** This FEAT specifies the skin. PLAN-020 already shipped the data ground (q/apply-ops over `[{op pattern template}]`); this is purely additive ergonomics — zero change to the gate, the NIF, or the recorded-edit contract.

Proven precondition (PTC sandbox, this session): the proposed sugar constructors desugar to **byte-identical** op-data to what code_edit_test.exs hand-writes today (`(= sugar hand)` -> true, single + multi-op). ∴ reifiability (PLAN-018) is preserved by construction.

* The friction today (why this FEAT exists)

To rename `x`->`y` in `f.ex`, the agent today writes:

#+begin_src clojure
(tool/code-edit
  {:path "f.ex" :lang "elixir"
   :tree (q/apply-ops
           (tool/code-parse {:src (slurp "f.ex") :lang "elixir"})
           [{"op" "update"
             "pattern" {"node" "identifier" "value" "x"}
             "template" {"node" "identifier" "value" "y"}}])})
#+end_src

Four friction points:
1. **Manual parse->edit->write plumbing** — the agent re-reads, re-parses, threads the tree by hand every time.
2. **`lang` is redundant** — derivable from the path extension (`.ex`->elixir), yet must be passed twice (parse + edit).
3. **Raw form_tree literals** — `{"node" "identifier" "value" "x"}` is verbose, string-keyed, easy to typo (a typo'd key silently no-ops past the gate).
4. **No verb vocabulary** — "rename this identifier" is spelled as a generic update-op, not as intent.

* Design: three layers, each a PTC value (homoiconic — nothing compiled)

All ship as additions to `priv/preludes/q.clj` (or a sibling `edit.clj` prelude). No Elixir/Rust change for L1-L3; L4 is one optional NIF-adjacent helper.

** L1 — node constructors (data -> data, pure)

#+begin_src clojure
(defn q-id   [v]      {"node" "identifier" "value" v})
(defn q-call [f args] {"node" "call" "children" (into [(q-id f)] args)})
;; one per high-frequency kind, derived by REFLECTION over the projector's kind
;; vocabulary where possible (no-drift principle).
#+end_src

** L2 — verb sugar (intent -> ONE op, which is data)

#+begin_src clojure
(defn rename-id [from to] {"op" "update" "pattern" (q-id from) "template" (q-id to)})
(defn rewrite   [pat tmpl] {"op" "rewrite" "pattern" pat "template" tmpl})
(defn wrap-in   [pat tmpl] {"op" "wrap"    "pattern" pat "template" tmpl})
#+end_src

Agent writes intent (`(rename-id "x" "y")`); the value IS the op the reducer records. Proven identical to the hand-written op.

** L3 — the `(edit …)` fn: collapse the parse->apply->write pipeline

#+begin_src clojure
;; (edit "f.ex" (rename-id "x" "y") (rename-id "a" "b"))
(defn edit [path & ops]
  (let [lang (lang-of path)
        tree (tool/code-parse {:src (slurp path) :lang lang})]
    (tool/code-edit {:path path :lang lang
                     :tree (q/apply-ops tree (vec ops))})))
#+end_src

`(vec ops)` is exactly the recorded op-list. `edit` is sugar; `code-edit` stays the gated seam. A durable codemod stores the `ops` vector, not the closure.

** L4 — `lang-of` (only new native-adjacent piece)

Path-extension -> `pi_code_engine::LanguageId`:
- a) pure-PTC ext->lang map in prelude — zero native change, must mirror engine set (drift risk).
- b) expose `PiKernelNif.language_for_path/1` (engine has `LanguageId::new` + profile lookup at lib.rs:195) — single source of truth. PREFERRED.

* Why NOT s-expr-as-primitive (rejected branch)

If `(edit path :op :args)` were the *primitive* (a runtime special form), the recorded edit would be opaque syntax, not a value — breaking PLAN-018's contract that a recorded `:xf` be reifiable data the reducer can diff/compose/prove `q/equal?` over. Sugar-over-data keeps both. Same pattern as shipped `q/update` (closure, interactive) vs `q/apply-ops` (data, durable).

* Acceptance (when implemented)
- `(edit "f.ex" (rename-id "x" "y"))` writes through the existing gate; a broken edit still leaves the file untouched.
- `(rename-id "x" "y")` returns data byte-identical to the W5 hand-written op (regression-asserted, as proven this session).
- A durable codemod authored with the sugar rehydrates and replays from the stored op-list (not a closure).
- `lang-of`/`language-for-path` agrees with the engine's profile lookup for ex/rs/py/js/ts at minimum.
- No change to code-edit's gate, the projector NIF, or the recorded-edit shape.

NOTE [2026-06-30]: IMPLEMENTATION ARCHITECTURE REVISED (two assumptions in the original design falsified by sandbox probes before coding):

1. **Cross-namespace prelude calls do NOT work in one bundle.** Proved: a prelude fn in ns `edit` calling `(q/apply-ops …)` fails compile with "unknown namespace q/" — the prelude compiler does not seed sibling namespaces' exports during analysis (only the built-in set + the current ns). ∴ L3 CANNOT be a prelude fn that calls q/*.

2. **A prelude fn wrapping tool/* bypasses the preflight side-effect guard** (codex_regression_test P1 #2): `check_undefined_tools` can't see a tool hidden inside a prelude export, so effectful orchestration in a prelude defeats pre-execution safety. ∴ L3 should NOT be a prelude fn that calls tool/code-parse/code-edit either.

REVISED LAYERING (cleaner — "Elixir materializes, PTC transforms"):
- **L1/L2 (pure data sugar)** → ship as a NEW pure prelude namespace appended to q.clj OR a sibling. Constructors (`q-id`) + verb sugar (`rename-id`) return plain data, zero q//tool/ deps → compiles clean, stays side-effect-honest. KEEP q's existing public fns untouched (PLAN-018 standalone-link contract); add the sugar in the SAME file under the SAME `q` ns is fine since they're pure and q already depends on nothing.
- **L3 (effectful pipeline)** → a NATIVE tool `code-apply` (Elixir, in SpellAgent.Code): args `{path, ops}` → read file, infer lang (L4), parse via PiKernelNif, q-apply the ops (call the compiled q prelude in-process, same path tools.ex already uses), route through the EXISTING gate_* pipeline. Orchestration in Elixir = visible to preflight, transactional, no prelude-guard bypass. The recorded edit is still the `ops` data list (reifiability preserved).
- **L4 (lang-of)** → NIF `language_for_path/1` over engine `registry().match_path(Path)` → `profile.id.as_str()` (LanguageId has `as_str`/Display). Single source of truth, no ext-map drift.

NET: the agent writes `(tool/code-apply {:path "f.ex" :ops [(q/rename-id "x" "y")]})` — one effectful call, ops are pure data built by pure sugar. Sugar-over-data contract intact; safety + reifiability strictly better than the filed prelude-fn L3.
