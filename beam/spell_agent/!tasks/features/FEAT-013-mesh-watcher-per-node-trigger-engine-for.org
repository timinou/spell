* Edge cases
- two nodes both see the same post (Khepri replicates): both attempt to fire ->
  the claim dedup ensures ONE runs :do (DC-6). The headline correctness test.
- :do crashes: the firing claim's lease expires -> another node may re-fire
  (crash-safe, PT-5). Bound re-fire by fuel so a permanently-failing :do stops.
- watcher down (not started in a headless test): black/watch still POSTS the
  intention (durable); it simply isn't fired until a watcher runs — best-effort (F.2).
- :count threshold watch: fires when by_match count >= N (monotone threshold,
  04 §3); pair with :ttl so a never-reached threshold expires (PT-4 shortfall).

* PRE-CODING CORRECTION (oracle MeshFinalCheck, agent://1-MeshFinalCheck — P1.1)
Watch-firing exactly-once CANNOT rest on a session-plane claim alone across nodes.
- The crack: per-node watchers W1@N1, W2@N2 both observe the replicated event E,
  both claim the firing, and because Khepri reads are LOCAL (read-your-writes only,
  not linearizable for other writers), each sees only its own claim and both run
  :do → double fire. Exactly-once firing is a NON-MONOTONE (Layer-3) decision; a
  session-plane optimistic claim (Layer-2) cannot provide it under partition.
- FIX (choose at build, default A):
  - Option A (clean, preferred when Khepri is the store): firing is a NODE-PLANE
    micro-decide — a Ra command on the node cluster that atomically marks
    (intention_id, event_seq) as fired and commits exactly once. Reuses
    Mesh.Consensus (FEAT-012) machinery, not a new mechanism.
  - Option B (single-node / Memory, or Khepri-trigger mode): keep claim-dedup but
    make it best-effort with a mandatory :settle_ms + leader-consistent re-fold
    before :do, and DOCUMENT it as best-effort exactly-once (not guaranteed under
    partition). Acceptable because :do actions are themselves idempotent-or-decided
    (a :do that spawns is fine to occasionally double; a :do with irreversible
    effect must itself route through decide).
- Single-node (Store.Memory, one ETS table, one watcher) is already exactly-once
  (no replication window) — Option B suffices there. Multi-node Khepri uses Option A.
- net: FEAT-013 depends on FEAT-012 for Option A. Update the DAG: 013 ⟸ 010 AND
  (for the multi-node exactly-once path) ⟸ 012. Single-node 013 needs only 010.
