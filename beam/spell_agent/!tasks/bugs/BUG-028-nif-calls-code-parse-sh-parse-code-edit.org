* Summary
`PtcRunner.Lisp.run` sandboxes PTC programs (heap cap, timeout, tool-call limits), but raw NIF calls into the Rust kernel (pi_kernel_nif tree-sitter parse/unparse, brush_nif shell parse) run OUTSIDE that sandbox. `safe_parse`/`safe_unparse` catch Elixir exceptions, but a NIF hard-crash or unbounded-work input (pathological tree-sitter parse, huge source) can hang or trap the whole tool call. For an always-on alpha this is an availability risk.

* Evidence
- lib/spell_agent/code.ex:parse_source/1, gate_unparse/1, safe_* wrappers — catch exceptions only.
- lib/spell_agent/sh.ex:parse_tool/1 → BrushNif.parse (no size/time bound).
- No per-NIF-call timeout or input-size cap.

* Fix shape
- Bound NIF inputs at the body boundary: reject over-size source before the NIF call (a config cap).
- Run long/uncertain NIF calls under a dirty scheduler or a supervised Task with a timeout, so a hang cannot wedge the session loop.
- Ensure a NIF crash degrades to an `%{"error" => ...}` tool result, never a session crash.

* Acceptance
- A pathologically large or malformed input to code-parse/sh-parse returns a bounded error, not a hang or crash.
- A test drives an over-size input and asserts the bounded-error contract.
