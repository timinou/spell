* Summary

The PTC-Lisp reader (=ptc_runner/lib/ptc_runner/lisp/fast_parser.ex=) does NOT
support namespaced keywords (=:ns/name=, idiomatic Clojure). Worse, it fails
SILENTLY: a namespaced keyword is split into a bare keyword + a stray symbol with
NO error at the read site, so the malformation detonates downstream as a cryptic,
location-shifted error.

* Reproduction (verified 2026-06-27, reader probe)

#+begin_src elixir
PtcRunner.Lisp.FastParser.parse(":q/no-match")
;; => {:program, [keyword: "q", symbol: "/no-match"]}     ← TWO tokens, no error
PtcRunner.Lisp.FastParser.parse(":a/b/c")
;; => {:program, [keyword: "a", symbol: "/b/c"]}          ← same
PtcRunner.Lisp.FastParser.parse(":plain")    ;; => {:keyword, "plain"}   (ok)
PtcRunner.Lisp.FastParser.parse(":foo-bar")  ;; => {:keyword, "foo-bar"} (ok)
#+end_src

How it surfaced: =(def no-match :q/no-match)= in a prelude (=priv/preludes/q.clj=,
PLAN-020) failed to COMPILE with:

#+begin_example
%PtcRunner.Lisp.Prelude.ValidationError{reason: :invalid_signature,
  message: "malformed def in prelude:
            [symbol: \"no-match\", keyword: \"q\", symbol: \"/no-match\"]"}
#+end_example

The =def= macro received THREE forms where it expected two — because the single
keyword had silently become =[keyword \"q\", symbol \"/no-match\"]=. The error
names =def=, not the keyword, three tokens away from the real cause.

* Root cause (verified in source)

=fast_parser.ex=:
- =parse_keyword/1= (L408): =take_while(..., &keyword_char?/1)= — reads keyword
  chars after =:=, stops at the first non-keyword char.
- =keyword_char?/1= (L829): =c in ?a..?z or ?A..?Z or ?0..?9 or [+, -, *, <, >,
  =, ?, !, _]= — does NOT include =/=.
- =symbol_rest_char?/1= (L831): DOES include =/=.

So =:q/no-match= reads =:q= as a keyword, stops at =/=, then =/no-match= is
consumed as a separate SYMBOL (=/= is a legal symbol char). No boundary check
flags the adjacency; two tokens fall out of one lexeme.

* Why this is a real bug (not just "unsupported")

1. SILENT. Even if namespaced keywords are intentionally unsupported, the reader
   MUST error at the read site (=could not parse keyword= or =unexpected '/' in
   keyword=), not emit two tokens that corrupt an enclosing form and fail
   elsewhere with an unrelated message. Silent token-splitting violates the
   read-time error contract the rest of the parser holds (e.g. unterminated
   keyword already errors at L411-412).
2. CLOJURE-SUBSET CLAIM. PTC presents as a Clojure subset; =:ns/name= keywords
   are everyday Clojure (=:db/id=, =:http/status=). An agent porting Clojure idiom
   hits this with no usable diagnostic.
3. DEBUGGABILITY. The error points at the wrong form (=def=), so the cost is
   paid in confused debugging, exactly the failure mode the rich undefined-var
   hint machinery (SPELL PATCH-2 D-5) was built to prevent elsewhere.

* Two possible fixes (decide first — affects scope)

(A) MINIMAL / SAFE — reject at the read site. Detect a =/= immediately following
    keyword chars and return a clear =syntax error: namespaced keywords are not
    supported (':' ... '/')= at that offset. Pure defensive guard; no new
    semantics; no atom-table impact. Restores the read-time error contract.

(B) FULL — support namespaced keywords. Extend =keyword_char?= (or add a
    =keyword_ns_char?= phase) to admit a single =/= separating ns and name, and
    intern the qualified keyword. NB this is a SEMANTICS decision with an
    atom-interning dimension — must go through =SourceAtoms.intern= and respect
    the bounded-vocab / atom-DoS posture (cf. FUP-007). Heavier; needs its own
    review.

RECOMMENDATION: ship (A) now (the silent-failure is the actual bug); file (B) as
a follow-up if namespaced-keyword SUPPORT is wanted. (A) is a few lines in
=parse_keyword/1= + a parser test; (B) is a language-feature change.

* RESCOPE (2026-06-27): from "fail loud" to FULL SUPPORT — DIV-13 reclassification

Initial framing was minimal (fix (A): reject at the read site). On investigation
the substrate-strengthening option is both correct and cheap, so this BUG now
targets FULL namespaced-keyword support and the reclassification of DIV-13.

** Why DIV-13 "by design" no longer holds (it fails its own classification test)

The PTC design framework (docs/ptc-lisp-specification.md "Design Philosophy" +
"Classifying a Divergence") says a difference is a legitimate DIV only if one of
FOUR rules justifies it: (1) no try/catch → signal values; (2) eager not lazy;
(3) Java-named conventions; (4) data-properties signal / program-faults raise.
A divergence that REJECTS a supported, finite Clojure form WITHOUT a rule behind
it is a BUG, not a DIV (the doc states this explicitly, and DIV-14 was already
reclassified DIV→BUG on exactly this ground: "simplicity is not one of the four
rules").

DIV-13's stated rationale is: "Simplicity. No user-defined namespaces means
namespace-qualified keywords have no use." BOTH clauses are now false:
  - PTC HAS namespaces everywhere: tool/, data/, json/, budget/, clojure.string/,
    and the prelude (ns NAME ...) system with qualified calls (crm/get-user,
    q/match). Namespaced keywords are the natural DATA companion to a language
    that already namespaces its CODE.
  - No rule forbids them. They are finite, eager, deterministic, raise nothing
    on the program. Rejecting them is an unmotivated rejection of a supported
    finite form → BUG by the doc's own test.

** Representation cost is ZERO (the atom-DoS worry does not apply)

SourceAtoms.intern/1 already returns an ATOM only for the bounded vocabulary and
a BINARY for everything else (issue #953 fix). A user keyword :my_kw is already
{:keyword, "my_kw"} (binary) → keyword_value/1 → LispKeyword.new("my_kw"). A
namespaced keyword rides the IDENTICAL path: {:keyword, "ns/name"} →
LispKeyword.new("ns/name"). No atom-table growth, no new runtime type, and
core_to_source already renders it (":#{k}" → :ns/name). The only gate is the
character-class checks that currently exclude `/`.

** Implementation scope (focused, multi-touch but small)

  1. lib/ptc_runner/lisp/fast_parser.ex — parse_keyword/1: after the name, accept
     an OPTIONAL single `/` + a second name segment, producing {:keyword,
     "ns/name"}. Reject a trailing/empty/double-slash (`:a/`, `:a/b/c`) with a
     clear read-site error (keep the (A) guard as the malformed-case floor).
  2. lib/ptc_runner/lisp/keyword.ex — @valid_name regex: allow one `/` separating
     two grammar segments (NOT a leading/trailing/repeated slash).
  3. lib/ptc_runner/lisp/runtime/predicates.ex — runtime (keyword "ns/name")
     coercion: allow the qualified form (it currently raises per DIV-13). Decide:
     keep runtime stricter than literals? No — runtime + literal should agree for
     the qualified form. Update @keyword_pattern accordingly.
  4. DECIDE: `:a/b/c` (multi-slash) — Clojure rejects (a keyword has at most one
     `/`). PTC should reject it too, with a clear error (NOT a silent split).
  5. Tests to FLIP (currently assert rejection): name_keyword_test.exs "string
     with slash raises (DIV-13)"; the manual conformance DIV-13 cases
     (test/support/lisp_conformance_cases/manual.ex ~L6858-6876); any parser_test
     keyword cases. Add: literal :ns/name parses; round-trips via core_to_source;
     (keyword "ns" "name") 2-arity if that path exists; equality + map-key use;
     `:a/` and `:a/b/c` error clearly.
  6. DOCS: docs/clojure-conformance-gaps.md DIV-13 → reclassify to a fixed BUG
     entry (renumber per the doc's "GAP-* later judged → renumber" convention);
     docs/ptc-lisp-specification.md L180 (remove the "not supported" line);
     docs/conformance/clojure-core-audit.md DIV-13 note.
