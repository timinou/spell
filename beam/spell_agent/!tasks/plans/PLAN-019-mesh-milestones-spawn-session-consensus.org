* BOUNDARY REFINEMENTS [2026-06-27] (after docs/elixir-ptc-boundary.md)

The Elixir/PTC boundary doc (two end-to-end traces) sharpens the milestone specs
along three axes it makes explicit: (1) the ONE sandbox primitive
PtcRunner.Lisp.run(source, context:, tools:, caller: :in_process_v1) that every
userland surface routes through; (2) "Elixir materializes, PTC transforms"; (3)
the four transparent Elixir jobs — materialize private shapes → JSON-safe data,
inject as data/* + tools map, bound-coerce the return, fail soft. Apply per
milestone:

** M1 (FEAT-011 spawn-session) — three hard contracts the boundary makes explicit
- %MissionHandle{} MUST cross the PTC boundary STRING-KEYED (materialize job #1).
  spawn-session returns the handle to a PTC program, so it is a plain string-keyed
  map ("session","region","ref","watermark","parent","status"), NOT a bare struct.
  await-session accepts {handle|session} where handle is that map (or its
  "session" string). Mirror Tools.to_callable's stringify_keys + Harness.ui_map
  pattern: a struct is an Elixir-internal convenience; the value that touches the
  sandbox is data.
- spawn-session + await-session are NATIVE meta-tools that join Tools.meta_tools/0
  beside define-tool, under the SAME raise-on-error contract (boundary trace 2A ①:
  "meta-tools are themselves ordinary tool-map entries"). Budget-exhausted →
  raise "parallel_capacity_exceeded"; the invoke_tool contract renders it as an
  LLM-facing error, EXACTLY as define_tool's raises do. Do not invent a second
  error channel.
- capability attenuation = Map.take(Tools.build_tools_map(), args["tools"]) |>
  Map.merge(Mesh.verbs(child_sid, …)) IS the inject job #2 (hand the child a
  bounded tools map). The child Session.run receives args as a stringify_keys
  context, same as to_callable. Fail-soft: a child crash frees its slot (Task
  monitor) and its posted findings persist — the surface never bricks.

** M2 (FEAT-012 black/decide) — the :fold is userland PTC, reuse Hist.Lens exactly
- black/decide's :fold is a POLICY (which findings, how reduced) = userland PTC,
  run through the SAME sandbox via the SAME pattern Hist.Lens uses: materialize the
  region's findings WHERE seq <= watermark into string-keyed, JSON-safe maps
  (mirror Lens.project/3 — pre-extract the structural facts a fold needs, never
  pass an Elixir struct/tuple into the sandbox), inject as data/findings, run the
  :fold source with caller: :in_process_v1, then read step.return. A bad :fold is a
  bad verdict payload, never a corrupt commit.
- the INVARIANT half stays compiled Elixir: seal (store seq frontier), verdict id =
  hash(region<>question<>watermark_seq), Ra node-election, the exactly-once commit.
  Materialize+inject+coerce around a PTC transform; the consensus mechanism is the
  primitive beneath it. This is hist/lens.ex's "Elixir owns primitives+invariants;
  PTC owns policies+lenses" applied to consensus.
- ACTION: build a small Mesh.Consensus.project_findings/2 (the Lens.project analogue
  for mesh records) so the fold sandbox sees only data. Do NOT let the :fold touch
  %MeshRecord{} structs directly.

** M3 (FEAT-013 watch :do) — already boundary-clean, restate the contract
- the :do fired on a matching post is frozen PTC run through the sandbox with
  data/event bound to the post (the reaction dual: event → effects). The watcher
  (Elixir) owns the exactly-once invariant (claim / node-plane micro-decide); the
  :do BEHAVIOUR is userland. No refinement to the split — but ensure the post P is
  materialized to a string-keyed map before binding as data/event (same job #1), so
  the :do never sees a %MeshRecord{} struct.

** M4 (FEAT-014/015 panes) — compiled panes for v1, note the data path

  (regions/board/spawn) follow that SAME compiled pattern for v1 (consistency over a

** M5 (FEAT-018 combinators) — SHIP AS PTC SOURCE, not compiled Elixir (biggest shift)
- The ergonomic combinators are PURE COMPOSITIONS of the M1 primitives, so by the
  boundary doctrine ("reach for data, not code") they ship AS PTC SOURCE — default
  :ptc tools registered from priv/mesh/*.ptc (the hist/lenses precedent:
  @external_resource .ptc files loaded as data, runnable + forkable by the agent),
  NOT compiled Elixir verbs:
  - scatter  = (map (fn p -> (tool/spawn-session …)) prompts)   ; fan-out
  - gather   = (map (fn h -> (tool/await-session {:handle h})) handles)  ; fan-in
  - mesh-map = scatter then gather                              ; the common case
  - ask      = (tool/await-session {:handle (tool/spawn-session …)})  ; gather-of-one
  These are userland Lisp over spawn/await; writing them in Elixir would re-trap
  policy in compiled code the agent can't read/fork — the exact anti-pattern the
  boundary doc warns against.
- ONLY the parts that need an Elixir PRIMITIVE stay compiled: narrowing
  (Narrow.signature_at derives an output shape — a structural fact the sandbox
  cannot compute), and the opts[:inherit_memory] passthrough in Session.run (S-E,
  an Elixir merge point). Everything else is .ptc.
- prompt:: reader form is a ptc_runner reader macro (vendored), not an Elixir verb.

** M7 (FEAT-017 context_lens) — materialize in Elixir, transform as a .ptc lens
- The cohort projection MATERIALIZES in Elixir (the union of own hist + sibling
  hists @ watermark + region records <= W → one string-keyed data bag), reusing
  Hist.Lens.project + Mesh.Store queries — the materialize job. The actual COHORT

  conversation) is a TRANSFORM, so it ships as a .ptc lens over that bag (the
  SOURCE-FOLD layer in the FEAT-017 addendum), shared pull/push with memory fold.
  Build the Elixir materializer + one default .ptc cohort lens; the agent can fork
  the lens without an Elixir deploy.

** Cross-cutting: the materialize boundary is now a NAMED contract
- Every mesh value that crosses into the sandbox (MissionHandle, a fold's findings,
  a :do's event, the context bag) goes through a project/materialize function that
  emits string-keyed, JSON-round-trippable maps with NO structs/tuples/pids — the
  Lens.project contract. Add these as the mesh analogue of Hist.Lens.project_node/1.
  Every value that crosses back (a fold's verdict payload, a reaction's gaze) is
