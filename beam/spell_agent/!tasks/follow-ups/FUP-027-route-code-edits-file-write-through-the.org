* Initial Message

how would you mkae this spell_agent work well with the edit tool? with an interface that just *makes sense* for this? e.g. if CodePath were lispy, how would edit be done?

* Summary

=code/edit= (PLAN-020 W5) writes the edited file with a native, FS-atomic
=File.write= + rename. It is NOT covered by the PTC =execute= layer's
transactional file-write rollback, which tracks the =edit=/=create= PTC tools \u2014
not an arbitrary native tool's =File= write. So a program that calls =code-edit=
and then =(fail ...)= leaves the file changed. W6 review flagged this; the W5
moduledoc was corrected from an overclaim ("transactional by construction") to an
honest boundary, and this FUP tracks the real fix.

* What is deferred

Make a successful =code-edit= write participate in the SAME all-or-nothing
rollback the =execute= tool gives =edit=/=create=, so a later failure in the
enclosing program restores the pre-edit file.

* Options (decide when taken on)

  1. ROUTE THROUGH THE TRACKED PRIMITIVE. Have =code-edit= perform its write via
     whatever the =execute= layer records for rollback (the same seam =edit=/
     =create= use), instead of a bare =File.write=. Cleanest if that seam is
     reachable from a native tool; investigate where the execute layer journals a
     file write and whether a native tool can enlist in it.
  2. SNAPSHOT/RESTORE JOURNAL. =code-edit= snapshots the target's prior bytes
     before writing and registers a restore thunk the run executes on failure.
     Self-contained but duplicates the execute layer's journal.
  3. ROUTE THROUGH =pi_kernel_nif::apply_edit= + the edit broker. The broker
     (=crates/pi-edit-broker=, intent->commit->conflict, =txn_journal=) already
     does transactional, multi-session-coordinated writes. =code-edit= could
     unparse the edited tree and hand a whole-file replace action to =apply_edit=.
     This is the architecturally richest path (cross-session conflict detection
     for free) but needs =apply_edit= to accept a whole-file/form-tree
     replacement action, which is its own design (today it takes CodePath edit
     actions). PLAN-020 W5 SUBSTRATE NOTE already names this.

* Why deferred (not blocking)

The W6 fixes made the write SAFE in isolation: FS-atomic (temp+rename, no partial
file), parse-gated (no invalid source), empty-guarded (no truncation). The ONLY
remaining gap is cross-effect rollback within one failing program \u2014 a real but
narrower property. The honest moduledoc tells a caller to sequence =code-edit=
last or restore from VCS until this lands.

* Acceptance (when taken on)

  - A program =(do (tool/code-edit {...}) (fail "x"))= leaves the target file at
    its PRE-edit content.
  - Multiple =code-edit= calls in one program are all-or-nothing on a later fail.
  - No regression to the W5/W6 safety properties (atomic, gated, empty-guarded).

* Module of record

=beam/spell_agent/lib/spell_agent/code.ex= (=edit_tool=/=gate_write=). The
execute-layer rollback seam (in =ptc_runner=) is the integration target; option 3
involves =beam/pi_kernel_nif= =apply_edit= + =crates/pi-edit-broker=.

NOTE [2026-06-30]: [2026-06-27] INVESTIGATION + DECISION (PLAN-022 P1b). The FUP's three options were written in the Spell-HARNESS mental model. Verified facts in the BEAM ptc_runner project:

1. There is NO execute-layer file-write rollback in the BEAM ptc_runner. The `journal` field in EvalContext is for (task) idempotent caching, not file rollback. There are NO tracked edit/create native tools here; `code-edit` is the ONLY file writer. So FUP option 1 ("route through the seam edit/create use") has no seam to route through. The transactional rollback the FUP references is the Spell harness's `execute` tool — a different system.

2. Tool execution runs in a SPAWNED SANDBOX WORKER process (PtcRunner.Sandbox.execute -> Process.spawn), NOT the caller. EMPIRICALLY CONFIRMED with a probe: a tool calling Journal.record (process-dict) inside Lisp.run sees active?=false, and the caller draining after sees 0 records. So a caller-side process-dictionary journal CANNOT cross the boundary.

3. For the AGENT path, spell_agent does NOT own the per-program Lisp.run boundary — the fork's loop (sub_agent/loop/ptc_tool_call.ex execute_program) does. So spell_agent cannot bracket each agent-authored program from outside.

CONSEQUENCE: a correct, path-agnostic rollback must drain the journal IN THE WORKER, because code-edit's record AND the program's (fail) both occur in the same worker process (internally consistent process dict). The drain must be triggered by a post-eval verdict known in-worker.

DECISION (option 2, worker-side, with a general fork hook): 
  (a) SpellAgent.Code.Journal — a WORKER-SIDE process-dict stack: record/1 snapshots (path, prior-bytes|:absent) before each code-edit write; finalize/1 drains by verdict (:ok -> commit/drop; :fail|:error -> restore LIFO). Lives in spell_agent (owns the code-edit policy).
  (b) A GENERAL post-eval finalizer capability in the fork: Lisp.run(..., on_complete: fn verdict -> ... end) runs the finalizer IN-WORKER after eval, before the worker exits. Default nil = current behavior (no rollback) = purely additive + best-effort. This is a legitimately general runner feature (saga/compensation), not code-edit-specific in the fork.
  (c) spell_agent wires on_complete -> &Code.Journal.finalize/1 across the Lisp.run callsites it controls AND threads it through SubAgent -> LispOpts for the agent loop.

SEQUENCING: the fork hook touches lisp.ex, which FEAT-024 (PLAN-022 P1a) is concurrently editing. To avoid a concurrent-edit conflict, the fork-hook portion of P1b is sequenced AFTER P1a lands (await), then done serially.

DOCUMENTED LIMITATION (v1): rollback covers code-edits in the MAIN program flow. A code-edit inside a pmap/pcalls-spawned sub-worker records in THAT sub-worker's dict (separate process), outside the top-level finalizer's reach — a narrower follow-up if it ever matters (rare: agents rarely fan out file writes). The headline acceptance ((do (code-edit ...) (fail ...)) restores the file) is in the main-flow case and IS covered.
