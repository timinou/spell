NOTE [2026-06-30]: [2026-06-27] ROOT CAUSE FOUND (PLAN-022 P1c investigation) + partial fix applied.

The aggregate-only failures are NOT a shared-STATE leak as first hypothesized — they are LOAD-SENSITIVE TIMEOUTS. Captured the actual error of the aggregate failures: `execution exceeded 1000ms limit` / reason: :timeout. Evidence:
- Each flaky file passes deterministically IN ISOLATION (3x green).
- The 6 flaky files (closure_capture, eval_describe, eval_json, prelude/discovery, prelude/upstream_roundtrip, quote_collections + combinations) run GREEN TOGETHER (105 passed, 3x).
- They fail ONLY in the full 6700-test suite, with a VARYING count run-to-run at fixed --seed 0 (56, then 4 on a re-run) — the signature of scheduler CONTENTION, not state.
- Mechanism: PtcRunner.Lisp eval runs each program in a spawned sandbox worker with a DEFAULT 1000ms timeout (Lisp.run :timeout default). Under full-suite async parallelism, hundreds of async tests + their sandbox workers compete for schedulers; an eval that takes <1000ms in isolation exceeds 1000ms under load and the run returns {:error, reason: :timeout}. Confirmed: NO async test mutates Application env / persistent_term (ruled out the state-leak theory); the contaminating variable is CPU contention.
- This is PRE-EXISTING + independent of PLAN-022 work: the pristine submodule (87468fa0, my changes stashed) showed 10 aggregate failures with the SAME timeout signature; my FEAT-024 + FUP-027 changes did not introduce it (mine swung 56->4 across two identical-seed runs).

Updated the assertion to the current correct behavior (renamed to "a quoted list is inert quoted-data, not a parse error"). This was a genuine stale assertion, deterministic, now green.

* RESOLVED [2026-06-30]

The timeout half (the deferred remainder) is fixed. Both halves of this FUP are
now done.

** Root cause (confirmed) — a config that never reached the eval path
config/test.exs ALREADY widened the budget (=config :ptc_runner, default_timeout:
10_000=, commit d336737e), and =Sandbox.execute/run_bounded= ALREADY read it via
=Application.get_env(:ptc_runner, :default_timeout)=. But =PtcRunner.Lisp.run/2='s
=run_params/1= hardcoded =timeout: Keyword.get(opts, :timeout, 1000)= and passed
that EXPLICIT 1000ms into the sandbox, shadowing the config-aware default. So every
eval that did not pass an explicit =:timeout= capped at 1000ms regardless of the
test-env widening. Under full-suite async parallelism the sandbox-worker children
fight for schedulers and a trivially-fast program is starved past 1000ms ->
={:error, reason: :timeout}= — the aggregate-only, count-varies-at-fixed-seed
signature documented above.

** Fix (ptc_runner fork commit 0ea476c4, on =spell= branch)
  - =run_params/1= now falls back to the =:default_timeout= Application env (then
    1000ms), mirroring the existing =default_max_heap= precedent at the compile
    path and the Sandbox reads. PROD default unchanged (1000ms); test env gets its
    intended widening.
  - De-fragiled two =Session= demos (doctest + session_test) that picked an
    arbitrary =timeout: 1_000= purely to show option storage/override (NOT timeout
    behaviour) and were themselves load-fragile at exactly 1000ms -> 30_000.
  - error_handling:299 stale-assertion half was already fixed (fork 89220fcd).

** Verification (acceptance met)
