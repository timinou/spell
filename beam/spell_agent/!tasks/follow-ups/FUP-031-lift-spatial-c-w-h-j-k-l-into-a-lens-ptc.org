PLAN-009 (Freeform TUI) / the "every chord generalizes to agent-authored layouts" consolidation (PLAN-024). Sibling of FUP-005 (pane-vocabulary generalization) — this is the OTHER half of C-w: the geometry, not the pane name.

* Problem
`SpellAgent.Tui.Spatial.extreme/2` (rank-by-rect-edge — "which placed region is furthest in direction D") is pure and generic: it takes `[{slot, %Rect{}}]` and a direction, returns a slot. But it is invoked ONLY from `App.frame_target/1` / `App.frame_regions/1` — compiled Elixir, not exposed as a `lens/` verb. Consequently:

1. An agent that reshapes the body into a custom split arrangement has no way to QUERY "what's spatially adjacent to focus in direction D" from PTC — it can only use the tree-order ring (`lens/focus next/prev`), never a geometry-aware jump.
2. A NEW spatial relation (e.g. "focus below-and-right", a diagonal jump, or "cycle only panes in this row") cannot be authored as a reaction — `Spatial` has no PTC-callable surface at all.
3. `App.frame_regions/1` gates each candidate through `Ui.safe_pane(slot)` (line ~527: `if Ui.safe_pane(slot), do: [{slot, rect}], else: []`), so even once FUP-005's pane registry lands, `frame_regions` needs updating to consult the registry, not just `Ui.safe_pane`'s fixed atom set — these two FUPs must land together or a registry-backed pane will be spatially invisible to C-w even though it is nameable.

* Why this matters for the "every intent generalizes" goal
The RING (`C-j/k`) already generalizes for free (`Lens.focusables/1` collects any `type: "pane"` node, confirmed no gate on pane vocabulary). The SPATIAL jump (`C-w` + direction) is the one navigation primitive that stays compiled-only after FUP-005 ships — closing this is what makes "every chord ... automatically inherits" literally true for BOTH axes, not just the ring.

* Proposed change
- Add `lens/frame-target {:dir "left"|"right"|"up"|"down" :area {...}}` (or thread the frame area via `data/area`, mirroring `RenderProbe`'s convention) — a PTC-callable wrapper over `Surface.resolve_holes |> Surface.layout |> Spatial.extreme`, over the CURRENT tree (closed over like `lens/focus`).
- Update `App.frame_regions/1`'s pane-candidate filter to consult the (post-FUP-005) pane registry instead of the bare `Ui.safe_pane/1` whitelist, so a registry-backed agent pane is a valid spatial target.
- Consider whether `frame_target/frame_regions` in `App` should simply become thin callers of the new `Lens`/`Spatial` PTC-facing function (collapse the duplicate geometry logic into one place — the "one source of truth" principle), rather than keeping two call paths.
- Reuse `Spatial.extreme/2` as-is; this is a NEW CALLER (a `lens/` verb), not a rewrite of the ranking algorithm.

* Depends on
FUP-005 (pane registry) should land first or alongside — `frame_regions`' pane-candidate gate needs the same registry-backed `safe_pane` this FUP already plans to build.
