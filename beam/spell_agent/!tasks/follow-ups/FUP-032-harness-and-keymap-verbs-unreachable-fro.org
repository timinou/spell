* Context
Discovered while building PLAN-024 Wave 1 (`harness/declare-pane`, FUP-005).

`SpellAgent.Harness.tools/2` (the `harness/*` + `keymap/*` PTC verb map) is
NEVER merged into `SpellAgent.Tools.build_tools_map/0` — the tools map every
live mission turn actually calls through (`Session.run/2` ->
`build_session_tools/5` -> `Tools.build_tools_map()`). Confirmed via full
repo-wide search: the only 2 call sites of `Harness.tools/2` are:

- `SpellAgent.Tui.Reaction.Ptc.run/3` — a REACTION's closed-over gaze/forest
  (fires when a bound chord dispatches; the reaction body itself gets the
  full `harness/`+`keymap/` surface).
- `SpellAgent.Tui.Cell.Tools.read_only/2` — the CELL query tier, which
  explicitly DENIES every mutator (`keymap/bind`, `layout/set`, `theme/set`,
  `sh`, `define-tool` — see the module's own comment + `cell_tools_test.exs`).

So today, a live agent mid-conversation (the main mission loop) has NO path to
call `keymap/bind`, `keymap/define-reaction`, `harness/declare-pane`, or any
other `harness/`/`keymap/` verb directly. It can only:
1. Author a REACTION via `keymap/define-reaction` from... nowhere (chicken-egg:
   that verb is itself a `keymap/*` verb, unreachable from the main loop) —
   actually not even a reaction can call `keymap/define-reaction` since a
   reaction is a *use* of harness/keymap, not necessarily their author.
2. Author a CELL query that reads harness/* (read-only), but cannot bind/react.

This means the ENTIRE "agent reshapes its own keybindings live" story (PLAN-346
W3's stated goal, and this session's PLAN-024 thesis) is currently only
testable/exercisable via direct `Harness.tools(forest, ui)` calls in a test
harness — NOT by a real running mission. `layout/`+`view/`+`theme/`+`lens/`
(the render-mirror surface) ARE correctly merged into `build_tools_map/0` via
`freeform_tools/0` — only `harness/`+`keymap/` are missing.

* Why this wasn't caught earlier
Every existing test (`harness_test.exs`, `cell_tools_test.exs`,
`cell_clock_test.exs`, `cell_demos_test.exs`) calls `Harness.tools(forest, ui)`
DIRECTLY or goes through the cell tier — never through
`SpellAgent.Tools.build_tools_map()`. So the gap has zero test-visible
symptoms; it only surfaces when tracing "can a live mission actually author a
keybinding," which nothing exercises today.

* Open design question (why this is a FUP, not a quick fix)
Merging `Harness.tools/2` into `build_tools_map/0` raises a real question the
codebase hasn't answered: should the MAIN mission loop be able to mutate
`KeymapRegistry`/gaze DIRECTLY (bypassing the reaction indirection), or should
this remain reaction-scoped by design (a deliberate capability boundary: the
agent authors reactions via a DIFFERENT verb it can't yet reach, and only a
fired reaction gets the harness/keymap surface)? This has capability-
attenuation implications (`spawn-session`'s child clamping, BUG-017's non-
transitive escape lesson) that need a real decision, not a reflexive merge.

* Proposed investigation
1. Trace: was this deliberate (PLAN-346's own design) or an oversight? Check
   PLAN-346 W3's acceptance criteria against what actually shipped.
2. If deliberate: document WHY explicitly in `Harness`'s moduledoc (currently
   silent on this) and in `docs/freeform-tui-architecture.md`.
3. If an oversight: decide the right merge point — likely a NEW `harness/`-
   scoped tools fn in `Tools.build_tools_map/0`'s `freeform_tools/0` (mirroring
   how `layout/`+`view/` are merged), closing over the LIVE App gaze + forest
   (needs a named/reachable gaze source, since `SelfView`'s own moduledoc notes
   "the App-local cursor is not reachable by name" — this may need solving
   first, or scoping the merge to gaze-less verbs like `keymap/bind`/
   `keymap/define-reaction`/`harness/declare-pane` while leaving gaze-reading
   verbs — `harness/state`, `harness/cursor-id`, etc — cell/reaction-scoped
   since they legitimately need a bound gaze).
