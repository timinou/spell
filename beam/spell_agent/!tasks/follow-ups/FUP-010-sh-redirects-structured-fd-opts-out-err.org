* What is deferred
Structured redirect options on a shell command/pipeline, expressed as DATA on the
call (never >/>>/< operator tokens, keeping the no-operator inject-proof rule):

    (tool/sh ["rg" "TODO"] {:out "hits.txt" :append true})
    (tool/sh ["sort"]       {:in  "input.txt"})
    (tool/sh ["build"]      {:err "build.log"})

brush wires the fds; the argv stays pure (each element one literal argument).
The same opts shape should extend to tool/sh-pipe (redirect the pipeline's final
stdout / first stdin).

* Why it was deferred (the real risk)
Writing to an arbitrary :out path is a genuine side effect with a blast radius
(overwrite an unintended file, traverse outside the workspace, clobber a symlink
target). Unlike argv (inert until executed), a redirect MUTATES the filesystem.
That deserves its own design + reviewer pass:
- path policy: absolute vs workspace-relative; refuse traversal / symlink games?
- :append vs truncate semantics, and the default (truncate is destructive).
- :in must exist / be readable; error mapping into the {:exit :out :err} contract.
- interaction with cwd (relative redirect paths resolve against which dir?).
- whether redirects are even the right abstraction vs "write :out from Lisp".

* Acceptance (when taken on)
- redirects as opts on the vector, validated (path policy enforced, clear errors).
- brush fd wiring verified: (tool/sh ["echo" "hi"] {:out f}) writes "hi
" to f.
- :append vs truncate proven distinct; missing :in surfaces a clean error.
- a path-traversal / symlink-clobber attempt is rejected (or explicitly allowed by
  documented policy) — reviewer swarm on the fd-overwrite surface.
- result contract unchanged (still {:exit :out :err :lines}).

* Not a bug

write via a file tool) works for the common case.
