* Initial Message

what would a 'babashka on the BEAM' look like? you may consider wiring brush through rust NIFs too. Show me alternative designs and how they fit the current intention and enable homoiconic representations for everything

* Parent
PLAN-011 (sh+brush). Deferred from W0: the brush NIF is REQUEST/RESPONSE only —
it runs a command to completion, captures all stdout/stderr into temp files, and
returns one {:exit :out :err :lines} value. There is no incremental/streaming
output.

* What is deferred
A streaming variant where a long-running command's stdout is delivered to the
BEAM as it is produced (line- or chunk-wise), rather than only as a final buffer:

    (sh/stream ["tail" "-f" "log"] (fn [line] …))     ; or a channel/stream value
    (sh/stream ["cargo" "build"]   …)                 ; see progress live

* Current state (verified)
- run/pipe capture output to TEMP FILES and read them back AFTER completion
  (beam/brush_nif-vendored/native/brush_nif/src/run.rs — finish/2 seeks+reads the
  temp file post-run). This was a deliberate W0 choice: temp files avoid the
  ~64KB pipe-buffer deadlock with no concurrent drainer. It is correct for
  bounded commands but cannot stream.
- timeout bounds runtime; a `tail -f` would just hit the timeout and return its
  buffered prefix.

* Why it was deferred
Streaming is real machinery, not a flag:
- the NIF must message the BEAM with chunks as they arrive (a dirty NIF holding a
  pid, or an enif-managed resource + scheduled sends) — lifecycle + backpressure.
- a BEAM-side stream/channel abstraction and how PTC-Lisp consumes it (does the
  sandbox even model an async stream? today tool calls are synchronous values).
- cancellation mid-stream, and how a partial stream maps into the result contract.
- ordering vs stderr interleaving.
W0 explicitly shipped the synchronous value model first; this is the async upgrade.

* Open design question
Does the PTC evaluator's synchronous tool-call model accommodate a streaming
result at all, or does this need a new primitive (a channel value, or a
callback-per-chunk that re-enters the sandbox)? Settle this BEFORE building —
it may belong with the broader reactive/effects work (PROJ-004 / PLAN-012's
deferred-holes direction) rather than as a standalone sh feature.

* Acceptance (when taken on)
- a long-running command streams stdout to the BEAM incrementally (no waiting
  for completion, no 64KB deadlock).
- cancellation stops the stream and reaps the child (reuse the W0 timeout/cancel
  + no-leak machinery, verified by a sentinel test).
- a final summary {:exit …} still arrives at stream end.

* Pointers
- engine: beam/brush_nif-vendored/native/brush_nif/src/run.rs (temp-file capture
  is the thing that would change to a pipe + chunked sends).
- the W0 child-reaping-on-cancel fix is the precedent for clean teardown.

* Not a bug
Bounded commands (the overwhelming majority) work perfectly with the current
synchronous model. This is an additive capability for the streaming minority.

* INVESTIGATION (2026-06-21): PLAN-012/FEAT-011 spawn-session makes this easy

** The user's hunch is right: the spawn machinery is the streaming machinery
FEAT-011 (tool/spawn-session — "the reflexive seam") + the new (untracked)
SpellAgent.SessionRegistry are precisely the process-lifecycle primitives
streaming needs. The hard part of streaming was never "read a pipe" — it was
"manage an async producer process with cancellation + backpressure + delivery."
The mesh work already builds that.

** What exists (verified)
- SpellAgent.SessionRegistry (lib/spell_agent/session_registry.ex): a GenServer
  tracking LIVE sessions by pid, with register/finish/live/live? and {:DOWN, …}
  monitoring (handle_info on process death). I.e. a supervised live-process
  registry with automatic teardown — exactly the lifecycle a streaming command
  process needs.
- SpellAgent.Session (session.ex): the session runner process model.
- FEAT-011 spawn-session: a native tool that spawns a CHILD session as a
  supervised process, budget-bounded (ParallelBudget.try_acquire), handed an
  attenuated tool set + a region. It is "eval(eval) as a tool" — the runtime
  spawning a managed sub-process and streaming its activity.

** Why this unlocks streaming cheaply
A streaming command IS a spawned, supervised producer process. Map the analogy:
  spawn-session: child session process, budget-acquired, monitored, streams
                 turns/activity back to the parent, cancellable, auto-reaped on
                 DOWN.
  sh/stream:     child COMMAND process (brush), budget-acquired, monitored,
                 streams stdout CHUNKS back to the caller, cancellable, reaped on
                 timeout/DOWN.
Same shape. So instead of inventing streaming lifecycle in the NIF, sh/stream
should REUSE:
  - SessionRegistry-style monitoring (or a sibling CommandRegistry) for the
    running command process + automatic teardown on death.
  - the ParallelBudget gate (a streaming command holds a slot like a child
    session does) — prevents unbounded concurrent streamers.
  - the same {:DOWN, …}/cancel teardown the W0 timeout fix already proved
    (child reaped, no leak).

** Revised design direction (supersedes the "open question" in the draft above)
The draft asked "does the synchronous PTC tool-call model accommodate streaming?"
FEAT-011 answers it: a spawned session does NOT return a synchronous value — it
streams activity to a process and the parent observes it. sh/stream should follow
the SAME pattern rather than trying to make a tool call return a lazy stream:
  - sh/stream spawns the brush command under a monitored process (the dirty NIF
    holds a pid and sends {chunk, data} messages to the BEAM, or brush writes to a
    pipe drained by a dedicated Elixir reader process).
  - the consumer is a BEAM process / the session's render clock, not a Lisp lazy
    seq. (Char-by-char chatty? debounce off a clock, exactly like the inspector
    FUP-006 does for live session inspection.)
∴ sh/stream is a SIBLING of spawn-session, not a new sandbox primitive.

** Dependency
This now DEPENDS ON (or at least should land after) FEAT-011/the mesh
process-lifecycle work, to reuse SessionRegistry + ParallelBudget rather than
duplicate them. Doing it before means building throwaway lifecycle code.

** Revised acceptance
- sh/stream spawns a brush command as a MONITORED process (SessionRegistry-style),
  budget-gated, streaming stdout chunks to a BEAM consumer.
- cancellation / timeout reaps the child (reuse W0 no-leak machinery, sentinel test).
- automatic teardown on process DOWN (no orphan, no registry leak).
- a final {:exit …} summary on stream end.

** Modules of record
- lifecycle precedent: lib/spell_agent/session_registry.ex (live-proc registry +
  DOWN teardown), FEAT-011 spawn-session (budget-bounded supervised spawn).
- budget: ParallelBudget (FEAT-013 wiring).
- engine: beam/brush_nif-vendored/native/brush_nif/src/run.rs (temp-file capture
  becomes a pipe + chunked sends for the streaming variant).
- debounce precedent: FUP-006 (live inspector off the render clock).

NET RANK: this is now the most COHERENT next sh item — it rides a shipped pattern, completes the babashka story (long-running greps/builds), and its one novel piece (chunk delivery) is a primitive worth having generally. Recommend as the lead candidate when sh work resumes.
