* Initial Message

what would a 'babashka on the BEAM' look like? you may consider wiring brush through rust NIFs too. Show me alternative designs and how they fit the current intention and enable homoiconic representations for everything

* Parent
PLAN-011 (sh+brush). Deferred (risk R4): the BEAM brush NIF does NOT resolve URI
tokens (skill://, local://, agent://, …) inside argv. This blocks demo 7, which
is documented as intentionally absent in test/sh_demos_test.exs.

* What is deferred
URI-scheme resolution inside a shell argv element, so:

    (sh:: cat skill://my-skill/SKILL.md)
    (tool/sh {:argv ["cat" "local://PLAN.md"]})

resolve the URI to a filesystem path (or content) before brush runs the command —
the same way the rest of Spell auto-resolves these schemes.

* Current state (verified)
- The TS/NAPI brush path HAS this: crates/pi-natives/src/exec/scheme_preprocessor.rs
  (WordPreprocessor + SchemeCallback, the W5 work referenced in the original
  babashka design), resolving scheme:// tokens through the kernel SchemeRegistry.
- The BEAM NIF (beam/brush_nif-vendored) does NOT wire any WordPreprocessor —
  argv elements are escaped and passed verbatim. A skill:// token reaches the
  command as the literal string "skill://…", which the command then can't open.
  (Confirmed: no WordPreprocessor/SchemeRegistry refs in the NIF src.)

* Why it was deferred
The WordPreprocessor was built for the NAPI/TS host. Reaching it from a BEAM NIF
needs one of:
- construct the kernel SchemeRegistry BEAM-side (does it exist in the Elixir
  runtime, or only TS?), OR
- bridge resolution back to the BEAM via a host callback (the NIF messages an
  Erlang process to resolve a token, like the SchemeCallback precedent) — this is
  the more BEAM-native design but adds a NIF<->BEAM round-trip per token.
Neither is a small bolt-on; it is a focused integration with its own review.

* Design question to settle first
WHERE does resolution happen?
  (a) Elixir-side, BEFORE the NIF call: SpellAgent.Sh expands URI tokens in argv
      (a pure Elixir pass over the vector) before handing argv to BrushNif.run.
      Simplest, no NIF change, no callback — probably the right v1.
  (b) Rust-side, via a WordPreprocessor in the NIF with a BEAM callback.
      Matches the brush WordPreprocessor model, but heavier.
Option (a) likely wins: argv is already a vector of strings in Elixir; resolving
skill:// there is a map over the vector with the existing Elixir scheme resolver
(if one exists — verify SpellAgent has a scheme/URI resolver, else that's a
prerequisite).

* Acceptance (when taken on)
- (sh:: cat skill://NAME/SKILL.md) reads the skill file content.
- resolution happens for EACH argv element independently (still one arg each,
  still inject-proof — a resolved path is one escaped word).
- unresolvable / unknown scheme → clean error in the {:exit :err} contract,
  never a crash.
- enable demo 7 in test/sh_demos_test.exs (currently a documented-absent note).

* Pointers
- precedent: crates/pi-natives/src/exec/scheme_preprocessor.rs (shell_escape +
  scheme resolution already coexist there).
- surface: SpellAgent.Sh (option a — preprocess argv before BrushNif.run).
- demo: test/sh_demos_test.exs "Demo 7" comment block.

* Not a bug
The shell works without URI tokens; this is an ergonomic integration that brings
the BEAM path to parity with the TS path.

* INVESTIGATION (2026-06-21): who resolves a skill, and the gating finding

** The gating finding: skill resolution is TS-ONLY. The BEAM has no resolver.
- grep for "skill" across beam/spell_agent/lib/ -> ZERO hits. The BEAM agent has
  no skill concept, no SchemeRegistry, no internal-URL router.
- The canonical resolver lives in TS: packages/coding-agent/src/internal-urls/
  router.ts (InternalUrlRouter.resolve/1) dispatching per-scheme handlers
  (agent-protocol.ts, local-protocol.ts, memory-protocol.ts, …). skill:// is a
  KERNEL_OWNED_SCHEME (router.ts:21-35): "skill -> dynamic callback bridges to
  session.skills + sub-path fs read" (BUG-394). So even in TS it short-circuits to
  the kernel (a callback into session.skills), not a pure-fs read.
- The Rust precedent (crates/pi-natives/src/exec/scheme_preprocessor.rs,
  SchemeWordPreprocessor) resolves <scheme>://<body> via an Arc<SchemeRegistry>
  + SessionContext — but that registry is the KERNEL's, populated TS-side. It is
  not constructed in the BEAM runtime.

** What "presence of a skill" actually means
A skill is NOT a static file path. It is `session.skills` — a per-session
registry of installed skills, each with a SKILL.md and a directory. skill://NAME
resolves to that skill's dir; skill://NAME/sub/path reads a file under it. So
"does skill X exist" = "is X in this session's skills set", a SESSION-STATE
question, not a filesystem stat. (This is why TS makes it a kernel callback, not
a path rule.)

** Consequence for the design — option (a) is NOT free
My FUP draft assumed option (a): "resolve in Elixir before the NIF, using the
existing Elixir scheme resolver." THAT RESOLVER DOES NOT EXIST. So FUP-011 is
really two layers:
  1. PREREQUISITE: a BEAM-side notion of "this session's skills" + a resolver for
     skill:// (and the fs-backed schemes local://, agent://). Either:
       (i)  port the per-scheme handlers to Elixir (a SpellAgent.InternalUrls
            module mirroring internal-urls/router.ts), seeded from wherever the
            BEAM session learns its skills, OR
       (ii) the BEAM session simply has no skills yet (is that true? verify how a
            BEAM session is launched and whether skills are even installed for it).
  2. THEN the easy part: SpellAgent.Sh maps over argv expanding resolvable
     scheme tokens before BrushNif.run (still inject-proof: a resolved path is one
     escaped word).

** Revised scope / honesty
This is NOT a half-day. The blocker is "does the BEAM agent have skills at all,
and if so where is that state?" If the BEAM agent has no skill system yet, FUP-011
is premature — skill:// has nothing to resolve TO. local:// (finalized-plan
artifacts) and agent:// (subagent output) may be the realistic first schemes,
since those are fs/store-backed and session-local.

** First question to answer before any code
Does a BEAM-launched session (mix spell.tui) install/track skills? If no, this
FUP narrows to local://-style fs-backed schemes only, and skill:// waits for a
BEAM skill system. If yes, find that state and build the resolver against it.

** Modules of record
- TS canonical: packages/coding-agent/src/internal-urls/router.ts + *-protocol.ts.
- Rust precedent: crates/pi-natives/src/exec/scheme_preprocessor.rs.
- BEAM target (to CREATE): a SpellAgent.InternalUrls resolver + the skills-state
  source it reads.
