* Summary
BUG-034 cost real debugging time because a `block`/`paragraph`/`list` leaf widget carrying a `children` key silently DROPS that child at layout time \u2014 no error, no warning. Only a `split` lays out `children`. An author who reaches for the wrong nesting (block-with-children instead of widget-with-block-field) gets a blank interior and no signal.

* Proposed
`LayoutDiagnostic.validate/1` (already the author-time lint that catches empty splits, non-encodable leaves, unresolved forms) should ALSO flag a leaf widget node that carries a `children` key which will be ignored. A warning-level diagnostic ("`children` on a `<type>` node is ignored; a border wraps a widget via its `block` field, and only `split` lays out children") turns a silent-drop into an immediate, actionable message.

* Scope
- Identify the leaf widget types (everything that is not `split`/`pane`) and the keys they actually consume (`text`/`items`/`block`/`style`/...).
- In validate/place, when a leaf node has a `children` (or other structurally-ignored) key, emit a warning diagnostic (not a hard error \u2014 it still renders, just without the dropped part).
- Test: a `{"type" "block" "children" [...]}` node produces the warning; a correct `{"type" "list" "block" {...}}` does not.

* Priority
Low \u2014 a DX/hardening improvement, not a correctness bug (the render is well-defined, just not what a confused author intended). Filed from BUG-034's follow-up note.
